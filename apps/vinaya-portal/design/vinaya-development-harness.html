Overview

Who this is for

Teams where several people direct coding agents in one repository

Vinaya is for teams past the point where one developer and one agent can hold a task in their head: where one agent's output starts breaking another's, and where nobody can say what an agent did or why. It connects task contracts, human decisions, checks, recovery and the record into one shared development process, with the same controls on planned and urgent work.

Why now

Teams have capable agents and real controls in each tool. What they lack is one process that connects them, so a second person can pick up where the first stopped.

What it adds

Branch protection and CI govern the push. Vinaya governs the task: a brief a reviewer can check against, a named pause when work stops, and a record a second person can resume from.

What it keeps

Your agents, your forge, your tracker, your CI. One file turns the harness on. Every decision that binds the codebase is made by a named human: the Principal, whichever engineer is driving that work at the time.

Introduction

Harness engineering

The shift from coding agents to shared engineering

Coding agents now take on whole pieces of work: they inspect repositories, edit files, run tests and prepare pull requests. In a shared codebase several people direct several agents at once, and the hard problems move to the harness around the agent: the context it receives, the boundaries it works within, the checks on its output, and the record people correct the system from.

Each agent can finish its own task while its changes conflict with another, rely on a mistaken assumption, or satisfy a request that was never clear enough to review. Tests pass without proving the assembled feature meets the goal; that judgment stays with product, and Vinaya gives it a complete record to judge from. Decisions made in individual chats are hard for the rest of the team to find, understand and carry forward. Coding agents have their own runtimes and tools; a team also needs these controls across tasks, reviewers, repositories and people.

Vinaya: a development process teams can governVinaya is that layer: an agent harness for software teams. It works with the agents a team already uses and adds shared controls around their work: configuration, gates, a record of governed actions, and a live view in Studio. A team can declare its own process; the Vinaya process is the default. In it, every role is an agent except one: the Principal, the engineer driving the work at that time, who approves plans, posts rulings and merges. Any engineer can hold the seat; every decision is attributed to the one who made it.

Walkthrough · how the process works

One task, brief to merge

Planned. Issue #419 arrives with a brief: Surface is billing/charge.ts and its tests; objective, a retried webhook must not charge the customer twice. The Operator starts the loop. Round 1: the Developer adds an idempotency key; a Reviewer flags that the brief assumed the key is stored, but the table has no column for it. The loop pauses, named for the Principal. Ruling posted: add the column in this task, extend the Surface to the migration. Round 2 is green at Ring 0 and Ring 1; the planned task's reviews report; the Principal merges. The Archivist closes #419 with the ruling in the record.

Hot. A CLI test is flaky on CI. The Principal opens #1001 hot with a light brief, one objective and the files, and works the fix with one agent in their own CLI. No rounds. The Principal decides no review is needed for this Issue, pushes, Ring 0 and Ring 1 run as always, and merges. Same gates, same Log. The record keeps the decision as well as the work: review.decision waived, hot.commit, gate.result green at each ring, archive.task_closed. Both paths are visible side by side in Mission Control.

What you get

Five features, one default process

Feature

Configuration

One file, vinaya.config.json, declares which process, agents, forge, log destination and gates a repository uses. Empty file, full harness.

Feature

Gates

Deterministic checks that block commits and merges failing tests, typecheck, lint or policy, on your machine and at the forge; audits that detect drift after merge.

Feature

Log

Every governed act kept as a typed, attributed event, delivered live to the destination you configure.

Feature

Studio

The readers of the record: the dashboard and Mission Control. You do not configure it; you get it.

Feature

Dev Process

The socket: what a development process must declare to run on the harness. The Vinaya process is the default.

Underneath the loop runs Atta Engine, the generic workflow runtime on LangGraph: checkpoints, halt and resume, recovery. It holds no Vinaya policy.

What keeps the process grounded

Planning

Facts the product checks

The Planner reads the code first, declares dependencies and conflicts, and asks before writing. Each claim the Planner makes about the code is checked against the repository before the brief is dispatched.

Hot mode

A light brief, live

No Planner. The hot Issue keeps one objective, the files and the facts read. No development rounds. Whether reviewers run is the Principal's decision for that Issue; the same gates apply; the Principal merges.

Recovery

Resume from reality

When execution cannot continue safely it stops at a recoverable pause that says who must act. A ruling is posted and the loop resumes from the record.

Retrospecting

The record answers

Studio answers from the record: did a cheaper model finish, are the reviewers strict, what did a task cost, where did the time go, which check catches most, which findings recur.

Improvement

Propose, then a human approves

The Improver reads those answers and proposes new projects. A human approves them; they go back to product.
