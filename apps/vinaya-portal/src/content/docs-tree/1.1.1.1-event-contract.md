# Event contract — definition

Summary: The typed shape every Log line must have: ten closed event families, a versioned header, strict objects, and rules that keep old lines readable as the schema grows.
Parent: Log
Badges: 10 families · Schema 1–3 · Strict · Additive only

## About the event contract

Every line in the Log is one event, and every event follows one contract. A single schema defines every valid line. Each line is checked against it before it is written, and again before it is sent or read back. A line that does not fit is never written.

The contract is pure: building and checking a line touches no file, network or process. It ships in the `@attalabs/aeg-core/log` package, with one schema per family, one for the header, and one for the whole line.

This page states the rules. For every field of every event, see [Events](/docs/process/events).

## How it works

Each line has three parts:

- **The header** (`meta` and `subject`): who wrote the line, when, where, and about what. The harness builds it. A caller passes only the event itself and can never set its own header.
- **The family and event** (`kind` and `event`): what happened.
- **The family's own fields**: the details of that event.

Every line reads, in order: `meta`, `subject`, `kind`, `event`, `duration_ms` (optional), `payload`, then the family's fields. `payload` is always an empty object `{}`; families carry their content in named fields.

## Families

`kind` is one of ten families. It is a closed list. `event` is one of a fixed set within each family.

| Family | Events | Has a producer |
| --- | --- | --- |
| `dispatch` | `dispatched`, `outcome_received`, `dispatch_failed` | Yes |
| `dev_review_loop` | `loop_started`, `round_started`, `gate_result_read`, `verdicts_read`, `findings_compared`, `stop_condition_met`, `paused`, `resumed`, `cancelled`, `unpushed_work_resume`, `round_ended`, `journal_finalized`, `infrastructure_retry`, `driver_heartbeat`, `driver_exited` | Yes |
| `forge_write` | `validated`, `refused`, `written` | No, kept in the schema only |
| `gate` | `summary`, `checked` | Yes |
| `operation` | `completed` | Yes |
| `usage` | `observed` | Yes |
| `role_attempt` | `attempted` | Yes |
| `handoff` | `raised`, `resolved` | Yes |
| `effect` | `verified`; `attempted` and `observed` in the schema only | `verified` only |
| `custom` | `recorded` | Yes |

The old families `command` and `tokens` are refused by name: `command` became `operation`, and `tokens` became `usage`.

## The header

The header has a version, `meta.schema`. Each version adds fields to the one before.

| Version | Adds |
| --- | --- |
| `1` | `ts`, `run_id`, `seq`, `repo`, `vinaya`, `doctrine`, `host`, `machine` |
| `2` | `event_id`, `process_id`, `actor_id`, `lineage { run, attempt, parent }`, `input_versions { manifest_version?, objectives_version, brief_hash, ruling_ordinal, pause_bound_ruling?, policy_digest }`, `provenance` |
| `3` | `work { ref, repo, change, revision }`, `flow { id, version }`, `runtime`, `source` |

`subject` always holds `issue` (null when none) and `role`; optionally `pr`, `sha`, `round` and `objectives_version`.

```steps
### New lines are always schema 3
The harness writes `schema: 3` on every new line. Versions `1` and `2` exist only so old lines keep parsing.

### Missing data is null
Data the harness cannot find is `null`, never invented. The one default is `flow.id`, which reads `vinaya` when unset.

### Foreign values pass through unchanged
`subject.role` is one of the known roles, or `unattributed`. `meta.actor_id`, `work.ref` and `flow.id` are opaque, so an actor from another tool, a work reference that is not an Issue, and a flow that is not Vinaya are written and read back as they are.

### Unsafe run ids are refused
`run_id` must match `^[A-Za-z0-9_.-]{1,128}$`. Any other value is refused when the line is written.
```

## Strictness

- **No extra keys.** Every object is strict. An extra key anywhere, including inside `payload`, fails the check.
- **A failing line is dropped.** It is not written, and the harness warns once per process.
- **Closed lists.** Every list of values is closed, except where the schema keeps a free string on purpose: `severity_scale`, `paused.reason_code` (a code token), `operation`, `usage.source` and `role_attempt.actor`.
- **Bounded strings.**

| Value | Limit |
| --- | --- |
| `confidence_reason` | 280 characters |
| Finding `description` | 1000 characters |
| Code tokens | `^[A-Za-z0-9._-]{1,64}$` |
| Custom event text | 500 characters |

## Compatibility

The schema only grows, so a line written today can still be read tomorrow, and a line written long ago can still be read today.

```accordion
### New fields are always optional
A field added to an existing event is optional, so lines written before it still parse. Examples: `verdicts_read.findings`, `verdicts_read.reviewers`, `paused.reason_code`, `driver_exited.exit_code`, `driver_exited.error_class`, and the four confidence fields on `gate_result_read`.

### Retired events stay readable
`gate` · `checked` with `pass` or `skip`, `effect` · `attempted` and `observed`, and the whole `forge_write` family stay in the schema even though nothing writes them.

### New header fields need a new version
Schema 3 was added as a new version, not as extra fields on 2. An older server that meets a schema 3 line keeps it as an unknown-version record instead of rejecting it.

### Two generations of the review-input manifest
Schema 3 accepts lines that leave out `manifest_version` and `pause_bound_ruling` (older lines), and lines that write `manifest_version: 2` with an explicit, possibly null, ruling. Any other manifest version is rejected. This rule is for readers; new lines always write both fields.

### Custom events need schema 3
A `custom` event under a schema 1 or 2 header is invalid.

### Unknown versions are kept, not thrown away
A line whose `meta.schema` is not `1`, `2` or `3` is kept word for word as an unknown-version record. That is a different outcome from an invalid line.
```

Compatibility is proven by tests that replay saved example lines of every version.

## Roll out a schema change

The Log server is strict about unknown keys: a line carrying a field the server does not know is stored as an unknown-version record. So the order matters.

```steps
### Deploy the server's schema first
Redeploy the Log server with the new schema: run `bunx wrangler deploy` from `apps/log-server`.

### Then release the CLI
Release the CLI version that writes the new fields only after the server knows them.

### Check that they match
Run `vinaya log selftest`, or `vinaya doctor` with `logs.readHeaders` set. Both compare the server's schema digest with the CLI's. A mismatch or a missing digest is a `warn` in doctor and a `FAIL` in selftest, and the message names the redeploy command.
```

## Configuration

There is nothing to configure. The contract is fixed. The only way to add event names is `logs.events`, which adds names inside the `custom` family; see [Custom events](/docs/features/log/custom-events).
