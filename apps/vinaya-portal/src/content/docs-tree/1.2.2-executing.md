# Executing — definition

Summary: One Issue goes in; one pull request ready for the Principal's merge comes out, or a pause that names who must act. This stage covers the loop, batches, hot mode, the Operator, pauses and parent branches.
Parent: The Vinaya process
Badges: The loop · Batches · Hot mode · Two reviewers

## About Executing

Executing is the second stage of the Vinaya process. One Issue goes in. One pull request the Principal can merge comes out, or a pause that says why and who must act. See [Overview](/docs/process) for where it sits in the whole process.

Executing has three modes. They all run on the same Issue object, and any Issue kind (planned, backlog or hot) can take any mode. Every pull request lands on its Issue's parent branch.

| Mode | Who codes | Rounds | Gates and review |
| --- | --- | --- | --- |
| The loop | A Developer agent in a sandbox, through controller-run tools | Until ready, or a pause | Every gate; two reviewers each round; the controller decides |
| Batch | The loop over many Issues; the controller picks the next within capacity | Per Issue | Same as the loop |
| Hot mode | The Principal and an agent, live, editing directly | None | Every gate at commit and push; two reviewers once, on demand; review again after a push |

```callout-note
Batches and hot mode are planned.
```

## How it works

Some promises hold in every mode:

- **The brief freezes at dispatch.** A change is a new Intent version with a reason, never an edit.
- **Named documentation is delivered.** Documentation the brief names reaches the Developer, and the Developer cites it in its result.
- **Two independent reviewers.** Code and Security are both required. They run in parallel, each in a fresh session. A missing or malformed review counts as no review.
- **The Developer publishes only through the controller's tools.** In hot mode the Principal publishes; the gates are the same.
- **A pause names who acts.**
- **Ready for merge is terminal.** Merge is the Principal's.

In the loop, a run goes like this:

```steps
### Prepare the run
Fast-forward the checkout, check dispatch readiness, then freeze and pin the brief.

### Prepare required sources
The controller builds a manifest of the documentation the brief names, with a receipt for each delivery.

### Dispatch the Developer
Round 1 gets a full context packet; later rounds get a delta packet.

### Publish through the controller's tools
The Developer commits and pushes through the tools. Ring 0 runs at commit and push.

### Accept the Developer's result
The controller accepts a typed turn result from the Developer.

### Read the mechanical gate
CI on the current head, mergeability, and a re-check of the premises. From round 2, the confidence rule applies.

### Review
Fresh Code and Security reviewers judge the pull request on one review-input manifest.

### Assess the round
The controller decides: **revise** sends current findings to the same Developer session; **pause** is retried by the controller itself, repaired by the Operator, corrected by the Planner, or ruled on by the Principal; **publish** posts the verdicts and the pull request is ready for the Principal's merge.
```

You start a run in one of three ways:

````tabs
=== Normal
```bash
vinaya task run <tranche> <n>
vinaya task run --issue <n>
```

=== Direct
```bash
vinaya dev-review-loop --task <n>
vinaya dev-review-loop --resume <pr>
vinaya dev-review-loop --cancel <pr>
```

=== Through the Operator
The Operator calls `task_start`, `task_resume` and `task_cancel`. See [The Operator](/docs/process/executing/the-operator).
````

To walk through a run end to end, follow a guide: [Deploy backlog issues](/docs/process/guides/from-one-issue), [Deploy medium work](/docs/process/guides/from-a-tranche), or [Deploy hot issue now](/docs/process/guides/hot-issue) for hot mode.

### Who takes part

| Role | In Executing | Human or agent |
| --- | --- | --- |
| Developer | Executes one frozen brief in a sandbox through the controller's seven tools. Never holds a forge credential; never pushes, merges or rules. | Agent; one session resumed across rounds |
| Reviewer (Code) | Judges the pull request against its brief and objectives | Agent; fresh each round |
| Security | Judges secrets, unsafe configuration and exposed surfaces | Agent; fresh each round |
| Operator | Starts, watches, resumes and cancels tasks through six task tools; presents pauses. Never plans, codes, rules, approves or merges. | Agent |
| Principal | Rules on pauses, merges, enters hot mode | Person |
| Execution Planner | Proposes a versioned plan correction when a running task proves its plan wrong (planned, with batches) | Agent |
| Planner | Receives `missing_source` pauses and pre-pull-request `widen_surface` requests, and supersedes the brief | Agent |

The **controller** (also called the driver) is not a role. It is harness machinery: it spawns every agent, holds the forge login, and derives every decision through one pure decision function. See [Roles](/docs/process/roles).

## Where the gates run

Each step of a loop run meets these gates. See [Gates](/docs/process/gates) for every check.

| Step | What runs | Ring |
| --- | --- | --- |
| Prepare the run | `dispatch-readiness` and a recompute of the facts; the brief is frozen and pinned | 1 |
| Developer works | The Developer publishes only through the controller's tools | — |
| Commit and push | The [commit checks](/docs/process/gates/ring0-commit-checks) (`brief-shape`, `pr-report-density`, `doc-coverage`, `exec-bits`, `changeset-coverage`, `main-branch-refusal` and the rest), then the [push checks](/docs/process/gates/ring0-push-checks) (`coherence`, `branch-topology`, `first-push-dispatch`, `quoted-command` and the rest). A refusal returns to the Developer in the same session. | 0 |
| Pull request opened or updated | `closes-n`, `surface-scope`, `test-plan`, `evidence-fresh`, `body-bare-digits`, plus every Ring 0 check again | 1 |
| Mechanical gate read | Scope, evidence and CI for the current head | 1 |
| Reviewers | Code and Security, fresh, on one immutable review-input manifest | — |
| Assess the round | `review-gate` validity; the controller decides | 1 |
| Before merge | `principal-test-plan-wait`; every required check green on the current head | 1 |

The controller also runs gates of its own, outside the 37 checks:

- the publication preconditions (wrong branch, unexpected base, moved head);
- the protected-path gate;
- the credential scan;
- the enforcement-controls check before every unattended dispatch;
- the after-turn confinement check;
- the agent-config security scan (`securityScan.command`) when a change touches `.claude/**`, `.mcp.json` or `.agents/**`.

In hot mode there is no loop and no controller. Ring 0 runs at the Principal's commit and push, Ring 1 on the pull request, and review runs once on demand. See [Hot mode](/docs/process/executing/hot-mode).

## Configuration

These keys in `vinaya.config.json` shape a run. See [Vinaya keys](/docs/process/vinaya-keys).

| Key | What it sets | Default |
| --- | --- | --- |
| `reviewPolicy.codeReviewThreshold` | The severity at which code review blocks | `MAJOR` |
| `reviewPolicy.securityThreshold` | The severity at which security review blocks | `HIGH` |
| `reviewPolicy.maxRounds` | Revision rounds before a Principal ruling | 3 |
| `reviewPolicy.maxTaskMinutes` | Active working-time budget; `0` turns it off | 180 (Vinaya's own repository sets 600) |
| `dispatch.agent` | Which runtime plays the roles (`claude`, `codex`) when `--agent` is absent | — |
| `dispatch.timeoutMs` | Wall-time ceiling for a Developer dispatch | Four hours |
| `dispatch.reviewerTimeoutMs` | Ceiling for each reviewer dispatch | Twenty minutes |
| `runtimeDir` | Where the controller keeps its files. Absolute, outside the repository, repo-local only. | `~/.vinaya/runtime/<owner>-<repo>` |
| `securityScan` | The agent-config scan the controller runs | — |

```callout-warning
For an unattended run, `runtimeDir`, `reviewPolicy`, `securityScan` and `principals` are read from the default branch, never from the pull request. See [Trust](/docs/features/configuration/trust).
```

The rule that pauses on a finding open for two rounds is fixed, not a setting.

## What gets logged

| Step | Events |
| --- | --- |
| Loop lifecycle | `dev_review_loop` · `loop_started`, `round_started`, `round_ended`, `paused`, `resumed`, `cancelled`, `stop_condition_met`, `journal_finalized` |
| Liveness, for Mission Control | `dev_review_loop` · `driver_heartbeat` (at most every five minutes), `driver_exited` |
| Developer and reviewer turns | `dispatch` · `dispatched`, `outcome_received` or `dispatch_failed`; `role_attempt` · `attempted`; `usage` · `observed` |
| Gate results | `dev_review_loop` · `gate_result_read`; `gate` · `summary` and `checked` |
| Reviews | `dev_review_loop` · `verdicts_read` (with a `findings` array), `findings_compared` |
| Pauses | `handoff` · `raised` and `resolved` |
| Recovered hiccups | `dev_review_loop` · `infrastructure_retry` |
| Writes to the forge | `effect` · `verified` |
| Operator and broker calls | `operation` · `completed` |

The Log is fail-open telemetry. It never authorizes or resumes a run: recovery reads the control store and principal-authored forge markers, never a Log event. See [Events](/docs/process/events) for every field.

## Troubleshooting

```accordion
### A run paused. Who acts?
The pause names who acts: the controller itself, the Operator, the Planner or the Principal. See [Pauses and rulings](/docs/process/executing/pauses-and-rulings).

### A commit or push was refused during a run
Ring 0 refused it. The refusal returns to the Developer in the same session, so the Developer fixes it where it happened.

### The run stopped at the round cap
A non-green round that reaches `reviewPolicy.maxRounds` pauses for a Principal ruling.
```
