# The Vinaya process — overview

Summary: The default process Vinaya installs. Work is planned by someone who read the code, each task runs through the loop under a frozen brief, two reviewers judge it, every gate runs, and a person merges.
Parent: Dev Process
Badges: Default process · Four stages · One Principal

## About the Vinaya process

The Vinaya process is the default process, and the default implementation of [Dev Process](/docs/dev-process/overview). It plugs into the harness the same way any other process would; its [Integration](/docs/process/integration/process-contract) pages document how it fulfils the contract. A team can run it as it is, or bring its own.

In one sentence: work is planned into tasks by someone who read the code first; each task runs alone through the loop under a frozen brief whose facts the harness has checked; two independent reviewers must both report, and the controller derives the outcome from their findings; a person merges.

Every role is an agent except one: the **Principal**, the engineer driving the work, who approves plans, rules when a run pauses and merges. See [Roles](/docs/process/roles).

## The four stages

```cards
- [Thinking](/docs/process/thinking) What enters execution. The Architect declares a Goal as a milestone, and the Planner writes every task as an Issue an agent can run.
- [Executing](/docs/process/executing) One Issue in, one mergeable pull request out. The Operator runs the tasks; an agent builds and two fresh reviewers check.
- [Retrospecting](/docs/process/retrospecting) What shipped and why. Merged work closes itself: the task, the tranche and the milestone.
- [Self-improvement](/docs/features/self-improvement) How runs become proposals. The Improver reads the Log and proposes changes; the Principal approves.
```

[Gates](/docs/process/gates) run across the stages: the checks that refuse unsafe work on your machine, on the pull request and after merge.

## How it works

```steps
### Thinking
Someone reads the code and writes down what must change. The output is always a GitHub Issue: planned (inside a tranche), backlog (a stand-alone fix) or hot (must change now). Planning happens here: the Planner cuts the work into tasks and you approve the plan.

### Executing
The Operator starts each ready task. A Developer agent builds it in a sandbox, two fresh reviewers judge the pull request, and every gate runs. The run ends with a pull request ready for you, or a pause that names who must act.

### Retrospecting
After you merge, the task, the tranche and the milestone are closed and their record is completed, mostly without anyone starting it.

### Self-improvement
The Improver reads the Log and proposes changes, and the Principal approves.
```

The gates run across the stages: at commit and push, on the pull request, and after merge.

Each stage is usable without the one before it. You can enter with a Goal, a tranche or one Issue. See the guides in [What's next](#whats-next).

```callout-note
The Improver is a harness agent, not a process role: it reads the Log and proposes changes, and the Principal approves. See [Self-improvement](/docs/features/self-improvement).
```

## How work is shaped

| Unit | What it is | Where it lives |
| --- | --- | --- |
| Goal | A product outcome and the tranches that serve it | A GitHub Milestone |
| Tranche | A set of related tasks with declared dependencies and conflicts, in dispatch order | A `vinaya/tranche:<slug>` label on its Issues |
| Task | One frozen brief, one branch, at most one pull request, one parent branch | A GitHub Issue |
