# Log — definition

Summary: Every governed act kept as a typed, attributed event, delivered live to the destination you configure: a folder on your machine or a server.
Parent: Features
Badges: Typed events · Live delivery · Folder or server · Custom events

## About the Log

The Log is the record of everything governed that happens in a repository. Each check result, each write to the tracker or the code host, each run of a task and each archive is one event. An event says what happened, to what, who did it, and when.

The Log belongs to the harness, not to a process. It reads the same whatever process runs on top. [Studio](/docs/features/studio), a harness feature, is one reader of it.

## How it works

```steps
### Something governed happens
A check runs, a task round ends, an Issue is written. The part of the harness that owns that act builds one event for it.

### The event is checked
Every event follows one typed contract: a closed family, a fixed event name, a header the harness builds, and strict fields. A line that does not fit is never written.

### Secrets are removed
Secrets are redacted and home paths rewritten before the line is written, and again before it is sent or read back.

### The event is delivered at once
It goes to the destination you configured, as it happens. Events are never batched at the end of a run, and delivery never slows or fails the run.

### Telemetry reads it back
`vinaya sync` gathers stored events into a local cache, where [Telemetry](/docs/features/telemetry)'s questions about cost, time and review strictness read them.
```

```callout-note
Events never go to the forge: no Issue or pull-request comment, no CI artifact.
```

## Record your own events

A repository can declare events of its own under `logs.events` and record them with `vinaya log emit`. Each one is checked against its declaration and written like any other event. See [Custom events](/docs/features/log/custom-events).

## The commands

```commands
log selftest
log emit
log send
sync
```

## Configuration

Set the destination under `logs` in `vinaya.config.json`. It names exactly one destination; with no `logs` set, events go to a folder under `runtimeDir`.

| Key | What it sets |
| --- | --- |
| `logs.folder` | A folder destination: an absolute path outside the repository |
| `logs.url`, `logs.headers` | A server destination and its ingest credential, as `${VAR}` filled from the environment |
| `logs.readHeaders` | The server's read credential, used by `vinaya sync` |
| `logs.events` | Your declared custom events |

An unattended run, such as an agent or a CI job, takes its destination from the default branch only, so a pull request cannot redirect events. See [Redaction and trust](/docs/features/log/redaction-and-trust) and [Configuration](/docs/features/configuration).

## Troubleshooting

```accordion
### My events are in the folder, not on the server
An unattended run falls back to the folder when the default branch could not be read or declares a different url. Run `vinaya doctor` and look at `[logs-fallback]`. Once the cause is fixed, run `vinaya log send` to deliver the waiting events. See [Delivery](/docs/features/log/delivery).

### CI records nothing
CI never writes to a folder. It needs a `logs.url` that the default branch approves and a non-empty credential in every `${VAR}` of `logs.headers`.

### I am not sure the server and the CLI agree
Run `vinaya log selftest`. It compares the server's schema digest with the CLI's and names any missing credential variable.
```
