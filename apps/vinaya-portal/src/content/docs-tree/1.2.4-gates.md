# Gates — definition

Summary: Checks that refuse unsafe work at three points: on your machine, on the pull request, and after merge. They run for every writer, human or agent, and cannot be skipped.
Parent: The Vinaya process
Badges: 37 checks · Ring 0 · Ring 1 · Ring 2 · Always on

## About gates

A written rule gets broken under pressure, even by an honest agent. A gate turns that rule into a check a machine runs, so the rule holds without anyone watching.

Each gate reads facts it can verify (the diff, the pull request, the Issue, the forge) and answers pass or fail. It never judges quality and never decides how severe a finding is. Reviewers judge; the pinned review policy decides what blocks.

Vinaya ships **37 core checks**:

- **17 implement generic gates.** Every process must answer these questions, such as "is the evidence current?" or "is the review valid?". Vinaya answers them with its own checks.
- **20 are Vinaya-specific.** They exist because of how Vinaya works: briefs, tranches, task branches, Issue grammar, writing rules.

```callout-note
The gate mechanism itself (the result format and where checks can run) is generic and belongs to the harness. See [Process contract](/docs/dev-process/process-contract). The checks on this page are Vinaya's.
```

## How gates run

Gates run in three rings. Each ring catches what the one before it cannot reach.

```steps
### Ring 0 · on your machine
At every commit and push, the installed hooks run the checks before anything leaves the machine. A refusal comes back in the author's own session with the exact error, so an agent fixes it where it happened.

### Ring 1 · on the pull request
The same checks run again in CI, from the same code, so the hooks and CI cannot disagree. Pull-request checks and the review gate run here too, and merge is blocked while any is red. Validated Issue and pull-request writes are checked before they reach GitHub. This ring catches every writer the hooks cannot reach: the web interface, other tools, people.

### Ring 2 · after merge
Audits run on every merge and once a day. They close finished work and report drift from any source, such as a push to a branch whose work is already done, or a push straight to `main`.
```

```callout-tip
With every rule enforced at the hook and again on the pull request, a red pull request on a gated rule points to a defect in the gate, not to a careless agent.
```

All three rings are always on. A team cannot switch a ring off; see [Configuration](#configuration) for the two narrow opt-outs.

## Run the checks yourself

The hooks and CI run the checks for you. You can also run them by hand.

````tabs
=== Everything
Runs every check that can run locally.

```bash
vinaya check --all --local
```

=== Only your changes
Runs the checks scoped to the files you changed, as the commit hook does.

```bash
vinaya check --all --diff-only --local
```

=== One check
Runs a single check by name.

```bash
vinaya check exec-bits
```
````

Each check either passes, or fails with one line per problem. A check can also report a wait rather than a defect, for example while a Principal test-plan item is still unticked.

## Customize the checks

A team adapts the checks in `vinaya.config.json`. Configuration selects and parameterizes checks; it never loads code.

````tabs
=== Add a check
Scaffold your own check, then register it under your own namespace.

```bash
vinaya new check
```

A check that declares `validates: 'body'` or `validates: 'issue'` joins the pull-request or Issue write path with no further wiring.

=== Replace a check
Give a `checks` entry the exact name of a core check. Your check runs instead, and `vinaya doctor` says so.

=== Silence a check
Scaffold an explicit no-op that replaces a core check. This is the only sanctioned way to turn one off.

```bash
vinaya new noop-check surface-scope
```
````

```callout-warning
A core check can never be dropped silently, and no ring can be switched off. Every silenced check is a visible no-op in your repository.
```

## Configuration

| Key | What it sets |
| --- | --- |
| `checks` | Which checks run, with what scope (`diff` or `full`), environment and timeout. Adds, replaces or silences checks. |
| `rings` | The two opt-out flags below. |
| `prePush` | Extra test files the push hook always runs. |
| `securityScan` | The scanner the review loop runs before the security review. |
| `gateCutovers` | Issue or pull-request numbers below which a newer rule does not apply. |
| `proseGates` | Inputs for the writing checks, such as where reader-facing docs live. |
| `decisionRecords` | Where decision records live, for the writing checks. |

The `rings` flags both default to `true`:

```json:vinaya.config.json
{
  "rings": {
    "ring1_forgeWriteInterception": true,
    "ring2_asyncAudits": true
  }
}
```

```accordion
### What `ring1_forgeWriteInterception: false` skips
The brief-section and body checks on pull-request and Issue writes. Every CI workflow still runs, as do the title, bare-digit and Premise checks on pull-request writes and all five Issue checks.

### What `ring2_asyncAudits: false` skips
The post-merge task archive and the daily dead-branch scan. Direct-push-to-`main` detection and the tranche archive still run.
```

## What gets logged

Every check run writes to the Log:

| Event | When | Carries |
| --- | --- | --- |
| `gate` · `summary` | Once per run | How many checks ran, passed, failed and were skipped, and which failed |
| `gate` · `checked` | Once per check that did not pass | The check, its outcome and a short reason code |

A passing check is counted, not logged one by one. The reason is a short code, never the check's message, so nothing from a pull-request body leaks into the Log. See [Events](/docs/process/events) for every field.

## Troubleshooting

```accordion
### A check passed at commit but fails at push
The commit hook runs only the checks scoped to the files you changed. The push hook also runs the checks that scan the whole repository. Run `vinaya check --all --local` to see what push will see.

### A check passed locally but fails on the pull request
Some checks need an open pull request or run in their own workflow, so they only run in CI. The review gate and the Principal test-plan wait are examples.

### I need to get past a check that is wrong
Fix the check, or replace it with your own. If it must be off, use `vinaya new noop-check <name>` so the change is visible and reviewed.
```
