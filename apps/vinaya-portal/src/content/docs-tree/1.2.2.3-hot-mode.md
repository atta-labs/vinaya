# Hot mode — definition

Summary: For a change that must land now, or when the loop itself is broken. The Principal and an agent edit a task branch live, with no loop and no rounds; every gate still runs, and review runs once on demand under a run identity.
Parent: Executing
Badges: Principal · Live · No rounds · Review on demand

## About hot mode

Use hot mode for a change that must land now, or when the loop itself is broken. You, the Principal, edit a task branch live with an agent beside you. There is no sandboxed Developer, no rounds and no controller. Every gate still runs at commit and push, review still happens, and the record still gets a run.

In hot mode the agent acts as the Principal. It edits, commits and pushes with your own login; merge stays yours. There is no credential exception and no confined session. You are accountable for every commit the agent makes. The agent's own local edits are not recorded, as with every agent's local edits.

```callout-note
Hot mode is planned.
```

To walk through it, follow the guide [Deploy hot issue now](/docs/process/guides/hot-issue), or try the [hot demo](/vinaya-process/demo/hot).

| Role | In hot mode |
| --- | --- |
| Principal | Writes the hot Issue and does its readiness check in person (recorded); runs `hot start`; launches any agent in the worktree; merges |
| Agent | Acts as the Principal: edits, commits and pushes to the task branch; may run `hot review` |
| Code reviewer, Security | Dispatched once per `hot review` attempt, in parallel, as in the loop |
| Operator | Never enters hot mode: `hot start` refuses when called through the task-tools MCP server |
| Developer, controller | Not involved |

## How it works

```steps
### Write the hot Issue
Write an Issue of kind `hot` and do its readiness check yourself.

### Start
Run `vinaya hot start --issue <n>`. It freezes the brief, creates the task branch and worktree, and mints a run identity.

### Work
You or the agent commit and push to the task branch through the ordinary hooks.

### Review on demand
Run `vinaya hot review --issue <n>` when you want the two reviewers to judge the pull request.

### Merge
Merge through the unchanged merge gate. A push after review voids the verdicts, so review again first.
```

### The hot Issue

A hot Issue is a GitHub Issue of kind `hot`, labelled `vinaya/hot`. Its body follows the backlog single-fix profile:

- `**Project:**`
- one or two `## Objectives`
- `## Premises`
- `## Surface`
- a Boundary with `Pinned files:`
- `## Test plan`
- optionally `## Observed`
- the line `Readiness: performed by the Principal`

Like every Issue, it carries `**Parent:**`. See [Issue kinds](/docs/process/thinking/issue-kinds).

### Start a hot run

```bash
vinaya hot start --issue <n>
```

`hot start`:

- reads `principals` from the default branch, and refuses if the default branch cannot be read, if the Issue's author is not a principal, or if it is called through the task-tools MCP server (advisory until authority is fully specified);
- refuses while a live driver lock or a pause record exists for the task;
- freezes the brief, creates `task/issue-<n>` and its worktree from `origin/<parent>`, and records the worktree path beside `driver.pid.json`;
- mints a run identity, emits `run_started`, and prints `export VINAYA_RUN_ID=<id>`.

To build the worktree from a branch that is already pushed, use `--adopt-branch`:

```bash
vinaya hot start --adopt-branch <name> --issue <m>
```

This pushes no reservation and freezes a brief naming that branch. It is how an integration branch gets its review. See [Parent and integration branches](/docs/process/executing/parent-and-integration-branches).

### Work

You or the agent commit and push to `task/issue-<n>` through the ordinary hooks. Three rules always hold:

| Rule | Enforced by |
| --- | --- |
| Never a push to `main` | Branch protection, the pre-push hook and the direct-push-to-`main` audit. `check-push-target` refuses any other target from a hot worktree. |
| Always a registered worktree | `hot review` and `pr report --push` refuse outside the recorded path. `hot review` refuses a head commit whose committer is not a principal. |
| Parent branch always declared | `**Parent:**` on the Issue (absent means `main`). The worktree forks from the parent and the pull request targets it. |

### Review on demand

```bash
vinaya hot review --issue <n>
```

You or the agent run it on demand, from the registered worktree, on the open pull request:

```steps
### Check the pull request
Refuses if the body lacks `Closes #<n>` or the brief hash resolves to null.

### Number the attempt
Numbers the attempt within the hot run.

### Stage the inputs
Stages the candidate inputs with the loop's own functions and takes the turn-confinement snapshot.

### Dispatch both reviewers
Dispatches the code reviewer and the security reviewer in parallel, under the hot run identity.

### Build verdicts and manifest
Builds the verdicts and the review-input manifest with the loop's builders.

### Post the verdicts
Posts both verdicts with effect key `hot-<runId>-<attempt>-<role>-verdict` and owner `hot-review:<task>:<runId>`, reads them back to verify the binding, and writes no summary comment.

### Finish the report
Writes the `AEG:BEYOND-SURFACE` block and runs `pr report --push`.
```

### Review again after a push

A push after `hot review` voids the verdicts, because the review gate binds to the head. Review does not run again by itself: the next `hot review` is attempt n+1, keyed `hot-<runId>-<n+1>-…`.

### End

`hot review` emits `run_ended` when both verdicts are posted. Merge is yours, through the unchanged merge gate. The review gate needs no loop and accepts a head branch that is not `task/issue-<n>`.

### Run identity

`hot start` mints one run per hot fix. `run_started` and `run_ended` mark a task that has no loop. Each review attempt adds two `role_attempt` and two `effect` events. `task_status` shows the task as `hot`, with its pull request and last attempt.

## Gates

| When | What runs | Ring |
| --- | --- | --- |
| Commit and push | Every Ring 0 check through the hooks, plus three new diff-scoped checks: a credential scan, a commit-header check (registered beside `commit-msg`), and protected paths on task branches | 0 |
| Pull request | `closes-n`, `surface-scope`, `test-plan`, `evidence-fresh`, `body-bare-digits`; Ring 0 and the three new checks run again in CI | 1 |
| Review | `review-gate` on the verdict pair from `hot review` | 1 |
| Before merge | `principal-test-plan-wait`; required checks green on the current head | 1 |

```callout-warning
Hooks can be skipped with `--no-verify`. For a hot pull request, CI is the guarantee.
```

The three new checks read `git diff --cached` when `VINAYA_COMMIT_HOOK=1`, and `git diff ${BASE_SHA:-origin/main}...HEAD` otherwise. See [Gates](/docs/process/gates).

## Configuration

Hot mode adds no settings. It uses `principals` from the default branch.

Two questions are still open: whether the protected-path check applies on branches that are not task branches, and whether to fail open or closed when the forge is unreachable.

## What gets logged

- `run_started` and `run_ended` (new, for a task without a loop).
- Per review attempt, `role_attempt` and `effect` events with distinct `effect_id`s.
- Hooks and CI emit `gate` events as usual.

See [Events](/docs/process/events).
