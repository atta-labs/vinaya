# Isolation — the task boundary a dispatched agent runs inside

Status: draft

This file is the durable contract `worker-isolation-v1` task 1 (`#549`) exists to produce: it names every actor that touches a dispatched task, what each one is trusted to do, and the mechanism that makes the untrusted actors' limits real rather than a convention. Task 1 wrote this file and proved the chosen mechanism (Part 2's probe) without wiring `dispatchRole` to it. `worker-isolation-v1` task 3 (`#560`) is the later task that wiring belonged to — see "§4, What task 3 wired," below, for what changed and what remains open. The Broker row's own AUTHORIZATION half (role/operation/target/input-version/ownership grant-checking, distinct from OS confinement) was built by `worker-isolation-v1` task 2 (`#557`) — see §1's Broker row.

## 1. The six boundaries

<!-- AEG:CLAIM: apps/cli/src/lib/dispatch.ts contains:const child = spawn(spawnCommand, spawnCommandArgs, { -->
Every dispatched role runs through one chokepoint, `dispatchRole`'s single `spawn(spawnCommand, spawnCommandArgs, …)` call. Since task 3, an UNATTENDED dispatch (`DispatchOpts.unattended` — the automated `task run`/`dev-review-loop` driver's own developer/reviewer dispatches, or a manual `vinaya dispatch --unattended`) whose repo has `dispatch.requireWorkerIsolation: true` set (`config.ts`) runs `spawnCommand`/`spawnCommandArgs` wrapped through `worker-boundary.ts`'s `resolveWorkerBoundaryLaunch` — the OS-level confinement this table specifies — and refuses before any spawn if that boundary cannot be established. Every OTHER dispatch (attended, or `requireWorkerIsolation` left at its off-by-default value — see §4) still runs the pre-task-3 shape exactly: `env: { ...process.env, VINAYA_RUN_ID, VINAYA_ROLE, VINAYA_TASK, VINAYA_ROUND }`, full parent-environment inheritance, no OS-level confinement. The table below is the target contract the CONFINED path is measured against; "Permitted" is what the actor MAY do under the contract, "Forbidden" is what an unconfined spawn allows that the contract withdraws.

| Boundary | What it is today | Trust level | Permitted operations | Forbidden operations |
|---|---|---|---|---|
| **Controller** | The `vinaya` CLI process itself — the driver code in `apps/cli/src/lib` (`dispatch.ts`, `dispatch-task.ts`, `dev-review-loop.ts`) that decides what to dispatch and reads the result. Runs as the Operator's own user, in the Operator's own shell. | Fully trusted | Read/write the Operator's own `HOME`, keychain, and ambient environment; hold the Operator's forge login (`gh auth token`) and model runtime credentials; spawn Worker, Reviewer and Repository-subprocess children; read/write the local outbox (`~/.vinaya/`); post forge writes (via `forge-write.ts`'s principal allowlist, `refuseUnlessPrincipal`). | Nothing withheld — it is the root of trust everything else is scoped from. It never itself executes brief-authored or PR-authored instructions (`lintReviewerPrompt`, `loop.md` "Reviewers" — a reviewer's prompt is facts-only, never developer- or PR-body-authored prose) — that separation is what keeps the controller trustworthy enough to hold these credentials. |
| **Worker** | The dispatched Developer role's vendor coding-agent child process (`claude`/`codex`/`gemini`, `role: 'developer'`), executing the frozen brief inside its own worktree (`.worktrees/task/<tranche>/<n>`). | Untrusted execution surface — runs brief-driven, and after round 1, review-finding-driven, agent-authored tool calls, including arbitrary `Bash` | Read/write inside its own worktree; run its declared toolchain (typecheck/lint/test/build) there; use a repo-scoped, short-lived forge credential for `git push` and `gh pr create`/`pr edit` on ITS OWN branch only (see §3, Broker); reach the model runtime endpoint to keep functioning as an agent. | Read the Operator's `HOME` outside its worktree; read or write the OS keychain; invoke an OS credential helper (`git-credential-osxkeychain` or equivalent); reach the Operator's ambient sockets (`SSH_AUTH_SOCK`, a container/docker socket); signal or introspect the parent (controller) process; read any environment variable the controller did not explicitly allowlist (in particular, never the Operator's own broad `gh auth token`/`GH_TOKEN`). These six are exactly Part 2's probe assertions. |
| **Reviewer** | The dispatched code-reviewer/security role's vendor coding-agent child process (`role: 'code-reviewer'` / `role: 'security'`), dispatched fresh every round, never resumed (`loop.md` "Reviewers"). | Untrusted execution surface, narrower than Worker | Read the repository at the judged head (its own checkout or worktree, read-only in intent); write `findings.txt`/`report.txt`/`objectives.txt` to its own driver-chosen work directory (`reviewerWorkDir`, under `~/.vinaya/dev-review-loop/<task>/…`); reach the model runtime endpoint. | Everything Worker is forbidden, PLUS any forge-write credential at all (a Reviewer never runs `git push` or `gh pr`/`gh api` writes — the driver posts verdicts on its behalf after both roles return, `loop.md` "Publication"). A Reviewer holding even Worker's scoped push token would be strictly more privilege than its job needs. |
| **Operator** | The human running `vinaya` commands from their own shell. | Root of trust | Everything the Controller can do, plus what only a human can do: sign in through a real browser, tick `[principal]` Test Plan boxes, apply the `vinaya/waiver:docs` label, post Principal rulings, merge. Supplies (or, once a Broker exists, delegates minting of) every credential the Controller, Worker and Reviewer boundaries ultimately depend on. | Nothing withheld by this contract — the Operator is the human this whole boundary protects, not a boundary constrained by it. |
| **Repository subprocess** | Trusted, controller-spawned CLI tools that are NOT a coding agent and never execute brief- or PR-authored instructions: `gh` (`packages/aeg-forge-state/src/gh.ts`, `github-token.ts`), `git`, and `vinaya check`'s own custom-check children (`apps/cli/src/checks/runner.ts`). | Trusted, but env-scoped by convention already (see §2) | Read/write whatever the Controller explicitly grants it via its constructed environment — `gh`/`git` today get the full ambient environment plus a PATH augmentation (`systemEnv`, `gh.ts`); a custom check gets exactly `ENV_BASELINE_KEYS` plus its own declared `CheckSpec.env` entries (`buildCheckEnv`, `checks/runner.ts`). | Anything the Controller does not pass into its constructed environment — this row already demonstrates the allowlist pattern §3 extends to Worker/Reviewer; it forbids nothing new because it is Controller-authored code, not agent output. |
| **Broker** | `apps/cli/src/lib/broker.ts` (`worker-isolation-v1` task 2, `#557`) — a role/operation/target/input-version/ownership authorization gate in front of `effects.ts`'s `EffectExecutor`, not yet the credential-minting component this row originally described. Its job today: authenticate a Worker's or Operator's invocation context and refuse a request for an ungranted operation, a target bound to a different task, a protected administrative path, or a replayed/stale input version — before any poster closure ever runs. | Real, for the authorization gate; the credential-minting half below remains design-only, its implementation not yet planned | Grant a Worker `branch-push`/`pr-open`/`pr-comment`; grant an Operator `task-execute`/`task-observe`; refuse both roles `ruling-post`/`criteria-edit`/`protected-merge`/`review-publish`/`human-resolve` unconditionally — human resolution of a paused/escalated run stays on the Principal's own `forge-write.ts` `refuseUnlessPrincipal` channel, never this broker. Separately, and still unbuilt: mint the ONE scoped, short-lived forge-write credential a Worker needs to push its own branch and open its own PR, and resolve the model runtime credential each dispatched child needs, without ever handing either child the Operator's own broad `gh auth token` or a wholesale environment spread. | Expose an unrestricted raw forge method or generic shell through the broker (`requestEffect` takes a closed `operation` string checked against a grant table, never a caller-supplied `gh` argv); mint a credential scoped to more than one repository, to the Operator's own account/login, or to forge-admin/merge scopes; hand a Reviewer any forge-write credential at all (see Reviewer row); ever be the Worker's OR the Reviewer's own environment inheriting the Controller's ambient `process.env` wholesale — every value the Broker hands through is named, not spread. |

## 2. Existing precedent this contract extends, not invents

<!-- AEG:CLAIM: apps/cli/src/checks/runner.ts contains:const ENV_BASELINE_KEYS = ['PATH', 'LANG', 'HOME', 'HTTPS_PROXY', 'HTTP_PROXY', 'NO_PROXY', 'TMPDIR'] as const -->
An explicit env allowlist already exists in this codebase, just not on the dispatch path this contract governs: `apps/cli/src/checks/runner.ts`'s `buildCheckEnv` constructs a custom check's child environment from `ENV_BASELINE_KEYS` (`PATH`, `LANG`, `HOME`, the proxy variables, `TMPDIR`) plus each check's own declared `CheckSpec.env` entries — never a `{ ...process.env }` spread. `dispatchRole`'s own attribution variables (`VINAYA_RUN_ID`/`VINAYA_ROLE`/`VINAYA_TASK`/`VINAYA_ROUND`) are already set only on the child's environment, never mutated onto the parent's (`apps/cli/specs/log.md`, "the CHILD process's environment only"). Neither precedent scopes what the child inherits FROM the parent — that half is what this contract adds, and what `buildCheckEnv`'s pattern (name every key explicitly, never spread) generalizes to Worker/Reviewer.

<!-- AEG:CLAIM: apps/cli/src/lib/dispatch.ts contains:export function writeDispatchSettings(): string | null { -->
A second, narrower precedent already exists on the dispatch path itself: `writeDispatchSettings` (`dispatch.ts`) generates a per-dispatch Claude Code `settings.json` (`--settings <path>`) denying backgrounded `Bash`/`Agent` calls and whole-suite test runs, and setting `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`. This is a tool-permission boundary enforced by the vendor's own hook mechanism, not a process/OS boundary — it constrains what tool CALLS the agent may make, not what the underlying OS process can reach if it makes them anyway (a `Bash` call the hook allows can still `cat ~/.ssh/id_ed25519` today). The two boundaries are complementary, not redundant: this contract's OS-enforced boundary is the backstop for exactly the tool calls the vendor-hook boundary permits. `writeDispatchSettings` still degrades to `null` on a write failure rather than throwing (an unwritable `GLOBAL_VINAYA_HOME/dispatch-settings`, a disk/permission fault) — but `dispatchRole` (round 5 review, MEDIUM fix) now refuses an unattended, isolation-required Claude dispatch before any spawn when that happens, the same fail-closed shape the OS boundary's own refusal already takes, rather than silently launching with this vendor-hook boundary missing.

## 3. Mechanism, host capabilities, authentication path and refusal conditions (O3)

**Chosen mechanism: Apple Seatbelt (`sandbox-exec` + a generated `.sb` profile).** This is the mechanism Part 2's probe (`apps/cli/scripts/isolation-probe.ts`, `.sb` profile fixture) proves. It was chosen over a container for the reason the brief's own Traps name: "a container with privileged host mounts is not isolation," and this repo's supported dispatch host today is the Operator's own macOS development machine — Seatbelt is the OS-native, no-install, no-daemon mechanism available there, and it enforces the boundary at the kernel (MAC framework) layer, not by convention.

- **Supported host:** macOS (Darwin). `sandbox-exec` ships with the OS at `/usr/bin/sandbox-exec` — confirmed present and functional on this task's own render host. Apple has marked the `sandbox-exec` command-line tool deprecated (it prints no runtime warning on this host but Apple's own documentation carries the deprecation notice) while the underlying kernel enforcement (the Sandbox/MAC framework, `libsandbox`) remains the mechanism macOS's own App Sandbox and every shipped system daemon profile continue to build on — this contract depends on the kernel enforcement, not the CLI wrapper's long-term support status, and names the CLI wrapper as a documented replaceable adapter (a future migration to the `Sandbox.framework` C API or a maintained macOS-sandboxing wrapper package would swap the invocation in `apps/cli/scripts/isolation-probe.ts` without changing this contract's boundary rows). **Primary source:** Apple's `sandbox-exec(1)`/`sandbox_init(3)` manual pages and the Seatbelt profile language they document (`(version 1)`, `(allow …)`/`(deny …)` rules over `file-read*`/`file-write*`/`network-outbound`/`signal`/`process-info*`/`process-exec` operations, path filters via `subpath`/`literal`/`path-literal`).
- **A container is out of scope for this task's probe** (no Linux/CI dispatch host is in scope here — Issue #549's Out explicitly excludes "whole-repository process extraction," and the tranche's other open tasks (`task-log-v1` `#550`, `control-store-v1` `#551`, `task-operator-v1` `#558`) are where a Linux/CI-hosted equivalent (a rootless container with no privileged host mount, an explicit `--env` allowlist, and a bind-mounted worktree as the only writable path) would be specified, following this same six-row contract, when that host is actually supported.

**What the probe demonstrates (mapped to the six Worker/Reviewer forbidden operations above):**

1. **Environment** — the sandboxed child's own `spawn`/`env` option carries an explicit allowlist (the same discipline as `buildCheckEnv`), never a `{ ...process.env }` spread; a value the parent holds but does not name (proven with a marker variable) is absent from the child's `process.env`.
2. **HOME** — a Seatbelt `(deny file-read* file-write* (subpath "<real $HOME>"))` rule, with an `(allow …)` carve-out for the child's own worktree/work directory (which, on a developer machine, is itself typically a subpath of `$HOME` and needs its own explicit exception) and for a synthetic `HOME` the child is launched with instead. A second `file-write*` rule, `(deny file-write* (require-all (require-not (subpath "<allowed dir>")) (require-not (subpath "<fake HOME>"))))`, closes every OTHER writable path the profile's baseline would otherwise leave open (`/tmp`, `/var`, anywhere else a bare process can write) — "read/write inside its own worktree" (§1, Worker row) is the ceiling on writes, not one open path among several. **The profile itself starts `(deny default)` plus `(import "system.sb")`** (Apple's own baseline covering the dyld/library-loading, mach-bootstrap, and sysctl-read operations any process needs merely to start), not a blanket `(allow default)` — every other OS surface the six named checks don't themselves exercise (other mach services, iokit, sysctl-write) is denied by default rather than left ambiently reachable, with one further narrow carve-out: `(allow file-read* (subpath "<runtime interpreter's own install directory>"))`, since the interpreter reads its own binary and adjacent shared libraries beyond the bare `execve` the process-exec rule (item 4, below) grants.
3. **Keychain** — the same deny rule extended to `~/Library/Keychains`, `/Library/Keychains`, `/System/Library/Keychains`, PLUS a `(deny mach-lookup (global-name "com.apple.securityd") …)` rule naming every mach service Keychain Services itself resolves through. File access is only one route into the keychain — the Keychain Services API talks to `securityd`/`trustd` over mach IPC, not through a file descriptor on the database — so the file-read/write deny alone would leave a direct API call (bypassing any CLI) unblocked; the mach-lookup deny closes that route at the OS level. **Documented scope limit:** the probe itself is JS-only and has no native binding to call the Keychain Services API directly, so it exercises two routes (direct file access, and the `security` CLI — Keychain Services' own command-line front end) and reads either succeeding as accessible; the mach-lookup deny's effect on a true in-process API call is asserted by the profile, not independently exercised by this probe.
4. **Credential helper** — no longer a literal-path deny list. `process-exec` is default-DENIED for the whole profile, with a single `(allow process-exec (literal "<runtime interpreter's own path>"))` exception, since the disposable probe's own confined child never needs to exec anything but itself. A literal-path deny naming the credential-helper binary is bypassable by copying that binary into the child's own writable scratch directory and executing the copy under a path the deny list never named; default-deny-plus-allowlist is not, because the copy is still absent from the allowlist regardless of where it sits. This closes `git credential fill` (and any other exec attempt) structurally rather than by naming known binaries. **A real Worker's own allowlist will be wider** — its actual toolchain (`git`, its declared build/test/lint commands) needs to exec real binaries — but the PRINCIPLE this probe proves stays the same: name every binary the confined role is trusted to run, and deny the rest by default, never the inverse (name only what's forbidden).
5. **Socket** — a blanket `(deny network-outbound)` rule denies every outbound connection the confined child could make — TCP, UDP, and any unix-domain socket, including a container/docker socket — since this probe never needs to reach anything over the network. A second, narrower `(deny network-outbound (remote unix-socket (path-literal "<canonicalized SSH_AUTH_SOCK>")))` rule names the ssh-agent path specifically; the blanket rule already subsumes it, but it stays as the profile's own documented answer to this check's specific negative. The path MUST be canonicalized (`realpath`) before it is written into the profile — `/var/run/…` on this host resolves to `/private/var/run/…`, and Seatbelt matches the canonical path, not the symlinked convenience path a shell sees in `$SSH_AUTH_SOCK`.
6. **Parent process** — `(deny signal)` and `(deny process-info* (target others))`: the child cannot `kill(ppid, 0)` to probe the parent's liveness, nor introspect it through `libproc`/`ps`. `(target others)` is load-bearing, not cosmetic — an unscoped `(deny process-info*)` also blocks the confined runtime's own self-introspection at startup and crashes it (`SIGTRAP`) before it ever reaches the probe's checks; scoping to `others` keeps the boundary (the child cannot inspect its PARENT) while leaving the child free to inspect itself.

**Non-obvious constraints the probe surfaced, load-bearing for any real wiring later:**

1. **The confined process's `cwd` must itself be inside an allowed subpath.** Both `bun` and `node` walk up from `cwd` at startup resolving config/module files; launching the sandboxed child with `cwd` still pointed at a denied directory (the real repo tree, in the probe's own case) fails opaquely rather than cleanly — a real Worker/Reviewer dispatch MUST set `cwd` to the confined directory it is being handed (its own worktree), never leave it defaulted to the controller's `process.cwd()` the way `dispatchRole` does today (§2, "What this task does not change").
2. **The entry script/binary the confined child runs must itself live inside an allowed subpath.** The probe copies itself into its own scratch directory before invoking `sandbox-exec` rather than pointing the sandboxed child at its real on-disk location under the repo tree — a Worker/Reviewer dispatch already satisfies this naturally (the vendor CLI binary and the target worktree both need their own explicit allow rules; a task's own worktree is exactly the directory this contract intends to leave readable).
3. **A denied `unix-socket` connect surfaces as `ENOENT`, not `EPERM`.** Apple's sandbox deliberately reports a Seatbelt-denied `network-outbound`/`unix-socket` connection the same way as a socket that was never there, rather than confirming the resource exists — code relying on this boundary must never treat `ENOENT` from a socket connect as proof of absence; the probe treats "a path was resolved to test, and the connection failed for any reason" as blocked, full stop.
4. **A path substituted into the profile must be escaped for the profile's own string-literal syntax.** A worktree path (or any other value a Worker's dispatch might supply) can in principle contain a double quote or a backslash; substituting it unescaped into a Seatbelt `"..."` literal would let that character terminate the literal early and splice attacker-influenced text into the compiled profile. The probe's own `buildSandboxProfile` escapes every substituted value (`\` and `"`) before it is written into the rendered `.sb` file — a real launcher must do the same for anything it substitutes.
5. **Every path substituted into the profile must be `realpath`'d, not only the SSH socket (item 3, above).** A directory from `os.tmpdir()` can itself resolve through a symlinked alias exactly like `/var/run/…` does — macOS's own `/var` resolves to `/private/var` — so a scratch/work directory minted under `tmpdir()` must be canonicalized before it is handed to `buildSandboxProfile`, the same as the SSH socket path already is; a subpath `allow`/`deny` rule written against the alias silently fails to match the resolved path the kernel actually checks. Once the default baseline denies by default (item 2, above) this is load-bearing rather than latent: under a permissive `(allow default)` baseline a mismatched `allow` was masked (reads still succeeded through the baseline itself), but a mismatched rule against a `(deny default)` baseline fails closed instead — the confined child cannot read or write even its own allowed directory.

**The runtime's authentication path inside the boundary.** A dispatched agent (Worker or Reviewer) is itself a vendor coding-agent CLI — it needs its OWN model-runtime credential to keep functioning at all, which is a DIFFERENT concern from the forge-publication credential the traps call out separately:

- **Model runtime credentials** (what the vendor CLI needs to keep answering) are resolved once by the Controller and passed through the same named-allowlist env construction as every other value the child receives — never a blanket `HOME`/keychain read, since the sandbox denies both. Where a vendor CLI's own auth lives in an on-disk session file rather than an env var, the Controller reads that ONE file itself (outside the sandbox, where it already has full HOME access) and hands the resolved credential through as a named env value or a narrowly `(allow file-read* (literal …))`-listed synthetic path inside the sandbox — the sandbox profile never grants blanket access to the real credential file's real location.
- **Forge-publication credentials** (what lets a Worker `git push`/`gh pr create` its own branch) are never the Operator's own `gh auth token`. Minting a repository-scoped, short-lived token before dispatch and handing it through as a named value, exactly like a model credential, is the Broker's still-unbuilt CREDENTIAL half (§1) — never inherited from the ambient environment. A Reviewer receives no forge-publication credential of any kind (§1, Reviewer row) because it never needs to write to the forge.
- **This task does not implement the Broker's credential-minting half.** No minting code, no scoped-token API call, ships in this PR — that wiring remains future work, not yet assigned a task. What this task fixes in place is the BOUNDARY the Broker will hand credentials across, and proves the boundary is real on the supported host. The Broker's AUTHORIZATION half (role/operation/target/input-version/ownership grant-checking in front of `effects.ts`) is a separate concern from credential minting and was built later by `worker-isolation-v1` task 2 (`#557`, `apps/cli/src/lib/broker.ts`) — it does not require the OS-confinement or credential-minting work this task leaves undone.

**Refusal conditions — when the contract cannot be met, dispatch must say so rather than silently degrade:**

- `sandbox-exec` is absent, or the generated profile fails to compile (`sandbox-exec` exits before ever reaching the target binary) — the probe treats this as a hard failure, never a silent fallback to an unconfined spawn.
- The host is not Darwin — this contract names no supported mechanism for that host yet; a future task adding one (§ "A container is out of scope," above) must extend this same table, not bypass it.
- A value the Worker/Reviewer genuinely needs (a model credential, the scoped push token) cannot be resolved — this is a dispatch-time failure the Controller reports, never a reason to widen the sandbox profile or fall back to full environment inheritance to make the dispatch "work anyway."

## 4. What task 3 wired (`worker-isolation-v1` task 3, `#549` → `#560`)

<!-- AEG:CLAIM: apps/cli/src/lib/worker-boundary.ts contains:export function resolveWorkerBoundaryLaunch( -->
`apps/cli/src/lib/worker-boundary.ts` is the launcher this file's Part 2 probe (`isolation-probe.ts`) never was: it builds a real Worker/Reviewer profile (`buildWorkerSandboxProfile`) and resolves a real `sandbox-exec`-wrapped launch (`resolveWorkerBoundaryLaunch`), reusing the probe's own default-deny-plus-named-allowlist principle and Seatbelt string-literal escaping (re-implemented there, not imported — the probe's own script directory ships outside the published package). `dispatchRole` (`dispatch.ts`) calls it for an UNATTENDED dispatch whose repo has opted in.

**A declared, visible setting, platform-conditional by default (round 2 review, HIGH).** `DispatchOpts.unattended` (set on every automated `task run`/`dev-review-loop` developer and reviewer dispatch, and available on `vinaya dispatch --unattended`) marks a dispatch as unattended; the SEPARATE `dispatch.requireWorkerIsolation` config field (`config.ts`) decides whether an unattended dispatch actually REQUIRES the boundary. Round 1 shipped this off by default everywhere, including Darwin — leaving O3's "fail closed" opt-in even on the one host the mechanism works on, which round 2 review read as not matching O3's own unconditional wording. The resolved default is now `loadConfig()?.dispatch?.requireWorkerIsolation ?? process.platform === 'darwin'`: `true` automatically on the declared supported environment, `false` elsewhere unless a repo explicitly opts in. Only when the resolved value is `true` does an unavailable boundary refuse the dispatch, before any spawn (§3's refusal conditions, applied literally — never a silent fallback). This repo's own CI (`.github/workflows/*.yml`, `ubuntu-latest`) and its own current operational hosts are Linux, so their behavior is unchanged by this default either way; a Mac-hosted deployment now gets O3 as its automatic behavior with zero configuration.

**What a resolved launch actually differs from the probe's own contract, and why:**

1. **Network is denied by default, allowed only on ports 80/443 (round 3 security review, HIGH — narrowed from round 2's blanket allow), plus the ssh-agent socket denied specifically.** A real Worker must reach the model runtime endpoint to keep functioning as an agent (§1, Worker row) — the probe's own blanket `(deny network-outbound)` would starve it — but round 2's blanket `(allow network-outbound)` left every other destination open too: a credential threaded into the confined env (item 6, below) is inherited by any subprocess a dispatched agent runs, and Seatbelt confinement has no notion of "which process in the tree may use this socket," only which destinations the whole tree may reach. Restricting to 80/443 closes every non-HTTP(S) exfiltration channel (a raw-socket beacon, DNS tunneling over a raw UDP socket, an SSH relay, any other port). **What it does NOT close, live-verified rather than merely undecided:** an HTTPS POST to an attacker-controlled host on port 443 is indistinguishable, at this layer, from the legitimate model-runtime call the confined process must be allowed to make — closing that needs a destination check above the port number, and this task confirmed LIVE that Seatbelt's own `remote` filter cannot express one on this host: `(remote tcp "example.com:443")` and `(remote ip "<literal IP>:443")` both fail to compile with `sandbox-exec: host must be * or localhost in network address`, so no hostname/IP allowlist is expressible in a Seatbelt profile at all here. This is the concrete reason Anthropic's own `secure-deployment` documentation (see the ruling response in this task's own PR body) recommends an EGRESS PROXY rather than a sandbox-profile allowlist — a proxy is the only place that can actually inspect and gate the destination, and building one remains materially larger than this task's own bounded surface, a deliberately deferred, separate, task-sized item, not silently built or silently skipped here. **DNS resolution reopens a narrower version of the same gap (round 4 review, BLOCKER fix; round 5 review, LOW — disclosed here).** A hostname lookup never opens a raw UDP/TCP socket itself — it goes through `mDNSResponder` over a local unix-socket connection plus `mach-lookup` IPC — so the port-80/443-only restriction above left no confined dispatch able to resolve any model-runtime hostname at all until round 4 added a scoped route to the resolver (`(allow network-outbound (remote unix-socket (path-literal "/private/var/run/mDNSResponder")))` plus `mach-lookup` to `com.apple.dnssd`/`com.apple.mDNSResponder`/`com.apple.mDNSResponderUnix`). That route is necessary — `O1`/`O3` cannot hold on the declared supported host without it — but it also lets a confined process trigger arbitrary hostname lookups, which the resolver performs over the real network on the process's behalf: a resolution-based exfiltration channel (data encoded as subdomains of an attacker-controlled domain) distinct from, and not closed by, the HTTP(S)-proxy gap this item already names. Scoping it needs the same egress-proxy architecture as the port-443 gap, above — deliberately not built here, disclosed rather than left implicit.
2. **Process-exec is allowed under a resolved allowlist** (the confined role's own worktree/allowed directory, the runtime interpreter's install dir, `git --exec-path` when resolvable, this dispatcher's own bun install directory (round 5/6 review, BLOCKER fix — see below), and whatever of `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`, `/usr/local/bin`, `/opt/homebrew/bin` exist on this host), not the probe's single self-re-exec literal — a real Worker runs its own declared toolchain. This does not reopen the credential-helper gap §3 item 4 closed: the Keychain row's file AND `mach-lookup` denial (§3 item 3) blocks a credential helper's actual secret-extraction route regardless of which binary, or which copy of one, attempts it — the process-exec allowlist governs what can RUN, not what can reach `securityd`. A concretely-resolved helper binary (`git-credential-osxkeychain` and equivalents, under a resolved `git --exec-path`) is additionally named as its own layered `process-exec` deny, for defense in depth. **This repo's own toolchain is bun**, and `CANDIDATE_SYSTEM_BIN_DIRS` never covered a standard bun install (`~/.bun/bin`, under the otherwise fully-denied real `HOME`): every live test through round 4 passed `binaryPath: process.execPath` (the test runner's own bun binary), which incidentally granted bun's own directory as `runtimeDir` and masked that a confined role given a DIFFERENT `binaryPath` — the real production shape, a vendor coding-agent binary, not bun itself — could not exec `bun` at all, breaking both `O1`'s build/test-subprocess requirement and `writeDispatchSettings`'s own `bun "${scriptPath}"` PreToolUse hook command. The round 5 fix (`resolveBunExecDir`, `worker-boundary.ts`) closed that gap for THIS repo's own dogfooding (`bun apps/cli/src/index.ts`) but assumed `process.execPath` IS the bun binary — true only when the dispatcher process is itself bun-hosted. Round 5 review, BLOCKER (round 6 fix): the published, declared-supported entry point (`apps/cli/scripts/build.ts`'s `--target=node` build, a `#!/usr/bin/env node` shebang) runs under Node, where `process.execPath` never contains `bun` at all — silently granting exec over the wrong directory on the one entry point this task's own brief names as production. `resolveBunExecDir` now resolves `bun` the same "never assumed, verified live" way `resolveGitExecPath` already resolves `git` — a `which bun` lookup, independent of which runtime hosts the dispatcher process.
3. **`HOME` is not replaced with a synthetic directory.** The confined child's `HOME` env value is the genuine home path — so a tool that constructs `$HOME/.something` resolves predictably — while the PROFILE still denies file access to that real home path except for the resolution's own named, NARROW carve-outs (round 2 review tightened these twice, round 4 review tightened them again — see items 4–5, below): the confined directory (read-only during round-1 bootstrap), a fresh scratch tmp dir, and two repo-scoped subdirectories of `GLOBAL_VINAYA_HOME`. The env value and the filesystem permission are independent; Seatbelt enforces the latter.
4. **Round-1 Developer bootstrap: the confined directory is READ-ONLY, with only `.git`/`.worktrees` writable (round 2 review, CRITICAL fix).** When no worktree exists yet, `dispatchDeveloper` (`dev-review-loop.ts`) falls back to the repo root as the confined directory (its own Step 0 is `git worktree add`, which needs to write into the shared repo's `.git/` metadata — a directory scoped to the not-yet-existing worktree alone cannot satisfy that). Round 1 granted this fallback full read+write, which let a confined, brief-driven Developer rewrite `vinaya.config.json` — read live and uncached by the trusted Controller's own `loadConfig()` on every later dispatch — or poison `aeg-root/roles/*.md` doctrine, persistently defeating this very boundary and the repo's own trust configuration. `resolveWorkerBoundaryLaunch`'s `bootstrapWritableSubpaths` closes this: the repo root is read-only, and only `git worktree add`'s own two write targets (`.git`, `.worktrees`) are writable — for the `developer` role only; any other role falling back to the repo root (a Reviewer with no candidate built) gets a read-only repo root and no writable subpaths inside it at all. `dispatchDeveloper` passes the worktree itself as the confined directory (full read+write, the steady-state case) once `existsSync` confirms it exists (round 2+ of a review loop, not to be confused with this task's own round 2). This remains narrower isolation than the Worker row's "read/write inside its own worktree" describes for the steady state until worktree creation moves to the (trusted) Controller side — a disclosed, bounded gap, not the target end state, and still future work.
5. **`GLOBAL_VINAYA_HOME` is NOT exposed at all, except the two exact FILES this dispatch's own outbox line and resume record live at (round 2 review, MAJOR fix; round 4 review, HIGH + BLOCKER fix; round 5 review, CRITICAL fix superseded all three).** Round 1 carved out full read+write for the entire `~/.vinaya` directory — including its own `config.json` and every other task's/repo's state on the machine. Round 2 narrowed WRITE to exactly `outbox`/`dispatch-resume` but left the whole directory READ-ONLY, so a confined role could still read `config.json` plus every other task's and repo's state — round 4 security review, HIGH, found this live. Round 2 also left the write grant itself a BARE top-level name, so a confined role could write into ANY other repo's or task's outbox/resume file too — round 4 code-review, BLOCKER, found this could forge another task's audit log or steal another task's live vendor `resumeId` and resume its session directly. Round 4 scoped the write grant to `outbox/<repoSegment>` and `dispatch-resume/<repoSegment>` — THIS dispatch's own repo only — but that DIRECTORY is still shared by every OTHER task's and role's own outbox line / resume record for the same repo, since neither path nests one directory per task or role: round 5 security review, CRITICAL, found this live — a confined Developer for task N could read a CONCURRENTLY-RUNNING code-reviewer's or security reviewer's own resume record for the SAME task and resume that session directly with the vendor binary already in the profile's own exec-allow list. Round 5 replaces the directory-subpath grant with `WorkerBoundaryLaunchOpts.vinayaHomeWritableFiles` — the exact outbox/resume-record FILE this dispatch owns, via `(literal ...)`, never `(subpath ...)` — so no sibling task's or role's file in the same directory is exposed, verified live (a sibling literal path in the same directory, and a directory listing of it, both still fail with a real permission denial; the target file itself, whether pre-existing or written for the first time, both succeed). The containing directory is pre-created by the TRUSTED, unsandboxed controller (`dispatch.ts`, the same way `writeDispatchSettings` pre-creates its own directory) before this resolution runs, so `writeLaunchRecord`'s own `mkdirSync(dirname(path), { recursive: true })` inside the sandbox needs only the pre-existing `file-read-metadata` traversal grant on that directory's own exact `(literal ...)` path, not a write grant on it. Never `config.json`.
6. **A real model-runtime credential route now exists (round 2 review, BLOCKER fix).** Round 1 shipped no route for a vendor CLI's own auth at all — `WORKER_ENV_ALLOWLIST_KEYS` had no credential-shaped entry, and the profile denies both the real HOME (where an OAuth session file typically lives) and the Keychain — so a confined dispatch, even a resolved one, could not actually function as an agent. `RUNTIME_CREDENTIAL_ENV_KEYS` (`worker-boundary.ts`) now threads a vendor-specific env-var credential through by name when the parent has one set (`buildWorkerEnv`'s new `extraAllowlistKeys` parameter): `ANTHROPIC_API_KEY` for Claude, verified live on this authoring host (`claude --help` documents it as a real, independent auth path via the `--bare` flag's own description — `--bare` itself is not threaded through, since its own doc says it skips hooks, which would silently disable the PreToolUse background-deny mechanism this task's own brief named a trap to preserve). `OPENAI_API_KEY`/`GEMINI_API_KEY`/`GOOGLE_API_KEY` for Codex/Gemini follow public convention, NOT verified live — neither binary is installed on this host, disclosed rather than guessed.
7. **`process-fork` is explicitly allowed (round 3 review, F1 live-enforcement testing — found live, not by inspection).** A SEPARATE Seatbelt operation from `process-exec`, denied by `(deny default)` like everything else unless named. Every test of this profile before this fix asserted the generated profile as TEXT only; the first test to actually run a real confined shell through real `sandbox-exec` (item 1's own live network test, incidentally) found a confined child could exec its own toolchain (item 2, above) but could not FORK to run any of it — `bash: fork: Operation not permitted` on something as basic as a subshell or a command substitution. This profile shipped with that defect from its first version through round 2 review; nothing in this contract's own six checks (§3) or task 3's prior test suite exercised a real subprocess spawn, so it stood undetected until a live test happened to try one. `(allow process-fork)` takes no filter (fork has no path/target argument the way exec and file operations do) — the forked/exec'd child remains scoped by every OTHER rule in this profile exactly as before.

**Still unbuilt:** the Broker's forge-write credential-minting half (§1, §3's "authentication path") — no scoped forge-write token is minted or handed through by this wiring. A Worker running `git push`/`gh pr create` inside the confined boundary today has no forge credential at all (never the Operator's own `gh auth token` — deliberately absent from `worker-boundary.ts`'s `WORKER_ENV_ALLOWLIST_KEYS`) and so cannot publish; that remains the Broker's own next task, not this one's. An egress-scoping proxy (item 1, above) also remains unbuilt, and this task now has live proof — not merely an undecided detail — that a Seatbelt-profile allowlist can never substitute for one on this host.
