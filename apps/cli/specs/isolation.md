# Isolation — the task boundary a dispatched agent runs inside

Status: draft

This file is the durable contract for worker isolation: it names every actor that touches a dispatched task, what each one is trusted to do, and the mechanism that makes the untrusted actors' limits real rather than a convention. It was written, and the chosen mechanism proved by a standalone probe, before `dispatchRole` was wired to it; §4, "What the dispatch wiring does," below, describes the wiring and what remains open. The Broker row's own AUTHORIZATION half (role/operation/target/input-version/ownership grant-checking, distinct from OS confinement) is built — see §1's Broker row.

## 1. The six boundaries

<!-- AEG:CLAIM: apps/cli/src/lib/dispatch.ts contains:const child = spawn(spawnCommand, spawnCommandArgs, { -->
Every dispatched role runs through one chokepoint, `dispatchRole`'s single `spawn(spawnCommand, spawnCommandArgs, …)` call. **This chokepoint's OWN confinement decision is split by vendor, behind one provider-neutral interface** (`worker-boundary.ts`'s `ConfinementRequest`/`resolveClaudeConfinement`/`resolveCodexConfinement`, each taking a role, its task worktree, its scratch directory and the hosts it may reach) — `dispatchRole` calls the matching one once per unattended dispatch, rather than branching on the vendor itself to decide whether/how to build confinement. **Neither vendor is wrapped in the hand-built Seatbelt profile `resolveWorkerBoundaryLaunch`/`buildWorkerSandboxProfile` built any more** (retired for Claude first, then for Codex too — those functions remain in `worker-boundary.ts`, unreferenced from this file now, since deleting them is separate, later work by Principal decision). For **Claude**, its own native sandbox, driven by the settings file `writeDispatchSettings` already writes, holds the boundary; §4a describes it. For **Codex**, its own documented `workspace-write` sandbox and network proxy, driven by a config.toml this task stages into a per-task `CODEX_HOME`, hold the boundary instead; §4b describes it. Unlike Claude, an unattended Codex dispatch whose sandbox/network-proxy mechanism is unavailable REFUSES rather than degrading (O4) — Codex carries no per-dispatch floor outside this boundary the way Claude's settings file does. The unconfined shape — `env: { ...process.env, VINAYA_RUN_ID, VINAYA_ROLE, VINAYA_TASK, VINAYA_ROUND }`, full parent-environment inheritance, no OS-level confinement — still runs for every attended dispatch of either vendor, and for an unattended Claude dispatch on a Linux host without `bubblewrap`/`socat` (§4a's own fallback, never a refusal — Claude's own, not Codex's). The table below is the target contract the CONFINED path is measured against; "Permitted" is what the actor MAY do under the contract, "Forbidden" is what an unconfined spawn allows that the contract withdraws.

## 2. Existing precedent this contract extends, not invents

<!-- AEG:CLAIM: apps/cli/src/checks/runner.ts contains:const ENV_BASELINE_KEYS = ['PATH', 'LANG', 'HOME', 'HTTPS_PROXY', 'HTTP_PROXY', 'NO_PROXY', 'TMPDIR'] as const -->
An explicit env allowlist already exists in this codebase, just not on the dispatch path this contract governs: `apps/cli/src/checks/runner.ts`'s `buildCheckEnv` constructs a custom check's child environment from `ENV_BASELINE_KEYS` (`PATH`, `LANG`, `HOME`, the proxy variables, `TMPDIR`) plus each check's own declared `CheckSpec.env` entries — never a `{ ...process.env }` spread. `dispatchRole`'s own attribution variables (`VINAYA_RUN_ID`/`VINAYA_ROLE`/`VINAYA_TASK`/`VINAYA_ROUND`) are already set only on the child's environment, never mutated onto the parent's (`apps/cli/specs/log.md`, "the CHILD process's environment only"). Neither precedent scopes what the child inherits FROM the parent — that half is what this contract adds, and what `buildCheckEnv`'s pattern (name every key explicitly, never spread) generalizes to Worker/Reviewer.

<!-- AEG:CLAIM: apps/cli/src/lib/dispatch.ts contains:export function writeDispatchSettings( -->
The agent-config security scanner extends that same env-allowlist precedent, not the dispatch path. The dev-review-loop's driver runs the configured scanner (`securityScan.command`) itself, before dispatching the security reviewer, as a repository subprocess over the head-verified candidate copy — the directory appended as a final argument, spawned via `execFile` never a shell — with an environment built from `WORKER_ENV_ALLOWLIST_KEYS` (the same keys as `ENV_BASELINE_KEYS`) and nothing else, so no forge credential ever reaches a scanner running pull-request-authored configuration. It runs from a fresh, empty sandbox directory used as both the working directory and `HOME` (the allowlist's real `HOME` overridden), never the candidate checkout — so an `.npmrc` the pull request committed, or the real user's, can never steer `npx` package resolution to an attacker registry under the pinned name; the candidate is only ever the scan target argument. It is the driver, holding the forge token, that never executes that config; the scanner runs in a stripped environment and a neutral sandbox that does, which is why the two are kept apart. The scan carries a time limit and an output cap, and its result is a fact piece in the security prompt only (`apps/cli/specs/loop.md`, "The agent-config scan is the driver's job too"). The reviewer itself is denied `npx` (§6's grant table), so it can never run the scanner inside its own dispatch — the boundary this subprocess exists to hold.

A second, narrower precedent already exists on the dispatch path itself: `writeDispatchSettings` (`dispatch.ts`) generates a per-dispatch Claude Code `settings.json` (`--settings <path>`) denying backgrounded `Bash`/`Agent` calls and whole-suite test runs, and setting `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`. This is a tool-permission boundary enforced by the vendor's own hook mechanism, not a process/OS boundary — it constrains what tool CALLS the agent may make, not what the underlying OS process can reach if it makes them anyway (a `Bash` call the hook allows can still `cat ~/.ssh/id_ed25519` today). The two boundaries are complementary, not redundant: this contract's OS-enforced boundary is the backstop for exactly the tool calls the vendor-hook boundary permits. `writeDispatchSettings` still degrades to `null` on a write failure rather than throwing (an unwritable `hooks/` directory inside the dispatched task's own run folder, a disk/permission fault) — but `dispatchRole` now refuses an unattended, isolation-required Claude dispatch before any spawn when that happens, the same fail-closed shape the OS boundary's own refusal already takes, rather than silently launching with this vendor-hook boundary missing.

## 3. Mechanism, host capabilities, authentication path and refusal conditions

**This section, and §4 below, describe the hand-built Seatbelt profile — a mechanism NEITHER vendor goes through any more.** Claude stopped first; Codex stops too, as of this revision — §4a describes Claude's own native sandbox, §4b describes Codex's own `workspace-write` sandbox and network proxy. Everything below this line, through the end of §4, is preserved as the historical record of a mechanism this repo built, proved, and then retired for both vendors it ever confined — kept, not deleted, because deleting `resolveWorkerBoundaryLaunch`/`buildWorkerSandboxProfile` and the probe they formalize is separate, later work (Principal decision).

**Chosen mechanism: Apple Seatbelt (`sandbox-exec` + a generated `.sb` profile).** This is the mechanism the standalone probe (`apps/cli/scripts/isolation-probe.ts`, `.sb` profile fixture) proves. It was chosen over a container for the reason the brief's own Traps name: "a container with privileged host mounts is not isolation," and this repo's supported dispatch host today is the Operator's own macOS development machine — Seatbelt is the OS-native, no-install, no-daemon mechanism available there, and it enforces the boundary at the kernel (MAC framework) layer, not by convention.

- **Supported host:** macOS (Darwin). `sandbox-exec` ships with the OS at `/usr/bin/sandbox-exec` — confirmed present and functional on the supported host. Apple has marked the `sandbox-exec` command-line tool deprecated (it prints no runtime warning on this host but Apple's own documentation carries the deprecation notice) while the underlying kernel enforcement (the Sandbox/MAC framework, `libsandbox`) remains the mechanism macOS's own App Sandbox and every shipped system daemon profile continue to build on — this contract depends on the kernel enforcement, not the CLI wrapper's long-term support status, and names the CLI wrapper as a documented replaceable adapter (a future migration to the `Sandbox.framework` C API or a maintained macOS-sandboxing wrapper package would swap the invocation in `apps/cli/scripts/isolation-probe.ts` without changing this contract's boundary rows). **Primary source:** Apple's `sandbox-exec(1)`/`sandbox_init(3)` manual pages and the Seatbelt profile language they document (`(version 1)`, `(allow …)`/`(deny …)` rules over `file-read*`/`file-write*`/`network-outbound`/`signal`/`process-info*`/`process-exec` operations, path filters via `subpath`/`literal`/`path-literal`).
- **A container is out of scope for the probe** (no Linux/CI dispatch host is in scope here — whole-repository process extraction is excluded, and a Linux/CI-hosted equivalent (a rootless container with no privileged host mount, an explicit `--env` allowlist, and a bind-mounted worktree as the only writable path) would be specified, following this same six-row contract, when that host is actually supported.

**What the probe demonstrates (mapped to the six Worker/Reviewer forbidden operations above):**

1. **Environment** — the sandboxed child's own `spawn`/`env` option carries an explicit allowlist (the same discipline as `buildCheckEnv`), never a `{ ...process.env }` spread; a value the parent holds but does not name (proven with a marker variable) is absent from the child's `process.env`.
2. **HOME** — a Seatbelt `(deny file-read* file-write* (subpath "<real $HOME>"))` rule, with an `(allow …)` carve-out for the child's own worktree/work directory (which, on a developer machine, is itself typically a subpath of `$HOME` and needs its own explicit exception) and for a synthetic `HOME` the child is launched with instead. A second `file-write*` rule, `(deny file-write* (require-all (require-not (subpath "<allowed dir>")) (require-not (subpath "<fake HOME>"))))`, closes every OTHER writable path the profile's baseline would otherwise leave open (`/tmp`, `/var`, anywhere else a bare process can write) — "read/write inside its own worktree" (§1, Worker row) is the ceiling on writes, not one open path among several. **The profile itself starts `(deny default)` plus `(import "system.sb")`** (Apple's own baseline covering the dyld/library-loading, mach-bootstrap, and sysctl-read operations any process needs merely to start), not a blanket `(allow default)` — every other OS surface the six named checks don't themselves exercise (other mach services, iokit, sysctl-write) is denied by default rather than left ambiently reachable, with one further narrow carve-out: `(allow file-read* (subpath "<runtime interpreter's own install directory>"))`, since the interpreter reads its own binary and adjacent shared libraries beyond the bare `execve` the process-exec rule (item 4, below) grants.
3. **Keychain** — the same deny rule extended to `~/Library/Keychains`, `/Library/Keychains`, `/System/Library/Keychains`, PLUS a `(deny mach-lookup (global-name "com.apple.securityd") …)` rule naming every mach service Keychain Services itself resolves through. File access is only one route into the keychain — the Keychain Services API talks to `securityd`/`trustd` over mach IPC, not through a file descriptor on the database — so the file-read/write deny alone would leave a direct API call (bypassing any CLI) unblocked; the mach-lookup deny closes that route at the OS level. **Documented scope limit:** the probe itself is JS-only and has no native binding to call the Keychain Services API directly, so it exercises two routes (direct file access, and the `security` CLI — Keychain Services' own command-line front end) and reads either succeeding as accessible; the mach-lookup deny's effect on a true in-process API call is asserted by the profile, not independently exercised by this probe.
4. **Credential helper** — no longer a literal-path deny list. `process-exec` is default-DENIED for the whole profile, with a single `(allow process-exec (literal "<runtime interpreter's own path>"))` exception, since the disposable probe's own confined child never needs to exec anything but itself. A literal-path deny naming the credential-helper binary is bypassable by copying that binary into the child's own writable scratch directory and executing the copy under a path the deny list never named; default-deny-plus-allowlist is not, because the copy is still absent from the allowlist regardless of where it sits. This closes `git credential fill` (and any other exec attempt) structurally rather than by naming known binaries. **A real Worker's own allowlist will be wider** — its actual toolchain (`git`, its declared build/test/lint commands) needs to exec real binaries — but the PRINCIPLE this probe proves stays the same: name every binary the confined role is trusted to run, and deny the rest by default, never the inverse (name only what's forbidden).
5. **Socket** — a blanket `(deny network-outbound)` rule denies every outbound connection the confined child could make — TCP, UDP, and any unix-domain socket, including a container/docker socket — since this probe never needs to reach anything over the network. A second, narrower `(deny network-outbound (remote unix-socket (path-literal "<canonicalized SSH_AUTH_SOCK>")))` rule names the ssh-agent path specifically; the blanket rule already subsumes it, but it stays as the profile's own documented answer to this check's specific negative. The path MUST be canonicalized (`realpath`) before it is written into the profile — `/var/run/…` on this host resolves to `/private/var/run/…`, and Seatbelt matches the canonical path, not the symlinked convenience path a shell sees in `$SSH_AUTH_SOCK`.
6. **Parent process** — `(deny signal)` and `(deny process-info* (target others))`: the child cannot `kill(ppid, 0)` to probe the parent's liveness, nor introspect it through `libproc`/`ps`. `(target others)` is load-bearing, not cosmetic — an unscoped `(deny process-info*)` also blocks the confined runtime's own self-introspection at startup and crashes it (`SIGTRAP`) before it ever reaches the probe's checks; scoping to `others` keeps the boundary (the child cannot inspect its PARENT) while leaving the child free to inspect itself.

**Non-obvious constraints the probe surfaced, load-bearing for any real wiring later:**

1. **The confined process's `cwd` must itself be inside an allowed subpath.** Both `bun` and `node` walk up from `cwd` at startup resolving config/module files; launching the sandboxed child with `cwd` still pointed at a denied directory (the real repo tree, in the probe's own case) fails opaquely rather than cleanly — a real Worker/Reviewer dispatch MUST set `cwd` to the confined directory it is being handed (its own worktree), never leave it defaulted to the controller's `process.cwd()` the way an unconfined `dispatchRole` dispatch does (§2).
2. **The entry script/binary the confined child runs must itself live inside an allowed subpath.** The probe copies itself into its own scratch directory before invoking `sandbox-exec` rather than pointing the sandboxed child at its real on-disk location under the repo tree — a Worker/Reviewer dispatch already satisfies this naturally (the vendor CLI binary and the target worktree both need their own explicit allow rules; a task's own worktree is exactly the directory this contract intends to leave readable).
3. **A denied `unix-socket` connect surfaces as `ENOENT`, not `EPERM`.** Apple's sandbox deliberately reports a Seatbelt-denied `network-outbound`/`unix-socket` connection the same way as a socket that was never there, rather than confirming the resource exists — code relying on this boundary must never treat `ENOENT` from a socket connect as proof of absence; the probe treats "a path was resolved to test, and the connection failed for any reason" as blocked, full stop.
4. **A path substituted into the profile must be escaped for the profile's own string-literal syntax.** A worktree path (or any other value a Worker's dispatch might supply) can in principle contain a double quote or a backslash; substituting it unescaped into a Seatbelt `"..."` literal would let that character terminate the literal early and splice attacker-influenced text into the compiled profile. The probe's own `buildSandboxProfile` escapes every substituted value (`\` and `"`) before it is written into the rendered `.sb` file — a real launcher must do the same for anything it substitutes.
5. **Every path substituted into the profile must be `realpath`'d, not only the SSH socket (item 3, above).** A directory from `os.tmpdir()` can itself resolve through a symlinked alias exactly like `/var/run/…` does — macOS's own `/var` resolves to `/private/var` — so a scratch/work directory minted under `tmpdir()` must be canonicalized before it is handed to `buildSandboxProfile`, the same as the SSH socket path already is; a subpath `allow`/`deny` rule written against the alias silently fails to match the resolved path the kernel actually checks. Once the default baseline denies by default (item 2, above) this is load-bearing rather than latent: under a permissive `(allow default)` baseline a mismatched `allow` was masked (reads still succeeded through the baseline itself), but a mismatched rule against a `(deny default)` baseline fails closed instead — the confined child cannot read or write even its own allowed directory.

**The runtime's authentication path inside the boundary.** A dispatched agent (Worker or Reviewer) is itself a vendor coding-agent CLI — it needs its OWN model-runtime credential to keep functioning at all, which is a DIFFERENT concern from the forge-publication credential the traps call out separately:

- **Model runtime credentials** (what the vendor CLI needs to keep answering) are a SUBSCRIPTION LOGIN and nothing else. No agent authenticates with an API key: no API-key environment variable is read by any dispatch path, allowlisted into a confined child, accepted by the pre-spawn credential check, or named as a fallback in a refusal — a Principal ruling, not a default this repo can configure away. The Controller resolves the one on-disk session the vendor CLI itself wrote (outside the sandbox, where it already has full HOME access) and stages a task-scoped copy the profile already grants — never the real credential file's real location, and never a credential VALUE on the child's environment. `buildWorkerEnv` takes no per-vendor passthrough parameter at all, so there is no key to thread one through under; `WORKER_ENV_ALLOWLIST_KEYS` names no credential-shaped variable (asserted by test). Two vendors have such a login today, and `SUBSCRIPTION_LOGIN_AGENTS` (`worker-boundary.ts`) is the list:
  - **`claude`** — the OAuth session credential, staged by `stageOAuthCredential` (next bullet): the `.credentials.json` file in the Claude config directory where a host has one, else the macOS Keychain entry `Claude Code-credentials` where Claude Code keeps it on a Mac. The Controller reads the Keychain with `/usr/bin/security find-generic-password -s <service> -w` from OUTSIDE the sandbox (darwin only, 5 s timeout, `null` on any failure) and stages only the `claudeAiOauth` object — never the unrelated MCP tokens the same item carries — into the scratch config directory at mode 0600. The profile still denies the Keychain; `USER` and `LOGNAME` are in the worker environment allowlist (account names, not secrets) because Claude Code's own lookup needs them, and `CLAUDE_CODE_TMPDIR` is pointed at the granted scratch directory because Claude keeps working files under `/tmp/claude-<uid>` regardless of `TMPDIR`.
  - **`codex`** — the cached ChatGPT session, replayed into a task-scoped `CODEX_HOME` by `codex login --with-access-token` (below). `CODEX_ACCESS_TOKEN` is that login's own stdin bootstrap value, read by the trusted Controller from the operator's own cached session — a subscription token, not an API key — and never set on the confined child's environment.
  - **`gemini`** — no subscription login exists in Vinaya yet, so an unattended `gemini` dispatch REFUSES before any spawn (`dispatch.ts`'s `NO_SUBSCRIPTION_LOGIN_REASON`) rather than reaching for a key. This refusal is about the login, not the boundary: it fires whether or not the worker sandbox is required on this host. An ATTENDED `gemini` dispatch is untouched — a human at their own terminal signs their own vendor CLI in.
  - **Implemented for Claude's OAuth session.** Without that staging, a confined `claude` dispatch on a host authenticated by subscription/OAuth would have no route to its own credential at all — the profile's own HOME deny (item 2, above) denies `<realHome>/.claude/.credentials.json` unconditionally, so the dispatched `claude` process tried OAuth, found nothing readable, and hung silently to the dispatch's own timeout ceiling with zero output. `worker-boundary.ts`'s `stageOAuthCredential` (called from `resolveWorkerBoundaryLaunch` when `stageOAuthCredential: true`, which `dispatch.ts` sets only for `agent === 'claude'`) reads `resolveOAuthConfigSourceDir(process.env, realHome)/.credentials.json` — `CLAUDE_CONFIG_DIR` when the parent process already overrides it, else `<realHome>/.claude`, Claude's own documented default — from OUTSIDE the sandbox (the trusted Controller has full HOME access), and, when that file exists, copies its contents into a `claude-config/` subdirectory of the staged configuration directory (`readWriteDirs` already grants this — **no new profile grant, no widened Keychain/credentials-file rule**). The confined child's own `CLAUDE_CONFIG_DIR` env var (via `buildWorkerEnv`'s `attribution` parameter, which always wins) is repointed at that staged copy, so `claude`'s own config-dir lookup finds a working credential without ever touching the real path. The real `<realHome>/.claude/.credentials.json` and the Keychain stay denied — proven live, under the SAME resolved launch that successfully authenticates from the staged copy, in `apps/cli/tests/lib/dispatch/worker-boundary.test.ts`'s "OAuth credential staging, live sandbox-exec" describe block.

    **The staged configuration directory belongs to the TASK, not to one dispatch.** Where `stageOAuthCredential` once staged into the profile's own per-dispatch scratch temp directory (a fresh `mkdtemp` removed by `resolveWorkerBoundaryLaunch`'s own `cleanup()` as soon as that one dispatch returned), it now stages into a directory the caller names explicitly: `WorkerBoundaryLaunchOpts.stagedConfigDir`, which `dispatch.ts` resolves to `<runtimeDir>/tasks-execution/<task>/sessions/<role>-<agent>-config`, beside that dispatch's own `<role>-<agent>.json` resume record. That one change is what makes a round-2 resume work at all: the per-dispatch scratch dir meant round 2 repointed `CLAUDE_CONFIG_DIR` at an EMPTY, freshly-minted directory, where `claude --resume <sessionId>` found no session store and died with "No conversation found with session ID" — the round-1 transcript having been deleted with the round-1 scratch dir. The task-scoped directory survives between rounds (it is NOT in `cleanup()`'s removal set; only the per-dispatch scratch temp dir, still minted for `TMPDIR` scratch use, is), so round 2 finds the round-1 session store it continues. It is keyed by role+agent, not by task alone, because `dev-review-loop.ts` dispatches its code-reviewer and security roles CONCURRENTLY — one shared `CLAUDE_CONFIG_DIR` would be two live `claude` processes racing on the same `.claude.json`/session store, the same concurrency hazard §6's role-scoped settings directory already closes. It stays well outside the real `~/.claude` (under the run's own `runtimeDir`), is granted read+write exactly like a reviewer's own work directory (its parent `sessions/` folder gets only the metadata-traversal grant, never recursive read of a sibling role's session record), and is removed when the task's loop genuinely ENDS — its review published, or the task cancelled (`dev-review-loop.ts`'s `cleanupAllStagedAgentConfigs`) — never on a pause, whose own resume needs exactly the store this would delete. **Codex's staged home follows the same rule**: `CODEX_HOME` is `<stagedConfigDir>/codex-home`, persistent across rounds; a round whose home already carries a staged session (`auth.json` present) reuses it rather than re-running the `codex login`/preflight/`codex plugin add` chain — `plugin add` is not idempotent against an already-installed plugin, so reuse is also the only safe path.
- **Forge-publication credentials** (what lets a Worker `git push`/`gh pr create` its own branch) are never the Operator's own `gh auth token`. Minting a repository-scoped, short-lived token before dispatch and handing it through as a named value, exactly like a model credential, is the Broker's still-unbuilt CREDENTIAL half (§1) — never inherited from the ambient environment. A Reviewer receives no forge-publication credential of any kind (§1, Reviewer row) because it never needs to write to the forge.
- **The Broker's credential-minting half is not implemented.** No minting code and no scoped-token API call exists — that wiring remains future work. What is fixed in place is the BOUNDARY the Broker will hand credentials across, and proves the boundary is real on the supported host. The Broker's AUTHORIZATION half (role/operation/target/input-version/ownership grant-checking in front of `effects.ts`) is a separate concern from credential minting and is built in `apps/cli/src/lib/broker.ts` — it does not require the OS-confinement or credential-minting work left undone here.

**Refusal conditions — when the contract cannot be met, dispatch must say so rather than silently degrade:**

- `sandbox-exec` is absent, or the generated profile fails to compile (`sandbox-exec` exits before ever reaching the target binary) — the probe treats this as a hard failure, never a silent fallback to an unconfined spawn.
- The host is not Darwin — this contract names no supported mechanism for that host yet; a future task adding one (§ "A container is out of scope," above) must extend this same table, not bypass it.
- A value the Worker/Reviewer genuinely needs (a model credential, the scoped push token) cannot be resolved — this is a dispatch-time failure the Controller reports, never a reason to widen the sandbox profile or fall back to full environment inheritance to make the dispatch "work anyway." **Implemented for the model-runtime credential:** `dispatch.ts`'s own pre-spawn check, once the boundary itself has resolved, refuses before any spawn when no subscription login was found to stage — `stageOAuthCredential` for Claude, the cached Codex session for Codex. There is no second route to fall back to, since no agent authenticates with an API key, so this check now reads that one fact. Its refusal (`missingSubscriptionLoginReason`) names WHERE this looked and HOW to sign in, in the dispatch's own stderr: for Claude, the `.credentials.json` path under the Claude config directory (`CLAUDE_CONFIG_DIR` when set, else `~/.claude`), the Keychain entry `Claude Code-credentials`, and `claude`'s own `/login`; for Codex, `auth.json` under `CODEX_HOME` (else `~/.codex`) or this host's credential store, and `codex login`. Never an API key, and never a bare "no credential" with nothing the operator can act on. Before this check existed, this exact gap produced 0-byte vendor output and a hang to the dispatch's own timeout ceiling rather than an immediate, named refusal.

For Codex subscription sessions, the trusted Controller reads only the cached `tokens.access_token` value before confinement, then runs `codex login --with-access-token` (reading that value from stdin) against the task-scoped `CODEX_HOME` — the real Codex CLI does not authenticate from a bare `CODEX_ACCESS_TOKEN` environment variable alone (live-verified: adding that variable to a process whose `CODEX_HOME` already carries a working `auth.json` breaks bearer auth entirely), so this step is what actually produces a working session: Codex's own `login` subcommand derives `account_id`/`refresh_token` and writes them, with the access token, into a real `auth.json` inside that scoped home. The operator's real `auth.json`, refresh token, home, and Keychain are never mounted or copied — only this freshly-derived, scoped one exists inside the confined `CODEX_HOME`. The bounded auth preflight (`runRealCodexAuthPreflight`) runs against this same scoped `CODEX_HOME`, never the operator's real one, so a login that produced a session Codex cannot actually use is refused before the developer loop starts, not silently accepted. The task-scoped Codex home also sets `shell_environment_policy.ignore_default_excludes = false` and excludes `CODEX_ACCESS_TOKEN` by name, so the bootstrap token is never handed to a repository-controlled subprocess Codex spawns; the confined child's own spawn environment carries `CODEX_HOME` alone, never a credential value. The sibling API-key exclude this policy once carried is gone with the key itself: no dispatch path allowlists a vendor key through from the Controller's own environment any more, so an operator's own unrelated key cannot reach the confined child to downgrade a staged session in the first place.

**What this does not close.** The staged `auth.json` is a real file, readable wherever `CODEX_HOME` is readable — and Seatbelt confinement has no concept of "which process in the tree may read this path," only which paths the WHOLE confined tree may reach (the same structural limitation § 3 item 2 above already discloses for network egress). A repository-controlled command Codex spawns can read that file directly off disk and exfiltrate it over the same outbound HTTPS access every Worker legitimately needs for the model runtime endpoint — filtering the environment variable closes the inheritance route, not the filesystem one, and this gap is not closed by anything in this file. Closing it for real needs either a mechanism not built here (a credential broker that never places a durable bearer token on any path the confined tree's own repository commands can reach) or a Codex-native, per-process filesystem scope Seatbelt cannot express and no documented way to configure was found. Subscription authentication for Codex, as implemented here, is accepted with this residual, structural gap disclosed rather than silently assumed closed.

## 4. What the dispatch wiring does

`apps/cli/src/lib/worker-boundary.ts` is the launcher the standalone probe (`isolation-probe.ts`) never was: it builds a real Worker/Reviewer profile (`buildWorkerSandboxProfile`) and resolves a real `sandbox-exec`-wrapped launch (`resolveWorkerBoundaryLaunch`), reusing the probe's own default-deny-plus-named-allowlist principle and Seatbelt string-literal escaping (re-implemented there, not imported — the probe's own script directory ships outside the published package). `dispatchRole` (`dispatch.ts`) calls it for an UNATTENDED dispatch whose repo has opted in.

**Always on where supported.** `DispatchOpts.unattended` (set on every automated `task run`/`dev-review-loop` developer and reviewer dispatch, and available on `vinaya dispatch --unattended`) marks a dispatch as unattended; there is no config setting behind it. On macOS the boundary is required, and an unavailable boundary refuses the dispatch before any spawn (§3's refusal conditions, applied literally — never a silent fallback). On any other host an unattended Claude dispatch runs as it always has, since no mechanism exists there. An unattended Codex dispatch refuses on such a host and names why, because its per-run `CODEX_HOME` — Vinaya's machine-state command rules and the staged login — exists only inside the boundary, and without it the run would use the operator's real `~/.codex`. This repo's own CI (`ubuntu-latest`) runs on Linux, so its behavior is unchanged.

**What a resolved launch actually differs from the probe's own contract, and why:**

1. **Network is denied by default, allowed only on ports 80/443, plus the ssh-agent socket denied specifically.** A real Worker must reach the model runtime endpoint to keep functioning as an agent (§1, Worker row) — the probe's own blanket `(deny network-outbound)` would starve it — but a blanket `(allow network-outbound)` would leave every other destination open too: a credential threaded into the confined env (item 6, below) is inherited by any subprocess a dispatched agent runs, and Seatbelt confinement has no notion of "which process in the tree may use this socket," only which destinations the whole tree may reach. Restricting to 80/443 closes every non-HTTP(S) exfiltration channel (a raw-socket beacon, DNS tunneling over a raw UDP socket, an SSH relay, any other port). **What it does NOT close, live-verified rather than merely undecided:** an HTTPS POST to an attacker-controlled host on port 443 is indistinguishable, at this layer, from the legitimate model-runtime call the confined process must be allowed to make — closing that needs a destination check above the port number, and live verification confirmed that Seatbelt's own `remote` filter cannot express one on this host: `(remote tcp "example.com:443")` and `(remote ip "<literal IP>:443")` both fail to compile with `sandbox-exec: host must be * or localhost in network address`, so no hostname/IP allowlist is expressible in a Seatbelt profile at all here. This is the concrete reason Anthropic's own `secure-deployment` documentation recommends an EGRESS PROXY rather than a sandbox-profile allowlist — a proxy is the only place that can actually inspect and gate the destination, and building one remains materially larger than this boundary itself, a deliberately deferred, separate item, neither silently built nor silently skipped. **DNS resolution reopens a narrower version of the same gap.** A hostname lookup never opens a raw UDP/TCP socket itself — it goes through `mDNSResponder` over a local unix-socket connection plus `mach-lookup` IPC — so the port-80/443-only restriction above would leave no confined dispatch able to resolve any model-runtime hostname at all, so the profile adds a scoped route to the resolver (`(allow network-outbound (remote unix-socket (path-literal "/private/var/run/mDNSResponder")))` plus `mach-lookup` to `com.apple.dnssd`/`com.apple.mDNSResponder`/`com.apple.mDNSResponderUnix`). That route is necessary — a confined agent cannot function on the declared supported host without it — but it also lets a confined process trigger arbitrary hostname lookups, which the resolver performs over the real network on the process's behalf: a resolution-based exfiltration channel (data encoded as subdomains of an attacker-controlled domain) distinct from, and not closed by, the HTTP(S)-proxy gap this item already names. Scoping it needs the same egress-proxy architecture as the port-443 gap, above — deliberately not built, disclosed rather than left implicit.
2. **Process-exec is allowed under a resolved allowlist** (the confined role's own worktree/allowed directory, the runtime interpreter's install dir, `git --exec-path` when resolvable, this dispatcher's own bun install directory (see below), the real `node` install directory the task-tools MCP server starts (see below), the active Apple developer directory (see the next paragraph), and whatever of `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`, `/usr/local/bin`, `/opt/homebrew/bin` exist on this host), not the probe's single self-re-exec literal — a real Worker runs its own declared toolchain.

   **The active Apple developer directory is granted read AND exec (never write), resolved at launch.** `/usr/bin/git` on the declared-supported host is not the real git — it is a thin Command Line Tools `xcrun` shim that, on first use, dlopen's `/Library/Developer/CommandLineTools/usr/lib/libxcrun.dylib` and re-execs the real tool from UNDER the active developer directory. A profile that granted `/usr/bin` read+exec but nothing under that developer directory therefore let `git` START but crash before doing anything, with `xcrun: error: unable to load libxcrun (… file system sandbox blocked open())` — found live once the worker sandbox became always-on, failing every Developer, code-reviewer and security dispatch on the Principal's Mac. `resolveWorkerBoundaryLaunch` resolves the directory fresh from `xcode-select -p` at every launch (never one hardcoded path — a host may point it at full Xcode or at the Command Line Tools), `realpath`s it, and adds it to the exec-allow list ONLY when it actually exists, so it carries both exec (its own `process-exec` rule) and read (the read-allow list is derived from the same set), never write (it is absent from every `file-write*` allow, and the "close every other writable path" deny covers it). `null` off darwin or on a host `xcode-select` cannot answer for — the profile then simply grants nothing extra, the same best-effort posture `git --exec-path`/`which bun` resolution already takes. This does not reopen the credential-helper gap §3 item 4 closed: the Keychain row's file AND `mach-lookup` denial (§3 item 3) blocks a credential helper's actual secret-extraction route regardless of which binary, or which copy of one, attempts it — the process-exec allowlist governs what can RUN, not what can reach `securityd`. A concretely-resolved helper binary (`git-credential-osxkeychain` and equivalents, under a resolved `git --exec-path`) is additionally named as its own layered `process-exec` deny, for defense in depth. **This repo's own toolchain is bun**, and `CANDIDATE_SYSTEM_BIN_DIRS` never covered a standard bun install (`~/.bun/bin`, under the otherwise fully-denied real `HOME`): a live test that passes `binaryPath: process.execPath` (the test runner's own bun binary) incidentally grants bun's own directory as `runtimeDir` and masks that a confined role given a DIFFERENT `binaryPath` — the real production shape, a vendor coding-agent binary, not bun itself — could not exec `bun` at all, breaking both the confined role's build/test subprocesses and `writeDispatchSettings`'s own `bun "${scriptPath}"` PreToolUse hook command. `resolveBunExecDir` (`worker-boundary.ts`) therefore cannot assume `process.execPath` IS the bun binary — that holds only when the dispatcher process is itself bun-hosted, as in this repo's own dogfooding (`bun apps/cli/src/index.ts`). The published, declared-supported entry point (`apps/cli/scripts/build.ts`'s `--target=node` build, a `#!/usr/bin/env node` shebang) runs under Node, where `process.execPath` never contains `bun` at all, which would silently grant exec over the wrong directory on the production entry point. It resolves `bun` the same "never assumed, verified live" way `resolveGitExecPath` already resolves `git` — a `which bun` lookup, independent of which runtime hosts the dispatcher process.

   **The real `node` install directory the task-tools MCP server starts is granted read AND exec (never write), resolved at launch.** A confined Claude or Codex session that launches the task-tools MCP server (`adapters.ts`'s `node <bin>` self-host registration, and `npx`'s own node) crashed with `EPERM … posix_spawn 'node'`: the `node` on PATH resolves THROUGH its symlink to a real binary outside every granted directory. Homebrew links `/opt/homebrew/bin/node` into `/opt/homebrew/Cellar/node/<version>/bin/node`, so the `/opt/homebrew/bin` grant never reaches the Cellar `bin/` the exec actually lands in; nvm puts it under `~/.nvm/versions/node/<version>/bin/node`, inside the otherwise fully-denied real `HOME`. `resolveRealNodeExecDir` (`worker-boundary.ts`) resolves it the same `which node` → `realpath` → `dirname` way `resolveBunExecDir` resolves `bun`, so the symlink is followed to the real install `bin/` on either host layout, and adds it to the exec-allow list ONLY when `node` exists — carrying exec (its own `process-exec` rule) and read (the read-allow list is derived from the same set), never write, `null` and nothing extra granted on a host with no `node`. A profile-rendering test proves the grant lands on both a Homebrew-style Cellar path and an nvm-style versioned path.
3. **`HOME` is not replaced with a synthetic directory.** The confined child's `HOME` env value is the genuine home path — so a tool that constructs `$HOME/.something` resolves predictably — while the PROFILE still denies file access to that real home path except for the resolution's own named, NARROW carve-outs (see items 4–5, below): the confined directory (read-only during round-1 bootstrap), a fresh scratch tmp dir, and the exact, absolute, task-scoped files and directories this dispatch's own caller names (item 5, below). The env value and the filesystem permission are independent; Seatbelt enforces the latter.
4. **Round-1 Developer bootstrap: the confined directory is READ-ONLY, with only `.git`/`.worktrees` writable — now a residual fallback, not the steady state.** O1 moved worktree creation to the (trusted) driver side this item's own last sentence named as future work: `dev-review-loop.ts`'s `createTaskWorktree` creates the task's own worktree, OUTSIDE any sandbox, before the first Developer dispatch ever runs — so `devWorktreeDir` (`dispatchDeveloperOnce`) is non-null from round 1 on in the normal case, and the brief's own Step 0 (`packages/aeg-core/src/brief-render.ts`) now only ENTERS the worktree (`cd .worktrees/<branch> && bun install …`) rather than running `git worktree add` itself. The grant is kept rather than removed — a disclosed, inert residual, not a reason to STOP, since the fallback is now purely defensive (an attended operator manually re-running an older Step 0's own `git worktree add` by hand would still need it) and any other role falling back to the repo root (a Reviewer with no candidate built) is unaffected either way.
5. **No machine-wide root is exposed at all, except the exact FILES this dispatch's own outbox line and session record live at.** The `~/.vinaya` directory holds its own `config.json` and every other task's and repo's state on the machine, so it is neither readable nor writable as a directory, and no bare top-level `outbox`/`dispatch-resume` name is granted either: that would let a confined role forge another task's audit log or steal another task's live vendor `resumeId` and resume its session directly. Scoping the write grant to `outbox/<repoSegment>` and `dispatch-resume/<repoSegment>` — THIS dispatch's own repo only — is still not enough, because that DIRECTORY is shared by every OTHER task's and role's own outbox line / resume record for the same repo (neither path nests one directory per task or role): a confined Developer could read a CONCURRENTLY-RUNNING code-reviewer's or security reviewer's own resume record for the SAME task and resume that session directly with the vendor binary already in the profile's own exec-allow list. So the grant is `WorkerBoundaryLaunchOpts.vinayaHomeWritableFiles` — the exact outbox/resume-record FILE this dispatch owns, via `(literal ...)`, never `(subpath ...)` — so no sibling task's or role's file in the same directory is exposed, verified live (a sibling literal path in the same directory, and a directory listing of it, both still fail with a real permission denial; the target file itself, whether pre-existing or written for the first time, both succeed).    **The grants now follow the run-file layout, and are absolute rather than relative to one root.** Every file a task's run writes lives under `<runtimeDir>/tasks-execution/<task>/` (`apps/cli/src/lib/run-paths.ts`), while the telemetry outbox stays under the Vinaya home — two roots, so `WorkerBoundaryLaunchOpts` takes absolute `extraWritableFiles`/`extraWritableDirs`/`extraReadOnlyDirs` instead of subpaths of a single `vinayaHomeDir`. What a confined dispatch is granted is unchanged in kind, and narrower in effect: its own session record (`sessions/<role>-<agent>.json`) and its own telemetry outbox line as exact `(literal ...)` files; its own task log file (see the next paragraph); its own round's work directory (`rounds/<n>/<role>-work…`) for a reviewer; and its own `hooks/` directory read-only, with the one documentation log file inside it named writable. The scope that used to be part of a FILENAME in one flat per-repository directory is the FOLDER now, so a sibling task's session record, held verdicts and hand-off files are not merely unnamed — they are in a directory this profile never mentions. `vinaya.config.json` is still never named, and the containing directory is still pre-created by the trusted, unsandboxed controller before this resolution runs.

   **The task log file is granted writable as a literal, never its folder.** A confined role's own `log()` calls record its events, and when the configured destination is a log SERVER the role cannot confirm one from inside the boundary — the real HOME where `gh` keeps its delivery credential is denied, so the trust-anchor read fails — so `log()` falls back to the FOLDER destination, `<runtimeDir>/logs/<repoSegment>/<task>.ndjson`. No grant named that file, so the fallback append died with "log outbox target could not be opened", silently losing the role's whole telemetry stream — the third of the three failures the always-on sandbox introduced. `dispatch.ts` now resolves that folder path (forcing the folder destination, exactly what the child falls back to) and adds it, plus its single rotation backup `<task>.1.ndjson` (`log-sink.ts` writes it when the live file crosses its size cap, so a cross-the-cap append inside the boundary cannot silently reintroduce the same denial), to `extraWritableFiles` — each as an exact `(literal ...)`, never the containing `logs/<repoSegment>/` folder, whose siblings (every OTHER task's log) stay unnamed. The folder is pre-created by the trusted, unsandboxed controller before this resolution runs, so the confined child's own append needs only the literal grant plus the metadata-traversal its parent already carries.
6. **A real model-runtime credential route exists.** `WORKER_ENV_ALLOWLIST_KEYS` has no credential-shaped entry, and the profile denies both the real HOME (where an OAuth session file typically lives) and the Keychain, so without a route a confined dispatch could not function as an agent. The route is a STAGED SUBSCRIPTION LOGIN, never an environment-variable key: §3's "Model runtime credentials" bullet has the mechanism per vendor (`stageOAuthCredential`'s scoped `CLAUDE_CONFIG_DIR` copy for Claude, the task-scoped `CODEX_HOME` for Codex, a refusal for Gemini), and this same section's refusal-conditions bullet has the pre-spawn refusal that fires when none resolves. `buildWorkerEnv` carries no per-vendor API-key variable — no agent authenticates with an API key, so the confined child's environment has no route for one to arrive by at all.

7. **`process-fork` is explicitly allowed.** A SEPARATE Seatbelt operation from `process-exec`, denied by `(deny default)` like everything else unless named. Asserting the generated profile as TEXT alone cannot show this; only a real confined shell through real `sandbox-exec` does: without the allow, a confined child could exec its own toolchain (item 2, above) but could not FORK to run any of it — `bash: fork: Operation not permitted` on something as basic as a subshell or a command substitution. Only a live test that spawns a real subprocess catches that. `(allow process-fork)` takes no filter (fork has no path/target argument the way exec and file operations do) — the forked/exec'd child remains scoped by every OTHER rule in this profile exactly as before.
8. **`resolveWorkerBoundaryLaunch` execs the SAME `realpathSync`'d binary path it derives `runtimeDir`/`execAllowDirs` from.** Deriving `runtimeDir` (and therefore the profile's own process-exec allowlist) from `realpathSync(opts.binaryPath)` while passing the ORIGINAL, un-realpath'd `opts.binaryPath` as the `sandbox-exec` exec target would break the officially documented macOS install layout. Seatbelt's `process-exec` check matches the LITERAL path handed to `execve`, before any symlink resolution of its own — live-verified: a PATH entry symlinked into a separate directory (`~/.local/bin/claude` → `~/.local/share/claude/versions/<version>`, the exact shape Anthropic's own macOS installer produces and `dispatch.ts`'s own `which claude` resolution returns) was denied outright (`execvp() ... Operation not permitted`) even though the profile's exec-allow rule correctly covered the REALPATH'd target directory — the mismatch was between what was GRANTED and what was actually EXEC'D, not a missing grant. That would defeat the boundary on the mainstream, documented install of the declared-supported host even with a valid staged subscription credential: the sandboxed exec itself would never reach the vendor binary. So `opts.binaryPath` is resolved exactly once and that SAME value is used both to derive the exec-allow grant and as the literal `sandbox-exec` argument — the two cannot diverge structurally.
9. **`file-read-metadata` is allowed unconditionally, for every path, not only the named allow/read-only lists above.** A real `node` binary walks from its own entry-script path up through EVERY ancestor directory to the filesystem root, `lstat`-ing each one as part of its own module resolution and `realpath` of the entry script — live-reproduced: with no rule naming any ancestor of `allowedDir`/`runtimeDir` (e.g. `/private`, itself an ancestor of macOS's own tmp layout), a confined `node <script>` failed immediately with `EPERM: operation not permitted, lstat '/private'`, before the confined role — whatever it is — ever ran a line of its own code. This does not reproduce against `bun` (a live test with a `bun`-hosted `binaryPath` masks the gap) but hits any Node-hosted vendor CLI: `codex`/`gemini` are commonly shipped as `node`-shebang npm packages, unlike `claude`, which is a native Mach-O binary on this authoring host and unaffected either way. `file-read-metadata` is a SEPARATE Seatbelt operation from `file-read*` (content) — granting it exposes only a path's existence/size/permissions/mtime, never its CONTENTS; verified live that the real HOME/Keychain/OAuth-credential `file-read*` denies are completely unaffected by this rule (a confined read of a real credential file's own CONTENTS still fails `EPERM` with this rule present). Scoping this to only the specific ancestor directories each dispatch's own `allowedDir`/`execAllowDirs`/`vinayaHomeDir` actually need would require enumerating every possible ancestor of an unpredictable, host-varying allowlist (a git/bun/homebrew install path, the vendor binary's own real install location) — judged intractable and no more secure than this single blanket metadata-only allow, since metadata alone lets a confined process learn only that SOME path exists, never what it holds.
10. **O2: the operator's own git configuration is granted READ-ONLY, by two exact paths, never the whole real `HOME`.** `~/.gitconfig` and `~/.config/git` were denied outright by the HOME-deny rule (item 2, above) until this task — a confined `git` command inside the worktree could exec (item 2's own exec-allow list already covers the real binary) but could not READ the operator's own identity, aliases or `[include]` directives, since those paths sit under the denied real home and nothing named them as a carve-out. `gitConfigReadOnlyPaths(realHome)` (`worker-boundary.ts`) names exactly these two paths; `resolveWorkerBoundaryLaunch` folds them into `readOnlyDirs` unconditionally, the same narrow, named-grant discipline the developer directory (item 2) and the task-tools `node` directory (item 2's own second paragraph) already use. Read-only: nothing inside the sandbox is trusted to rewrite the operator's own git configuration.

## 5. The run-directory guard — owner-only, symlink-refusing, with one exemption above the runtime root

Every run-file directory under `runtimeDir` (`apps/cli/src/lib/run-paths.ts`'s `ensureRunDir`, itself a thin wrapper over `@attalabs/aeg-core`'s `mkdirNoSymlinks`, exported so `packages/aeg-core`'s own control-store writers share the identical check rather than a second copy) is created and re-asserted owner-only (mode `0700`) on every write, walking one path segment at a time from the filesystem root down to the target directory. This is a co-tenancy defense, not a hardening nicety: `runtimeDir` is a shared, configurable tree, and any account able to write into it before this process's own run can pre-plant a symlink or a wrong-owner directory at a missing ancestor — `mkdirSync(dir, { recursive: true })` treats an existing symlink-to-directory as already present and silently follows it, so every writer reaching this store's own file operations next would operate inside whatever real directory that symlink resolves to.

The guard draws its line at `runtimeDir` itself, called `trustedRoot` in `mkdirNoSymlinks`'s own signature:

- **At or below `runtimeDir`** — this store's own tree. A symlink at any segment here is refused outright, unconditionally, whether or not this call happens to be the one that finds it "pre-existing": a co-tenant who plants a symlink below a shared `runtimeDir` must be caught regardless of ordering. A real directory here with an owner other than this process's own user, or a mode wider than this check trusts, is refused the same way.
- **Above `runtimeDir`** (its own ancestors, never this store's own territory) — a symlink here is tolerated, but never blindly. Its target is resolved to a real path and that REAL directory is ownership/mode-checked exactly as a non-symlink ancestor already is; the symlink's own metadata is never consulted. This exemption exists because an operating-system-owned ancestor above `runtimeDir` can legitimately be a symlink — the default temp root on the declared-supported host resolves through exactly one (`/var` → `/private/var`) — and refusing it outright would make every run-directory creation under the platform's own default temp root fail on an otherwise untouched checkout, with no attacker and nothing to refuse.

What this does NOT relax: a symlink planted below `runtimeDir` is still refused, full stop, and the ownership/mode trust check itself is identical in both zones — only WHICH paths get the "resolve through it" treatment versus the "refuse outright" treatment changes, and that split is drawn once, structurally, at `runtimeDir`, never by matching a known temp-root path by name.

**`extraFiles` resolves through its own parent, never the whole path.** `buildWriteAccessScope`'s `extraFiles` entries are always files that do not exist yet at scope-build time (the Developer has not written its confidence/round-response answer this round) — resolving one the same way `allowedDir` is resolved (`realpathSync` on the whole path) throws on the not-yet-existing leaf and falls back to it RAW, unresolved. `write-access.mjs`'s own live comparison resolves the opposite way — `realpathSync(path.dirname(filePath))`, joined with the basename — and its PARENT does exist (`dev-review-loop.ts`'s `dispatchDeveloper` creates that round's Developer folder before this dispatch ever runs). **What this does not do.** It does not replace §§3–4's Seatbelt boundary — that boundary confines the underlying OS PROCESS (what files/sockets/mach services it can reach) on the one host it is proven on; this policy constrains what TOOL CALLS the vendor's own agent loop will make in the first place, on every host, the same distinction §2 already draws for the background-deny hooks. It does not widen what a role's doctrine already permits — every `allow` entry here names a command already documented in `roles/developer.md`/`roles/reviewer.md`/`roles/security.md` as that role's own. It does not confine the CONTENT a `Write`/`Edit`-allowed file can hold, only WHICH paths are writable at all.

**O3 — this is detection after a turn, not confinement during one, and here is exactly what it cannot see:**

- **A read of a secret.** The check hashes WRITES (paths that changed on disk) and scans OUTPUT already produced; it has no visibility into a `Read`/`cat`/`security find-generic-password` call that merely copies a credential's bytes into the agent's own context without ever writing them to a path this task hashes or printing them to the dispatch's own stdout in a recognized shape. Exfiltration through the model's own next response, worded to evade the patterns in O2, is not caught here.
- **A request to a listed host.** Every request to a domain §4a/§4b's own `allowedDomains`/`network_proxy.domains` permits (GitHub, the npm registry, the model runtime endpoint) is, at this layer, indistinguishable from a legitimate one — this check never inspects network traffic at all, only the filesystem and the turn's own recorded output, so a credential value tunneled out over an otherwise-permitted HTTPS connection is invisible to it, exactly as §4's own disclosed egress gap already states for the confinement layer itself.
- **A change reverted before the check runs.** The check's own "after" hash is taken once, when the dispatch returns — a path changed and then changed BACK to its original content before that moment (inside the SAME turn, by the SAME confined process) hashes identical to its "before" state and is invisible to a before/after comparison by construction. Detecting an intermediate state needs a continuous audit log of every write, not two snapshots.
- **Access through a route outside the vendor sandbox.** This check runs from the trusted Controller, after the vendor process has already exited — it has no way to observe, and therefore no way to refuse, anything that happened through a route §§3–4/§4a/§4b's own confinement never covered in the first place (the disclosed HOME-read gap for Codex, the unverified Keychain/credential-helper/socket/parent-process rows — §8, below). A gap in the DURING-turn confinement is not narrowed by an AFTER-turn hash check that only ever looks at the paths this task names; it is an entirely separate failure mode this section's own mechanism cannot compensate for.

This section's mechanism is a backstop against a turn that WROTE where it must not have, or OUTPUT a credential shape this task recognizes — the same honest-miss-only posture `loop.md`'s own Documentation read-gate already discloses for itself ("an honest miss is always caught... it buys nothing against a session already willing to fabricate evidence"). It is never presented as, and must never be read as, a replacement for the confinement §§3–4/§4a/§4b describe.
