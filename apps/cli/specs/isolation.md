# Isolation — the task boundary a dispatched agent runs inside

Status: draft

This file is the durable contract `worker-isolation-v1` task 1 (`#549`) exists to produce: it names every actor that touches a dispatched task, what each one is trusted to do, and the mechanism that makes the untrusted actors' limits real rather than a convention. It is written before any credential-wiring change lands — `dispatchRole` (`apps/cli/src/lib/dispatch.ts`) still spawns every role with full environment inheritance and no filesystem confinement today; this file specifies the target boundary and Part 2's probe proves the chosen mechanism can enforce it on this host. Wiring `dispatchRole` itself to the mechanism below is a later task's surface (`task-operator-v1`, `#558`), not this one's — see "What this task does not change," below.

## 1. The six boundaries

<!-- AEG:CLAIM: apps/cli/src/lib/dispatch.ts contains:const child = spawn(binaryPath, spawnArgs, { -->
Every dispatched role today runs through one chokepoint, `dispatchRole`'s single `spawn(binaryPath, spawnArgs, …)` call, with `env: { ...process.env, VINAYA_RUN_ID, VINAYA_ROLE, VINAYA_TASK, VINAYA_ROUND }` — full parent-environment inheritance plus four attribution variables, no `cwd` override, no OS-level confinement. The table below is the target contract that call site is measured against; "Permitted" is what the actor MAY do under the contract, "Forbidden" is what today's spawn allows that the contract withdraws.

| Boundary | What it is today | Trust level | Permitted operations | Forbidden operations |
|---|---|---|---|---|
| **Controller** | The `vinaya` CLI process itself — the driver code in `apps/cli/src/lib` (`dispatch.ts`, `dispatch-task.ts`, `dev-review-loop.ts`) that decides what to dispatch and reads the result. Runs as the Operator's own user, in the Operator's own shell. | Fully trusted | Read/write the Operator's own `HOME`, keychain, and ambient environment; hold the Operator's forge login (`gh auth token`) and model runtime credentials; spawn Worker, Reviewer and Repository-subprocess children; read/write the local outbox (`~/.vinaya/`); post forge writes (via `forge-write.ts`'s principal allowlist, `refuseUnlessPrincipal`). | Nothing withheld — it is the root of trust everything else is scoped from. It never itself executes brief-authored or PR-authored instructions (`lintReviewerPrompt`, `loop.md` "Reviewers" — a reviewer's prompt is facts-only, never developer- or PR-body-authored prose) — that separation is what keeps the controller trustworthy enough to hold these credentials. |
| **Worker** | The dispatched Developer role's vendor coding-agent child process (`claude`/`codex`/`gemini`, `role: 'developer'`), executing the frozen brief inside its own worktree (`.worktrees/task/<tranche>/<n>`). | Untrusted execution surface — runs brief-driven, and after round 1, review-finding-driven, agent-authored tool calls, including arbitrary `Bash` | Read/write inside its own worktree; run its declared toolchain (typecheck/lint/test/build) there; use a repo-scoped, short-lived forge credential for `git push` and `gh pr create`/`pr edit` on ITS OWN branch only (see §3, Broker); reach the model runtime endpoint to keep functioning as an agent. | Read the Operator's `HOME` outside its worktree; read or write the OS keychain; invoke an OS credential helper (`git-credential-osxkeychain` or equivalent); reach the Operator's ambient sockets (`SSH_AUTH_SOCK`, a container/docker socket); signal or introspect the parent (controller) process; read any environment variable the controller did not explicitly allowlist (in particular, never the Operator's own broad `gh auth token`/`GH_TOKEN`). These six are exactly Part 2's probe assertions. |
| **Reviewer** | The dispatched code-reviewer/security role's vendor coding-agent child process (`role: 'code-reviewer'` / `role: 'security'`), dispatched fresh every round, never resumed (`loop.md` "Reviewers"). | Untrusted execution surface, narrower than Worker | Read the repository at the judged head (its own checkout or worktree, read-only in intent); write `findings.txt`/`report.txt`/`objectives.txt` to its own driver-chosen work directory (`reviewerWorkDir`, under `~/.vinaya/dev-review-loop/<task>/…`); reach the model runtime endpoint. | Everything Worker is forbidden, PLUS any forge-write credential at all (a Reviewer never runs `git push` or `gh pr`/`gh api` writes — the driver posts verdicts on its behalf after both roles return, `loop.md` "Publication"). A Reviewer holding even Worker's scoped push token would be strictly more privilege than its job needs. |
| **Operator** | The human running `vinaya` commands from their own shell. | Root of trust | Everything the Controller can do, plus what only a human can do: sign in through a real browser, tick `[principal]` Test Plan boxes, apply the `vinaya/waiver:docs` label, post Principal rulings, merge. Supplies (or, once a Broker exists, delegates minting of) every credential the Controller, Worker and Reviewer boundaries ultimately depend on. | Nothing withheld by this contract — the Operator is the human this whole boundary protects, not a boundary constrained by it. |
| **Repository subprocess** | Trusted, controller-spawned CLI tools that are NOT a coding agent and never execute brief- or PR-authored instructions: `gh` (`packages/aeg-forge-state/src/gh.ts`, `github-token.ts`), `git`, and `vinaya check`'s own custom-check children (`apps/cli/src/checks/runner.ts`). | Trusted, but env-scoped by convention already (see §2) | Read/write whatever the Controller explicitly grants it via its constructed environment — `gh`/`git` today get the full ambient environment plus a PATH augmentation (`systemEnv`, `gh.ts`); a custom check gets exactly `ENV_BASELINE_KEYS` plus its own declared `CheckSpec.env` entries (`buildCheckEnv`, `checks/runner.ts`). | Anything the Controller does not pass into its constructed environment — this row already demonstrates the allowlist pattern §3 extends to Worker/Reviewer; it forbids nothing new because it is Controller-authored code, not agent output. |
| **Broker** | Not yet implemented — the component this contract specifies but does not build (Part 2 proves the underlying OS mechanism only). Its job: mint the ONE scoped, short-lived forge-write credential a Worker needs to push its own branch and open its own PR, and resolve the model runtime credential each dispatched child needs, without ever handing either child the Operator's own broad `gh auth token` or a wholesale environment spread. | Design-only in this task; a real implementation is `task-operator-v1`'s surface (`#558`) | Issue a Worker a credential scoped to: this one repository, `contents:write` + `pull-requests:write` only, expiring well inside one dispatch's timeout window; resolve and hand through the specific model-auth value (an API key, or a narrowly-scoped read of the vendor CLI's own on-disk session credential) each dispatched child needs to keep functioning as an agent. | Mint a credential scoped to more than one repository, to the Operator's own account/login, or to forge-admin/merge scopes; hand a Reviewer any forge-write credential at all (see Reviewer row); ever be the Worker's OR the Reviewer's own environment inheriting the Controller's ambient `process.env` wholesale — every value the Broker hands through is named, not spread. |

## 2. Existing precedent this contract extends, not invents

<!-- AEG:CLAIM: apps/cli/src/checks/runner.ts contains:const ENV_BASELINE_KEYS = ['PATH', 'LANG', 'HOME', 'HTTPS_PROXY', 'HTTP_PROXY', 'NO_PROXY', 'TMPDIR'] as const -->
An explicit env allowlist already exists in this codebase, just not on the dispatch path this contract governs: `apps/cli/src/checks/runner.ts`'s `buildCheckEnv` constructs a custom check's child environment from `ENV_BASELINE_KEYS` (`PATH`, `LANG`, `HOME`, the proxy variables, `TMPDIR`) plus each check's own declared `CheckSpec.env` entries — never a `{ ...process.env }` spread. `dispatchRole`'s own attribution variables (`VINAYA_RUN_ID`/`VINAYA_ROLE`/`VINAYA_TASK`/`VINAYA_ROUND`) are already set only on the child's environment, never mutated onto the parent's (`apps/cli/specs/log.md`, "the CHILD process's environment only"). Neither precedent scopes what the child inherits FROM the parent — that half is what this contract adds, and what `buildCheckEnv`'s pattern (name every key explicitly, never spread) generalizes to Worker/Reviewer.

<!-- AEG:CLAIM: apps/cli/src/lib/dispatch.ts contains:export function writeDispatchSettings(): string | null { -->
A second, narrower precedent already exists on the dispatch path itself: `writeDispatchSettings` (`dispatch.ts`) generates a per-dispatch Claude Code `settings.json` (`--settings <path>`) denying backgrounded `Bash`/`Agent` calls and whole-suite test runs, and setting `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`. This is a tool-permission boundary enforced by the vendor's own hook mechanism, not a process/OS boundary — it constrains what tool CALLS the agent may make, not what the underlying OS process can reach if it makes them anyway (a `Bash` call the hook allows can still `cat ~/.ssh/id_ed25519` today). The two boundaries are complementary, not redundant: this contract's OS-enforced boundary is the backstop for exactly the tool calls the vendor-hook boundary permits.

## 3. Mechanism, host capabilities, authentication path and refusal conditions (O3)

**Chosen mechanism: Apple Seatbelt (`sandbox-exec` + a generated `.sb` profile).** This is the mechanism Part 2's probe (`apps/cli/scripts/isolation-probe.ts`, `.sb` profile fixture) proves. It was chosen over a container for the reason the brief's own Traps name: "a container with privileged host mounts is not isolation," and this repo's supported dispatch host today is the Operator's own macOS development machine — Seatbelt is the OS-native, no-install, no-daemon mechanism available there, and it enforces the boundary at the kernel (MAC framework) layer, not by convention.

- **Supported host:** macOS (Darwin). `sandbox-exec` ships with the OS at `/usr/bin/sandbox-exec` — confirmed present and functional on this task's own render host. Apple has marked the `sandbox-exec` command-line tool deprecated (it prints no runtime warning on this host but Apple's own documentation carries the deprecation notice) while the underlying kernel enforcement (the Sandbox/MAC framework, `libsandbox`) remains the mechanism macOS's own App Sandbox and every shipped system daemon profile continue to build on — this contract depends on the kernel enforcement, not the CLI wrapper's long-term support status, and names the CLI wrapper as a documented replaceable adapter (a future migration to the `Sandbox.framework` C API or a maintained macOS-sandboxing wrapper package would swap the invocation in `apps/cli/scripts/isolation-probe.ts` without changing this contract's boundary rows). **Primary source:** Apple's `sandbox-exec(1)`/`sandbox_init(3)` manual pages and the Seatbelt profile language they document (`(version 1)`, `(allow …)`/`(deny …)` rules over `file-read*`/`file-write*`/`network-outbound`/`signal`/`process-info*`/`process-exec` operations, path filters via `subpath`/`literal`/`path-literal`).
- **A container is out of scope for this task's probe** (no Linux/CI dispatch host is in scope here — Issue #549's Out explicitly excludes "whole-repository process extraction," and the tranche's other open tasks (`task-log-v1` `#550`, `control-store-v1` `#551`, `task-operator-v1` `#558`) are where a Linux/CI-hosted equivalent (a rootless container with no privileged host mount, an explicit `--env` allowlist, and a bind-mounted worktree as the only writable path) would be specified, following this same six-row contract, when that host is actually supported.

**What the probe demonstrates (mapped to the six Worker/Reviewer forbidden operations above):**

1. **Environment** — the sandboxed child's own `spawn`/`env` option carries an explicit allowlist (the same discipline as `buildCheckEnv`), never a `{ ...process.env }` spread; a value the parent holds but does not name (proven with a marker variable) is absent from the child's `process.env`.
2. **HOME** — a Seatbelt `(deny file-read* file-write* (subpath "<real $HOME>"))` rule, with an `(allow …)` carve-out for the child's own worktree/work directory (which, on a developer machine, is itself typically a subpath of `$HOME` and needs its own explicit exception) and for a synthetic `HOME` the child is launched with instead.
3. **Keychain** — the same deny rule extended to `~/Library/Keychains`, `/Library/Keychains`, `/System/Library/Keychains`.
4. **Credential helper** — `(deny process-exec (literal "<path to git-credential-osxkeychain>") (literal "/usr/bin/security"))`: the child cannot invoke the OS credential-helper binaries at all, so a `git credential fill` inside the sandbox cannot resolve a keychain-stored token even if git itself is reachable.
5. **Socket** — a `(deny network-outbound (remote unix-socket (path-literal "<canonicalized SSH_AUTH_SOCK>")))` rule. The path MUST be canonicalized (`realpath`) before it is written into the profile — `/var/run/…` on this host resolves to `/private/var/run/…`, and Seatbelt matches the canonical path, not the symlinked convenience path a shell sees in `$SSH_AUTH_SOCK`.
6. **Parent process** — `(deny signal)` and `(deny process-info* (target others))`: the child cannot `kill(ppid, 0)` to probe the parent's liveness, nor introspect it through `libproc`/`ps`. `(target others)` is load-bearing, not cosmetic — an unscoped `(deny process-info*)` also blocks the confined runtime's own self-introspection at startup and crashes it (`SIGTRAP`) before it ever reaches the probe's checks; scoping to `others` keeps the boundary (the child cannot inspect its PARENT) while leaving the child free to inspect itself.

**Three non-obvious constraints the probe surfaced, load-bearing for any real wiring later:**

1. **The confined process's `cwd` must itself be inside an allowed subpath.** Both `bun` and `node` walk up from `cwd` at startup resolving config/module files; launching the sandboxed child with `cwd` still pointed at a denied directory (the real repo tree, in the probe's own case) fails opaquely rather than cleanly — a real Worker/Reviewer dispatch MUST set `cwd` to the confined directory it is being handed (its own worktree), never leave it defaulted to the controller's `process.cwd()` the way `dispatchRole` does today (§2, "What this task does not change").
2. **The entry script/binary the confined child runs must itself live inside an allowed subpath.** The probe copies itself into its own scratch directory before invoking `sandbox-exec` rather than pointing the sandboxed child at its real on-disk location under the repo tree — a Worker/Reviewer dispatch already satisfies this naturally (the vendor CLI binary and the target worktree both need their own explicit allow rules; a task's own worktree is exactly the directory this contract intends to leave readable).
3. **A denied `unix-socket` connect surfaces as `ENOENT`, not `EPERM`.** Apple's sandbox deliberately reports a Seatbelt-denied `network-outbound`/`unix-socket` connection the same way as a socket that was never there, rather than confirming the resource exists — code relying on this boundary must never treat `ENOENT` from a socket connect as proof of absence; the probe treats "a path was resolved to test, and the connection failed for any reason" as blocked, full stop.

**The runtime's authentication path inside the boundary.** A dispatched agent (Worker or Reviewer) is itself a vendor coding-agent CLI — it needs its OWN model-runtime credential to keep functioning at all, which is a DIFFERENT concern from the forge-publication credential the traps call out separately:

- **Model runtime credentials** (what the vendor CLI needs to keep answering) are resolved once by the Controller and passed through the same named-allowlist env construction as every other value the child receives — never a blanket `HOME`/keychain read, since the sandbox denies both. Where a vendor CLI's own auth lives in an on-disk session file rather than an env var, the Controller reads that ONE file itself (outside the sandbox, where it already has full HOME access) and hands the resolved credential through as a named env value or a narrowly `(allow file-read* (literal …))`-listed synthetic path inside the sandbox — the sandbox profile never grants blanket access to the real credential file's real location.
- **Forge-publication credentials** (what lets a Worker `git push`/`gh pr create` its own branch) are never the Operator's own `gh auth token`. They are the Broker's one job (§1): mint a repository-scoped, short-lived token before dispatch and hand it through as a named value, exactly like a model credential — never inherited from the ambient environment. A Reviewer receives no forge-publication credential of any kind (§1, Reviewer row) because it never needs to write to the forge.
- **This task does not implement the Broker.** No minting code, no scoped-token API call, ships in this PR — `task-operator-v1` (`#558`) is where that wiring is a declared Surface. What this task fixes in place is the BOUNDARY the Broker will hand credentials across, and proves the boundary is real on the supported host.

**Refusal conditions — when the contract cannot be met, dispatch must say so rather than silently degrade:**

- `sandbox-exec` is absent, or the generated profile fails to compile (`sandbox-exec` exits before ever reaching the target binary) — the probe treats this as a hard failure, never a silent fallback to an unconfined spawn.
- The host is not Darwin — this contract names no supported mechanism for that host yet; a future task adding one (§ "A container is out of scope," above) must extend this same table, not bypass it.
- A value the Worker/Reviewer genuinely needs (a model credential, the scoped push token) cannot be resolved — this is a dispatch-time failure the Controller reports, never a reason to widen the sandbox profile or fall back to full environment inheritance to make the dispatch "work anyway."

## What this task does not change

`dispatchRole`'s own `spawn` call (`apps/cli/src/lib/dispatch.ts`) still inherits the full parent environment today, unchanged by this PR — this file specifies the target boundary and Part 2's disposable probe proves the chosen mechanism on this host; it does not wire `dispatchRole` to invoke `sandbox-exec`, does not add a `vinaya.config.json` key, and does not touch `writeDispatchSettings`. Wiring the Worker/Reviewer spawn path to this contract, and building the Broker described in §1/§3, are `task-operator-v1`'s declared Surface (`#558`), which conflicts with this task only in the shared-directory sense (`Conflicts-with`, both tasks' briefs) — it depends on this one having chosen and proven the mechanism first.
