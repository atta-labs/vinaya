# The dev-review-loop — command, rounds, exits, publication and pause

Status: draft

`vinaya dev-review-loop --task <n> --agent <claude|codex|gemini>` (`apps/cli/src/commands/dev-review-loop.ts`, `devReviewLoopCommand`) runs the developer/reviewer round loop for one task Issue, unattended, until it publishes or pauses. The full design is the Linear "Tech spec — Developer Review Loop" (rev 4); this file is the durable, in-repo reference for what shipped across `dev-review-loop-v1` tasks 4–6 — the state machine, the driver, publication and pause — not a restatement of the whole spec.

`packages/aeg-core/src/dev-review-loop/` is the policy layer: `assessRound` (task 4, `#414`) is the ENTIRE decision logic — every stop condition, every confidence rule, the `Decision` a round produces — as one pure function, no `fs`/`fetch`/`process.env`/subprocess/prompt anywhere in that directory. `apps/cli/src/lib/dev-review-loop.ts` (`devReviewLoop`, tasks 5–6) is the driver: it turns real forge/dispatch facts into `Observations`, calls `assessRound`, and acts on the `Decision` it returns. It never re-implements a stop condition or a confidence rule.

## The command

`vinaya task run <tranche> <n> --agent <claude|codex|gemini>` (`apps/cli/src/commands/task-run.ts`, `taskRunCommand`, task-run-v1 task 2) is the normal entry: it composes `task brief`'s own preparation (renders and freezes the brief, starts no agent) with this loop, so one command runs the whole way from a planned Issue — `n` a tranche task ordinal there, resolved to its real forge Issue by preparation — to a reviewed pull request, exactly one developer started. `dev-review-loop` below is `task run`'s own debug/direct entry, kept for resuming a paused run and for driving the loop straight off an Issue number without going through preparation:

```
vinaya dev-review-loop --task <n> --agent claude|codex|gemini [--json]
vinaya dev-review-loop --resume <pr> --agent claude|codex|gemini [--json]
```

`--task <n>` starts a fresh loop against task Issue `<n>` — `n` is a GitHub Issue number, not a tranche task ordinal. `--resume <pr>` continues a previously paused loop from its held state (see "Pause and `--resume`" below); it takes a pull-request number, since a paused loop is anchored to an already-open PR, not an Issue. `--agent` falls back to `dispatch.agent` in `vinaya.config.json` when omitted. Both forms build the same `LoopInput` union and make exactly one call into `devReviewLoop` — `apps/cli/specs/surface.md`'s one-command-one-effects-call rule. `task run` never grows a `--resume` flag of its own (O2): a paused run is resumed through this SAME `--resume <pr>` path directly, since `runTask` (`task-run.ts`) composes `devReviewLoop` fresh every call and carries no resume state of its own.

`LoopInput` also carries an optional `model` (issue-661, O1) — `runTask` resolves it once (an explicit `--model`, else the Issue's own suggested agent-class through the vendor's class-to-model table, else nothing) and spends it in exactly one place: the developer's own `dispatchRole` call in `dispatchDeveloper` (see "Every prompt a RESUMED developer session receives," below, for that same call site). Absent, `dispatchRole` runs this vendor's default, unchanged. Neither reviewer role resolves a model of its own — out of that task's boundary.

`task run` itself takes the identical `--agent`/config-fallback treatment (task-run-v1 task 13, `#508`, O10): a repository that declares `dispatch.agent` in `vinaya.config.json` once needs no `--agent` flag on `task run`, `dev-review-loop`, or `dispatch` — the whole run and every resume is `vinaya task run <tranche> <n>` with nothing else to remember. A `--agent` flag given with no value is still a usage error, never silently rescued by the config default.

## Preparing a brief fast-forwards a clean checkout that is only behind (`#839`)

Every merged pull request moves the remote default branch, so the next start from a checkout that has not pulled sits behind the remote tip. Preparation (`vinaya task run`, `task_start`, `vinaya brief render`) freezes a brief only from a known tree, and until this task any HEAD that differed from the remote tip was refused ("checkout HEAD … is behind the remote default branch … — fetch and update before preparing a brief"). The Operator has no shell, so every merge left the next start blocked until a person ran `git pull` by hand — four times across 2026-09-27/28, this repository and an adopter.

`fastForwardToRemoteIfSafe` (`apps/cli/src/lib/brief-assembly.ts`) now runs BEFORE that staleness check, and is the one function both callers of the check share. When the checkout is on the default branch, carries no uncommitted change to a tracked file, and is strictly behind the remote tip, it is fast-forwarded to the tip (`git merge --ff-only`, after a `git fetch` of the default branch — never a reset, rebase, or checkout, so a checkout with anything local can never lose it) and preparation continues, writing one line to stderr naming the old and new commit (O1). HEAD is re-read after the fast-forward, so the frozen brief's own `**Revision:**` records the tip it was actually rendered from.

The three unsafe cases are never moved — each refuses, naming which one it found and the exact command that clears it (O2): a checkout on another branch (or a detached HEAD → `git switch <default>`), one with uncommitted changes to tracked files (→ `git stash`; untracked files never block), or one carrying local commit(s) the remote does not have — ahead or diverged — which are never discarded (→ `git push`). Local commits are told apart from a plain lag by `git merge-base --is-ancestor HEAD <remote-tip>`, run after the objects are fetched but before anything moves. When the remote cannot be reached (`git ls-remote` fails, or the fetch does) preparation refuses exactly as before (O3). A checkout already at the tip is a no-op here; the unchanged `checkDirtyPinnedFiles` still guards a dirty pinned file on such a checkout, as before.

## Background start survives the client conversation (`control-store-v1` task 7, `#559`)

`vinaya task run <tranche> <n> --agent <vendor> --background` (and the `--issue <n>` form) is a second start mode on the SAME command — foreground behavior (above) is unchanged when `--background` is absent. `apps/cli/src/lib/task-run-background.ts`'s `startBackgroundRun` returns a durable run handle (`{task, runId, epoch, pid, host, startedAt, logPath}`) only once the control store has durably recorded controller ownership — `acquireOwnership` (a fresh epoch), then `writeRun`/`writeInput`/`appendTransition` under it — never before; a failure at that write terminates the child it just spawned rather than leaving an unacknowledged orphan running.

The controller itself is a SECOND OS process: the exact interpreter and entry script this process was started with (`process.argv[0]`/`[1]`, the identical self-reinvocation `checkStaleDriver`'s own `defaultReexecSelf` already uses for a stale-driver re-exec), re-invoked as `task run --issue <task> --agent <vendor>`. That child runs the ordinary foreground path end to end — its own preparation, its own one-driver-per-task pid lock, `devReviewLoop` — nothing about `runTask`/`devReviewLoop` themselves changes; this file's job is only to acknowledge, durably, that the child was launched to own the task before telling the caller it may disconnect. The child is spawned `detached: true` (its own process group, the same mechanism `apps/cli/src/checks/runner.ts`'s own group-kill launcher already relies on) with its stdout/stderr routed into the SAME per-task loop log `task status --follow` already tails, so the client's own terminal or conversation exiting never terminates it and nothing it prints is lost.

**Reattachment, not a second launch.** A repeated `--background` call against a task whose controller is still live (same host, same pid, same captured start-time/command — the identical process-identity check `dispatch.ts`'s `matchesCapturedIdentity`/`getProcessSnapshot` already apply to a dispatched role's child) returns the SAME handle and spawns nothing new. One recorded on a DIFFERENT host refuses (`ControllerConflictError`) rather than guessing. `vinaya task status`'s own `deriveLoopState` reads the identical control-store identity as a fallback (`findRecordedControllerRun`) once the legacy `driver.pid.json` lock — written later, by the child's own `devReviewLoop` — reads absent or dead, so a background run's identity is visible even in the brief window right after this launch. That fallback trusts same-host pid liveness alone, deliberately never `ps` (this file's own "never a `ps` scan" trap for `task-status.ts`); the stronger, `ps`-backed identity check stays reserved for the launch-time reconciliation below, where mistaking a recycled pid for a live controller would risk a genuine double-launch.

**Restart reconciliation.** A controller recorded for the task that is genuinely gone — dead pid, or a live pid whose captured identity no longer matches (recycled) — has any of its still-`'started'` effect records fenced `'uncertain'` (`fenceStartedEffectsAsUncertain`, the SAME function `--cancel`'s own fencing already calls) before a fresh epoch is acquired, so a late-arriving result from the dead controller can never be mistaken for confirmed once a new one owns the task. A new controller must also remain alive with the captured identity through the bounded startup probe before the caller receives a handle; an early exit records a paused transition and points the operator to the loop log. `--background` is refused outright, before anything is spawned, on a host this driver cannot supervise (`checkHostSupervisionCapability` — today, `win32`, since detachment relies on POSIX process-group signaling and the same system `ps` `getProcessSnapshot` already depends on).

## Where the driver's own files live

Every file a task's run writes — this driver's included — lives under one
configured directory, laid out by task and by round:

```
<runtimeDir>/tasks-execution/<task>/
  driver.pid.json     the one-driver-per-task lock
  control/            the control store: ownership, transitions, loop state,
                      effects, resolutions, escalations, review-input
                      manifests, and `pause-state.json`
  sessions/           vendor session ids, one record per role+agent
  hooks/              the documentation read-gate's files and the dispatch
                      settings that wire them
  output/             raw agent output, and this driver's own `driver.log`
  rounds/<n>/         that round's held verdicts (`reviewer.md`,
                      `security.md`), each role's work directory, its
                      read-only `candidate` and per-role scratch copies, and
                      `developer/` — the Developer's own confidence and
                      round-response files (`task-files-v1` 2, Issue #649)
```

`runtimeDir` is a **repo-local** `vinaya.config.json` setting; absent, it
defaults to `~/.vinaya/runtime/<owner>-<repo>`. Four rules keep a configured
value from becoming a way into this driver's own files:

- **Repo-local only.** It is stripped from the machine-global
  `~/.vinaya/config.json` with a loud warning, exactly like `checks`,
  `roles`, `principals`, `releaseActor` and `tokens`. Only
  `defaultRuntimeDir` adds the `<owner>-<repo>` segment, so a machine-wide
  value would collapse every repository into one tree and hand two
  repositories' identically-numbered tasks the same driver lock, the same
  ownership epochs, and the same `sessions/<role>-<agent>.json` — the file a
  confined dispatch holds an exact-file write grant on.
- **Absolute, and outside the repository.** A relative value would resolve
  against each process's own cwd, so the driver and a `vinaya` subcommand run
  from elsewhere would disagree about where the control store is; a value
  inside the working tree would put the lock, the epochs and the held
  verdicts somewhere a confined role can write.
- **Default branch only, for an unattended caller.** Every driver marks
  itself unattended before it resolves anything (`markProcessUnattended`), so
  a configured value is honoured only when the DEFAULT BRANCH declares the
  same one — a pull request cannot redirect this driver's own files by
  editing its own diff.
- **Resolved once, then handed down.** The controller passes its resolved
  value to every dispatched child (`VINAYA_RUNTIME_DIR`), so a child never
  re-derives one and the two can never disagree — which they could, whenever
  the default-branch read came back empty because `gh` was offline.

Every directory here is created `0700` (`ensureRunDir`), whichever writer
gets there first. `apps/cli/src/lib/run-paths.ts`'s
`runPath` is the only function that names a location in here, and
`apps/cli/tests/run-paths-only.test.ts` fails the build if anything else
assembles one. Every one of this driver's own `ensureRunDir` calls — the
reviewer work directories, held-verdict markers, pause state, driver lock,
forge-effect records — passes this task's own `runtimeDir` as the second
argument, the boundary below which `mkdirNoSymlinks` refuses a symlinked
ancestor unconditionally; above it, an operating-system-owned symlink (the
declared-supported host's own default temp root) is tolerated once its real
target passes the same ownership/mode check (`apps/cli/specs/isolation.md`
§5 has the full guard).

**Log delivery is the one exception** — events reach their configured `logs`
destination live (`apps/cli/specs/log.md` § The destination), a folder under
this same `runtimeDir` by default, but a server's own local retry queue
still lives under the machine-local Vinaya home regardless
(`log-sink.ts`'s `telemetryOutboxRoot`). The driver threads the two as
separate deps — `LoopDeps.runtimeDir` and `LoopDeps.resolveLogAppendPath`
(the exact path THIS process's own `log()` calls will land at, for polling
its own line landing) — they were one, which is how this driver's own
per-task files ended up inside the telemetry outbox to begin with.

`vinaya task sweep --include-legacy` is the one reader of a folder an
earlier layout left behind (`task-files-v1` 3, O3) — a run in flight when
this landed had to finish, or be cancelled, first, and nothing here reads
or migrates one on its own; that command is an operator's or a
principal's own call, never something a run in progress reaches for.

## The sweep, at the start of every run (`task-files-v1` 3, `#650`, O2; non-blocking and narrated as it runs — Issue `#697`)

This run's own narration begins before the sweep ever makes a forge
lookup: right after the task and its developer branch are resolved (both
the `--task` and the `--resume` path, above), the loop log (`<task
folder>/output/driver.log`, the same file `vinaya task status --follow`
tails) and this process's own stderr both receive the run-start marker
and a `sweep — running` line — before the sweep's own `gh` calls, and
before the one-driver-per-task lock below is even read. The sweep is
then STARTED, not awaited: `devReviewLoop` calls
`apps/cli/src/lib/task-sweep.ts`'s `sweepModernTasksAsync`
(`LoopDeps.sweepTasksAtStart`) and keeps going immediately, so the
run's first developer dispatch never waits on it, however many folders
it still has to classify. `vinaya task sweep` on demand is unaffected —
it still calls the original, synchronous `runTaskSweep`/
`classifyTaskFolder`, unchanged; the async path exists only for this
driver's own start-of-run call, since a synchronous, sequential `gh`
call per folder would otherwise starve the event loop that carries a
concurrently dispatched agent's own output.

Every OTHER task folder whose Issue is closed or whose pull request is
merged or closed is removed, exactly as the synchronous sweep decides
it — the keep-policy itself is unchanged, only how it runs:
`classifyTaskFolderAsync` mirrors `classifyTaskFolder`'s decision and
reason text over non-blocking `gh` lookups, run with a small bounded
concurrency rather than one after another. Each folder's own decision is
printed to stderr — `[<completed>/<total>] removed|kept <folder>:
<reason>` — the moment that folder's own classification finishes, never
batched into one line after every lookup completes. A folder found
`finished` is classified a SECOND time, immediately before it is
removed: a task revived in the interval (its Issue reopened, its pull
request moved) is read again and kept, never deleted on the first,
now-stale answer. `excludeScope` is this run's own task — never swept by
its own driver, since the forge could in principle report it finished (a
stale read, or a genuine race against an external close) at the exact
moment this run is about to write into that same folder.

The driver's own start-of-run call never reaches the legacy-layout half
of the sweep (`sweepLegacyLayout`, `--include-legacy`) at all — its
result was always discarded here even before this change (`runTaskSweep`
returned it, but the driver's own call only ever read the modern half),
so skipping it outright removes wasted, synchronous work rather than
changing any observable behavior; `vinaya task sweep --include-legacy`
remains the only way to read or remove anything in the earlier layout.

A sweep failure — a `gh` read timing out, a folder that resists removal
— is reported to this run's own stderr (`vinaya dev-review-loop: sweep
failed — …`) and otherwise ignored: it is never a reason THIS run pauses
or exits, the same "the mechanics stalled, not a review verdict"
tolerance a flush failure already gets (below). The sweep is awaited
exactly once, in this function's own `finally`, alongside the outbox
flush — so a run that finishes before the sweep does still lets it
finish cleanly rather than exiting mid-removal.

## One driver per task (`review-validity-v1` task 7, `#498`)

`devReviewLoop` refuses a second concurrent start on the same task, on the same machine, before dispatching anything: right after the task is resolved (both the `--task` and the `--resume` path), it reads a pid record at the root of the task's own run folder, `<runtimeDir>/tasks-execution/<task>/driver.pid.json` (`apps/cli/src/lib/run-paths.ts`'s `runPath`, the one function every run file resolves through). A record whose pid answers a `process.kill(pid, 0)` liveness probe is alive — the new start throws (the process-level, non-zero-exit refusal `index.ts`'s top-level catch already produces for every other pre-flight error in this driver) and dispatches nothing. A record whose pid does not answer the probe is treated as absent — a prior driver's crash never blocks the next start — and this run takes it over. Both cases print one `vinaya dev-review-loop: `-prefixed line to stderr naming the pid and start time involved, so a double-paste is visible in the terminal; per Issue #498's objectives revision, this is stderr only, no new Vinaya Log event kind — `packages/aeg-core/src/log/schema.ts`'s `DevReviewLoopEventSchema` is outside this task's declared Surface, and none of its ten existing event literals fit a guard refusal that dispatches nothing. The record is written once, right after this check, and cleared in one `finally` that wraps the entire rest of the driver for a normal `publish`/`pause` return and an uncaught error alike — **except** the re-exec hand-off below (`#548`, O1), which clears and re-writes the SAME record explicitly, inline, because that path calls real `process.exit` and never reaches this `finally` at all (see below). The `--resume` path's own earlier validation throws (a stale head, a missing ruling, a missing held state) happen before the task is resolved, so no lock is ever taken on those paths — there is nothing to clean up there either. Everything durable and cross-machine — a real lease, session persistence, crash resume — is `control-store-v1`'s design; this guard is the narrow, machine-local stopgap until then.

**Acquiring a lock nobody holds is atomic (issue-711 O4, code review round 1, security MEDIUM).** `readDriverLock` then `writeDriverLock` used to be a plain check-then-write — two genuinely concurrent starts could both read "absent/dead" and both then write, each believing it alone had won. `acquireDriverLockAtomic` (`dev-review-loop/pause-resume.ts`) closes that: an exclusive create (`wx`) that fails outright (`EEXIST`) if the path already exists, so the filesystem itself — not a caller's own read — decides which of two racing writers gets the lock. A loser re-reads once and refuses, naming the winner, exactly like the ordinary "already running" case; only a vanishingly narrow residual (the winner's own process died between its write and the loser's re-read) falls back to a plain write rather than looping forever.

**The watching driver (`runDriverLoop`, O4) holds this SAME lock for its entire life — through every pause and every resume attempt it makes, never clearing and re-acquiring it in between.** `LoopInput.retainDriverLock`, set only by `runDriverLoop`'s own internal calls (never by the CLI or a direct caller), carries a random per-run token (`randomUUID()`) `runDriverLoop` generates once, at its own start, and tells `devReviewLoop` to keep the lock held under that exact token regardless of which reason a round pauses for — not only `'infrastructure'`/`'stale_driver'` — because the watching driver is never "done" at a pause the way a one-shot `--task`/`--resume` call is. Its own repeated calls back into `devReviewLoop` are the SAME pid re-entering the SAME lock it already holds: the entry-gate check above recognizes a lock as its own only when BOTH its pid AND its `token` match (code review round 2, MAJOR/security LOW) — a bare pid match is never enough, since the OS can reissue a crashed driver's exact pid to a fresh, unrelated invocation for the same task, whose own pid would then equal that stale lock's pid too, with no real ownership continuity behind it; that case falls through to the SAME liveness/takeover path an ordinary lock read does. Once pid and token both agree, the lock simply continues, unbroken, under this one process. A genuinely SEPARATE `task run`/`dev-review-loop` for the same task is refused the whole time this driver watches, exactly as the ordinary case above — a second driver is never able to start just because the first is between rounds rather than mid-dispatch. `runDriverLoop` itself releases the lock at the ONE point `devReviewLoop`'s own `finally` never runs for: once its watch loop decides the task is genuinely over (merged, closed, or `--cancel`'s own resolution), it clears the lock itself before returning.

## No round-end flush ([task-files-v1] 5, Issue #652, O3)

There is no flush of any kind left in this driver: not at a round's end, not on any pause exit, not in the loop's own final `finally`, and `vinaya dispatch`'s own trailing flush is gone the same way. The comment-posting flush command itself is deleted outright now, along with the artifact commands and the collector workflow that fed from it (`apps/cli/specs/log.md` § No path to a tracker or a code host, task-files-v1 6, O1) — there is no `vinaya log flush`/`log export-artifact`/`log collect-artifact` left anywhere in this codebase for this driver or `vinaya dispatch` to call. Every `log()` call this driver makes reaches its configured `logs` destination live, as it is logged (`apps/cli/specs/log.md` § The destination): a folder destination is appended to directly, a server destination is drained from the local retry queue immediately after each append. There is nothing left to bound per call, nothing to defer to a later flush, and nothing for a pause or a crash to ship before exiting — the append already **is** the delivery, so the driver reads and writes nothing from the log destination at all beyond that one `log()` call.

Every event the loop is about to emit is still checked against its own schema (`DevReviewLoopEventSchema`, minus the `meta`/`subject` envelope fields only `buildHeader` fills) INSIDE `logEvents`, before `log()` ever sees it — a violation throws, naming the failing field, rather than reaching the destination at all. A thrown error here is caught by the round loop's own outer `catch`, below, and becomes a decided `pause{reason:'infrastructure'}` like any other unexpected failure on this path, never a crash.

**The loop's own exit sites are two: `publish`, and an explicit stop.** Every other failure the round loop can hit — a gate error, a dispatch error, a forge read error, any thrown exception on the driver's own path, a re-exec that cannot proceed — is a decided `pause`, never a re-thrown exception that ends the process. The round loop's own outer `catch` (wrapping `runRoundLoop`) used to log a `driver_exited` trace and re-throw, ending the invocation on ANY uncaught error from anywhere inside it — a `gh` call, `assessRound`, a rejected promise. It no longer does: the SAME trace is logged, but the error becomes `pause{reason:'infrastructure', detail: <the error's own message>}`, written and posted through the identical pause bookkeeping every other pause reason already uses (best-effort, like everything else in this paragraph — a forge write failing HERE too is swallowed, never a second chance to crash on the way out), and the function returns normally with that decision. `'infrastructure'` and `'stale_driver'` are the two reasons this can ever be — the loop's own "the mechanics stalled, not a review verdict" pauses (see "Infrastructure failures" and the re-exec section, below) — and for exactly these two, the outer `finally` skips `clearDriverLock`: the process is not done, it hit a recoverable hiccup, and clearing the lock would make that indistinguishable from a genuine, settled, Principal-decided pause (escalation, max_rounds, confidence, reappearance, no_push, objectives_changed, ruling_posted, brief_superseded, policy_changed — every one of which still clears the lock exactly as before). `task run --issue <n>` is the one command that revives a task in either state, dead lock or not, pause held or not.

## The per-task driver log (task-run-v1 task 15, O6)

Every driver — `task run` and `dev-review-loop` alike, since `task run` is a thin composition that calls `devReviewLoop` internally for the entire developer/reviewer dispatch — tees its own role-prefixed stream to one file: the task's own `<runtimeDir>/tasks-execution/<issue>/output/driver.log` (`apps/cli/src/lib/loop-log.ts`). It sits in `output/`, beside the raw agent output, because it is human-readable narration — never a structured event a check reads, and deliberately nowhere near the telemetry outbox. The repo no longer appears in the path: the runtime directory is already per-repository, so two repositories sharing an Issue number still get two files. `devReviewLoop` resolves this path once per run, from the same `repo`/`task` every other per-run path already uses, and writes a `=== run started <ISO time> role=… pid=… run_id=… ===` marker before anything else — the delineation a file spanning several relaunches (a pause, a `--resume`, a stale-driver restart) needs to read as one continuous narration rather than an overwritten one. Nothing here ever truncates the file.

`dispatchRole` (`apps/cli/src/lib/dispatch.ts`) is the one place that actually writes to it: when the loop names a `roleLogPath` in its `DispatchOpts`, every lifecycle line it already writes to the terminal (`writeLifecycle` — heartbeats, timeout warnings, the tee-path announcement) and every rendered agent-event line are ALSO mirrored, plainly (no ANSI escape codes — a log file is read later, never through a TTY), into that file — alongside, never instead of, the existing per-dispatch `<runtimeDir>/tasks-execution/<task>/output/<effectId>.log` raw-byte tee.

`vinaya task status <tranche> <n> --follow` (and `--issue <n> --follow`) tails this file live, `tail -f` style (`followLoopLog`, `loop-log.ts`): it prints whatever the file already holds, then polls for growth and prints only the new bytes, indefinitely — a file that does not exist yet (no driver has ever run) is simply polled until it appears, never refused. `--issue <n>` names the Issue directly; the `<tranche> <n>` form resolves it through the same read the ordinary single-task status view already uses. Either way, the state of any run is one command away, regardless of where it was launched.

## Rounds

Round 1's entry (`review-validity-v1` task 5, `#488`, O4) checks the forge before dispatching anything: an already-open pull request on the developer's branch means ATTACH — no developer is dispatched at all, the recorded session is read so a later round resumes it, and round 1 enters its gate directly. That read now goes through launch reconciliation (`recoverDeveloperLaunch`/`reconcileLaunch`, `dev-review-loop/developer-dispatch.ts` — `control-store-v1` task 3, O3): every seam that used to read the durable resume record blind (this attach, and the no-push/no-PR resumes in `afterDeveloperTurnBeforePrPoll`) first reconciles the developer's prior launch. A prior launch whose own child process is still alive on this host is `live` — a second worker is never spawned onto the same task; a required session that is genuinely gone (an attempt interrupted before its vendor session was ever bound) throws `LaunchContinuityLost`, which the loop's outer handler turns into a decided `pause{reason:'infrastructure'}` (an explicit pause, never a silent fresh start); a recoverable session — now including one bound on an INTERRUPTED attempt, since `dispatch.ts`'s launch record persists the session across the interruption (`control-store-v1` task 3, O1) — resumes that EXACT session. No launch record at all (the common case) falls back to the same durable resume-record read as before, unchanged. A branch that exists on the remote with no open PR yet resumes that same recorded session ONCE, instructed to open the PR through the validated path, and waits for it. Neither case starts a fresh developer. Only when the branch does not exist remotely at all does round 1 dispatch the developer fresh, brief read verbatim from the task Issue's frozen brief comment (`fetchFrozenBrief`), then wait for the PR it opens. `fetchFrozenBrief` and every other `--json comments` read this driver makes (`developer-dispatch.ts`'s `sh`, `dev-review-loop/gate-reading.ts`) reads with a 64 MiB `maxBuffer` (task-log-v1 8, Issue #626, O3), not `execFileSync`'s 1 MiB default — an Issue whose own comment payload had already grown past that default (the round-end flush's old, unconditional default, above) used to fail this exact read with `ENOBUFS`, permanently stalling the loop's own next dispatch on the very Issue it needed to read; a task already in that state can dispatch again without needing its Issue's history trimmed first. `fetchFrozenBrief`, and every other reader of "the frozen brief" in this codebase, resolve through `@attalabs/aeg-core`'s `resolveNewestFrozenBrief` (task-run-v1 task 4, `#483`, O3): a Principal can correct a wrong frozen brief with `vinaya task brief <tranche> <n> --supersede --reason <text>`, which appends a new, higher-versioned `aeg:brief:v<k>` comment naming its predecessor and the reason rather than editing or deleting the original — the loop always reads the newest version, never the first one posted.

**The round journal is the task's, not this process's (task-run-v1 task 21, `#541`, O9; rebuilt from the control store and the forge's own markers, never a log event — [task-files-v1] 4, Issue #651).** `initialLoopState` starts `state.rounds` empty on every process start — a driver that attaches to a PR mid-loop used to publish a table that only ever showed its OWN rounds, even when the task had a longer real history (Origin, PR #536: five real rounds, the published table showed one, because the last driver journaled only its own). On the `existingPr` attach branch, `seedLoopHistory` calls `fetchLoopHistory` (`apps/cli/src/lib/dev-review-loop/journal-history.ts`) before this run logs a single event of its own: it reads the pull request's own principal-authored comments — one `RoundRecord` per developer round marker (`<!-- aeg:developer:round-<n> -->`, `parseDeveloperRoundMarker`; principal-authored only, the same trust boundary every other forge read in this driver already applies), and whether a ready-for-merge summary comment (`isPublishedSummaryComment`) has actually been posted, and where — and reconstructs them (`reconstructRounds`, `@attalabs/aeg-core`), together with the review gate's own verdict on the pull request's current state (the next paragraph but one). It reads NO log event, NO flushed log comment, and NO telemetry outbox: the Vinaya Log is fail-open telemetry and is never read to recover a run (`apps/cli/specs/log.md`; the Log tech spec's §1, "never the authority for … recovery"). This is what let the rebuild survive the log destination moving off the tracker — a replay of the loop's own flushed events broke the moment those events stopped going to GitHub. Honest about what a marker carries: it names only the round's number and head, so a reconstructed round's `countsBySeverity` is empty, its `confidence` is `null`, and the per-round wall time / files changed have no source and are reported unavailable, never a fabricated number (O3) — and the published table says so for those counts too, rather than printing a zero ("A round whose counts are unknown reports nothing," under Publication); what's never dropped is the round's own existence and number, and whether the run reached a published summary — which is what the numbering and the published table actually need. The control store's own authoritative round is recovered separately (`recoverLoopState`, below): the two together — control store and forge markers — are the whole round-history source.

Applied only when the task's review has NOT CONCLUDED: a concluded review already published its verdicts and ended the loop, so re-invoking the driver against that same, still-open PR is meant to re-derive that SAME round from scratch, not invent a round that never happened — `assessRound` always APPENDS to `state.rounds`, never deduplicates by round number, so seeding a round this run is about to recompute live would double it. When seeding does apply, the reconstructed rounds also correct `round` itself (`nextRoundNumber`, never regressing the more-precise, locally-held `latestHeldRequestChanges` recovery above when both agree or the local one is ahead) — an attach with no locally-held request-changes file to recover from (a different machine, or local state already cleaned) no longer restarts numbering at 1 when the forge markers show real prior rounds the review has not concluded past.

**Concluded means the summary AND a gate that has not failed on the current state — it is not a latch.** A pull request counts as a concluded review only while a principal-authored ready-for-merge summary comment is actually on the forge AND the review gate has not FAILED against the pull request's CURRENT head, objectives version, newest Principal ruling, frozen brief and policy. `reconstructRounds` takes the gate's verdict as an input fact beside the summary fact; `isConcludedJournal` (`@attalabs/aeg-core`) is the ONE predicate all three readers of "is this concluded?" call — the `--resume` replayed-resolution refusal ("Pause and `--resume`," below), this round-history seeding, and the held-clean carry path's "already published?" check.

Why both: a summary table records no head, so the summary alone is sticky in a way the pull request is not. A summary posted for an older head kept reading "done forever" after a red gate, a newer Principal ruling, a superseded brief or a moved head — observed live on an adopter pull request whose review had genuinely reopened on every one of those counts, yet whose every `--resume` was refused, and where a later run posted a `round-1` marker after round 3. A red gate, a newer ruling, a superseded brief or a moved head now reopen the review: the rounds seed, numbering continues past the last marker on the forge, and `vinaya dev-review-loop --resume` / `vinaya task run` continue the task. The gate is asked because it is the one evaluation already bound to every one of those facts — called in-process (`checkReviewGate` over the SAME input assembly the `review-gate` check itself builds, `apps/cli/src/lib/review-gate-input.ts`), never by shelling out to `vinaya check`, and never a second hand-built copy: the gate re-resolves policy and principals from the DEFAULT BRANCH's trust anchor and the head from the remote, and a copy reading the pull request's own checkout would drift. Reconstruction itself stays pure — it performs no forge read and no gate evaluation, it is handed the verdict.

The summary half is still the crash-vs-published signal it always was, NOT a round merely deciding `publish`: the control store's own `loop_state.phase` reads `'publish'` the moment `assessRound` decides it, written before `publishRound` ever posts, so a crash mid-publish (a `gh` failure) leaves no summary and the rounds correctly still seed.

The gate half is three-valued (`ReviewGateFact`), and the third value is load-bearing. `pass`/`fail` mean the gate genuinely evaluated. `unknown` means nobody asked — no summary is on the forge, so the answer could not change the outcome — or the evaluation could not be made at all (a failed forge read, an unresolvable head, a thrown evaluation), which is narrated once to stderr and never thrown: this rebuild is a recovery aid, not a gate. An `unknown` gate does NOT reopen a published review, because the two failure directions are not symmetric: reading it as reopened makes one transient `gh` hiccup dispatch a whole extra review round against a task that was genuinely finished and post its comments — the "a rerun posts nothing twice" invariant, lost for a fact nobody could check — while reading it as no-new-information costs at most one refusal that names the unevaluable gate, and clears itself on the next attempt. Nothing merges on an `unknown` either way: the `review-gate` check fails CLOSED on every one of these same unresolvable facts, and the merge gate's own evaluation is untouched by anything decided here.

**Deliberately never called on `--resume` (PR #544, round 2 review, BLOCKER).** `resumeFrom.round` is the exact round the paused process was on before it exited — its developer round marker is already on the forge, so seeding it here too, then letting this same resumed run recompute and append that identical round number again, is the precise double-count the paragraph above guards against — the attach branch never hits it because attach always continues at `held.round + 1`, one past anything reconstructed, while resume deliberately continues AT `resumeFrom.round` to give the ruling's fix a chance in the same round. `state.rounds` starts empty on resume and accumulates only the rounds this process itself computes from the resume point forward; a resume that goes on to publish reports a published table scoped to this process's own rounds, not the task's full history.

**An ATTACH onto an existing PR also recovers a held REQUEST-CHANGES round, rather than resetting to round 1 (task-run-v1 task 3, `#482`, O4).** A restarted driver's in-memory `LoopState` carries no round history at all, but the outbox's own held-verdict files (`round-<k>-reviewer.md`/`round-<k>-security.md`, `writeHeldVerdict`) do: `latestHeldRequestChanges` reads the highest round with both files still on disk, re-parsed through the same extractors `publishRound` trusts, and treats it as recoverable ONLY when it reads REQUEST CHANGES (never falls back to an older round once the newest one reads clean or fails to parse — that's read as nothing to recover, the same as no held state at all). When the branch's current head has moved past that round's judged head, the driver advances straight to that round's own gate check at round `k+1` — the normal green-gate path from there dispatches round `k+1`'s reviewers, never redelivering round `k`'s findings to the developer. When the head has NOT moved, those findings are delivered once, exactly as a continuous run would; a second attach that still finds the same unchanged head — a marker file (`round-<k>-attach-redelivered`, alongside the held-verdict files) records that the first redelivery already happened — pauses `no_progress` instead of trying a third time (Origin: PR #529, where every attach after a fix push kept re-delivering round 1's stale findings and drifted into a confidence-collapse pause).

**A held or published CLEAN verdict carries a patch-identical head move, at round start AND on `--resume` alike (issue-711, O1/O2/O3).** A verdict judges a patch; the head commit is only its address — the merge gate already reads it that way ("The same-patch rebase equivalence," below); before this task the loop did not. `latestHeldCleanVerdict` (`dev-review-loop/reviewer-dispatch.ts`) is the held-clean counterpart to `latestHeldRequestChanges` just above: the highest round with both held files still on disk, recoverable only when it reads APPROVE/PASS with every manifest field (base, brief hash, objectives version, ruling ordinal, policy digest) agreeing between the two roles. Right after every other round-start/resume recovery has run — the REQUEST-CHANGES read above, the forge-marker round bump, the control-store round recovery — one check, shared by both entry points, asks whether that held round still covers the branch's current head: `compareManifest` (the SAME comparison the gate and the driver's own pre-hold self-check already call — "One comparison, three callers," below) against a freshly re-resolved current manifest, now given `patchIdOf` (`patch-id.ts`'s `patchIdAt`, against `main`) so an exact sha match is no longer the only way a head binds. Bound (exact identity, or a proven patch-identical rebase/merge-from-base) — and only when the held round is not itself older than a round some OTHER recovery already established, and the head has genuinely moved at all — means no fresh review round: either the held pair posts directly, addressed to its OWN original head and manifest, never re-rendered against the new one, or, when the forge already shows it published, this run returns clean with no new write at all (its own `journal` would otherwise render a summary table with no row for the round it names, since `assessRound` never ran on this path). Any other field having drifted — most commonly the ruling ordinal, since an ordinary `--resume` is itself usually triggered by a NEW Principal ruling — fails the comparison and falls through to a genuine fresh round, exactly as before this task; carrying a verdict past a real ruling, or past a real change to the pull request's own diff, is never in scope. A round cap reached while this is the only pending work never pauses for it, since the round never reaches `assessRound` at all on the bound path; a cap that DOES fire for an unrelated reason names the comparison this check made, when the head move it saw was not patch-identical.

**The poll never starts against a branch the developer has not pushed (task-run-v1 task 13, `#508`, O1/O2/O3/O9).** The developer contract (`aeg-root/roles/developer.md`) states the push and the pull-request open are foreground steps — the developer's own turn does not end until `gh pr view` shows the pull request. The loop still checks rather than trusting this: after the fresh round-1 dispatch returns, `afterDeveloperTurnBeforePrPoll` reads the branch's remote head (`git ls-remote`) before ever polling for a pull request.

- No remote head at all, and a refusal/escalation comment (`<!-- aeg:developer:stop -->`, principal-authored) is posted on the task Issue: the loop ends AT ONCE with that reason — `pause{reason:'escalation'}`, posted on the Issue (there is no PR yet) — never entering the poll (O9). This is the origin bug (task #498, `#509`) generalized one step earlier: a developer that never even reaches the remote must not leave the loop waiting for a pull request nobody will ever open.
- No remote head, no stop comment: the loop resumes the SAME developer session ONCE, foreground, with the exact push-and-open commands — never a second resume for this (a repeat failure after the one resume is left to the poll's own bounded timeout, not a second dispatch).
- A remote head exists but no pull request yet (either originally, or after that one resume): resume once more to open it specifically, then poll.

Whichever path is taken, a poll that still gives up names everything it waited for — branch, the developer's own worktree HEAD if `.worktrees/<branch>` is locally readable, the remote head, and whether a pull request exists (O3) — so a principal reading the failure knows exactly which step was skipped, rather than the bare "no open PR appeared… within the poll budget" the original bug reports quoted.

1. **Gate.** `resolveHead`/`fetchCiConclusion` read the branch's live head and CI conclusion — never run locally (Traps: the mechanical gate is the CI system's own verdict, not a local re-run). `fetchCiConclusion` excludes the review gate's own check-run by name (`REVIEW_GATE_CHECK_RUN_NAME`, `review-gate-check-name.ts` — the one constant `check-review-gate.ts` also imports, never a second copy; `review-validity-v1` task 5, `#488`, O1) in every status, so a head with green CI and no verdicts yet reads green, never red because the gate itself hasn't posted one. A `principalOwed` core check (`CheckSpec.principalOwed` — `test-plan` today, the registry flag, never a name list; `review-validity-v1` task 15, `#532`, O1) whose only failures are the Principal's own unticked `[principal]` Test Plan boxes reads the same way: `vinaya check --all`'s own exit code (`isRunFailed`, `apps/cli/src/commands/check.ts`) excludes that check's failure from the run's aggregate verdict whenever every error it reported is `pending: true`, so the ONE GitHub check-run a bundled `scope: 'diff'` run reports under stays green and this gate never sees red for a box only the Principal can tick — enforcement of the unticked box itself lives in a check of its own, `principal-test-plan-wait`, which stays red while it remains unticked; `test-plan` keeps grading the `[agent]` half and the plan's structure. Never `review-gate` — that check answers for the review verdicts alone and reads no Test Plan state at all. A structural `test-plan` failure (no Test Plan section at all, a non-pending cause) still counts and still sends the developer back. **The gate also re-asserts the PR body's own `Premise:` pins at this same head** — `reassertPrBodyPremise` (`checks/bin/check-pr-premise-reassert.ts`), re-run every round against the LIVE PR body, never only at Step 0: a pin a later commit falsified (a symbol the head deleted since the brief was authored) reads exactly like a red mechanical check-run, its failing line(s) folded into the same `lastFailingChecks` the gate-red retry prompt already names — a stale premise is a developer finding sent back through the SAME retry path, never a reason for the driver itself to exit; a re-exec'd child re-asserts it again the moment it reaches its own first gate check, no separate re-exec-only path to fall out of sync with this one. A body with no `Premise:` block at all is unaffected, same as every PR before this task. Red sends the developer back for the same round, naming the failing check-run(s) — each by check name AND its own run id/`started_at` (`fetchFailingCheckRuns`/`describeFailingCheckRun`, `#607`, O3), so the evidence a pause is built from is auditable after the fact — never the review gate, which is excluded entirely, and never a bare "CI is red." `fetchFailingCheckRuns` reads the same already-deduped-to-the-newest-per-name list `fetchCiConclusion` does (`#595`'s own O3), so a failure a later same-named run has superseded with a pass never contributes to this list or to the gate's conclusion (`#607`, O1) — a genuinely failing CURRENT run still reads red and still sends the developer back exactly as before (`#607`, O2). After that dispatch the driver waits for the branch head to change (the same gate poll budget, `gatePollMaxAttempts`/`gatePollIntervalMs`) before reading the gate again — it never re-reads a still-unchanged head in a tight loop (`#479`: five re-dispatches in two minutes on one head). A developer turn that produces no push at all is one strike against a small, driver-owned bound (`MAX_GATE_STALLED_TURNS`, `dev-review-loop.ts`); consecutive strikes on one head that reach the bound end in `pause{reason:'infrastructure'}` naming the head and the failing check (never unbounded re-dispatch) — see "Driver-decided pauses," below, for why this reuses `'infrastructure'` rather than a dedicated reason. Green and round 1 goes straight to reviewers; green from round 2 on gates on developer confidence first (below).
2. **Reviewers.** Both roles are dispatched fresh every round (`dispatchRole` called anew — a reviewer session is never resumed; only the developer's is). Each reads facts-only (`renderReviewerPrompt`: objectives, Principal rulings, head, CI conclusion, the frozen brief's own source revision (`fetchSourceRevision` — task 4, `#483`, O2; the `NO_SOURCE_REVISION` sentinel on a brief from before this task that carries no `**Revision:**` line) — never developer- or PR-body-authored prose. `lintReviewerPrompt` reads the DRIVER's own text: `buildReviewerPromptPieces` labels every piece of the prompt `driver` (the labels, the numbering prefixes, the `(none)`/`(none found on the Issue)` fallbacks this renderer writes) or `fact`, `joinReviewerPromptPieces` renders them all, and `driverAuthoredPromptText` hands the lint the driver pieces alone — joined with newlines, so two fixed strings sitting either side of a held-out fact can never read as one banned phrase. The interpolated facts are Principal- and Planner-authored prose the driver neither controls nor censors: a ruling or an objective whose own wording happens to match a banned phrase reaches the reviewer verbatim instead of ending the round as an infrastructure failure. A match therefore always names text written in `reviewer-dispatch.ts` itself, and is fixed in the renderer, never by loosening the lint) and writes `findings.txt`/`report.txt` to a driver-chosen work directory, plus `objectives.txt` whenever the task carries objectives (the prompt names the file only then; a task with no `## Objectives` section never asks for it). `resolveIssueObjectives` (`review-validity-v1` task 2, `#476`, O1) is the one source of the `OBJECTIVES:` fact and the version threaded through the round: the newest principal-authored `<!-- aeg:objectives:v<k> -->` edit comment when one exists — its own `Version:` line is read as-is, never recomputed, since `vinaya issue objectives edit` already wrote it from the exact list it spliced into the live Issue body — else the principal-authored frozen brief's verbatim copy of the Issue's `## Objectives` section, versioned by the same `objectivesOf`/`objectivesVersion` pair the merge gate calls on its own live-body read. Never the live Issue body directly (PR #445's security round: any collaborator can edit a body and thereby author every reviewer's prompt). `buildVerdictFromReport` derives the verdict from findings (never hand-typed) and renders the same `VERDICT:`/`Judged head:`/`Objectives version:`/`Ruling ordinal:`/`Brief hash:`/`Policy digest:` shape `review-post.ts` uses elsewhere, carrying the manifest the round was dispatched against and one `O<n>: MET | NOT MET` line per objective. Before it does, it runs the SAME `checkObjectiveIdCoverage` `review post` already applies to a human-posted verdict (`review-validity-v1` task 4, `#478`, O4): an `objectives.txt` missing an id, or carrying an extra one, refuses (`ReviewerReportParseFailure`, the same one-fresh-retry treatment a missing artifact gets) rather than yielding a verdict that silently under- or over-reports what the round actually judged — an under-reporting reviewer never yields a version-bound verdict. `writeHeldVerdict` holds it in the outbox — nothing is posted to the forge before green (Section 10 stop condition, tasks 4–5). A work directory still missing `findings.txt`/`report.txt` (or `objectives.txt` on a task that carries objectives) after the dispatch is an infrastructure outcome, never a clean verdict — an empty `findings.txt` is still clean, exactly as the reviewer contract promises (`review-validity-v1` task 1, `#475`, O1); see "Infrastructure failures," below.

   Right after both reviewers return — before either verdict is written to the outbox — the driver re-resolves objectives one more time and compares the version to the one the round was dispatched against (`review-validity-v1` task 2, `#476`, O3). A mismatch means a principal posted an objectives edit while this round's reviewers were running: both verdicts are discarded in memory, never held and never published, and the round ends in `pause{reason:'objectives_changed'}` (below) rather than judging the round against a list the reviewers never actually saw. The driver does the identical re-check for the newest principal ruling ordinal (`review-validity-v1` task 3, `#477`, O3): a mismatch there ends the round in `pause{reason:'ruling_posted'}` instead, for the identical reason — a ruling the reviewers never saw must not be judged against.

   **A `NOT MET` whose evidence is prose is reclassified before either verdict is even rendered.** `buildVerdictFromReport` runs every parsed `objectives.txt` line through `reclassifyProseOnlyNotMet` (`dev-review-loop/reviewer-dispatch.ts`): a `NOT MET` whose evidence is prose-located — `isProseLocation` (`@attalabs/aeg-core`, the SAME predicate `evaluateReviewFindings`'s body-located `MINOR` cap already applies to a finding's own `location` field, reused here over an objective's `evidence` field instead) reads it as naming only the PR body, a comment, or a role file — becomes `MET`, its evidence annotated `(prose note)`. This runs before the rendered `O<n>: MET | NOT MET` line is built and before the round's own `objectives` observation is assembled, so neither the posted verdict comment nor `assessRound`'s "any `NOT MET` objective is `changes_requested` regardless of findings" rule ever sees the reclassified line as unmet. A `NOT MET` naming a real source or test file is never touched — the same file-shape gate that protects a finding's location protects an objective's evidence here too.

   **The evidence report and the round marker comment are the driver's job now, never the Developer's.** Right after mergeability is confirmed and the round's head is resolved — before either reviewer is dispatched — the driver reads and clears the Developer's own round-response file (`DEVELOPER_ROUND_RESPONSE_FILE_NAME`) from THIS round's own Developer folder inside the task's folder (`runPath(..., { area: 'developer', round, file: DEVELOPER_ROUND_RESPONSE_FILE_NAME })`, `task-files-v1` 2, Issue #649, O1/O2) — never the worktree, and never a fixed path reused across rounds — best-effort: missing or malformed yields no citation, never a stall, and posts the round marker comment itself (`Head: <sha>`, `<!-- aeg:developer:round-<n> -->`, and a `FINDING_IDS:` line only when the Developer cited any) — the Developer's own turn ends at the push (`aeg-root/roles/developer.md`) and never posts this comment or runs `vinaya pr report --push` itself any more. `dispatchReviewer('reviewer', …)`, `dispatchReviewer('security', …)`, and the driver's own `runEvidenceReport` (the SAME `apps/cli/src/lib/pr-report-engine.ts` engine `vinaya pr report --push` calls, run in-process rather than shelled out to) all run inside one `Promise.all` — the report never waits on the reviewers, and the reviewers never wait on it. That concurrency is only real because every read `runEvidenceReport` performs — its `git`/`gh` calls, `vinaya check --all --diff-only`, and each Test Plan command it runs — is an async child (`node:child_process`'s promisified `execFile`, never `execFileSync`/`spawnSync`). On Bun 1.2.14 a synchronous spawn kept spinning the event loop while it waited, which incidentally let the other two `Promise.all` branches make progress anyway; Bun 1.4.2's synchronous spawn genuinely blocks the single thread, so a synchronous read here would have stalled both reviewer dispatches for as long as the report's own gate run and Test Plan commands took. A report failure is logged to the driver's own role log and otherwise ignored: it is never a pause and never counted toward `no_progress` — the origin incident this fix closes was ten-plus minutes lost to exactly that report, run synchronously, blocking the loop on a single tool call. The merge gate's own `evidence-fresh` check, unaffected by this task, is what actually enforces a fresh `AEG:EVIDENCE` block at merge time; the driver's automatic call is what keeps that check from ever finding the block stale in the first place. `runEvidenceReport` writes the regenerated body through the same forge-write path every `pr edit` takes, whose own `runBodyChecks` (`apps/cli/src/lib/forge-write.ts`) refuses on any finding by calling `process.exit(1)` directly — but `runReportForOpenPr` (`apps/cli/src/lib/pr-report-engine.ts`) never reaches that line at all: it goes through `collectBodyCheckErrors`, the non-refusing half of the same registry run `runBodyChecks` itself now delegates to, and turns a non-empty result into an ordinary `'body-checks-refused'` outcome carrying the same findings, folding into the SAME "logged and otherwise ignored" handling above rather than killing the driver outright and discarding the round with no trace. `runBodyChecks` itself, and every OTHER caller of it (issue/PR creation), are unchanged — they still exit the process on a refusal, exactly as before. **No Principal-owed wait state refuses this write, whichever check reports it.** The body-write path's exclusion (`isPendingOnlyFailure`, `apps/cli/src/lib/forge-write.ts`) reads `CheckError.pending` alone and no `CheckSpec` flag: any failing check whose EVERY reported error is `pending: true` is dropped from the refusal decision. That is deliberately WIDER than `isRunFailed`'s own `principalOwed`-gated rule above, and the two are not meant to converge — they answer different questions. `pending` means "has not happened yet," never "these bytes are wrong," and whether the outgoing bytes are wrong is the only question a pre-write validation asks; refusing on a wait state blocks the very write whose landing is what clears it. So `test-plan`'s unticked-`[principal]` half no longer refuses this write, and neither does `principal-test-plan-wait`, whose single error is also `pending` — even though that check is NOT `principalOwed` and must never become it, since that flag would turn its red green at the gate and an unticked `[principal]` box has to stay a merge condition. The per-round Evidence splice therefore goes through while the box is still unticked, and the Principal's tick — which re-runs the body checks against the live body — finds a real block bound to the judged head instead of the untouched template placeholder that turned `evidence-fresh` red. A structural failure still refuses here exactly as before: no Test Plan section at all, any non-`pending` error, or a mix of pending and non-pending errors on one check. A failure carrying no emitted error at all (a timeout, a malformed stderr) contributes no finding to this aggregation and never refused this write before the rule existed either — unchanged, and not what the rule decides.
3. **Verdicts.** `assessRound` combines both verdicts. Clean (both APPROVE/PASS, every objective MET) → `publish`. An `ESCALATE` from either role → `pause{reason:'escalation'}`, immediately, before any verdict is ever held or posted. Otherwise the findings are relayed to the developer for another round.

Round numbering: `round` advances only when a genuine review round concludes `changes_requested` and hands back another developer dispatch. A mechanical-gate-red retry and the confidence rule's one-extra-turn both resubmit the same round number — advancing on every developer dispatch would make a CI hiccup on round 1 silently trigger the round-1-never-asks confidence question.

## The Documentation read-gate (`driver-lifecycle-v1` task 7, Issue #625)

A brief's own `## Documentation` section (`issue-validation.ts`'s `parseIssueDocumentation`, rendered verbatim into the frozen brief right after Objectives) names the normative sources a task depends on, against the mechanism each governs. Whether one was actually read is never left to the Developer's own say-so: `dispatchRole` (`apps/cli/src/lib/dispatch.ts`), on every `developer` dispatch whose prompt carries that section, parses the URL-shaped sources out of it and passes them to `writeDispatchSettings`, which wires two hooks into that dispatch's own `--settings` file, keyed by this dispatch's `VINAYA_RUN_ID` (never a fixed path — two tasks dispatched concurrently on one box must never share one) —

- **`PostToolUse` (matcher `WebFetch`)** appends every fetched URL to a per-run log.
- **`Stop`** reads that log against the sources file and exits 2 — "prevents Claude from stopping, continues the conversation" (code.claude.com/docs/en/hooks) — naming every URL-shaped source not yet fetched, whenever one remains.

Dormant, never blocking, in three cases: a prompt with no `## Documentation` section (a round-2+ fix prompt, never the full brief again — the sources were already read to reach round 1's PR), a section carrying only in-repo paths, or the explicit `None` sentinel. A non-`developer` dispatch never gets a sources file at all — the obligation is `aeg-root/roles/developer.md`'s entry-gate item, not any other role's. Claude records `WebFetch` through its generated settings. Codex's documented built-in web search is not a `PostToolUse` receipt route, so its generated prompt requires `curl -L <URL>` through `Bash`; the Codex receipt hook observes only successful Bash/curl calls and Stop uses Codex's `decision: "block"` continuation contract. Its scoped `shell_environment_policy` excludes the brokered access token from every command Codex starts. Trusted automation explicitly opts into the generated hook source. Gemini remains unenforced and is named by a lifecycle warning rather than silently downgraded.

**What this does not do (round 2 security review, CRITICAL).** The sources/log files this gate reads and writes (`documentation-sources-<runId>.json`, `documentation-log-<runId>.jsonl`) live in the task's own `hooks/` directory (`<runtimeDir>/tasks-execution/<task>/hooks/`), which the dispatched Developer session's own Bash tool can reach, with `VINAYA_RUN_ID` readable from that session's own environment. Nothing here is process-isolated from the Developer the way `apps/cli/specs/isolation.md`'s Worker boundary is (that boundary, and wiring `dispatchRole` to a real OS-level sandbox, is `task-operator-v1`'s surface, not this gate's) — a session that deliberately edits or truncates either file defeats the check. What this gate actually buys: an honest miss is always caught, because the Developer never has to remember to self-report a fetch; it buys nothing against a session already willing to fabricate evidence, which is the same trust model every other self-reported artifact in this loop already carries (`.vinaya-confidence`, the Token report, a Test Plan's own pasted output) — caught, if at all, by the independent Reviewer/Security passes reading the session's own transcript, never by this hook.

## The confidence rule

Round 1 never asks for confidence. From round 2 on, a green gate reads `.vinaya-confidence` — written by the developer per `confidencePromptLine`'s instruction, to the exact absolute path that function's own argument names for THIS round, under that round's own Developer folder inside the task's folder (`task-files-v1` 2, Issue #649, O1) — before reviewers are ever dispatched:

- absent, asked once already → `pause{reason:'confidence'}`; absent, first time → re-ask once.
- below 50, one extra turn not yet spent → one more developer turn (spent once, ever), no reviewer dispatch; below 50 again → `pause{reason:'confidence'}`.
- 50 or over → dispatch reviewers.

**What each read logs.** `assessGate`'s own `gate_result_read` event carries a round's confidence exactly as read: a stated value/reason (`confidence_value`, `confidence_reason`), or `confidence_unavailable: true` for a missing or malformed statement — never a fabricated `confidence_value` of `0`. `extra_turn_spent` reports `state.extraTurnUsed` as it stood BEFORE this read — whether the rule's one extra turn was already spent — so a first statement and a statement made after that extra turn read apart. All four fields are optional and absent on round 1 and on a red gate, since neither ever reads the file. `loop_started`/`round_started` still fire only on a round's first gate call, but `gate_result_read` fires on EVERY call, including a re-ask's own second read: when the first read is absent and the developer is asked again, the second read's real value (or a second absence) gets its own event rather than leaving the round's log stuck on the first read's `confidence_unavailable: true` even after the loop went on to act on a real one.

## The four exits

`assessRound` decides every exit — the driver never re-derives one:

| Exit | Trigger | `Decision` |
| --- | --- | --- |
| green | both verdicts clean, every objective MET | `publish` |
| stalled | a fingerprint resolved earlier reappears (`reappearance`) | `pause` |
| capped | round count exceeds `reviewPolicy.maxRounds` (`doctrine-fixes-v1` task 1, `#543`, O4 — repository policy, default 3, resolved once by the driver into `LoopConfig.maxRounds`; no longer a hardcoded constant) | `pause{reason:'max_rounds', detail:'max rounds: <n>'}` |
| escalated | either reviewer returns `ESCALATE` | `pause{reason:'escalation'}` |

The confidence rule's own collapse (`pause{reason:'confidence'}`) is a fifth practical pause path layered on top of "stalled," gating whether a round even reaches a verdict.

**Escalation closes the journal too (PR #544, round 2 review, BLOCKER).** `assessRound` (`packages/aeg-core/src/dev-review-loop/assess-round.ts`) emits `journal_finalized{result:'stopped'}` on the `ESCALATE` path, the same as every other pause reason (`reappearance`, `max_rounds`, `confidence`) already did — this event is retained unchanged as telemetry ([task-files-v1] 4 changes only where the round HISTORY is read from, never which events the loop emits). It is no longer what tells an escalated task apart from a still-open one for recovery, though: the "already published" decision now reads the forge's own ready-for-merge summary comment (`journalFinalized.result === 'merged_ready'` from `fetchLoopHistory`), and neither an escalated nor a still-open task has one, so both correctly read as not published without this event being consulted at all.

### Infrastructure failures (O1/O2, `review-validity-v1` task 1, `#475`) and driver-decided pauses (`review-validity-v1` task 5, `#488`, O2/O5)

A review role's dispatch is retried once, into a genuinely fresh work directory (never the failed attempt's own), if its directory is still missing a required artifact after the first attempt; a second miss on the same role, and a red-gate developer turn that produces no push `MAX_GATE_STALLED_TURNS` times in a row on one head, are both `pause{reason:'infrastructure'}` — the driver's own two "the loop's own mechanics stalled, not a review verdict" exits, distinguished from each other only by the pause's `detail` text (the role and missing artifact(s), or the head and the failing check-run(s)).

**A sign-in refusal pauses, but spends no retry budget.** `authentication-failed` — the vendor refusing the dispatch because nobody is signed in on this host — is the one dispatch failure that says nothing about the task, the round, or the worker: no session was ever started, so nothing was lost and there is nothing to diagnose beyond signing in again. `assertDispatchOrEscalate` raises it as its own `DispatchSignInRefused`, checked ahead of the resumed-round stop-and-escalate (a vendor that cannot sign in refuses identically on the first round and the tenth, so a credential failure is never read as "this session worked last round and broke now"), and the outer handler turns it into the same `pause{reason:'infrastructure'}` every thrown driver-path failure becomes — but with a detail that says the developer could not sign in, and WITHOUT charging `MAX_INFRASTRUCTURE_RETRIES`. That budget bounds how often a task may be resumed past a recoverable hiccup with no genuine round in between; a host with no credentials never produced a round for it to bound, and counting the refusal would demand a Principal ruling for something a vendor login fixes. The exclusion is keyed on that cause alone (`spendsInfrastructureRetry`), never on "a pause that came through this code path", so every other infrastructure loop keeps its bound intact.

Neither corresponds to an `Observations` kind `assessRound` accepts, and this task's own declared Surface (Issue #488 §4) excludes `packages/aeg-core` — adding one, or a dedicated `PauseReason`, would mean editing it. `driverDecidedPauseEvents` (`dev-review-loop.ts`) instead hand-builds the exact same `stop_condition_met`/`paused`/`round_ended`/`journal_finalized` events every policy-decided pause gets, reusing the schema's existing, otherwise-unused `'principal_stop'` condition and generic `'principal_item'` paused-reason — never a new schema value — so a reader (or a machine parsing the outbox) sees a real, complete pause record either way. This closes a regression (PR #489 round 2, MAJOR): the reviewer-infrastructure pause used to be built by the driver's own hand-rolled `Decision`, skipping the log entirely. No verdict is held, none is published, and the round number does not advance (the same way a mechanical-gate-red retry never advances it). The pause comment names the failing role and the missing artifact(s), or the head and the failing check-run(s), it observed.

### Unpushed work is resumed once, then `no_push` (`doctrine-fixes-v1` task 1, `#543`, O2)

A gate-red retry or a conflict retry already waited for the branch's head to change before this task (above); if it doesn't, the driver now checks the developer's own worktree before charging the stall to the generic `MAX_GATE_STALLED_TURNS` bound: `git status --porcelain` (dirty files) and how many commits local `HEAD` sits ahead of its upstream, read fresh via `readUnpushedWorkDetail`. Either signal non-zero means the developer did real work and simply never pushed it — resumed ONCE, foreground, with a dedicated commit-and-push instruction (never the CI-red or conflict prompt, and never a second resume for this), recorded BOTH as a real `dev_review_loop` journal event (`unpushed_work_resume` — `branch`, `detail`; `packages/aeg-core/src/log/schema.ts`, round 2 review, MAJOR: only a PR comment used to carry this, invisible to `fetchLoopHistory`/`reconstructRounds`) and, unchanged, as its own marked PR comment (`<!-- aeg:loop:unpushed-work-resume -->`, idempotent per round+head like a pause comment). Still no new head after that resume is `pause{reason:'no_push'}` — a real `PauseReason` member (`packages/aeg-core/src/dev-review-loop/types.ts`), not a reuse of `'infrastructure'`, since a Principal reading the pause needs to tell "stopped after doing real, uncommitted-or-unpushed work" apart from "did nothing at all" — naming the branch and the dirty file(s) (or, worktree clean but commits ahead, saying so). A turn with neither dirty files nor commits ahead is the genuinely idle case and falls straight through to the existing `'infrastructure'` stall, unchanged. **`readUnpushedWorkDetail`'s dirty-file list carries no exemption at all (`task-files-v1` 2, Issue #649, O2).** Before this task, it excluded the loop's own two control files by exact name (`.vinaya-confidence`, `.vinaya-round-response`) — both were written by the developer's own turn, at this driver's own instruction, at the worktree root, the one place agent scratch sits inside a git tree. Both now live under that round's own Developer folder inside the task's folder, outside the worktree entirely, so neither name is ever written, read, or ignored here any more: a file bearing either old name that still turns up in `git status --porcelain` is ordinary untracked work, exactly like any other stray file — visible, never silently exempted.

This check runs only where a head-change wait already ran before this task (a CI-red retry or a conflict retry) — never the plain review-findings retry, whose own next `dispatch_reviewers` phase re-reads whatever head exists rather than waiting for one to CHANGE; extending it there would need every existing fixture for that path (there is no real push to wait for there today) to start simulating one.

### A reviewer report missing finding ids is resent once, then `report_uncitable` (`doctrine-fixes-v1` task 1, `#543`, O3)

`assessRound`'s `reappearance` exit is derived by comparing finding ids between rounds — but the loop's own per-round `findings.txt` carries no reviewer-authored id at all by construction until this task: the driver used to number findings purely by their position in the file (`F1`, `F2`, …), which is not a stable identity across two SEPARATE dispatches. `renderReviewerDispatchPrompt` now also asks for a `FINDING_IDS:` line in `report.txt` — one id per `findings.txt` line, in the same order, comma-separated — whenever `findings.txt` is non-empty (an empty findings list has nothing to cite and is never sent back for it). `dispatchReviewer` checks this after a report parses successfully; a findings-carrying report with no matching `FINDING_IDS:` line is sent back ONCE — a fresh dispatch (never `--resume`: this file's own module doc states, as a load-bearing invariant, that a reviewer session is never resumed, only the developer's), into a fresh work directory, its actual path named in the resend prompt exactly as the first dispatch's own prompt names its own — with a targeted instruction to cite ids. Still uncitable after that resend is recorded once as a marked PR comment (`<!-- aeg:loop:report-uncitable -->`, naming the role(s)); the round then proceeds on its own severities, exactly as any other changes-requested round does.

### Objectives changed mid-round (`review-validity-v1` task 2, `#476`, O3)

`'objectives_changed'` is a real `PauseReason` member (`packages/aeg-core/src/dev-review-loop/types.ts`) — this task's own declared Surface includes that package, unlike the driver-decided pauses above. The driver still decides it itself, the same way it decides `'infrastructure'`: comparing two `resolveIssueObjectives` reads (the one taken before dispatching this round's reviewers, the one taken right after both return) is not something `assessRound` can do from an `Observations` value, so the comparison lives in `dev-review-loop.ts`, and `driverDecidedPauseEvents` logs it through the same reused event shape. The pause's `detail` names the version the round was dispatched against, the version now current, and the exact `vinaya issue objectives edit` invocation that moved it — reconstructed by `describeObjectivesEdit` from the edit-audit comment's own `Previous:`/`Now:`/`Reason:` lines, never executed. As with the infrastructure pauses above, no verdict is held and none is published for that round, and the round number does not advance.

### Ruling posted mid-round (`review-validity-v1` task 3, `#477`, O3)

`'ruling_posted'` is the ruling-ordinal twin of `'objectives_changed'` above, same `PauseReason` member shape, same detection site, same reason for living in `dev-review-loop.ts` rather than `assessRound`: the driver compares the newest principal ruling ordinal it resolved when it dispatched this round's reviewers (`fetchNewestRulingOrdinal`, captured into `facts.rulingOrdinal`) against the ordinal it resolves right after both return, before either verdict is held. A mismatch means a principal posted a ruling while this round's reviewers were running — that round's verdicts are discarded in memory the same way (never held, never published), and the round ends in `pause{reason:'ruling_posted'}`, its `detail` naming the ordinal the round was dispatched against, the ordinal now current, and the ruling's own marker identifier (`<pr>-<k>`). No reconstructed command here — unlike an objectives edit, a ruling carries no replayable invocation, only its identifier and content. The next round's reviewers see the new ruling automatically: `dispatch_reviewers` re-resolves both `rulings` and `rulingOrdinal` fresh at the top of every round, mid-round check included.

### A conflicting head is sent back to the developer, never to a reviewer (task-run-v1 task 13, `#508`, O4/O5/O6/O7)

Mergeability is a forge fact the driver reads, never re-derives: `gh pr view <n> --json mergeable` returns `MERGEABLE`, `CONFLICTING`, or `UNKNOWN` (the forge still computing it — polled within the existing gate poll budget, never read as clean and never as conflicting, O7). The driver reads it TWICE:

- **Before dispatching reviewers** (O4): a `CONFLICTING` head means no reviewer starts and no CI is waited on for that head — the round instead routes back into the developer-dispatch branch with the loop's own conflict prompt, naming the conflicting file(s) (computed locally with `git merge-tree --write-tree`, since the forge's `mergeable` field alone doesn't name them). This reuses the SAME head-change-wait and `MAX_GATE_STALLED_TURNS` bound the CI-red retry already has — a conflict that never resolves ends in `pause{reason:'infrastructure'}`, its detail naming the head and the unresolved file(s), the same driver-decided-pause shape "Infrastructure failures," above, already documents.
- **Before publication** (O5): reviewers can run long enough that a clean head falls into conflict with the base while they worked. A branch found `CONFLICTING` at this second read has its held verdicts for that round discarded (deleted from the outbox, never posted) and the completion events already queued for that publish are dropped; the developer is resumed with the same conflict prompt, and the round number does not advance — the NEXT reviewer dispatch judges the resolved head.

The developer contract (`aeg-root/roles/developer.md`, O6) states the mirror image: the developer's own turn does not end with the branch behind the base in a way that conflicts — merge or rebase and resolve before pushing, never after. The loop's conflict prompt is what a developer sees if it ends its turn without having done this.

### A stale driver re-execs in place, and pauses only if that fails (task-run-v1 task 13, `#508`, O8; re-exec added by task-run-v1 task 15, O7)

`devReviewLoop` records the base branch's head once, at the very start of a run (fresh or `--resume`), and re-reads it at the top of every iteration of the round loop thereafter. A base that has moved since — and whose new commits touch this driver's own code (`DRIVER_OWNED_PATHS`: `apps/cli/src/lib/dev-review-loop.ts`, `apps/cli/src/lib/dev-review-loop/` — gate reading, reviewer dispatch, round assessment, publication, pause/resume, developer dispatch — `apps/cli/src/commands/review-post.ts`, or any of `packages/aeg-core/src`) — is a stale driver: it is, by construction, still executing the OLD driver's code even after a fix to it merges, and would otherwise keep judging rounds against a gate the new code has already changed the rules for, then publish a verdict the updated gate refuses.

Rather than handing this to a human, `checkStaleDriver` re-execs in place: it pulls the default branch (`git pull --ff-only origin main`), then re-spawns the exact same interpreter and entry script it was itself started with, reattaching to the same task with `dev-review-loop --task <n> --agent <vendor>` — **always this form, `buildReexecArgs` (task-run-v1 task 15, O7; narrowed by `[task-operator-v1]`/Issue #662, O4) never reconstructs `--resume <pr>` even when THIS run itself started that way.** The loop's own round-1 entry already treats `--task <n>` as "attach if a PR/pause state exists, start fresh otherwise" (a task-run-started process reattaches through this same door), which is exactly the position a re-exec needs: the round number recovers from the durable journal/held-verdict state, not from a `pause-state.json` a completed resume has already moved past. `--resume <pr>`'s own top-of-function gate authenticates a Principal's ruling by CONSUMING its resolution exactly once, durably (`resolveEscalation`/`consumeResolutionOnce`, "Escalation, resolution, and `--cancel`," below) — a re-exec that rebuilt `--resume <pr>` would re-enter that same gate a second time against the SAME already-consumed resolution and refuse (`ReplayedResolutionError`), uncaught, before this process's own outer `try`/`finally` even starts: a resumed loop that ran a full round, took the developer's next push, then hit a stale-driver restart mid-round exited with no pause and no reviewers (origin: live, 2026-09-19). A driver authenticates a ruling exactly once, at `--resume`'s own start — never again on a later round's own re-exec. This is never a weakening of the replay refusal itself: a genuinely fresh, human-invoked `--resume <pr>` against an already-consumed resolution still refuses exactly as before; only the driver's OWN internal re-exec no longer asks. The re-exec inherits stdio, so its output reaches whatever terminal or log was watching the original process; the original process then exits with the child's own exit code, handing off entirely — a moved base costs a restart, never a hand.

`pause{reason:'stale_driver'}`, naming both shas, is reserved for when the re-exec attempt ITSELF fails — the pull, or the spawn — never for the staleness alone. This is `packages/aeg-core`'s one `PauseReason` member the originating task added (in-Surface per that task's own blast-radius-ack, unlike the driver-decided pauses above); it is now reachable only along this narrower failure path.

**The lock hands off to the child before the spawn, not after (`#548`, O1).** A defect observed live (PR `#547`, 2026-09-12): the parent's own driver-lock record was still on disk, still naming its own live pid, at the exact moment `reexecSelf` spawned the child — the child's own entry-gate lock check (above) read that record, found it alive, and refused to start with "a driver is already running," while the parent (blocked in `spawnSync`, waiting for a child that never started) went on to exit with the child's non-zero code. Both processes ended; nothing paused, nothing posted — a pull request sat with green CI and no reviewers for six hours. The fix is ordering, not a new lease: `checkStaleDriver` now clears its own lock record (`clearDriverLock`) immediately before calling `reexecSelf`, synchronously, in the same tick — the child's entry-gate check then finds no record at all and starts normally, writing its own record under its own pid the same way any fresh invocation does. If the spawn itself never starts (`reexecSelf` returns `null` — the pull succeeded, but the interpreter could not be re-invoked), the parent re-writes its own lock record before falling through to the `pause{reason:'stale_driver'}` path above, since it is still the process driving this task.

**A driver that exits with no decision on record still leaves a trace, inside this task's Surface (`#548`, O2).** A genuinely new forge journal-event kind for this needs a `packages/aeg-core` schema change, out of this task's declared Surface, and is left for a later task with that Surface. What stays in-Surface: the SAME human-readable role log `~/.vinaya/loops/<owner>-<repo>/<issue>.log` (`loop-log.ts`) that `task status --follow` already tails gets one more line, `[dev-review-loop] driver_exited: reason=<reexec|error|signal> last_decision=<...>`, from exactly three call sites — right before the reexec-success `exitProcess` above, inside the round loop's own outer `catch` for a genuinely uncaught error, and from `SIGTERM`/`SIGINT` handlers registered once the round loop's own state exists — guarded so at most one line is ever written per run (`exitTraceWritten`). None of the three sites fire on a normal `pause`/`publish` return, which is what makes the line diagnostic rather than routine. `task-status.ts`'s `deriveLoopState` reads it back: a driver-lock record naming a DEAD pid — itself the signal that the last run never reached its own cleanup — now checks the role log for this trace before falling through to the published/paused reading, and reports a new `exited` state (`kind: 'exited', reason, lastDecision`) when one exists, rendered by both `vinaya task status --issue <n>` and `<tranche> <n>`.

## Which severities block is repository policy (`review-validity-v1` task 8, `#506`)

`buildVerdictFromReport` (`apps/cli/src/lib/dev-review-loop.ts`) derives a round's reviewer/security verdict from the dispatched role's own findings via `deriveCodeReviewVerdict`/`deriveSecurityVerdict` (`apps/cli/src/commands/review-post.ts`), which call `@attalabs/aeg-core`'s pure `evaluateCodeReview`/`evaluateSecurityReview` against `policy` — resolved ONCE per loop run, from the default branch's `vinaya.config.json` (`resolveReviewPolicy(loadTrustAnchorConfig())`), never from the PR's own checkout. Only CONSEQUENTIAL findings reach the evaluator: `consequentialFindings` (`@attalabs/aeg-core`) drops any finding the reviewer marked `resolved` — kept in the record, but no longer driving the verdict — while a finding at or above the threshold in any other state (`open`, `fix-claimed`, `reproduced`, or no state token) still blocks. That one filter is the SINGLE definition of "counts toward policy," and the merge gate (`checkReviewGate`) and `publishRound`'s own re-check below both apply the very same filter, so an APPROVE/PASS whose only at-or-above findings are `resolved` passes the gate and publishes exactly as it makes derivation approve — the three can no longer disagree about the same verdict comment. `assessRound` (`packages/aeg-core/src/dev-review-loop/`) is unchanged: it still reads only the already-derived `VerdictObservation.verdict`/`objectives` — the policy threshold that decided that value lives entirely in the driver, never in the pure decision layer, matching this file's own layering (`assessRound` is decision logic; the driver turns facts into observations). `publishRound`'s own re-check, below, is the same evaluator applied a second time, against the posted comment's own FINDINGS block, before treating the round as published.

## Attempt and finding telemetry (`task-log-v1` task 5)

`assessRound`'s own `verdicts_read` event (`packages/aeg-core/src/dev-review-loop/assess-round.ts`) now carries a `findings` array alongside its pre-existing `blockers` count — one entry per finding from both roles' verdicts this round, each naming which severity scale it was read against (`'code-review'`/`'security'`) and whether it counted as blocking under the effective policy (`policy_treatment: 'blocking' | 'non_blocking'`), computed in `reviewer-dispatch.ts`'s `buildVerdictFromReport` from the SAME `isProseLocation`/blocking-severities rule `@attalabs/aeg-core`'s `evaluateReviewFindings` applies internally — the reported `severity` itself is never overwritten by the prose-location cap, only how it counts toward this threshold (the durable record `journal-reconstruction.ts`'s own doc names as previously unavailable: "a round's real per-severity breakdown exists only in the live process's own in-memory `VerdictObservation.findings`, never logged verbatim").

Both reviewer dispatch call sites (`dispatchReviewer`, `resendForFindingIds`) now pass `DispatchOpts.inputVersions` from the round's own `ReviewInputManifest` (`facts.manifest`), so each reviewer/security attempt's logged lines carry the objectives version, brief hash, ruling ordinal and policy digest that round was dispatched against — the generic `dispatchRole` (`apps/cli/specs/log.md`) never resolves one itself.

An invalid reviewer report (`ReviewerReportParseFailure`/`ReviewerInfrastructureFailure`, "A findings.txt line that still does not parse," above) is caught before it ever reaches `assessRound` — no `verdicts_read` is logged for that round at all. The catch now also logs one `role_attempt` `attempted` line (`kind: 'role_attempt'`, `actor`: the failing role, `outcome: 'incomplete'` for a parse failure or `'infrastructure_failed'` for a missing-artifact retry exhaustion, `usage: null`) — a durable, structured record that this was a failed attempt, distinguishable from a round that genuinely found nothing, never relying on the pause comment's own prose alone.

## Publication (O1, task 6)

At `publish`, `publishRound` (`apps/cli/src/lib/dev-review-loop.ts`) posts, through this repo's `gh pr comment` forge-write mechanics, in order: the round's held reviewer verdict, the held security verdict, then one summary comment from `renderSummary` (`@attalabs/aeg-core`) built from the loop's own round records. The round marker comment ("Reviewers," above) is a separate, earlier post — at dispatch time, not publication — and is not one of these three. Each verdict post is re-read straight back off the PR and re-parsed through `extractCodeReviewVerdict`/`extractSecurityReviewVerdict` — the SAME extractors the merge gate itself calls, which now read each finding's id and re-review state beside its severity and location — and refused (thrown) if it does not resolve cleanly to the round's judged head. It is then re-evaluated against `policy` (task 8, `#506`, O3), through the SAME `consequentialFindings` filter the gate applies: a posted comment whose `VERDICT:` line reads APPROVE/PASS but whose own FINDINGS block carries a CONSEQUENTIAL (not `resolved`) finding at or above the threshold is refused, never published — a reviewer's own clean-looking verdict never overrides the evaluator, and, symmetrically, a finding the reviewer marked `resolved` no longer refuses a round the gate itself would pass. A finding at or above the threshold in any other state still refuses publication. The summary is checked BEFORE it is posted: both extractors run over the rendered text, and a summary that resolves as a real verdict through either one is refused rather than posted (`renderSummary`'s own contract is no `VERDICT:`/`Judged head:`/`Objectives version:`/`Ruling ordinal:` line; this is re-verified live rather than trusted).

**A round whose counts are unknown reports nothing, never a zero.** The count columns are written by `countCells` (`render-summary.ts`), and the question they ask of a round is whether its counts were RECORDED — never whether they are zero. A round the loop assessed carries every severity column, zeros included: `buildRoundRecord` (`assess-round.ts`) seeds all of them at zero before counting a single finding, so a round it measured and found nothing in is a recorded zero and still reads `0`. A round carrying none of those columns has no counts from any source — it was rebuilt from the pull request's own round markers after a restart, and a marker names a round's number and head and no finding breakdown at all ("The round journal is the task's, not this process's," above) — so each of its count cells reads the table's own not-reported glyph, the same `—` the confidence column already writes for a round nobody asked. Rendering those as `0` told a reader the round had been reviewed clean; one real task's published table read zero findings for four rounds whose counts were in fact unavailable. The header row is untouched by this, so `isPublishedSummaryComment`'s detection of a posted summary reads exactly as before, and only the confidence column is ever read back out of a posted table (`parseSummaryConfidenceRows`), so a count cell sharing the glyph is never parsed as a confidence figure.

**A round no reviewer saw reports no counts, and its outcome cell says why.** A round can end before any reviewer is dispatched: its gate observation was not green, or — from round 2 on — a below-threshold confidence sent the developer back ("The confidence rule," above). Neither round was ever assessed, so it has no findings from any source, and `buildUnreviewedRecord` (`assess-round.ts`) records it with NO counts — the same empty `countsBySeverity` a marker-reconstructed round carries, so `countCells` reports `—` for every severity column through the one path above, not a second renderer branch. Before this, such a round was recorded with `buildRoundRecord`'s seeded zeros and rendered `0` under a `changes_requested` outcome — a contradiction a reader hit when a round whose run had died on a full temp disk showed zero findings in every column beside "changes requested," a review that never ran. The outcome cell now names the reason instead of the round's log outcome: `not reviewed — checks red` for a red gate, `not reviewed — low confidence` for the confidence send-back (`outcomeCell`, `render-summary.ts`). What does NOT change: the loop's decision is untouched — the developer is still sent back exactly as before — and the round's own `round_ended` log event keeps its schema-constrained `changes_requested` outcome, so log readers are unaffected; only the `RoundRecord` the journal carries, and the row the table renders, change. A round the reviewers DID assess renders exactly as today, its zeros included when they found nothing.

Idempotency: each of the three posts is wrapped in `postForgeEffectOnce`, which records an effect id in the outbox as `started` before the `gh` call and rewrites it `posted` (with the returned URL) right after — mirroring `dispatch.ts`'s own effect-id-before/checked-after discipline, adapted to a comment post since `DevReviewLoopEvent` carries no `effect_id` field of its own. A rerun that finds an already-`posted` record for a given post returns its recorded URL without calling `gh` again — nothing is posted twice.

Supersession (editing a posted verdict, or marking one superseded after a later push) is out of `dev-review-loop-v1`'s scope: nothing is ever posted before green, so there is nothing to supersede in v1.

## The review-input manifest and its equivalence (`review-validity-v1` task 4, `#478`)

Before dispatching reviewers, the driver builds ONE `ReviewInputManifest` (`packages/aeg-core/src/review-input-manifest.ts`) from forge facts: the round's candidate head, its **base identity** (`baseSha`, the merge base of the candidate head and the default branch — never the default branch's raw tip, which a commit landing on the default branch after the candidate branched would make part of a two-dot diff against the pull request's own changes; resolved once per round through an injected `gitMergeBase` dependency that reuses `pr-report-engine.ts`'s own `resolveMergeBase`, the same `origin/main`-then-`main` fallback the Evidence block's Group A diff already resolves through — `control-store-v1` task 5, `#555`, O1), the frozen brief's own hash (`briefHash`, a `sha256` of its posted content — moved here from `dispatch-task.ts` so the read side and the write side share one implementation), the objectives version, the newest principal ruling ordinal, and the effective review policy's digest (`policyDigest`, which folds in the round-policy field `maxRounds` — the COMPLETE effective policy identity, `#555`, O1). This manifest — never separate ad hoc fields threaded past it — is the only source of `renderReviewerPrompt`'s `HEAD:` line (`ReviewerPromptFacts.manifest`) and of every structural line `buildVerdictFromReport` renders into a round's verdict/escalation comment (`Judged head:`, `Objectives version:`, `Ruling ordinal:`, `Brief hash:`, `Policy digest:`, `Judged base:` — the last two of those first four and `Judged base:` rendering unconditionally, `Brief hash:`/`Judged base:` as the literal `(none)` when no frozen brief / no base was resolvable, the same non-hex placeholder the gate's own extractor reads back as "nothing to bind"). `Judged base:` renders LAST of the structural head lines, appended after `Policy digest:`, so it never shifts the lines above out of the exact read windows their extractors pin.

**Parent-built manifest record in the control store (`#555`, O1).** The same manifest the round is dispatched against is persisted as a durable `manifest` record in `control-store-v1`'s store (`packages/aeg-core/src/control-store/`, a fifth record kind beside run/input/ownership/transition), built by the parent in `dev-review-loop/reviewer-dispatch.ts` (`buildManifestRecord`/`persistManifestRecord`) before reviewers dispatch. The record carries repository and work identity (the PR/branch this round belongs to) on top of the binding manifest — one immutable snapshot per `(task, round)`, a durable policy history keyed by round. It is written with the store's atomic, torn-write-free discipline but is NOT epoch-fenced (unlike `writeRun`/`writeInput`): a per-round snapshot is not a mutable state transition two owners could race on, and the driver's own cutover to acquired-epoch ownership is separate, later adoption work. Persisting it is best-effort — a snapshot that cannot be written never fails a round, because the echoed-comment binding is what actually gates a verdict.

**One comparison, three callers (O2/O3).** `compareManifest` — the candidate head/base pair bound together under the bounded acceptance rule below, then `briefHash`, `objectivesVersion`, `rulingOrdinal`, `policyDigest` each their own field — is the SAME function all three binding readers call: `checkReviewGate` (the merge gate), the driver's own pre-hold self-check, and `publishRound` (`dev-review-loop/publication.ts`), which now binds each posted verdict against the round's manifest on EVERY field, not just the head it re-checks (`#555`, O3). No field is bound on one side and ignored on the other: whatever the gate checks against a verdict comment's echoed lines, the loop and publication check too. The "echo" is never trusted as provenance either way — it is the PARENT's own dispatch-time fact, stamped into the rendered comment (or, for the loop's own same-process check, simply the in-memory manifest via `manifestAsEchoed`) and read back only to confirm a comment still covers the CURRENT manifest.

Right after both reviewers return — before either verdict is written to the outbox — the driver re-resolves the current manifest (objectives, newest ruling ordinal, and the frozen brief's hash, all freshly re-read; the policy is resolved once per loop run and so never drifts within a single run) and calls `compareManifest` against the manifest the round was dispatched with. A mismatch discards both verdicts in memory (never held, never published) and ends the round in one of: `'objectives_changed'`, `'ruling_posted'`, `'brief_superseded'` (a Planner superseded the frozen brief mid-round — same shape, new in this task), or `'policy_changed'` (the digest moved — reachable today only if a future change makes the loop's own policy read live, included for symmetry with the gate, which DOES re-resolve policy fresh on every run). See "Objectives changed mid-round" and "Ruling posted mid-round," above, for the two pre-existing reasons' own detail shape — `'brief_superseded'`/`'policy_changed'` follow the identical pattern (old value, new value, named in the pause detail).

**The same-patch rebase equivalence and base identity.** A verdict judges the pull request, not its base — a move of the base branch alone never invalidates it. Base identity is recorded for audit, but a base move is tolerated when the candidate binds by an EXACT head sha OR by PATCH IDENTITY. A verdict judged one head still counts against a DIFFERENT current head when `patchIdOf` (`git patch-id --stable` between the PR's base and each sha) resolves the same value for both — a merge from `main`, or a rebase, that changes not one line of the PR's own patch does not void an already-cast verdict; only a change to the patch itself does. When the candidate binds by an EXACT head sha, a base move is TOLERATED — the specific head was judged, not the base behind it. When the candidate binds by PATCH IDENTITY (a genuine equivalent rebase, the diff proven byte-identical), a base move is TOLERATED — the reviewer judged the patch, not the base. Only when the head does not bind at all (a different revision, not an equivalent rebase) is the base checked as a separate fact. The stated limit, unchanged: a base that moved under an identical patch can still hide a semantic conflict the earlier review never saw; CI at the new head — which the gate already requires green — is the guard for that, not a re-review. `git patch-id --stable` also ignores whitespace, so a whitespace-only push keeps the verdict too — deliberate for reformatting, and not free (whitespace can be semantic in some languages), but every non-whitespace change still drops the verdict correctly.

**Formerly deferred, now landed (`#555`).** Base identity and a durable policy history were named in the execution contract but waited for `control-store-v1`'s durable store. That store is now built AND adopted for the manifest record (above): base identity (`baseSha`) is bound under the narrowed acceptance rule, the round-policy field (`maxRounds`) is folded into the policy identity, and the per-round manifest snapshot persisted in the control store IS the durable policy history. What stays deferred is the DRIVER's own wholesale cutover to acquired-epoch ownership (replacing the pid-lock and the pause-state/effect side files) — separate, later adoption work, not widened here.

**An unresolvable base pauses the round.** `resolveMergeBase` throws `UnresolvableMergeBaseError` when no candidate ref (`origin/main`, then plain `main`) yields a real merge base for the candidate head — unrelated histories, or a default branch this checkout cannot resolve either name against. That throw reaches the same wrapping `try` every other setup-phase git read in `devReviewLoop` already reports through, and the round is decided a `pause(reason: 'infrastructure')` rather than silently falling back to a base that was never proven a common ancestor of the head.

## Reviewer isolation — one immutable candidate, isolated scratch space (`worker-isolation-v1` task 4, `#561`)

The manifest binding above (`compareManifest`) proves that a *verdict* still covers the candidate it was cast against — it never made the *filesystem* two reviewers read from immutable while they read it. Before this task, `dispatchReviewer` (`dev-review-loop/reviewer-dispatch.ts`) called `d.dispatchRole` with no `cwd` at all, so a dispatched reviewer's shell ran from wherever the driver process itself happened to be started — never guaranteed to be the round's own candidate content, and never guaranteed identical between the two reviewers dispatched the same round. `apps/cli/specs/isolation.md` (`worker-isolation-v1` task 1) names this gap directly in its own Reviewer boundary row ("read the repository at the judged head … read-only in intent") and is explicit that wiring `dispatchRole` to its full OS-level mechanism (Seatbelt, credential scoping) is a later task's surface, not this one's — `worker-isolation-v1` task 3 (`#560`) is that later task; see `isolation.md` §4. This section is the narrower, already-in-surface slice THIS task closes: a real `cwd`, real permission enforcement, no process confinement.

`apps/cli/src/lib/dev-review-loop/reviewer-isolation.ts` builds two kinds of directory, both inside that round's own folder (`<runtimeDir>/tasks-execution/<task>/rounds/<n>/`, holding `candidate` and one `<role>-scratch[-retry<n>]` per attempt alongside the round's held verdicts and reviewer work directories), both plain permission-enforced filesystem copies — never a second `git worktree`/`git archive` invocation:

- **One shared, read-only candidate per round** (`buildReviewerCandidate`, O1) — a copy of the developer's own local worktree (`.worktrees/<branch>`, the same path `readWorktreeHead`/`readUnpushedWorkDetail` already trust), taken once, before either reviewer dispatches, then `chmod`'d read-only (files and directories both) so a reviewer that tries to write inside it fails on the OS's own permission check. `.git`, `node_modules`, and `.worktrees` are excluded from the copy — a reviewer never needs installed dependencies or version-control internals to judge a diff — and so is everything the developer worktree's own `.gitignore` excludes, plus any filename `SECRET_FILENAME_RE` recognizes (`.env*`, an SSH private key, `.npmrc`/`.netrc`) regardless of `.gitignore` (round 2 review, HIGH: an untracked secret file — gitignored or not — was previously copied into the shared candidate verbatim, same as any tracked source file). No symlink is ever copied either (round 2 review, HIGH/MAJOR): the worktree under review is untrusted input, and `chmodSync` always follows a symlink on POSIX (there being no portable `lchmod`) — a copied symlink would let this same read-only pass silently change the permissions of whatever file it resolves to, a path that can sit entirely outside the candidate tree. `copyTree` refuses every symlink at the copy step, and `chmodTree` independently skips one too, should it ever find one anyway. The read-only pass never widens a file's mode past what the source worktree already granted (round 2 review, HIGH: a blanket `chmod 0o444`/`0o555` used to force every file world-readable regardless of its original mode, so a locally-generated secret sitting at `0o600` came out readable by any other user on the host); `chmodTree` instead strips write bits from — or, for the writable scratch copy, adds only the owner's own write bit back onto — each entry's own preserved-from-source mode. The candidate (and scratch) directory itself is created in one `mkdirSync(dest, { recursive: true, mode: 0o700 })` call, never a create-then-`chmodSync`-after pair (round 3 review, MEDIUM: the two-step form left `dest` briefly at whatever the process umask produces on this directory's fully predictable, task/round-derived path) — so its predictable path (round 2 review, MEDIUM) buys another host user nothing without also being the owning user, with no window either. `null` when the developer's own worktree doesn't exist on this machine (a fresh attach with nothing dispatched here yet, or a driver running on a different host), OR that worktree's own `HEAD` no longer matches the round's resolved candidate sha (round 2 review, MAJOR: a local worktree that moved on between push and dispatch must never be copied as if it still were the pinned candidate) — the round then dispatches reviewers with no `cwd` override, exactly as every round before this task; this degrade is deliberate (matching `persistManifestRecord`/`runEvidenceReport`'s own "the loop's own paperwork must never cost a round" posture), not a defect. `buildReviewerCandidate` itself only guards the pre-copy side of that check; the caller (`dev-review-loop.ts`) goes through `buildVerifiedReviewerCandidate` instead, which re-reads the SAME worktree head a second time once the copy returns and discards the candidate (via `cleanupReviewerIsolationForRound`), falling back to no `cwd` override, if it moved in between (round 2 review, MINOR; round 3 review, MAJOR: pulled out to its own function, taking the head-reader as a parameter, specifically so this race has a direct unit test rather than resting on the full driver harness) — closing the gap where a commit landing mid-copy could otherwise hand both reviewers a torn snapshot nothing else would catch.
- **A fresh, writable scratch copy per reviewer per dispatch attempt** (`buildReviewerScratch`, O2) — copied FROM that same shared candidate, never from the developer's worktree directly, and never shared between the two roles. This is the `cwd` each reviewer/security dispatch actually runs from (`DispatchOpts.cwd`, wired through `dispatchRole`'s `spawn` call for the first time by this task). A write or a local toolchain run inside a reviewer's own `cwd` can therefore never reach the shared candidate or the sibling role's own context. Rebuilt on every dispatch attempt (`dispatchReviewer`'s one-fresh-retry, `resendForFindingIds`'s resend) — a retried attempt never resumes a prior attempt's scratch, the same fresh-reviewer-session invariant "Reviewers," above, already states for the dispatch itself.

**Cleanup (O3).** A round's candidate and every scratch copy any attempt created are removed the moment that round's reviewer dispatches conclude — published, paused, or handed back to the developer for another round — via `cleanupReviewerIsolationForRound`, called from a `finally` around the round's `Promise.all([dispatchReviewer(...), dispatchReviewer(...), d.runEvidenceReport(...)])` so cleanup runs whether that block returned normally or threw. Restart and cancellation cleanliness are the same function at a wider scope (`cleanupAllReviewerIsolationArtifacts`): called once at driver start (fresh or `--resume`), right after the one-driver-per-task lock is acquired and before this run builds anything of its own, so a crashed or killed prior run's leftovers never leak into the next one; and from the driver's own `SIGTERM`/`SIGINT` handlers (same section as `terminateInFlightLaunchesOnShutdown`, above), so a cancelled run leaves nothing behind either. Every function in this module is best-effort — a failed build or a failed cleanup returns `null` or is silently swallowed, never thrown — matching every other filesystem-bookkeeping concern in this driver.

**What this does not change.** The manifest binding (`compareManifest`, above) is still what actually gates a verdict against a moved base or head — this mechanism only guarantees that two reviewers reading "the candidate" this round read the identical bytes, and that neither can alter what the other reads. It adds no environment scoping, no network confinement, no credential brokering. `worker-isolation-v1` task 3 (`#560`, `isolation.md` §4) later wired `dispatchRole`'s `spawn` call to OS-level confinement (env scoping, no credential brokering yet) for an UNATTENDED dispatch whose repo opts in (`dispatch.requireWorkerIsolation`, platform-conditional: `true` on Darwin, `false` on any other host, unless the config sets it explicitly one way or the other — `config.ts`'s own `?? process.platform === 'darwin'` fallback) — a Reviewer dispatched by this driver carries `DispatchOpts.unattended: true` alongside its own `cwd` (this section's own scratch directory) for exactly that reason, though a non-Darwin host with no explicit override still runs reviewer dispatches unconfined today, same as before task 3.

## Pause and `--resume` (O2, task 6)

At `pause{reason}`, the driver writes the round's held state (task, round, judged head, branch, PR number, reason, and — for `'infrastructure'` (the reviewer case, the gate-stalled-head case, and the conflict-never-resolved case; see above), `'no_push'` (the branch and the dirty file(s) observed after the one unpushed-work resume; see above), `'max_rounds'` (the configured `reviewPolicy.maxRounds` value; see "The four exits," above), `'objectives_changed'` (the old version, the new version, and the superseding command; see above), `'ruling_posted'` (the old ordinal, the new ordinal, and the ruling's marker identifier; see above), `'stale_driver'` (both shas; see above), `'brief_superseded'` (the old and new brief hash; see above), or `'policy_changed'` (the old and new policy digest; see above) — the detail it observed) to the outbox, then posts one comment on the PR marked `<!-- aeg:loop:paused:<reason> -->`, carrying the reason (plus that same detail, where one exists) and the exact resume command (`vinaya dev-review-loop --resume <pr>`, the real PR number substituted in). The pause comment carries no verdict grammar. The CLI command exits non-zero — the process-level signal an unattended dispatcher watches for.

**Every reason renders its detail, not only the ones `assessRound` computes one for (`[task-log-v1] 9`, Issue #631, O1).** `assessRound` itself (`packages/aeg-core`) never computes a `detail` for `'confidence'`, `'reappearance'`, or a reviewer's own `'escalation'` — before this task those pause reasons rendered with no detail at all, even though `renderPauseComment` (`dev-review-loop/pause-resume.ts`) never special-cased them; the gap was one level up, at the call site. The driver now narrates each from data it already has in scope, never a fact `assessRound` didn't already compute: `describeConfidencePauseDetail` reads the same `Confidence` value that decided which of the two confidence branches fired (absent on the re-asked turn, or a reported value still under 50); `deriveVerdictPauseDetail` reads the round's own `findings_compared` event for `'reappearance'` (the ids that reappeared) and the two dispatched verdicts themselves for `'escalation'` (which role(s) returned `ESCALATE`). Both are called only when `decision.detail === undefined`, so a reason `assessRound` already populated (`'max_rounds'`) is never overwritten. (The driver's own attach-redelivery `'no_progress'` pause is not one of these: it is decided in the driver, not by `assessRound`, and builds its own `detail` inline.)

**An absent guard precondition is distinguishable from one that held (`[task-log-v1] 9`, Issue #631, O3).** The driver-decided `'no_progress'` attach-redelivery pause (above, "The round journal is the task's, not this process's") is fired by an OR of two independent guard inputs — a local marker file this machine wrote on a prior attach, a control-store delivered-findings identity a (possibly different) machine wrote. Its `detail` now names which of the two was actually observed true (`present`/`absent` for the marker, `matched`/`absent` for the store identity), rather than a single sentence that reads identically whichever guard fired — or, were the guard ever to fire with neither genuinely true (a guard-logic defect, out of this task's scope), a comment now visibly wrong rather than indistinguishable from an ordinary redelivery pause.

**No pause exit flushes anything ([task-files-v1] 5, Issue #652, O3).** Every pause-exit call site (the crash-catch handler, the before-any-push escalation exit, and the general pause branch in the round loop) used to call a final `flushOutbox` BEFORE writing the escalation record, the pause-state file, or posting the pause comment, folding a failed flush into the pause's own `detail`. That call, `defaultFlushOutbox`, and the `detail`-folding helper are gone along with the round-end flush above: the events covering the pause window already reached the configured `logs` destination live, the moment each was logged, so there is nothing left to ship on the way out and no failure mode left to fold into `detail`.

The one exception is O9's before-any-push escalation (above): there is no PR yet, so that pause is posted on the task Issue instead, and its printed resume command is `vinaya task run --issue <n>` rather than a PR-anchored `--resume`.

**A pause with no pull request records one as ABSENT, and is cleared through its Issue (`unattended-run-v1` 22, Issue #781).** The before-any-push escalation used to record `prNumber: -1` in `pause-state.json` — a sentinel every reader's own "no pull request" guard (`=== null`) failed to recognize, so `task_cancel`/`task_resume` handed it to `fetchRulings` and shelled `gh pr view -1`, which `gh` parses as a flag: *"unknown shorthand flag: '1' in -1"*. A pause raised before any push was therefore unclearable by any tool. What changed:

- **The value at its source.** `PauseState.prNumber` and the task-tool catalog's own `EscalationInputsSchema.prNumber` (`packages/aeg-core/src/task-tools.ts`) are `number | null`, and both no-pull-request pause writers — the before-any-push escalation and the crash handler, whose local `prNumber` is still at its `-1` initializer — record `null`, the same value the durable `EscalationRecord.pr` already carried. The catalog change is a widening: every producer that records a real pull request still validates unchanged.
- **The readers, for a record already on disk.** `readPauseState` (`pause-resume.ts`) normalizes any non-positive `prNumber` to `null`, so a pause already paused on a real machine under the old sentinel reads as having none. Fixing only the producer would have left exactly the observed pause unclearable forever.
- **The command named, in the address form that works for THIS task.** `task run` takes two address forms and they are not interchangeable: `--issue <n>` is the tranche-LESS backlog path, and `assembleAndRenderBriefForIssue` refuses an Issue carrying a `vinaya/tranche:*` label outright — a refusal `task run` does not tolerate, so the process exits. A tranche task must be addressed `task run <tranche> <n>`. `noPushResumeArgv` (`pause-resume.ts`) picks between them off the pause's OWN branch, where `developerBranchFor` already recorded the answer at dispatch (`task/<tranche>/<n>` vs `task/issue-<n>`, read back by `parseTaskBranchIdentity`) — no forge call, and it cannot disagree with the branch the run is on. It is the single builder behind all three places that name this command: the Issue pause comment, `task_escalation_read`'s `permittedNextActions` (which used to render `--resume -1`), and the argv `task_resume` actually spawns — so none of the three can drift from the others. The agent AND model the paused run was dispatched under travel with all three, the launch included; the launch dropping `--model` silently re-resolved one from the Issue's own agent-class mapping instead.

  The two printed callers render that argv element by element, shell-quoted, rather than space-joining it (`noPushResumeCommandFor`'s own `shellQuote`). This is not cosmetic: the tranche segment is unvalidated forge input — `developerBranchFor` takes it from the Issue title's `[^\]]+` and `parseTaskBranchIdentity` accepts any `[^/]+` — and it lands inside a fenced command block a human or an Operator agent is told to run. The spawned argv was always safe (an array, no shell), so the printed form has to be the shell ENCODING of that same array; a space-join was a second, weaker builder wearing the first one's name, and it also rendered a different command than the one that runs for any tranche containing whitespace.
- **The ruling marker the Principal must write.** No shipped command posts a ruling on an Issue — `vinaya pr rule` counts existing markers through `gh pr view` and posts with `postMarkedComment('pr', …)`. So the pause comment names the marker line itself, on the comment's own first line, and the ordinal to exceed: `filterPrincipalRulings` recognises nothing without that exact line, and the authority gate refuses an ordinal that is not strictly newer. Telling a reader only "post a ruling on this Issue" left both facts unguessable. The marker is `<!-- aeg:principal:ruling:<ref>-<ordinal> -->` — `ref` is the pull request or Issue it concerns, and **the ordinal every reader compares is the SECOND number** (`RULING_MARKER_ORDINAL`, `packages/aeg-core/src/ruling-ordinal.ts`; `vinaya pr rule` posts `<pr>-<k>`). Which is why the comment builds it with `principalRulingMarker`, beside that same regex, rather than from a template of its own: a renderer that put the ordinal first emitted a marker parsing as ordinal `1` forever, so a ruling written exactly as instructed failed the very gate it was posted to satisfy for every pause whose baseline had reached `1`. The tests assert this by feeding the rendered marker back through the parser, never by comparing a literal.
- **The freshness baseline comes from where the ruling will be.** `bestEffortInputVersions` recorded `rulingOrdinal: 0` for a pause with no pull request, because it read the ordinal only off a pull request. That made the Issue-side gate vacuous: `newestIssueRulingOrdinal > 0` is satisfied by ANY ruling ever posted on the Issue, including one an earlier pause already consumed — a single stale approval would authenticate every later before-any-push resume and cancel. It now reads `fetchNewestIssueRulingOrdinal(task)` for that case (a `LoopDeps` field, injectable like its pull-request sibling), so each such pause records a real baseline a later ruling has to postdate.
- **`dev-review-loop --resume` says why it cannot help.** That entry derives its task from a pull request's body, so it has no entry for a pause that has none: it refuses naming the `task run --issue <n>` command that does work, rather than failing on the pull-request read.

`--resume <pr>`:

1. Reads the PR's body for its `Closes #N` reference to find the task.
2. Reads that task's held pause state from the outbox; refuses if none exists.
3. Requires a Principal-authored ruling comment on the PR (`fetchRulings`, non-empty) — refuses if none exists yet, UNLESS the held reason is `'infrastructure'`: the driver's own recoverable hiccup, never a human decision point (same treatment `'infrastructure'`/`'stale_driver'` already get from the driver-lock cleanup above), so `--resume` continues it on the bare command. Every other reason still requires one. A moved head on an infrastructure resume keeps the held round as-is (there is no ruling to re-derive a round-cap override from).
4. Re-resolves the PR branch's live head and compares it to the held state's recorded head.
5. **Head unchanged**: re-enters the round loop at the held round, dispatching the developer fresh with the Principal's ruling text as context instead of reviewer findings. This path deliberately re-dispatches fresh rather than reconciling a prior launch: a `--resume` after a Principal ruling is a new turn ON that ruling, not a continuation of the pre-pause session. (The vendor session id itself IS now durable across a restart — `dispatch.ts`'s launch record persists it, `control-store-v1` task 3, O1 — and the round-1 attach/no-push seams above DO resume it through reconciliation; the `--resume` ruling path is the one place that intentionally does not.)
6. **Head moved (task-run-v1 task 15, O8)**: accepted, never refused — "a ruling followed by a fix push" (the developer already acted on the ruling before `--resume` ran) is the normal case, not an error. The ruling is itself the round-cap override it declares: the round counter restarts at the ruling's own newest ordinal (`fetchNewestRulingOrdinal`) rather than continuing from the held round, which may already sit past the round cap and would otherwise re-trigger the very pause `--resume` exists to lift. No developer is dispatched on this pass at all (it already pushed) — the loop goes straight to the mergeable/CI-gate check and, once green, dispatches reviewers directly on the new head, exactly like a fresh round-1 attach to an already-open PR. No outbox state is ever reset by hand to reach this path.

**A resume against an escalation whose resolution is already consumed attaches instead of refusing, when nothing is still live to attach to (#674, O1).** `resolveEscalation`'s single-consumption guarantee (below, "Escalation, resolution, and `--cancel`") means a SECOND `--resume` naming the identical escalation id normally throws `ReplayedResolutionError` — but the run that consumed the FIRST resolution can itself end (an OS-level crash before it writes anything further, or a later pause whose reason/detail/round/head is textually identical to the original and so collides back onto the SAME natural key under `sameEscalationInstance`, `control-store/local.ts`) before the task's review ever actually concluded — this machine's own `pause-state.json` then never advances past the escalation `--resume` already consumed, and every later `--resume` attempt exits at once naming a replay, with no way to continue the task except a fresh attach. `--resume` now catches exactly `ReplayedResolutionError` for the `'resume'` decision and, before refusing, checks two facts: whether a driver still holds the task's own lock (`readDriverLock`/`isDriverPidAlive`), and whether the task's own review has CONCLUDED (`fetchLoopHistory`, the summary comment on the forge plus the review gate's verdict on the pull request's current state — never a log event). A live driver still refuses exactly as before, in the storage layer's own words — the single-consumption guarantee is never weakened for that case. A review that is GENUINELY CONCLUDED (`isConcludedJournal` — "Concluded means the summary AND a gate that has not failed on the current state," above) is refused too, but named for what it is: `loop already concluded at round <n> (summary posted <url>)` — and, when the gate could not be evaluated at all, saying so in the same line rather than implying the gate was asked and passed. That replaces the consumed-resolution wording, which describes a storage mechanism the reader never asked about and hid the real reason the loop would not continue. A summary posted against a genuinely red gate — a newer ruling, a superseded brief, a moved head — is NOT concluded and no longer refuses at all. Otherwise this run continues from the pull request's CURRENT state: it leaves `resumeFrom` unset entirely and falls into the SAME `existingPr` attach path a fresh `--task <n>` takes onto an already-open PR (round 1 entry, above) — reconciling the developer's prior launch, seeding round history from the pull request's own principal-authored markers, and recovering any held REQUEST-CHANGES round from disk — never re-consuming or fabricating a second resolution for the escalation `--resume` already resolved once.

**Every prompt a RESUMED developer session receives names the task, branch, worktree, and head (task-run-v1 task 21, `#541`, O11).** `dispatchDeveloper` prepends a small context block — `Resuming task Issue #<n>.` / `Branch: `<branch>`` / `Worktree: `<path>`` / `Remote head: <sha>` — to every prompt sent when `devResumeId` is already set (every dispatch after round 1's own genuinely fresh one, whether that resume happens later in the SAME process or after a relaunch): the push-and-open prompt, the open-the-PR prompt, the conflict prompt, the gate-red retry (which also now names the exact `git push` command rather than a bare "fix and push"), the round-findings/ruling prompt, and the confidence re-ask. Origin (task #538): a loop resumed the developer to open its pull request without naming the branch, and with forty stale worktrees present on the machine the session asked "which branch?" and ended its turn — a resumed session on a shared machine has no other way to know which of many worktrees this run means.

**v1 accepted loss:** resume re-enters with a fresh `LoopState` at the held round number — the round number itself governs the confidence rule's round ≥ 2 branching correctly, but (task 21, O9, above — deliberately NOT applied on `--resume`, see the double-count hazard noted there) the round history is not reconstructed on resume, so neither is the fingerprint/finding-identity memory (`lastIds`) a full crash-recoverable journal would carry across the pause boundary — the forge markers the history is now rebuilt from carry no per-finding-id state to recover it from in any case. A stall trigger that depends on cross-round finding identity (`reappearance`) resets at a resume. No infrastructure exists yet to serialize `LoopState`'s `Map`-typed fields across a process restart; building it is out of this task's boundary.

## The driver never ends on a pause (issue-711, O4)

Everything above describes `devReviewLoop` itself: one round-loop pass that returns the moment it decides `publish` or `pause`, unchanged by this task. `runDriverLoop` (`dev-review-loop.ts`) wraps it: `runTask` (`task-run.ts`) — `vinaya task run`'s own lib composition — calls this instead of `devReviewLoop` directly, so ONE `task run` process rides out however many pause/resume cycles a task takes, never handing back to an operator's own `--resume` for the ordinary case. This is `task run` only — "the normal entry" ("The command," above); `vinaya dev-review-loop` (`--task`, `--resume`, `--cancel` alike) stays exactly what it always was, "`task run`'s own debug/direct entry," a one-shot call straight into `devReviewLoop`/`cancelDevReviewLoop`, never itself a watcher. A `dev-review-loop --task <n>` invocation that pauses still returns and exits `1` immediately, precisely as before this task — the same debug tool a test, or an operator driving the loop by hand off a bare Issue number, already relies on.

The moment `devReviewLoop` returns a `pause` against an already-open pull request (`prNumber > 0` — the one exception, the pre-first-push escalation, below), `runDriverLoop` posts nothing new itself (the pause comment is already posted, by `devReviewLoop`) and starts polling three forge facts, on an env-overridable interval (`VINAYA_DEV_REVIEW_LOOP_WATCH_POLL_MS`, default 30s):

- **The pull request's own state** (`fetchPrState`, `gate-reading.ts`'s `gh pr view --json state`) — `MERGED` or `CLOSED` ends the driver at once, `finalDecision: {type: 'ended', reason: 'merged' | 'closed'}`, never a pause and never a resume attempt.
- **Whether this pause's own escalation has been resolved `'cancel'`** by a SEPARATE `--resume`/`--cancel`/`task_cancel` invocation (`readResolutionRecord`, keyed by the pause's own `escalationId`) — ends the driver the same way, `reason: 'cancelled'`.
- **Whether a Principal ruling newer than the pause has appeared** (`fetchNewestRulingOrdinal`, compared against the ordinal this watch captured the moment it started watching — "newer than the pause" is O4's own wording, never "any ruling ever posted," which could be one an earlier pause on this SAME task already consumed).

The moment a ruling is newer, `runDriverLoop` calls `devReviewLoop` again with EXACTLY the `{resumePr, agent, model}` shape a human's own `--resume <pr>` builds — the SAME function, the SAME authentication (`resolveEscalation`, single-consumption, "Escalation, resolution, and `--cancel`," below), never a second, parallel continuation path. `'infrastructure'`/`'stale_driver'` pauses need no ruling at all — they take the SAME bare-resume allowance a human's own `--resume` already gets for them (above), after one bounded wait (`VINAYA_DEV_REVIEW_LOOP_WATCH_INFRA_BACKOFF_MS`, default 60s) rather than watching for a ruling; a bare retry that itself fails (the bare-resume budget, `MAX_INFRASTRUCTURE_RETRIES`, already exhausted by earlier pauses) falls back to watching for a real ruling from that point on, rather than re-attempting the same failing bare call on every poll tick forever.

**The one-driver-per-task lock is held for the watching driver's ENTIRE life — never cleared between a pause and the resumed round.** "One driver per task," above, has the full mechanism (`LoopInput.retainDriverLock`'s own per-run token, the entry-gate's own pid-AND-token recognition, `acquireDriverLockAtomic`). A clear-then-reacquire gap around each resume attempt — this task's own first cut — briefly opened the task to a genuinely concurrent second `task run`/`dev-review-loop` during the watch (code review round 1, BLOCKER); holding the SAME lock unbroken, across every pause and every resume attempt this same pid makes, closes it — bound to a token, never the pid alone, so a crashed run's pid later reissued by the OS to an unrelated invocation is never mistaken for this driver's own continuity (code review round 2, MAJOR/security LOW). `runDriverLoop` clears the lock itself only once, at the one point `devReviewLoop`'s own `finally` never runs for: once the watch loop decides the task is genuinely over.

A resume attempt can itself fail — a benign race against an operator's own concurrent `--resume`/`--cancel` (`ReplayedResolutionError`), a transient forge read, or (in principle) a second driver that somehow still holds the lock. None of these crash this unattended watcher: the failure is reported to stderr and the SAME pause is watched again from scratch after one poll interval, never mistaken for this driver's own final decision.

A forge read this watcher makes WHILE polling (`fetchPrState`, `readResolutionRecord`, `fetchNewestRulingOrdinal`) can itself fail transiently — never crashes it either: caught and treated as "cannot tell yet," the SAME pause watched again after the next poll interval, exactly like a failed resume attempt (above).

**The one pause this never watches: the pre-first-push escalation** (O9, above) — `prNumber <= 0`, no pull request exists yet to poll or comment on. `runDriverLoop` returns it exactly as `devReviewLoop` decided it, unwatched; it is still resumed by hand with the `vinaya task run` command its own Issue comment prints — `<tranche> <n>` or `--issue <n>` according to its branch (O9's own paragraph, above) — or through the Operator's `task_resume` ("The Operator's continuation and cancellation", below). `commands/task-run.ts`'s own exit-`1` summary line still prints a `dev-review-loop --resume` command with this pause's absent pull-request number in it, and `packages/sources/src/commands.ts`'s `task run` help text still describes that line as naming `vinaya task run <tranche> <n>` — two separate, still-unfixed defects in printed text, neither in the pause record those readers consult.

**Exit codes.** `vinaya task run` (unchanged: `0` publish) now also exits `0` on `'ended'` — a watched pause that reached a genuine end is a normal, successful end to this process, never printed or exited as a `pause`. Exit `1` is reached only by the one un-watchable pause above; every OTHER pause reason a fresh `task run` can hit is watched through, by construction, so `1` stops meaning "an operator must now run a command" for the ordinary case — it means "there is no pull request yet to watch." `vinaya dev-review-loop`'s own exit codes are unchanged by this task (unconditionally: `0` publish, `1` pause, whichever reason).

`packages/sources/src/commands.ts`'s own `task run` catalog entry carries this same story for `vinaya --help`.

## Escalation, resolution, and `--cancel` (`control-store-v1` task 6, Issue #556)

Every pause now writes a durable `escalation` record to the control store — in `apps/cli/src/lib/dev-review-loop/pause-resume.ts`'s `writeEscalationRecord` — alongside the pre-existing `pause-state.json`/PR-comment pair, not in place of them: run identity (`runId`/`pid`/`host`), the round/head/branch/PR this pause belongs to, the input versions it was judged against (`briefHash`/`objectivesVersion`/`rulingOrdinal`/`policyDigest` — the round's own dispatched manifest when one exists, a fresh best-effort read of the same four facts otherwise, never a reason the pause itself fails), the reason and its `detail`, `evidence` (the last round's review context, when any was gathered), and `attemptedRecovery`/`recipient` from the fixed `PAUSE_REASON_PROFILE` table (moved here from `task-tools/read.ts`'s own copy, which now imports it rather than duplicating it). The record is keyed by `escalationId` — `escalationIdFor(task, round, head)`, `<task>-<round>-<head>` — the SAME round+head granularity `postPauseComment`'s own idempotency key already uses to tell two real pauses apart. A rerun of the IDENTICAL pause instance overwrites in place at that natural key; a GENUINELY DIFFERENT escalation colliding on it — a self-resumed round (`objectives_changed`/`ruling_posted`/`stale_driver`/`brief_superseded`/`policy_changed`, none of which dispatch a developer or guarantee a new head) hitting a second, different pause condition before the head ever moves — never overwrites the earlier one: `writeEscalation` (`local.ts`) claims the next free `-<n>` suffix instead, the same exclusive-create discipline a transition's own seq slot uses. The real id actually written is persisted back onto `PauseState.escalationId` (written BEFORE `pause-state.json`, so the id is always known in time), and every later reader — `resolveEscalation`, `task-tools/read.ts`'s `readEscalationPacket` — follows `PauseState.escalationId` when present, falling back to the natural key only for a `PauseState` written before this field existed. This is O1: an escalation read back from the control store carries everything a human decision needs with no chat history, and a colliding second pause never silently erases the first.

**A resolution — the human decision — is consumed at MOST ONCE per escalation (O2).** `resolveEscalation` (`pause-resume.ts`) is the single entry point both `--resume` and `--cancel` call: it reads the escalation record for the `escalationId` the caller names, refuses (`StaleEscalationError`) if none was ever written or it fails to parse, refuses (`WrongTargetResolutionError`) if the escalation's own recorded PR does not match the PR the caller is resolving against, then claims the resolution EXCLUSIVELY (`consumeResolutionOnce`, `packages/aeg-core/src/control-store/local.ts`) — the same `linkSync`-publishes-atomically discipline an ownership epoch claim uses, so a SECOND attempt at the identical `escalationId` collides on the same final name and comes back `'already-consumed'` rather than silently overwriting what is there. A second attempt — whether a genuine replay of the same decision, or a DIFFERENT decision (a cancel after an earlier resume) racing the first — is refused (`ReplayedResolutionError`). Single consumption is therefore a STORAGE guarantee, never an application-level check a caller could forget. On success, `resolveEscalation` appends a `TransitionRecord` (`paused` → `resumed`/`cancelled`) under the SAME epoch the resolution was just claimed under — the second of the two records and the second of the two transitions Issue #556's own Sizing note names (the escalation write and its own `running` → `paused` transition, at pause time, are the first of each).

Authentication reuses the EXISTING principal-authored-ruling-comment mechanism (`fetchRulings`/`principalAllowlist()`/`isPrincipal`) rather than inventing a new authority model — the "narrow injected authorization contract" the brief's Traps to avoid names: `--resume`/`--cancel` are LoopDeps-injected (`fetchNewestRulingAuthor`, alongside the pre-existing `fetchNewestRulingOrdinal`), defaulting to the real forge read in production and a fake in tests, never a stub that could leak production authority. The Operator does not author a ruling — a `resolution`'s `authenticatedBy`/`authenticatedFrom` name the principal-authored comment's author and marker (`<pr>-<k>`), never the caller invoking `--resume`/`--cancel` itself; which of the two ACTIONS to take is the operator's own command choice (`--resume` vs `--cancel`), never derived from the ruling comment's prose — presenting the decision (the pause comment, the ruling) stays separate from authenticating it (the principal-authored marker) and from choosing it (which command runs). An `'infrastructure'`/`'stale_driver'` resume — the driver's own recoverable hiccup, no ruling required (above) — still goes through `resolveEscalation`, authenticated as `'driver-self'`: still consumed at most once, so a duplicate bare `--resume` against the same held hiccup is refused too.

**`vinaya dev-review-loop --cancel <pr> --agent <vendor>`** (O3) is `--resume`'s mirror, never a `LoopInput` variant of `devReviewLoop` — a cancelled run has nothing left to continue, so `cancelDevReviewLoop` never re-enters the round loop. It resolves the task from the PR body, reads the held pause, authenticates via a principal-authored ruling exactly as `--resume` does, and calls `resolveEscalation` with `decision: 'cancel'` — refusing the same three ways (`wrong-target`/`stale`/`replayed`) resume does, so a paused escalation can be resumed XOR cancelled, never both, and never either one twice. Before any of that, it peeks the escalation record's own `agent` field (persisted at pause time — `EscalationFacts.agent`, `writeEscalationRecord`) and refuses if it does not match the operator-typed `--agent` here (code review, round 2, MAJOR: the flag used to decide termination with nothing persisted to check it against) — an escalation record written before this field existed carries no `agent` and falls back to trusting the flag, same as before this fix. On success it requests termination of whichever role is genuinely in flight through `control-store-v1` task 3's own identity-checked shutdown path (`terminateLaunchedChildOnShutdown`, `dispatch.ts` — the SAME `developer`/`code-reviewer`/`security` loop `LoopDeps.terminateInFlightLaunchesOnShutdown`'s default already runs on `SIGTERM`/`SIGINT`, factored out as `defaultTerminateInFlightLaunchesOnShutdown` so both callers share one role list — a safe no-op when nothing is in flight), passing the escalation's own persisted `agent` rather than the flag whenever the two were checked equal, then fences any effect record for the task still `'started'` — an in-flight forge post that was never confirmed — to `'uncertain'` (`fenceStartedEffectsAsUncertain`, `listStartedEffectKeys`/`markEffectUncertain` in `local.ts`) under the SAME epoch the resolution was just consumed under. Because that epoch is now current, a late-arriving result still trying to complete its write against the OLD, now-superseded epoch is refused by `StaleEpochWriteError` the instant it tries — a late result is fenced by the epoch mismatch itself, not by a race against this function. This is O3: cancellation is durable (a control-store record and transition, not a side effect that vanishes on process exit), idempotent (the SAME single-consumption guarantee O2 gives resume), and leaves nothing genuinely in flight either running or silently landing after the fact.

**A replayed resolution never bumps the epoch it was already consumed under (code review, round 2, HIGH).** `resolveEscalation` checks the durable resolution record BEFORE ever calling `acquireOwnership` — an ordinary replay of an ALREADY-consumed decision is refused (`ReplayedResolutionError`) without moving the task's shared epoch at all. What remains, and what fencing below still has to survive, is the narrower case of two genuinely concurrent FIRST attempts racing past that check before either has written a resolution: a losing one can still advance the task's shared epoch, even though it is refused moments later at `consumeResolutionOnce`. A genuinely winning call that already committed to fencing under the epoch it was handed would otherwise see its own `markEffectUncertain` throw `StaleEpochWriteError` uncaught, aborting before every started effect is fenced and before the outbox flush ever runs. `fenceStartedEffectsAsUncertain` (`pause-resume.ts`) is written to survive exactly this: on `StaleEpochWriteError` it re-acquires a fresh epoch (safe and correct, since its own cancellation intent is already durably consumed before this ever runs) and continues fencing whatever remains `'started'` under the new epoch, bounded by a small retry cap that fails loudly only on a pathological repeated race.

### Resumed/cancelled are now logged too (`task-log-v1` task 6, O2)

Everything above this point — the escalation record, the resolution record, the two transitions — is the control store's own durable state; none of it used to reach the Vinaya Log. `devReviewLoop` now logs a `dev_review_loop` `resumed` event the moment `resolveEscalation(..., 'resume', ...)` succeeds, before the round loop ever re-enters — `by: 'driver'` for a bare `'infrastructure'` recoverable-hiccup resume (`resolveEscalation`'s own `authenticatedBy: 'driver-self'` path), `by: 'principal'` for every other, ruling-authenticated resume. `cancelDevReviewLoop` logs a new `cancelled` event (always `by: 'principal'` — a cancel always requires a posted ruling) right before returning; it mints a fresh `loop_id` for the event, the same "one loop_id per process" convention every other pause/crash event already follows, since a `--cancel` invocation is its own process with no `LoopConfig.loop_id` to inherit from the run it is cancelling. Both were previously invisible to the Vinaya Log — a Principal's resume/cancel decision existed only as a control-store transition and a PR comment, never as a line a reader of the task's own outbox could find. See `apps/cli/specs/log.md`'s `dev_review_loop` family entry for the schema.

**One correlated history across kinds, within one process.** `devReviewLoop` sets `VINAYA_RUN` to its own run's `loop_id` before logging anything — every `dev_review_loop` event this process emits, AND every `effect`/`operation` event a downstream call into `effects.ts`/`broker.ts` fires in the SAME process (a pause post, an escalation write), share one `meta.lineage.run` (`apps/cli/specs/log.md`, "Attribution"). A pause's own `paused` event and the `effect` `attempted`/`observed`/`verified` sequence its own pause-comment post fires are therefore provably one story, not two independently-correlated streams — this task's own title made literal.

## The control store (`control-store-v1` task 1, Issue #551) — built; the manifest record now adopted (`#555`)

The "Formerly deferred, now landed" paragraph above named the gap: base identity and a durable policy history waited on a real durable store, because every side file this driver reads and writes today — `driver.pid.json`, `pause-state.json`, the `effect-<key>.json` idempotency records (`apps/cli/src/lib/dev-review-loop/pause-resume.ts`, `publication.ts`) — is unchecked JSON with a plain overwrite, and the one-driver-per-task guard is check-then-write pid liveness (above, "One driver per task"), never a fenced ownership token. `packages/aeg-core/src/control-store/` is that store, landed as a standalone library: four versioned record kinds (run, input, ownership, transition — `records.ts`), a strict parser that refuses an unknown version or torn content as **corrupt**, never as **absent** (the exact defect class every side file above shares, each wrapping `JSON.parse` in `catch { return null }`), one local storage implementation (`local.ts`) with atomic durable writes and an ownership epoch fenced at publish time: an ordinary overwrite writes its full content to a private temp file, `fsync`s it, then `rename`s it into place; an exclusive claim (an ownership epoch, a transition sequence slot) does the same `fsync`ed temp-file write, then publishes with a single `linkSync` — never `O_CREAT|O_EXCL` directly on the final `epoch-<n>.json` name, which would create that name before its content exists and let a second, genuinely concurrent claimant observe it mid-write. Two callers racing from the same observed epoch contend for the identical final name at that one `linkSync`, and the loser's later write is refused inside the store itself, not left to a caller to remember to check — and a one-time migration (`migration.ts`) from the legacy side files above, which refuses rather than guesses whenever ownership would be ambiguous (a legacy driver whose pid still answers a liveness probe, or a task that already holds a control-store epoch).

**Decision recorded here, per that task's own traps-to-avoid:** atomic files (temp file plus `rename` for an overwrite, temp file plus `link` for an exclusive claim) were chosen over a transactional database. This store's only real concurrency requirement is one exclusive owner per task, on one machine — a filesystem's own atomic-rename and atomic-link guarantees already meet it, and a database engine would be the "distributed coordination" the brief says not to introduce for a single-machine guard. PID liveness (`isDriverPidAlive`, above) is deliberately NOT this store's ownership model — it proves a process with that pid still runs, never that it still owns the task; the epoch fence replaces it with a content-verifiable fact instead.

**The manifest record is the first adopted piece (`#555`); the rest is not yet wired.** `control-store-v1` task 1 built and unit-tested the store and its migration path (`packages/aeg-core/src/control-store/*.test.ts`). Task 5 adds a fifth record kind — the `manifest` snapshot (`records.ts`, `writeManifest`/`readManifest` in `local.ts`) — and wires the driver to persist it per round (`dev-review-loop/reviewer-dispatch.ts`'s `persistManifestRecord`, called from `dev-review-loop.ts` before reviewers dispatch); that is the manifest half of "somewhere durable to live" the deferral named. What is still NOT wired: `dev-review-loop.ts` and `pause-resume.ts` continue to read and write the `driver.pid.json`/`pause-state.json`/`effect-<key>.json` side files, unchanged. Cutting the driver's own ownership over — replacing the pid-lock guard with an acquired epoch, and the pause-state/effect-record side files with control-store writes — is later adoption work, not this task's; that is why the manifest write above is deliberately not epoch-fenced.

**Partial adoption (`control-store-v1` task 2, Issue #552): the `effect-<key>.json` idempotency half only.** `apps/cli/src/lib/effects.ts`'s `EffectExecutor` replaced the `effect-<key>.json` local-flag half of the paragraph above with a new control-store `effect` record kind — for the two writers named there, `pause-resume.ts`'s `postIssuePauseComment`/`postPauseComment` and `publication.ts`'s `publishRound`, which now persist an effect's identity through the store before ever posting, and reconcile against the forge before retrying a `'started'`-but-unconfirmed one, rather than trusting a local `'posted'` flag alone. `driver.pid.json` and `pause-state.json` are untouched — the one-driver-per-task guard is still check-then-write pid liveness, and a pause's own durable state is still the legacy side file — and `dev-review-loop.ts`'s own three other `postForgeEffectOnce` call sites (`unpushed-work-resume`, `developer-round-comment`, `report-uncitable`) are untouched too. The epoch this executor fences each write against is acquired fresh per call, not the driver-wide acquired epoch the "Cutting the driver over" paragraph above describes — that broader cutover remains later adoption work.

### Durable launch identity and recovery (`control-store-v1` task 3, Issue #553)

Task 3 gives role launches durable identities and truthful outcomes, WITHOUT yet cutting the driver over to the control store's ownership epochs (that remains the deferred adoption above). Three pieces:

- **Launch intent persisted before spawn, session bound as soon as observable (O1).** `dispatchRole` (`apps/cli/src/lib/dispatch.ts`) writes a durable **launch record** — run id, a per-scope attempt counter, role, the child pid, and the vendor session id — to the same machine-local session record the resume record already used — now `<runtimeDir>/tasks-execution/<scope>/sessions/<role>-<agent>.json`, one folder per task rather than one flat directory per repository — BEFORE it spawns; it stamps the child pid the instant `spawn` returns, binds the session id the moment the stream first reports it (not only at a clean exit), and marks the record `interrupted` — never deletes it — on a timeout, crash, or refusal. So an attempt the driver's own death interrupts mid-turn keeps its session for recovery instead of losing it (the "failed attempts can lose session identity" defect, closed). This launch record is deliberately the launcher's OWN machine-local file, not a control-store ownership record: the generic launcher claims no task epoch (adoption deferred, above), and no strict versioned schema — the log's `DispatchOutcomeSchema`, or `control-store-v1`'s own records — carries a `role`/`attempt`/vendor-`sessionId` field. `readResumeRecord` is now a bound-session view over this record; `readLaunchRecord` exposes its full lifecycle with the same corrupt-vs-absent read `control-store-v1`'s `ParsedRecord` established.

- **A parent-validated outcome vocabulary (O2).** `normalizeOutcome` (`packages/aeg-core/src/control-store/outcomes.ts`) classifies a launch into `completed`, `incomplete`, `infrastructure-failed`, `timed-out`, `cancelled`, or `capability-refused`. The `completed`/`incomplete` split is decided entirely by whether the required artifacts exist and the declared postconditions hold — exit code is carried as input only, never the decider, so a process that exits 0 having produced nothing reads `incomplete`, never `completed`. Manner-of-death signals take precedence over the artifact read, so a killed or refused attempt is never blamed on the task. Built and unit-tested here; recovery below is its first consumer, with wider driver adoption deferred alongside the control-store cutover.

- **Recovery reconciles a prior launch before continuing (O3).** `reconcileLaunch` (pure) and `recoverDeveloperLaunch` (its disk-and-pid-reading wrapper) in `dev-review-loop/developer-dispatch.ts` turn a prior launch into one disposition: `live` (its child still runs on this host — never spawn a second worker onto the same task), `finished`, `resume` (continuity required and the exact session available — resume THAT session), `pause` (continuity required but the session gone — pause explicitly), or `none`. The developer's continuity is required; a reviewer's is never (a reviewer is always dispatched fresh, never resumed because the developer resumes — Traps to avoid), so no reviewer path calls this. The driver's round-1 attach and `afterDeveloperTurnBeforePrPoll` resume seams call `reconcileDeveloperResume`, which acts on that disposition — throwing `LaunchContinuityLost` for `live`/`pause` (the loop's outer handler turns it into the decided `pause{reason:'infrastructure'}` every thrown driver-path failure already becomes, so no new pause plumbing or `PauseReason` is added) and setting the exact session for `resume`. `none` — the common case, the only one every existing fixture reaches with its scratch `$HOME` — falls back to the unchanged durable resume-record read.

**A launch that never spawned starts fresh, it never blocks the task.** A refusal raised BEFORE any vendor process existed — an authentication refusal, a sandbox/boundary start-up refusal, a hook-setup refusal, a `spawn` that threw — writes a launch record with no bound session, because nothing ever ran to bind one. Recovery used to read that as the continuity-lost case and pause ("… before its vendor session was ever bound … would lose worker continuity"), so a task whose developer could not sign in was blocked behind a continuity rule with no continuity to protect: every later run and `--resume` re-read the same record and paused again. `reconcileLaunch` now answers a sixth disposition, `fresh`, for exactly that shape, and the resume seam dispatches a fresh developer session (narrating `launch_never_spawned` in the driver's own role log, never a pause). The distinction is `launchNeverSpawned`, decided from the record's own lifecycle facts and never from which `DispatchFailureReason` it carries — no child pid was ever stamped (the pid is written the instant `spawn` returns) AND the dispatcher itself reached a terminal `interrupted` record with a reason — so a pre-spawn reason added later needs no new case here. Everything else is unchanged: a launch that DID spawn and lost its session still pauses, because a bound session may carry turn state a fresh one loses; and a record left non-terminal (`launched`) with no pid — a dispatcher killed in the window between `spawn` returning and the pid being stamped — is read as possibly-spawned and still pauses.

### The loop's own recovery record (`control-store-v1` task 4, Issue #554)

Task 4 gives the round loop itself — phase, round, budgets, held results and delivered-findings identity — a sixth control-store record kind, `loop_state` (`records.ts`'s `LoopStateRecordSchema`, `local.ts`'s `writeLoopState`/`readLoopState`), one per task, overwritten in place on every transition. Deliberately NOT epoch-fenced, the same precedent the manifest record set (task 5, above): the driver's own cutover to acquired-epoch ownership over its mutable state remains separate, later adoption work, unchanged by this task — this record's real concurrency guard is still the pid-lock one-driver-per-task check the driver already runs before touching anything.

**What it carries.** `round`, a `phase` string mirroring `Decision['type']`, a `pauseReason` set only while paused, `budgets` (`mechanicalRetries` — the gate-red/conflict-retry stall count, `MAX_GATE_STALLED_TURNS`-bounded; `reviewRounds` — the round number itself, `ReviewPolicy.maxRounds`-bounded; `infrastructureRetries` — this task's cumulative `'infrastructure'`/`'stale_driver'` pause count, `MAX_INFRASTRUCTURE_RETRIES`-bounded, never reset by a restart), a `heldResult` round+head identity (the round whose verdict currently sits held on disk, awaiting delivery or publish), and a `deliveredFindings` round+head identity (the pair whose findings have already been delivered to the developer once). `dev-review-loop/round-assess.ts`'s `persistLoopState`/`loadLoopState` are the low-level write/read wrappers; `pause-resume.ts`'s `recoverLoopState` is the read every entry point actually calls.

**Written on every transition, not only at pause.** `dev-review-loop.ts` calls `persistCurrentLoopState` (a closure over the round loop's own live variables) at every genuine gate observation, every mechanical-retry increment (the instant `gateStalledStreak` increments, before it is ever known whether the bound is reached), every `dispatch_reviewers`/verdict outcome, every publish, and — via one shared call site — every pause, whichever branch decided it. A process that dies mid-episode (a kill, a crash) leaves this record at whatever it last wrote, not at whatever the last completed PAUSE happened to be.

**Read on start, attach, and resume alike.** `devReviewLoop` reads `recoverLoopState(task)` once, early — before the attach/fresh-dispatch branch even runs — and seeds `gateStalledStreak`/`heldResultIdentity`/`deliveredFindingsIdentity` from it (`0`/`null` when the record is `'absent'`, exactly the prior behavior for a task that has never persisted one). `infrastructureRetries` seeds the same `0` for `'absent'`, but `MAX_INFRASTRUCTURE_RETRIES` — never `0` — for `'corrupt'` (round 2 review, security HIGH): the outer `catch` that turns a thrown refusal into a decided pause persists whatever this variable holds at that moment, so seeding a corrupt record's replacement at `0` would silently WRITE BACK a healed, zeroed budget over the very record just refused as untrustworthy. `round` itself is taken as `Math.max` against the recovered value, applied AFTER every existing recovery mechanism (the ruling ordinal on `--resume`, the locally-held request-changes file, the forge-marker fallback) — never regressing any of them, only ever advancing past a task whose held files AND forge markers are BOTH unavailable. This is what lets recovery stop depending on that forge history alone: the journal (`fetchLoopHistory`/`reconstructRounds`) is now rebuilt from the pull request's own principal-authored markers rather than the loop's flushed log events ([task-files-v1] 4, Issue #651), and remains a projection still used to seed `state.rounds` for the published summary table on attach — but the control-store `round` is no longer the only thing standing between a lost local marker and a silent reset to round 1.

**The phase is recorded at takeover, before anything is dispatched (issue #812).** `persistCurrentLoopState` above is written only when the phase CHANGES, so a run that paused left `loop_state` reading `phase: 'pause'` — and a driver that later took the task over (a fresh start, a re-attach, or a `--resume`) wrote nothing of its own until its OWN first transition, which on a fresh developing turn can be an hour away. For that whole window `task status`/`task_status`, which read `loop_state.phase` for the "phase" column (`readLoopPhase`, `task-status.ts`), reported the live, coding run as `paused` (observed three times on 2026-09-27, on two task PRs after a resume and on a new adopter after a fresh start over a killed run). `devReviewLoop` now calls `persistCurrentLoopState('dispatch_developer')` once, right after `reviewPolicy()`/`repoRoot()`/`baseHeadAtStart` setup and BEFORE the resume/attach/fresh-dispatch branch — so ahead of every dispatch site (the fresh round-1 dispatch, the branch-exists resume, the attach redelivery, the whole `runRoundLoop`), on every entry point `runDriverLoop` funnels through (its first call and every `watchPauseThenResume` resume alike). The recovered `round` is preserved (`Math.max` against `recoverLoopState`, the same non-regressing seed applied again after the held-verdict/forge-marker recovery below), so this supersedes only the stale phase, never the round the earlier run reached. The older `pause-state.json` is left untouched — kept as history for the escalation read and the sweep — and needs no clearing: while this driver's lock is alive `deriveLoopState` already reads `running` over it (never `paused`), and this write is what stops the phase column from still saying `paused` underneath that `running` state. Every genuine transition overwrites this record in place, so a takeover that immediately goes to reviewers or publish records that within its own first phase change.

**A recovered mechanical-retry count survives exactly one reset.** The existing "reset `gateStalledStreak` to 0 on every genuine gate observation" rule (unchanged in spirit) would otherwise immediately clobber a seeded, non-zero value on the very first gate check a new process makes — indistinguishable in memory from a truly fresh situation. A one-shot flag (`mechanicalRetryRecoverySurvivesOneReset`, set only when the recovered value is non-zero) lets that first reset pass through unchanged instead; every later genuine observation resets exactly as before. A task with nothing recovered (seed `0`) never sets the flag at all — resetting `0` to `0` changes nothing, so a genuinely fresh task's behavior is untouched.

**Duplicate delivery is refused by the control store too, not only the local marker file.** The existing `round-<k>-attach-redelivered` marker file (task-run-v1 task 3, above) is unchanged — still written, still checked first. `deliveredFindingsIdentity`, recovered from the SAME control-store record, is checked alongside it: a match on `(round, head)` reads as already-delivered even when the local marker itself is missing (a different machine, an outbox that was cleaned) — the two are written together at the moment of delivery, so they never actually disagree in normal operation, but only one of them needs to survive for the duplicate to still be refused.

**The infrastructure-retry bound gates `--resume`'s own bare-command allowance.** O5's `'infrastructure'` pause has always resumed on the bare `vinaya dev-review-loop --resume <pr>` command, no Principal ruling required (a recoverable hiccup, never a human decision point). That allowance is now itself bounded: `--resume` reads the task's `infrastructureRetries` count before deciding, and once it reaches `MAX_INFRASTRUCTURE_RETRIES`, a ruling is required even for `'infrastructure'` — the same refusal a genuine decision-point reason already gives, its own message naming the count and the bound. A control-store read that comes back `'corrupt'` at this check is treated as "budget unknown, be conservative," never as `0` — a store read failure can never itself grant an unbounded bare-command resume.

**The bound is floored against the pause-state file too, not the control store alone (round 2 review, security HIGH).** `persistLoopState` is best-effort, like every other control-store write on this path (`persistManifestRecord`'s own precedent) — it never throws, so a persistent write failure for this one task (an unwritable control-store directory, a hand-cleaned one) reads back as `'absent'`, which seeds `0`. `writePauseState`'s `pause-state.json` is a different write path — a plain `writeFileSync`, never the control store's effect-executor machinery — and now carries its own `infrastructureRetries` snapshot from the SAME pause, written by the SAME call site as the (possibly failed) control-store write. `--resume` takes `Math.max` of the control-store read and the pause-state file's own count, so a control-store write that has been silently failing for this task's whole life can no longer, by itself, reset the bound to `0` and grant an unbounded bare-command resume — the exact hole the security finding named.

**The in-process seed floors against the SAME pause-state field too, not only the resume gate (round 3 review, MAJOR).** The gate check above answers "may this `--resume` proceed at all"; a separate question is what THIS resumed process's own live `infrastructureRetries` variable starts at once it does. Before this fix that seed came from `recoverLoopState(task)` alone — the control-store read — so a resume the gate legitimately granted (its own floor against `resumeFrom.infrastructureRetries` already keeping it under the bound) could still reseed the process's live counter LOWER than the truth if the control store was `'absent'` or understated. That process then persists whatever it computes back into `pause-state.json` on its own next pause, overwriting the one independent record the gate depends on with a value lower than the truth — quietly reopening the same unbounded-resume hole from the inside on a LATER round, after the gate itself had already closed it. The in-process seed now takes `Math.max` against `resumeFrom?.infrastructureRetries ?? 0` too (`null` on a fresh, non-resume start, where this is a no-op), so a resumed process can only ever carry the count forward or up, never quietly back down.

**A corrupt record refuses to guess, never resets.** `recoverLoopState` returning `'corrupt'` is not read as `'absent'`: `devReviewLoop` throws immediately, reaching the same outer `catch` every other setup failure on this path already does, which turns it into a decided `pause{reason:'infrastructure'}` — a corrupt record can pause the loop, but it can never silently zero out real budgets or authorize a round the reader cannot actually verify (the objective's own "missing telemetry cannot reset budgets or authorize progression," read narrowly: an unreadable record is refused, not treated as a green light). The replacement record that refusal persists is itself seeded at `MAX_INFRASTRUCTURE_RETRIES`, not `0` — see above — so refusing a corrupt record can only ever push the next `--resume` toward requiring a ruling, never away from it. This refusal now also covers a real filesystem fault, not only torn JSON (round 3 review, BLOCKER): `readIfExists` (`packages/aeg-core/src/control-store/local.ts`) has always rethrown a non-`ENOENT` read error (a permissions failure, an unreadable special file, an EIO) raw rather than reporting it as absence, but nothing downstream used to catch that throw before it escaped every reader of every record kind — `recoverLoopState`'s own call, before `devReviewLoop`'s try block starts, most concretely. `readRecord`, the one chokepoint every direct `parse<X>Record(readIfExists(path))` read in `local.ts` now goes through, converts any such fault into the SAME `{status: 'corrupt', reason: ...}` `parseWith` already reports for a schema violation or torn write — never a second, uncaught path back to the exact failure class round 1's BLOCKER first named.

### A killed driver leaves no orphan (`driver-lifecycle-v1` task 1, Issue #605)

A `SIGKILL`ed driver (or one that dies before reaching its own shutdown path) used to leave its dispatched child running, reparented to init, with its launch record still reading `'launched'`: the next start's `reconcileLaunch` found that pid still alive on this host and read it as `live`, refusing to start a second worker — correctly, in intent, but permanently, since nothing ever ended the orphan or corrected the record.

- **The driver terminates every in-flight role's own child on `SIGTERM`/`SIGINT` (O1).** `devReviewLoop`'s existing signal handlers (`dev-review-loop.ts`, registered once `decision`/`loopLogPath` exist — see "The per-task driver log," above) now call `LoopDeps.terminateInFlightLaunchesOnShutdown` FIRST, before the `driver_exited` trace and `process.exit`. Its default implementation calls `terminateLaunchedChildOnShutdown` (`dispatch.ts`) for `'developer'`, `'code-reviewer'`, AND `'security'` — round 3 review, MAJOR/HIGH: the reviewers are dispatched through the SAME `dispatchRole`/`LaunchRecord` machinery, concurrently, via `Promise.all` (see "Reviewers," below), so a signal arriving mid-round is exactly as capable of orphaning a reviewer's child as the developer's; an earlier version wired only the developer role. A role's own record still reading `'launched'` (a dispatch genuinely in flight) has its child terminated — `SIGTERM`, a bounded grace period, then `SIGKILL` if still alive (`terminateChildWithGrace`, the same escalation the dispatch timeout path already applies to an overrun child) — and is patched to `'interrupted'` with `failureReason: 'signal'`. A role with nothing in flight (its record already `'completed'`/`'interrupted'`, or absent) is a safe no-op. Because each call runs synchronously, with no yield back to the event loop before `process.exit`, a killed child's own `exit` handler (registered inside the same `dispatchRole` call) never gets a chance to re-patch its record out from under this write.

- **Recovery tells a live child of a live driver apart from an abandoned one (O2).** `classifyChildLiveness` (`dev-review-loop/developer-dispatch.ts`) reads a pid still alive at `record.childPid` as `'live'` ONLY when it is also still parented to `record.dispatcherPid` and that dispatcher pid itself still answers a liveness probe; otherwise it is `'orphaned'` — abandoned by a driver that died without reaching O1's shutdown path (a `SIGKILL`, or any crash outside the signal handlers). `reconcileLaunch`'s own `live` check is now `classifyChildLiveness(...) === 'live'`; an `'orphaned'` child falls through to the SAME finished/resume/pause path a `null` childPid always took. `recoverDeveloperLaunch` reaps an `'orphaned'` child BEFORE computing the disposition, so it never survives to race whatever worker this reconciliation is about to hand continuity to — the duplicate-worker guard's contract is unchanged; only a genuinely abandoned child stops being misread as a reason to block forever. Code review, MAJOR: the reap call goes through `deps.terminateChild` — a field on `ReconcileLaunchDeps`, defaulting to `terminateChildWithGrace` (`dispatch.ts`) in `defaultReconcileLaunchDeps` — never a direct import call, so the O2 reap step itself has a test seam: a test can inject a spy there and assert the reap actually happened, with no real OS signal sent.

- **Process identity is verified before `'live'` is ever returned (O3).** `dispatchRole` snapshots the child's own start time and command (`getProcessSnapshot`, a `ps -p <pid> -o …` read — every supported platform ships `ps`, so no new dependency), storing them on the launch record as `childStartedAt`/`childCommand`. Code review, MAJOR: a single read taken the instant `spawn` returns is not enough — a vendor CLI installed through a typical npm shebang launcher (`#!/usr/bin/env node`) performs a SECOND, user-space exec (the kernel's own shebang-triggered exec lands on `env`; `env` itself then execs `node`) that can still be in flight at that instant, so the read can describe the launcher rather than the process that survives. `dispatchRole` instead calls `captureSettledChildSnapshot` (`dispatch.ts`, internal): it polls (bounded, `IDENTITY_SETTLE_BUDGET_MS`) until two consecutive reads agree on `command` — a pid's start time is fixed at fork and never moves across `execve`, so only `command` is unstable here — before the snapshot is bound to the record. `classifyChildLiveness` re-snapshots the SAME pid at reconciliation time (by then long settled) and refuses to call it a match — reading `'not-ours'`, never touching it — whenever a field the record DID capture disagrees with the live snapshot, INCLUDING when the live snapshot can no longer read that field back at all (round 3 security review, MEDIUM: a transient `ps` failure at reconciliation time is never itself proof of identity — the comparison fails closed, it is never silently skipped just because one side came back empty). A record written before this task carries `null` for both fields and is compared as before: nothing captured, nothing to fail closed on, so a genuinely live launch on a live host is still found by the ppid/liveness check alone.

  Round 4 security review, HIGH: this identity guard used to protect only the RECOVERY side — `terminateLaunchedChildOnShutdown` (the O1 shutdown path, above) sent `SIGTERM`/`SIGKILL` to `record.childPid` on no identity check at all, so a driver killed before it ever reached its own recovery step could act on a STALE on-disk record (left by an earlier process instance, itself `SIGKILL`ed before reaching this same path) and signal a pid the OS had since recycled for something unrelated. The check is now `matchesCapturedIdentity` (`dispatch.ts`), factored out of `classifyChildLiveness`'s own inline comparison so both callers — reaping an orphan on recovery, and signaling a child on shutdown — share the identical rule: a field the record captured must be read back and agree, or the pid is left untouched. `terminateLaunchedChildOnShutdown` re-snapshots `record.childPid` and checks it against `matchesCapturedIdentity` before ever calling `terminateChildWithGrace`; a mismatch (or no live process at all) skips the signal but still patches the record to `'interrupted'` — there is nothing of THIS launch's own left in flight either way.

`apps/cli/tests/lib/dispatch/reconcile-launch.test.ts` covers O2/O3 as pure `reconcileLaunch`/`classifyChildLiveness` fixtures (fake pid-liveness, hostname, and snapshot deps — no real process touched), plus a `recoverDeveloperLaunch` case (code review, MAJOR) that builds a REAL orphan via a subprocess and injects a `terminateChild` spy, asserting the spy — not a real signal — is what reaped it; `apps/cli/tests/lib/dispatch.test.ts`'s `terminateLaunchedChildOnShutdown` suite covers O1 against a real spawned child, from a dedicated script subprocess (never importing `dispatch.ts` into the test file's own process — see that file's module doc on `GLOBAL_VINAYA_HOME`), and a separate case (code review, MAJOR) proves `captureSettledChildSnapshot` records the SETTLED identity, not a shebang launcher's own, by spawning a fake vendor binary that deliberately execs a second time after a delay.

## A task-operator read interface over these same records (task-operator-v1 task 1)

`apps/cli/src/lib/task-tools/read.ts` reads the pause record, held verdicts and the control store's own verdict effect records this file documents — never through a second write path, never through `ps`. Two functions:

- `readTaskLoopStateObserved(root, task)` wraps `task-status.ts`'s own `deriveLoopState` in a timestamp and a `fresh`/`unknown` marker — `unknown` only for `no_driver` (no record of any kind exists yet); every other `TaskLoopState` kind is `deriveLoopState`'s current, fresh answer, since it already resolves a superseded pause into `published` internally.
- `readEscalationPacket(root, task)` reads `pause-state.json` directly — independent of `deriveLoopState` — so it can tell a pause that predates the run's own newest published round (`freshness: 'stale'`) apart from the live one (`'fresh'`) apart from no pause ever recorded (`null`). Its result carries the pause's own `reason`/`detail`/`inputs` (task, round, head, branch, PR number — all already on the pause record, this file's own "Pause and `--resume`" section above), the last round's held verdict lines as `evidence`, and a fixed per-reason `requestedAuthority`/`attemptedRecovery`/`permittedNextActions` — `self` for the five driver-decided reasons this file already names (`objectives_changed`, `ruling_posted`, `stale_driver`, `brief_superseded`, `policy_changed` — the loop resumes on its own), `operator` for the two environment-shaped ones (`infrastructure`, `no_push`), `principal` for the four O2-exit reasons that need real judgment (`escalation`, `max_rounds`, `no_progress`, `confidence`, `reappearance`). It also reads the durable `EscalationRecord` this pause wrote (`control-store-v1` task 6, `#556`, code review round 2, MEDIUM) and surfaces it as two further fields: `runIdentity` (`runId`/`pid`/`host`) and `inputVersions` (`briefHash`/`objectivesVersion`/`rulingOrdinal`/`policyDigest`) — both `null` when no such record exists for this pause (written before this adoption, or a best-effort escalation write that itself failed at pause time), the pause itself still fully reported either way.

**The published round is one reader, over the control store's own `verified` verdict effects (`unattended-run-v1` task 8, `#738`).** Both `deriveLoopState` (which reports `published`) and `readEscalationPacket` (which grades a pause `stale` once superseded) answer "which round published" through the SAME exported `task-status.ts` function, `newestPublishedRound(root, task)` — never a second private copy, and never a glob over effect file names. It reads through the control store's own `readEffect` (`@attalabs/aeg-core`), whose `effect/<key>.json` layout `publishRound`'s two `pr-comment` effects (`<round>-reviewer-verdict`, `<round>-security-verdict`) land under: a round is published only when BOTH read `status: 'verified'` — the status the executor advances a confirmed post to. A `started` effect is a post whose confirmation was interrupted, `uncertain` a recovery that could not reconcile; neither is published. Rounds are bounded above by the durable `loop_state` record's own `round` (written at every transition, `publish` included), so a run with no `loop_state` has published nothing. Before this task the reader globbed a flat `control/effect-<n>-reviewer-verdict.json` for `status: 'posted'` — records the control store had already moved into its `effect/` subdirectory at `verified`, so a run that published read as `no driver` (observed on the log-server task's own loop).

**A start that was accepted reads as `starting`, never as `no driver`.** `task_start` answers as soon as the process it launched is alive and keeps its claim, while the run's own driver lock appears only after `task run` has rendered and posted the frozen brief and run its start-of-run sweep — forge-bound steps that routinely take tens of seconds. A status read taken in that window found no lock and reported `no driver`, which reads as a start that never happened; the obvious thing to do about that is start the task again, which is how a second developer ends up on one branch. So the reader consults the start claim `task_start` already writes (one file per request identity, in the unscoped control folder) as its LAST resort:

- A claim still inside the start handler's own stale-claim window — or one past it whose launched process is still alive — reads `starting (start request <id>)`. That is the same reading the handler's own supersede path takes of the same record, through the same `claimIsStale` predicate rather than a second copy of its window, so `starting` and "supersedable" can never come to mean two different spans of time.
- A claim past that window whose launched process is gone, with no driver lock to show for it, reads `start did not come up (start request <id>, accepted <time>)`. The start is named, so the next reader knows which request to look at, instead of being shown the absence a never-started task would show.
- **Every other state is unchanged, and every one of them wins.** A start claim only says a start was accepted; each state above it is backed by a record of something that happened to a run. A live driver lock reads `running` whatever a claim says, a pause reads `paused`, a published round reads `published`, and a dead lock with a `driver_exited` trace reads `exited` — the claim decides only where there was otherwise nothing at all to read. It is read through a thunk for that reason: the claim directory is listed only on the path that can use it, so a running task pays nothing for this.
- **A claim is matched to a task the way the call that wrote it addressed one.** A standalone target carries the Issue number; a tranche target carries the ordinal it was started by. So the reader is handed the task's own address — which the status row already holds — rather than resolving an ordinal itself, which would put a forge call inside a reader whose whole contract is that it makes none.
- **A task whose brief is not frozen yet reads `starting` too**, rather than `not started`. Rendering and posting the frozen brief happens inside the same preparation the driver lock waits on, so a launch that has not reached that step yet would otherwise be reported as a task nobody had started.
- **The claim layout stays known in one place.** The start handler exports the reader over its own path builder and parser (`readStartClaims`); nothing else lists that directory or parses those files. A second, independent glob is exactly how a flat effect-record reader once drifted from the control store's own layout and reported a published run as `no driver`.

Both phrases reach an Operator unchanged through `task_status`: the catalog's status item carries `state` as a plain string, so neither state needed a schema change.

**A claim stops being evidence long before it is deleted.** Only a failed launch and the supersede path ever release a claim, so the file for a start that WORKED outlives its run — and a run whose driver came up, worked, and then ended leaving nothing behind (an uncaught error in the loop body clears the driver lock in its `finally` without writing a `driver_exited` trace; a sweep removes the task folder outright) would otherwise be described by that claim as a start that never came up, forever. That is the same false report `no driver` was, with the sign flipped, so four things bound what a claim may say:

- **A driver lock the claim PREDATES wins.** A lock written at or after the claim was accepted is this start's own driver, or a newer run's; either way the driver appeared, so the claim stops speaking and the answer stays `no driver`. A lock the claim POSTDATES belongs to an earlier run — the `SIGKILL`/OOM-kill/reboot case leaves one behind with no `driver_exited` trace to read — and says nothing about a start accepted after it, so the claim is consulted normally. That distinction is the whole difference between reading the window correctly and reporting `no driver` throughout it: `task run` clears and rewrites the lock only after its forge-bound brief render, so the old file is on disk for exactly the tens of seconds this state exists to describe. A timestamp neither side can parse takes the silent branch, since a comparison that cannot be made is not evidence for the louder reading.
- **A confirmed launch marks its own claim.** `confirmed` is the launch outcome that means the run's driver lock appeared and named a live pid; the handler records the moment on the claim, and the reader ignores a claim carrying it. What became of that run afterwards is the business of the records the run wrote.
- **A claim past `START_CLAIM_REPORTING_WINDOW_MS` says nothing.** The two readings above cover most of what a stale claim could lie about; what neither covers is a launch whose confirm wait ended with its process merely alive (no confirmation to mark), whose run then DID come up and later ended leaving no lock at all. From the claim alone that is indistinguishable from a launch that never came up, so past this bound the reader stops believing it. The cost runs the other way: a genuine failed start read more than that long afterwards falls back to `no driver` rather than naming its request. Both readings send the Operator to `task_start`, so what is lost is the request identity in the phrase, not a correct next step.
- **A claim with no age this clock can measure is past every bound.** Both windows above are a subtraction, and two records defeat it: a `startedAt` that does not parse, and one dated further ahead than the stale grace itself — which a backward host clock step leaves behind (a VM suspend and resume, an NTP step correction, a claim written while the clock was ahead). Read as fresh, such a record passed no bound ever: not stale, so never superseded; not past reporting, so never pruned and never silent. The task then read `starting` for the life of the checkout with nothing coming up behind it, and the doctrine's action for `starting` is to read again — a run that does not exist, with no action that would ever start one. So an unmeasurable age counts as past both bounds instead. The cost runs the other way, and it is the survivable direction: a genuine start in flight whose clock jumped reads `no driver`, and `task_start` starts it again.

**A recorded pid is checked for identity, not only for liveness.** `process.kill(pid, 0)` answers for whatever holds the number now, and pids are recycled; left at that, an unrelated process inheriting the number reads as the launch still coming up and no later read ever corrects it. So the child's own `ps` identity is captured beside its pid at the one moment it is certainly still that child, and re-read and compared through the dispatch layer's own `matchesCapturedIdentity` before the pid is trusted — the same guard already applied wherever a pid is treated as a launch's own child. A claim that captured no identity (written before the fields existed) has nothing to check and is trusted as before. The predicate is shared with the start handler's supersede path for the same reason the staleness window is: the doctrine's action for a start that did not come up is `task_start`, and that only starts something if this tool agrees the launch is gone. A pid of `0` or a negative one is rejected by the store's own parser, since both address a process GROUP in `process.kill` and would answer alive unconditionally.

**A claim's own strings never reach a renderer raw.** `requestId` and `startedAt` come off a file on disk and land in `renderTaskStatusTable`'s fixed-width rows and in the `task_status` state string — the exact string the Operator doctrine keys its single action off. Replacing only the non-printable characters is not enough there, because the printable range includes the punctuation the state phrases are built from: a `requestId` reading `abc) — running (pid 4242` would render `starting (start request abc) — running (pid 4242)` and name a state the machine is not in. So `requestId` is narrowed to the alphabet its real values use — a hex identity — and its length is bounded. `startedAt` is not narrowed but RE-RENDERED, out of the instant it names rather than the characters it carries: a string built from a parsed number can carry nothing to escape from, and — the reason this is not merely another way to be safe — narrowing silently changed the VALUE. `2026-09-27 12:00:00Z` is a time `Date.parse` accepts; the alphabet turned its space into `?`, and the result parsed to nothing. `deriveLoopState` compares that field against the driver lock, so for exactly that spelling the comparison could not be made, an old dead lock suppressed a live claim, and the read fell back to the `no driver` this state exists to remove. What a reader is shown and what the windows aged are now one instant, however the claim on disk spelled it.

**A request identity out of a claim's CONTENTS is treated as a path component, because it becomes one.** `release` hands it to the store's own path builder for `rmSync`, so the parser rejects any `requestId` that is not a bounded hex-shaped identity, and the path builder refuses one too rather than trusting its caller. A reader that parses every file in the folder is exactly what widens who can put a string there. `startedAt` is still accepted freely and handled at the display side above: an odd claim is still a claim, and refusing to read one would cost the accurate reading this state exists to give.

**A claim file is size-bounded before it is parsed, must be a regular file, and dead claims are deleted.** The reader skips any file past a generous per-claim ceiling rather than reading it into memory to fail. The size is taken with `lstatSync`, and anything that is not a plain file is skipped outright: `statSync` FOLLOWS a symlink and reports `0` for a FIFO or a character device, so the ceiling passed exactly the inputs that hurt — reading a FIFO blocks with no timeout, hanging the whole synchronous status read and with it `task_status`, and a link to `/dev/zero` allocates until the process dies. A file whose CONTENTS name a different identity than its NAME is skipped too. The identity in the body reaches a path — `release` and the prune both hand one to `rmSync` — so a body naming another claim would delete that claim's file, possibly a live, still-preparing one, and leave the file it was read from in place to do it again on the next pass. The writer only ever puts a record at its own identity's path, so nothing this store wrote is rejected, and it is what makes the path the prune rebuilds provably the file each record came from. And because only a failed launch and the supersede path ever release a claim, the folder would otherwise grow one file per distinct start request for the life of the checkout: the start handler prunes, before writing its own claim, every claim past the reporting window with no live launch behind it — strictly weaker than the supersede path's own test, so pruning one only saves the next reader a parse. A read never deletes.

**The child's identity is captured with the SETTLING read.** A vendor CLI installed behind a `#!/usr/bin/env node` shebang performs a second, user-space `execve`, so `comm` read too early captures `env` rather than the image that survives. A capture taken mid-exec-chain can never match a later re-read, which would make `claimLaunchIsAlive` call a live launch gone and let the supersede path start a second one — so the capture goes through `captureSettledChildSnapshot`, the same read `task-run-background.ts` already uses on this spawn-then-capture shape, while the later CHECK stays a plain single read.

**The claim folder is listed once per status read.** `readStartClaims` lists and parses the whole unscoped control folder, and that folder only grows; reading it per row made a listing of N tasks pay N full scans of it. One deps object is threaded through every row of the same read instead, memoizing the listing — and it is still reached through the thunk, so a read where no row falls through to a claim lists nothing at all.

**The resolver behind the prepared-run tools gates on the frozen brief, not on a state kind.** `resolveIssueForRef` — the resolution behind `task_escalation_read`, `task_resume` and `task_cancel` — used `state.kind !== 'not_started'` as its proxy for "this task has been prepared or has a run". Once a planned task with an accepted start reads `starting`, no state kind means that any more: a PREPARED task whose driver has not written its lock yet reads `starting` too, and it has a pause and an escalation to read like any other. So the status VIEW carries `briefFrozenIssues` — the fact the reader already knows — and the resolver reads that. It rides on the view rather than on each row because `commands/task-status.ts` serializes a row verbatim into the public `--json` envelope, so a new row field would be a change to that schema. Gating on the kinds instead would answer "no open task matches" for a task that is open, listed and readable, purely because a start was in flight.

### Where a run is: round, phase, time in phase, and the last confidence

`task_status` and `vinaya task status` answer more than "is it running": each row carries WHERE the run is, and every field is read from a record that either exists or explicitly does not — an absent fact reads `null` (a dash, in the table), never an estimate.

- **Round and phase** come from the loop's own `loop_state` record — the same record this file's "The loop's own recovery record" section describes, whose `phase` string mirrors `Decision['type']`. The shown phase maps one-to-one from the recorded one (`TASK_PHASE_LABELS`, `packages/aeg-core/src/task-phase-history.ts`):

  | recorded phase | shown as |
  | --- | --- |
  | `dispatch_developer` | `developing` |
  | `ask_confidence` | `awaiting confidence` |
  | `dispatch_reviewers` | `reviewing` |
  | `publish` | `publishing` |
  | `pause` | `paused` |

  A phase added to the driver after this mapping reads back verbatim rather than being folded into a neighbour. There is deliberately no separate `waiting for CI` phase: the driver polls the head's checks while the record still reads `dispatch_developer`, so `developing` spans the developer's own turn AND the gate wait that follows its push — splitting the two would mean inferring a phase from a second source rather than reading the loop's own record.

- **Time in phase** is measured from that record's own `recordedAt` (the driver writes it at every transition), never from a lock's start time or any other wall-clock stand-in. A record written ahead of the reading clock reports zero, never a negative age.

- **Whether that phase is where the run still is** (`phaseIsCurrent`). A live driver is in its phase, and a pause is a place a run sits in — it waits there for a person — but only when the two records AGREE: `pause-state.json` is never cleared on resume, so a task that paused, resumed and then died mid-round still derives `paused` off that stale record while `loop_state` names the round it reached and the phase it was working in. A pause whose own recorded phase is not `pause` is therefore treated like any other stopped run. Everything else is a phase nothing is in any more: a published run is finished (nothing is publishing), and `no driver`/`exited` mean the driver vanished mid-flight, leaving the last phase it wrote. For those the table marks the cell — `publishing (last recorded)`, `developing (last recorded)` — and the time counts since that record rather than time being spent.

- **The last confidence** is the newest round any record still carries one for — and for a run IN FLIGHT past its first round, that is usually nothing at all: the driver reads the developer's statement and clears it at gate-green, before it persists the reviewing decision, and no other record keeps the figure. So the column shows a completed round's confidence only for a run that has published, and for an in-flight run it shows either the current round's own pre-review statement (marked `stated`) or the no-record dash. Closing that gap means the loop recording the assessed confidence on its own control record, which is a change to what the loop WRITES and is escalated rather than improvised here. The two sources that exist today: the developer's own `.vinaya-confidence` statement for a round the driver has not consumed yet, else the run's own published summary table (read from principal-authored comments only, and only for a run that has published — the one state in which a summary exists). A round the driver read and cleared, and never published, leaves no confidence record behind, and the field reports nothing for it rather than carrying an older round's figure forward under a newer number.

  The summary read is bounded too, and for the same reason the history read is: it asks about one pull request per PUBLISHED row rather than a fixed handful, so a successful read is remembered per pull request for the same lifetime (a published run's summary never changes, and no more than `REMEMBERED_PR_COMMENTS_MAX` of them are held at once) and one status read makes at most `SUMMARY_CONFIDENCE_READS_PER_STATUS_READ` fresh reads. Past that budget the cell reads `not read` rather than the dash: a read nothing made is an unknown, and reporting it as an absence would be the one invented fact this table avoids everywhere else.

  Three states, not two, because the records carry three. A round the loop ASKED and whose statement was missing or unreadable reads `absent` — never a substituted zero. A round the loop never asked at all has no confidence to report: round 1 is never asked (the confidence rule starts at round 2), its summary cell is the table's own not-asked glyph, and a reader is told nothing rather than that the developer skipped a statement nothing requested. And a figure read from the statement FILE is marked `stated` in the table (`95% (round 3, stated)`) because that file exists precisely while its round's review has not completed — the driver clears it the moment it assesses the round — so it is the developer's own claim about work in flight, not a completed round's outcome.

`vinaya task status` renders these as ONE table — the same columns whether it lists every open task or narrows to one — and the `task_status` result carries the same six facts as structured fields (`round`, `phase`, `minutesInPhase`, `phaseIsCurrent`, `lastConfidence`, `phaseHistory`), so an Operator presents its own table rather than parsing a state phrase. All of them are optional in the catalog schema, so a client written against the earlier item shape still parses every item.

### What a phase typically takes here, from this repository's own history

Each in-flight row also carries what its phase has typically taken on this repository's recently merged tasks (`apps/cli/src/lib/task-status-history.ts`). It is HISTORY — the table's column says so, every row carries its own sample count, and no field anywhere names an ETA, a remaining time or a deadline.

- **Where the intervals come from.** One bounded read: the most recent merged task branches (`MERGED_TASK_PR_READ_CAP` of them, from one `gh pr list` of merged pull requests), each one's comments fetched once — `1 + cap` forge calls for a whole status read, however many rows it lists. Intervals are extracted by a pure reader (`phaseSamplesFromPrComments`) from PRINCIPAL-AUTHORED comments only: a developer round marker to that round's last verdict comment is time spent reviewing; that verdict to the next round's marker is time spent developing. A non-principal commenter's round-marker- or verdict-shaped comment contributes nothing — the same trust boundary every other forge read in this loop applies — so nobody outside the allowlist can move what this repository reports as typical. The pull-request numbers that read names are checked as positive integers before they ever reach a subprocess argument list.

- **Read lazily, once per status read, and remembered for a lifetime that depends on the outcome.** The read happens on the first row whose phase has a history class AND is where its run currently is — a typical time answers "how long does this phase usually take", which only a run actually in that phase is asking — so a listing of planned, paused, published or driverless tasks costs no forge call at all, so a listing in which every task is `no driver` — or a single planned task — costs no forge call at all. One status read attempts the forge at most once whatever happens, so the `1 + cap` bound holds for a read of any number of rows, failing or healthy: retrying per row is exactly what a secondary rate limit punishes, and an Operator polling `task_status` would deepen a failure instead of backing off. That count is the whole forge cost of the column: the principal allowlist is resolved once by the status read and passed in, never re-fetched here (resolving it inside would add a trust-anchor read per status read, outside the bound and outside the timeout). Across reads, a success is honoured for `PHASE_HISTORY_CACHE_TTL_MS` and a failure only for the much shorter `PHASE_HISTORY_FAILURE_BACKOFF_MS`. Both lifetimes exist for one caller: `task_status` is served by the long-lived task-tool stdio server, one process per Operator session, so a process-lifetime cache would let one transient `gh` failure empty this column for a whole session and would still be serving the session's first read hours later, after newer tasks had merged.

- **A record that does not parse reports nothing rather than a zero.** A `loop_state` whose `recordedAt` is not a timestamp (the schema requires only a non-empty string) yields no time in phase at all, the same dash every other unrecorded fact gets.

- **Each `gh` read is bounded in time as well as in count.** The reads are synchronous, and that same server chains every request through one promise, so a `gh` that hangs would hold every other task's queued call behind it. Every read this feature makes carries the same timeout and output ceiling — the history reads, and the task-status reader's own `gh issue list`/`gh issue view` per task — and an expiry is just another failed read: the column empties, nothing raises. A comment whose `body` or author login is not a string, like a pull-request number that is not a positive integer on either read path, is dropped at the parse rather than handed to a parser that would throw the whole status answer away.
- **The median, never the mean**, with the sample count shown beside it: one pull request left open over a weekend would drag a mean into uselessness.
- **Too thin an answer is no answer.** A phase with fewer than `MIN_PHASE_HISTORY_SAMPLES` past intervals reports nothing, and so does a phase with no comparable interval at all — `publishing` (one comment post), `paused` (it ends when a person acts) and `awaiting confidence` (not separable from the developer turn it interrupts). A round whose verdicts were never posted as comments contributes no interval of either kind: the record does not say where that round's time went. Today the driver posts a round's verdicts when it publishes, so a multi-round pull request contributes one reviewing interval and no developing interval, which is why a repository can show a typical reviewing time and no typical developing time at all.
- **A forge failure costs the column, never the row.** A failed list read, a failed comment read, malformed JSON, a comment with no readable body or a read that timed out yields no typical time — the status read still answers. A read that reached NOTHING (the list read failed, or every pull request it named failed) is reported as failed and honoured only for the back-off above, so a later status read tries again rather than serving an emptiness the forge never actually reported; a partial read is real history and keeps the full lifetime.

`apps/cli/src/lib/task-tools/handlers.ts` binds these to the catalog's `task_status`/`task_escalation_read` tools (`packages/aeg-core/src/task-tools.ts`), composing them with `task-status.ts`'s forge-touching identity/PR lookup. `task_resume` (`resume.ts`) and `task_cancel` (`cancel.ts`) are real handlers of their own — see the section below. `apps/cli/src/lib/task-tools/router.ts` classifies a caller's free-text intent to the one tool that answers it, so an agent surface built on this catalog later never routes a read request into a mutating handler.

### One fixed table, returned by the tool and printed by the command

Three Operators asked for the same status on one day and answered in three layouts, each missing a different field, because `task_status` returned rows and every Operator laid a table out itself — and the pull request's CI and verdicts were in a second tool, so no single read showed whether a task was ready to merge. The result carries a `table` field for that reason: **one fixed table, rendered by the SAME function `vinaya task status` prints** (`renderTaskStatusTable`, `apps/cli/src/lib/task-status.ts`), so the tool and the command carry the same columns in the same order for the same records, and a status answer opens with that string exactly as returned (`aeg-root/roles/operator.md`).

- **Markdown, and padded.** The pipes make it a table wherever it is pasted; the padding keeps it readable in a terminal. One rendering serves both readers, so there is no second renderer to drift — the handler calls this one and never builds a layout of its own. A cell's own value cannot break the table it is in, and cannot hide it either. Most cells come from a closed vocabulary, but the tranche slug is whatever the forge label carried and a state phrase can carry a word off a record on disk — unauthored text in the same sense `task_pr_read`'s own trust boundary means it, so every cell leaves through the same `sanitizeForgeText` exit (strip, redact, defang, cap) and then has every `<` escaped to `&lt;`, its vertical bars escaped (`\|`, which renders as the bar) and its line breaks flattened to spaces. The angle bracket is not only the comment opener's: `<span hidden>`, `<div style="display:none">`, `<style>` and `<script>` all fit inside a forge label and each hides the cells and rows after it in any renderer that honours raw HTML, while one unescaped bar silently adds a column — both in a table the Operator is required to relay exactly as returned. No legitimate cell contains an angle bracket, so escaping every one costs a reader nothing.
- **Every matched task, never only the page.** `items` is paginated as before; `table` covers every row the call matched, so a call with no `task` lists every open task in the repository whatever `limit` and `cursor` do beside it.
- **The columns.** `task`, `issue`, `pr`, `state`, `round`, `phase`, `in phase`, `confidence`, `typical (history)` — every one of them the same fact the sections above describe — then five about the task's own pull request: `head` (abbreviated as git abbreviates), `ci`, `code review`, `security`, `gate`, and last `next`. A fact with no record reads `—`; a read that was attempted and failed reads `not read`, because a forge read that never answered is an unknown and not an absence.
- **One forge read per pull request, for all five of those columns.** `readTaskPrFacts` (`task-tools/pr-read.ts`) asks `gh pr view` for `headRefOid`, `statusCheckRollup` and `comments` together and derives every column from that one payload — never a read per column. It reuses `task_pr_read`'s own `toChecks` flattening and `buildReviewRecord` derivation rather than a second copy, handing `toChecks` a failure-detail reader that answers nothing: a failure SUMMARY is what `task_pr_read` exists to give, and reading a job log per red check would turn one status read into many forge calls for a cell that shows one word.
- **Check runs only — never a commit status, and the gate by its workflow too.** Both `ci` and `gate` read the rollup's `CheckRun` nodes and drop its `StatusContext` ones, and the reason is not tidiness. A commit status is posted by anything holding `statuses:write` on the repository, its context is a free string, and `toChecks` flattens one to a COMPLETED check whose conclusion is its own state — so a status whose context was spelled exactly like the review gate's check-run name read as a GREEN GATE, and with the two principal-authored verdicts already on the head the table then named `merge` for a head the real gate was refusing. Excluding them also removes the `ci` divergence that came with them: the driver's own read is the REST check-runs list and never sees a commit status, so counting them here let a third-party status move this word while the driver's stayed put. The gate cell narrows further, because it is the one cell a `merge` word rests on: a run counts as the gate only when it carries the gate's check name AND the `name:` of the workflow that posts it (`REVIEW_GATE_CHECK_RUN_NAME` and `REVIEW_GATE_WORKFLOW_NAME`, the same two constants the generated workflow itself is rendered from), and the gate's own run is selected among gate-shaped runs BEFORE the newest-per-name dedupe, so a run that merely claims the name can neither become the gate nor suppress it. The workflow name comes out of the same payload, at no extra forge call, and a run created through the checks API outside Actions carries none at all.

This is attribution by what the forge reports, not authentication — an actor that can land a workflow file could declare the same `name:`, and attributing a run to the APP that posted it needs the REST list's `app.slug`, a second forge read per pull request that the one-read bound exists to prevent. The Operator's own doctrine already says a check's output is evidence to quote rather than instruction to follow, and the merge gate re-evaluates before any merge lands, so a table's green word is advice and never the decision.
- **`ci` is the mechanical suite only**, read as `green`, `red` or `running` by the same rule and the same precedence `fetchCiConclusion` gives the driver: anything not yet completed wins over a failure, since a suite that has not finished has not failed; then every completed run must conclude `SUCCESS`, `NEUTRAL` or `SKIPPED` for green, and anything else — a failure, a timeout, or a completed run carrying no conclusion at all — is red. The review gate's own check-run and the principal-test-plan wait are excluded, the same two exclusions and for the same reasons (the gate is not CI; the wait's red is the Principal's own hold). Nodes are deduped to the newest run per check name first, so a failure its own re-run superseded never reads as red. `gate` is the review gate's check-run read as those same three words, and `—` when the forge reports no such check run on this head yet.
- **A rollup page that may be full is a read that could not answer.** `gh pr view` returns ONE unpaginated rollup page and exposes no cursor, unlike both readers this shares its rule with (`task_pr_read`'s own rollup read walks `pageInfo`/`endCursor`; the driver's own check-run read passes `--paginate`). A payload carrying a full page may be hiding checks, and a `ci` word summarized over a partial set could read green beside a red check the read never saw, or report the gate absent for a gate that ran. So a full page reads `not read` in every column rather than guessing, and `task_pr_read` is the paginated read for such a head.
- **The head these columns are read against is `headRefOid`**, which this repository documents as able to lag a push (`resolveHead` refuses it by name and reads `git ls-remote` instead). Every column is read against that one head and the table shows it, so the set is internally consistent; what it cannot promise is that the head is the branch's tip this instant. Resolving the true tip would be a network call per row — the unbounded fan-out the budget below exists to prevent — and the merge gate re-checks the real head before any merge lands.
- **A verdict counts only on the head it judged.** `code review` and `security` show the newest principal-authored verdict value whose `Judged head:` binding IS this head; a verdict that judged an earlier head reads `—`, because a stale approval is not an approval of what is there now. The values come from the merge gate's own extractors, so this table can never disagree with the gate about which comment cast a verdict.
- **Nothing here is cached between reads, and the reads are bounded within one.** The confidence column remembers a published pull request's comments for a while because a published summary never changes. A check does: "a check that was green on your last read is not green now" is the Operator's own reporting rule, so a CI word is read fresh every time or reported as unread. Within one status read it IS bounded — `PR_FACTS_READS_PER_STATUS_READ`, the catalog's own `DEFAULT_PAGE_LIMIT`, the size of the page `task_status` returns when a caller names no limit, so a default-sized answer never carries a column nothing read. It is still a ceiling, and for the reason the confidence column's own bound exists: these reads are synchronous and the long-lived task-tool server chains every request through one promise, so an unbounded number of them would hold every other task's queued call behind a listing of a busy repository — and a `gh` that never returns would hold it behind one subprocess, which is why this read carries its own timeout and output ceiling and no retry (a retry inside a synchronous read on a shared server multiplies the very hold the bound is for). It is deliberately HIGHER than the confidence column's bound, which it was first borrowed from, on two counts: that reader asks about published rows only while this one asks about every row with a pull request, and recovering a truncated row by name costs one Issue read plus one pull-request read where the listing would have spent one — a bound that makes the ordinary listing pay twice over is not a saving. Past the budget the remaining rows read `not read`, and the remedy for the row an Operator is acting on is to read that task by name: one row, always inside the budget, the same remedy the doctrine already gives for a task missing from a listing. That holds only because the reader **filters before it builds** — `gatherTaskStatusList` takes the selector itself and skips every ref the call did not name, before any per-row read is made. Filtering the rows afterwards, as this did at first, spent the budget in listing order on rows nobody asked about and then reported the named row's own columns as unread, leaving an Operator no way to get them at all; it also made a named read pay one Issue read per open task instead of one. The reader also remembers within its own read, so two rows naming one pull request pay once.
- **A read that wants no columns makes no call.** `gatherTaskStatusList` takes the depth of the read beside its selector, and the two ref resolutions behind `task_escalation_read`, `task_resume`, `task_cancel` and `task_pr_read` ask for `'skip'`: each reads a row's Issue and its pull-request NUMBER and discards the rest, so a facts read there is one `gh pr view` per invocation whose whole payload is thrown away — and `task_pr_read` then re-fetches the same rollup and the same comments itself. Those four tools never paid that read before this field existed and do not pay it now.
- **The handler returns the reader's own table, not a second rendering of it.** The reader filters before it builds, so the rows the handler pages over are the rows the reader already rendered; re-rendering took a second read time and host name for a footer already computed.
- **A published row pays ONE read for two columns.** The facts read's payload already carries the pull request's comments, and the published summary the confidence column wants is in them — so that column is served from the same payload rather than fetching it again. Its own bounded, remembered reader stays as the fallback for a facts read that failed or that the budget stopped.
- **`next` names the one thing to do about the row**, from the closed vocabulary the catalog declares (`TASK_NEXT_ACTIONS`: `wait`, `merge`, `rule`, `start`, `cancel`, `investigate`). The mapping is `aeg-root/roles/operator.md`'s own state-to-action table, read out of that file by a conformance test (`apps/cli/tests/lib/task-tools/operator-state-actions.test.ts`) rather than kept in step by hand — the same test that already binds each state to the tool that moves it. In code it is a `Record` over the state kinds and a second one over the pause dispositions, so a state or a disposition added without a next action beside it is a typecheck error rather than a row that renders nothing.
  - **A pause is routed by what it is waiting for**, never by the word `paused` alone, through the SAME disposition reader `task_start`'s own gate consults (`defaultPauseDisposition`) — so the action this table names and the tool that would actually move the run cannot disagree. A decision nobody has made reads `rule`; one already taken as resume, and an automatic hiccup the loop resumes itself, read `start`; one already taken as cancel reads `cancel`; a pause record this host cannot read reads `investigate`. It is read only for a paused row: reading it for a running one would cost every listing a control-store read for a cell that names no pause. A paused row whose disposition was not read reads `rule`, the doctrine's own default for that row.
  - **Merge-readiness wins over the state's own action**, because it is the newer fact: the review gate green AND both verdicts on this head clean means the row wants a merge, not another read — a run whose driver vanished on a green, approved head included. Clean means `APPROVE` and `PASS`, and `APPROVE` alone: `LGTM` is a value the extractor accepts and `checkReviewGate` does not, so naming `merge` for it would promise a merge the gate refuses. It never overrides three answers — `cancel` (a decision the Principal already made, which a merge would reverse), `investigate` (a record nothing could read), and a state where a driver is still live (`running`, `starting`), where the head this read judged is not the head the run will finish on and a merge would race the loop. The gate's own conclusion is the authority here; this reader never re-derives `checkReviewGate`'s rule, which reads labels, ruling ordinals and an input manifest a status read never fetches.
- **A phase past twice its own typical time carries `⚠` in its time-in-phase cell.** Both sides of that comparison are recorded history — the phase's measured age against the median of the same phase on recently merged tasks — so the mark says where this run sits against what already merged, never when it will finish. A phase with no typical time never carries it: there is nothing for it to be twice of, and a mark with no comparison behind it would be a judgement this table does not make. Exactly twice is not past twice.
- **One footer line, last.** The read time in UTC, the host that read it, and how many tasks it lists. A table pasted into an answer carries its own read time with it, so nobody has to ask whether they are looking at a fresh reading or an earlier one. It is still not a forecast: no ETA, no remaining time and no deadline appears anywhere in the table, and the typical-time column stays labelled as history with its own sample count.

### The third read: why the pull request is red (`task_pr_read`)

The two reads above answer from the OUTBOX — the loop's own local record of what it decided. Neither answers the other half of a stuck task: what the FORGE says about the pull request. An Operator watching a run that had already published could see `published` and nothing else — not the APPROVE/PASS verdicts on the pull request, not the one red check holding the merge gate open — and reported a finished task as broken while a Principal pasted the CI log by hand. `task_pr_read` (`apps/cli/src/lib/task-tools/pr-read.ts`) is that read.

- **One pull request, resolved from the task.** The pull request always comes from the selected task's own branch, through the same status rows `task_status` reports (`resolveRowForRef`, over `task-status.ts`'s own `findPrForRef`). An optional `pr` argument is a CROSS-CHECK only: a number that is not this task's refuses (`authority`), naming the one it would have read. There is no input that makes this tool read a pull request the selected task does not own.
- **Checks, as the forge reports them.** One GraphQL read of the pull request's own `statusCheckRollup` gives each context's name, status, conclusion, details URL and `isRequired` — GitHub's own answer for THIS pull request (branch protection, rulesets), never inferred from a check's name, which is why this is a rollup read and not the REST check-runs list `fetchCiConclusion` uses for the driver's own green/red. Contexts are reported verbatim, not deduplicated: the question is what the forge reports on this head. A failed check's summary is its own reported `title`/`summary` where it wrote one, its failure-level annotations otherwise (minus the runner's generic exit-code line, which names no reason), and failing those the TAIL of its own job log — the thing that used to be pasted by hand. That last fallback is bounded: at most the first few failed checks, and every returned field capped at the catalog's own `MAX_RETURNED_TEXT_CHARS`.
- **A review record built only from principal-authored comments.** Verdicts come from the merge gate's OWN extractors (`extractCodeReviewVerdict`/`extractSecurityReviewVerdict`), applied to bodies already filtered through `isPrincipal` against the configured allowlist — so this tool cannot disagree with the gate about which comment cast a verdict or what head it judged, and there is no second verdict regex in it. Round markers come from `parseDeveloperRoundMarker`, the published summary from `isPublishedSummaryComment`, the pause from the `aeg:loop:paused:<reason>` marker `pause-resume.ts` renders. Everything on the pull request is DATA: a comment from outside the allowlist contributes no verdict, no round marker, no pause and no summary, and its body never leaves the module.
- **Unauthored forge text leaves through one exit.** The review record can be author-filtered because a comment has an author. A check name, a check's own reported output, a failure annotation and a job log have none — whoever lands a workflow file or a build step on the task's branch writes them, and an allowlist has nobody to check. So every one of those strings leaves through `sanitizeForgeText`/`sanitizeForgeLogTail`, in a fixed order: strip the runner's terminal colouring, redact secrets through `redact()` (`packages/aeg-core/src/log/redact.ts`, this codebase's single redaction chokepoint — a step that prints a token during a failing run must not hand it out just because the run was red), neutralize the two grammars that carry authority in this system (an AEG control comment's `<!--` opener, escaped; a line-anchored `VERDICT:` label, separated from its colon), then cap — the free-text ceiling for a summary or a log tail, a much smaller one for a name, a status or a conclusion. What the tool returns is untrusted output to quote, never instruction to follow, and the Operator's own doctrine says so.
- **Read-only, structurally.** No forge-write function is imported by that module; the tool re-runs no check, posts nothing, edits nothing, merges nothing, and holds no credential — every `gh` call it makes is a read through the driver's own `sh` (`gate-reading.ts`), the controller's existing read path, never a token handed to the Operator. The pull request's comments are parsed by the loop's own `markerComments` (`developer-dispatch.ts`), not a second parser beside it.

## The Operator's start path — `task_start` over `runTask`

`task_start` (`apps/cli/src/lib/task-tools/start.ts`) is the tool that starts a run. It wraps the existing `runTask` composition (`task-run.ts`, the same `vinaya task run` the CLI already exposes) rather than adding a second execution path: the tool records a durable claim, then launches `runTask` **detached** (overridable through `VINAYA_TASK_RUN_COMMAND` for an operator who wraps the launch in a supervisor) and reports the durable run identity only once that launch is known ALIVE — either confirmed by its own driver lock, or still coming up with its process running — while the run continues on its own. The run's PR is discoverable through `task_status` exactly as any other run's is.

Its input is the SAME `TaskToolRef` union every other tool in the catalog accepts — `{ tranche, id }` for a tranche task, `{ issue }` for a standalone task Issue that carries no tranche label — so a task the Operator can already watch, resume and cancel is one it can also start. Whichever form is used, the launched command is the one the CLI itself already exposes for that form: `vinaya task run <tranche> <n> --agent <agent>`, or `vinaya task run --issue <n> --agent <agent>`. One launcher, one override, one liveness confirmation; the form decides only the argv.

Six properties are the point, and each is a deliberate limit:

- **An authenticated caller, from the invocation context.** The tool refuses (`authority`) unless a caller identity is present in the environment the server was started in (`VINAYA_MCP_CALLER`, resolved once by the server — `apps/cli/specs/self-hosting.md`). MCP is a transport, not authorization: the caller is never read from a tool argument. Started with no caller, the server still answers every read tool and refuses only `task_start`.
- **An explicit agent, read from repository config, never accepted as input.** The tool passes `--agent <agent>` to the launched run, resolved from the SAME `dispatch.agent` setting (`vinaya.config.json`) `vinaya task run` itself falls back to when no `--agent` flag is given. With none configured, the call refuses (`precondition`), naming the missing setting, BEFORE it ever claims the request — never launching a run that would exit on its own missing `--agent`. The tool carries no agent field of its own (that would be a catalog change, out of this surface).
- **One task, one address.** A standalone `{ issue }` target is checked against the forge before anything launches (`readTaskIssueFacts` — one `gh issue view`, state and labels): a number that is no Issue, or a closed one, is refused (`precondition`), and so is an Issue that carries a `vinaya/tranche:*` label, naming the tranche and pointing at the `{ tranche, id }` form instead. That last refusal is the point of the property: a tranche task already has an address, and accepting a second one for it would give it a second request identity, a second claim, and so two concurrent runs. The tranche is read from the LABEL alone, never from a title that happens to look like `[slug] 3` — the same rule `task-status.ts`'s own `TaskRef` and `developerBranchFor`'s branch shape already follow. A tranche target needs none of this: its own resolution already proves its Issue is open and labeled, so no second forge read is made for it.
- **A state another tool owns is refused, and only when that tool would really move it.** A LIVE driver is decided by the state: `deriveLoopState` (`task-status.ts`) reports `running` and the tool refuses (`precondition`) naming `task_status`, since a second start would put two developers on one branch. A start still COMING UP is decided by the state too, and for the same reason: `starting` is the only signal there is in the window before a driver lock exists, so the tool refuses it naming `task_status` as well. The claim behind that state makes a call's own REQUEST idempotent, but a start from another caller, or for the same task under a different payload, has a different identity, finds no claim to replay, and used to read straight past a state that was already saying a launch was in flight. It narrows the duplicate-developer race by exactly the span a claim can see. The state is read for the ADDRESS the start names — a claim written against a tranche ordinal names that ordinal, not the Issue, so a read passed no address would never match the form every tranche task uses — and it EXCLUDES the calling request's own claim, which is on disk before any state is read: counting it would make every start a duplicate of itself. The refusal is bounded at both ends: a claim stops reading `starting` once its process is gone and its grace has passed, and `start did not come up` is NOT refused — that state's own action is this tool. What it cannot reach is the instant where neither call has written a claim yet; closing that needs a real cross-process reservation per task, the same accepted race `runTask` already records against its own open-pull-request check. Everything else is decided by the PAUSE RECORD, through `defaultPauseDisposition`, and deliberately not by whether the state reads `paused`. That is not tidiness: `task run` composes the watching driver, which retains its lock at EVERY pause reason, so a pause whose driver is then killed leaves a dead lock plus an exit trace and derives `exited` while the record still holds the run. Gating the read on the state name let exactly that pause launch straight past the ruling the refusal exists to require — `runTask` would see `hasPauseState` and enter `devReviewLoop --resume`, whose own gate tests only that SOME ruling comment exists, with no ordinal-freshness check of `task_resume`'s kind. The disposition has five answers. **Awaiting a decision** refuses naming `task_resume`, which authenticates it against a Principal ruling. **Already resolved as resume** — the ruling was given and consumed, and the continuing driver then died — launches here, because `task_resume` answers `already_resumed` and starts nothing: an ok result rather than a refusal, which is why following it leaves nothing running. Reason **`infrastructure`** launches here too: the loop waives a ruling for that reason inside its own retry bound (`bareInfrastructureResume`) and recovers itself, while `task_resume` carries no such waiver and refuses `authority` for a ruling nobody posts for an automatic hiccup. That reason alone — the loop's bare-resume gate tests `infrastructure` and not `stale_driver`, so classing `stale_driver` self-resuming here would launch a run the loop then refuses; awaiting a ruling is its truthful answer. **Already resolved as cancel** refuses naming `task_cancel`. **Unreadable** — a pause record or resolution that would not read or parse — refuses too: a resolution that will not parse might be the cancel this gate protects, so it is never read as "no decision recorded". That case needs its own read: `readPauseState` answers the same `null` for "no record" and "a record that will not parse", and `writePauseState` is a plain non-atomic write, so the kill this path exists for can leave a truncated record — read as no pause it would launch as a FRESH dispatch rather than a resume, since `runTask`'s own `hasPauseState` reads that identical null. The file's existence is therefore checked separately from its contents. The `infrastructure` waiver is also bounded here rather than left to the loop, computed the loop's own way — the control store's recorded count floored against the pause record's, a `loop_state` that will not parse counted as past the bound. Past it the loop does NOT reliably refuse: it falls through to a gate that refuses only when the pull request carries no ruling comment at all, with none of `task_resume`'s ordinal-freshness check, so any older ruling would have authenticated a continuation past the bound. A pause record is never cleared on resume, so the disposition applies the same supersede rule `deriveLoopState` does — a record naming a round the outbox has published past reads `none`, and the task launches. `none` is also what lets `not_started`, `no_driver` and a genuinely pause-less `exited` run launch. A pause this tool CONTINUES is relaunched under the agent that run was dispatched with, read off its own pause record — the same field `task_resume` resolves its continuation's agent from. `runTask` takes its resume path for any task with a pause record, and the loop refuses outright when the agent it is handed is not the one the pause records, so relaunching a held run under whatever `dispatch.agent` the repository configures today would kill it on arrival — and `task_resume` answers `already_resumed` without launching for a ruled pause, so that state would have had nothing left that moves it. A pause recording no agent falls back to the configured one, which the loop accepts. A fresh start never consults it. Refusing every pause was itself a way of stranding a run: two shapes need no Principal act, and `task_resume` moves neither. Either read is wrapped, so a filesystem error cannot escape past the claim this call already wrote and leave every retry replaying `started: false` for a run that never began. Either refusal releases its own claim, and neither read happens on an idempotent replay: the gate guards a launch, not an answer.

  Every OTHER state launches, and the one that matters is **exited** — a driver killed, crashed, or ended by a signal, with no pause record written. `runTask` refuses only when an open pull request has a driver *actually still running* for it; with no live driver it re-attaches to that same pull request rather than opening a second one, which makes `task_start` the only tool that continues this state (`task_resume` refuses a run with no pause to resume from, and needs a fresh Principal ruling besides). Before this, the Operator's doctrine named `task_start` for a task never dispatched and `task_resume` for "a paused or exited run" — so a run that died by signal mid developer dispatch had no tool that worked at all, and the Operator correctly stopped and asked. The rule that replaced it is the general one: a state is refused only when the tool named in its place would actually move the run. `not_started`, `no_driver` and `published` take the same launch path for the same reason.
- **Reported alive, not just launched.** The tool resolves the task's forge Issue — a standalone target names its own; a tranche target is resolved over the open tranche-labeled Issues, an open Issue labeled `vinaya/tranche:<slug>` whose title's ordinal matches — the SAME resolution `vinaya task run <tranche> <n>`'s own preparation performs to find an ordinal's Issue (`resolveOpenTaskIssueForRef`, reusing `resolveTaskIssueRef`), NOT the frozen-brief-filtered `resolveIssueForRef` that `task_status`/`task_escalation_read` use. This is the point: `task_start` starts a PLANNED task whose brief that preparation has not frozen yet, so it must resolve over the pre-freeze list, exactly as preparation does — a task not yet listed by `task_status` is still startable, and refusing it with "no resolvable Issue" while its Issue is open and dispatch-ready was the bug this closes. It then waits, bounded, for that Issue's own driver lock (`driver.pid.json`) to appear and name a live pid — the observable `devReviewLoop` itself writes once its entry gate clears, right after `runTask`'s own preparation step (which renders and posts the frozen brief first, and can itself refuse — e.g. a checkout on another branch or carrying local commits the remote lacks, though a clean checkout that is merely behind is now fast-forwarded rather than refused, see "Preparing a brief fast-forwards a clean checkout that is only behind" above; the wait is sized to cover that). An ordinal that names no open task Issue is refused (`infrastructure`) before any launch, naming the tranche and ordinal it looked for.

  The wait has **three** outcomes, not two, and only one of them is a failure. The lock appears and names a live pid: **confirmed**. The process **exits or errors** before it does — a missing `--agent` binary path, a refused preparation, an ENOENT on the launcher: a failed start (`infrastructure`) carrying that run's own captured stderr, and the only outcome whose claim is released, so an identical retry launches again. The wait simply **runs out with the process still alive**: a run whose preparation outlasted the wait, which on a real repository it routinely does — posting the frozen brief and running the start-of-run sweep are forge-bound steps that happen before the loop writes any lock. That is a started run, reported as started, and its claim is KEPT. Releasing it was the defect: a launch that was still coming up was reported as an infrastructure failure and its claim dropped, so the obvious next thing an Operator does — call `task_start` again — would have put a second developer on one branch. Raising the wait does not fix that, because no fixed wait bounds a slow forge or a large sweep; only deciding from the process itself does. Confirmation, when it is wanted, is read where it is actually observable and actually current: the driver lock, through `task_status` on the next call.
- **Idempotent per request identity, and never idempotent against a dead run.** The identity is `caller + repo + target + payload digest` (`taskStartRequestIdentity`, `@attalabs/aeg-core`), and the target's ADDRESS FORM is part of it: a standalone target hashes a shape no tranche target can produce, so `{ issue: 729 }` and a tranche ordinal that resolves to Issue 729 are two requests and never share one claim. A tranche target hashes exactly the bytes it always has, so an identity computed before standalone Issues were startable still computes the same today — a claim an older build wrote is found by a newer one at the same path (and is read back through `normalizeStartRecord`, which understands both record shapes), so an upgrade never starts an in-flight run twice. The first call claims it in a durable store and launches; every later call with the same identity replays the same run and launches nothing more — UNLESS the claim is old enough that its own launch must already have concluded one way or the other (past its own confirm-wait bound, with a margin), and neither the process that launch spawned nor the task it names has a live pid, in which case the claim is superseded — released and re-claimed — and this call launches again rather than replaying a start that no longer exists. The launched process is asked FIRST and on its own: a claim records its own child's pid once the launch is known alive, and a live pid with no driver lock yet is precisely a run whose preparation is outlasting the wait — never a dead claim, however old it is, because superseding it would launch the second developer the claim exists to rule out. A pid a claim never recorded (an older build's record, a launch that never returned one) leaves the driver lock as the only signal, exactly as before. A claim still within its own confirm window is never touched this way: it may simply not have written its driver lock yet, and superseding it there would race the very call that owns it. Because the claim is written before the launch, a client that disconnects mid-call leaves at most one run — a reconnect replays the claim, it does not start again.

Attended mode only, the caller's own credentials: the detached run inherits the operator's own environment. There is no unattended start and no attended bypass; an unattended start waits on the worker-isolation boundary and a capability flag a later tranche adds. The tool's own catalog description carries the same limits.

Both runtime adapters register the shared MCP server (`vinaya task-tools serve`) that exposes this tool: Claude through the generated `.mcp.json`, Codex through its documented `[mcp_servers]` TOML — see `apps/cli/specs/self-hosting.md`.

## The Operator's continuation and cancellation — `task_resume`/`task_cancel` over the control store

`task_resume` (`apps/cli/src/lib/task-tools/resume.ts`) and `task_cancel` (`apps/cli/src/lib/task-tools/cancel.ts`) consume a paused escalation's durable state — never a caller-supplied claim of approval — and trigger the SAME existing mechanisms `vinaya dev-review-loop --resume`/`--cancel` already use, rather than a second execution or retry path:

- **`task_resume`** reads the pause record, the durable `EscalationRecord`, any `ResolutionRecord` already written for it, and the driver lock — all through the same reads `task_escalation_read`/`task_status` already expose — and refuses (`precondition`) on a missing pause, a pause superseded by a later published round, a missing or wrong-target escalation record, or a live driver already running for the task. With every check clear, it requires a Principal ruling comment read fresh off the run's own PR (`authority` when none exists — a forged decision is refused before anything is triggered) and then launches the existing `vinaya dev-review-loop --resume <pr> --agent <agent>` continuation, detached, exactly as `task_start` launches `runTask` — guarded by an idempotent claim keyed by the escalation's own identity, so the same escalation is never handed to two continuations. It never calls `resolveEscalation` itself: that single-use consumption happens inside the SAME continuation it triggers, unchanged, so there is no double-consumption race between this handler's own peek and the real write. It waits for that continuation on the same driver-lock observable `task_start` confirms against, bounded to a shorter wait since `--resume` carries no preparation step of its own to size a longer one for, and reports `outcome: 'started'` for either live outcome — confirmed by its lock, or still coming up with its process alive when the wait ends. Only a continuation that EXITS first is a failed start (`infrastructure`), carrying its own captured stderr, and only then is the claim released so an identical retry launches again; a live continuation keeps its claim, so a repeat call replays it instead of handing one escalation to a second worker. A repeated call against an escalation a prior call (or a race this call lost) already resumed answers `outcome: 'already_resumed'`, never a second launch — UNLESS that claim is old enough that its own launch must already have concluded, in which case the driver-lock gate above has already proved the task has no live driver — and the process that claim's own launch spawned is gone too — and the claim is superseded: released and re-claimed, so this call launches again rather than replaying `'already_resumed'` forever.
- **`task_cancel`** delegates its entire authenticated consumption to the existing `cancelDevReviewLoop` (`dev-review-loop.ts`) unchanged — the same Principal-ruling authentication, `resolveEscalation`'s wrong-target/stale/replayed refusals, in-flight-role termination, and fencing every still-`'started'` effect to `'uncertain'`. The handler's own job is translating that into a truthful outcome: `'confirmed'` (resolved, and any local in-flight process was signaled on this host), `'pending'` (resolved, but the run's own driver was on a different host, so this call cannot itself confirm the process stopped), or `'uncertain'` (an effect could not be confirmed complete and was fenced instead). A repeated call against an already-cancelled escalation reports `'confirmed'` again — never an error; a repeated call against one already resumed is refused (`precondition`).

**Clearing a pause that has no pull request (`unattended-run-v1` 22, Issue #781).** A pause the loop recorded before any pull request existed carries `prNumber: null` ("Pause and `--resume`", above), and both tools read its ruling from the task ISSUE — where that pause's own comment was posted, and the only place a ruling answering it can be. `developer-dispatch.ts`'s `fetchIssueRulings`/`fetchNewestIssueRulingOrdinal`/`fetchNewestIssueRulingAuthor` sit beside their pull-request siblings and hand the SAME `fetchIssueComments` read to the IDENTICAL pure parser (`filterPrincipalRulings`, `newestPrincipalRulingOrdinal`) under the IDENTICAL `principalAllowlist()`: an Issue comment authenticates a resume or a cancel on exactly the terms a pull-request one does — principal-authored, carrying the `aeg:principal:ruling:<ref>-<ordinal>` marker on its own first line (the ordinal being the second number), and with an ordinal newer than the one the escalation was raised under — never easier ones.

- **`task_cancel`** addresses such a pause by its task rather than by a pull request: `CancelInput` is `{cancelPr}` OR `{cancelTask}`, and the no-pull-request form skips the `Closes #N` derivation there is no pull request body to perform. The resolution it consumes binds against an escalation whose own `pr` is equally `null` (`resolveEscalation`'s `expectedPr` is nullable), and its `authenticatedFrom` reads `issue-<n>-<ordinal>` so the record names where its decision was read from.

- **`task_resume`** cannot delegate: `dev-review-loop --resume` derives its task from a pull request's body and has no entry for a pause with none. So for that one case this handler consumes the ruling ITSELF, as that escalation's own resolution through the same single-consumption `resolveEscalation` every other path uses, and only then relaunches — through the `vinaya task run` command `noPushResumeArgv` builds for this task's own branch, the one continuation such a pause has. Order matters: the ruling is consumed first, so a second resume of the same escalation is refused as a replay instead of handing it to a second run. What that costs is stated where it bites, and stated accurately: a consumed resolution is consumed for good — `consumeResolutionOnce` refuses the same `escalationId` however many rulings land afterwards, and an identical pause raised again even reuses that id (`sameEscalationInstance`) — so both the replay refusal and the failed-launch refusal name the command to run directly rather than promising a new ruling reopens anything.

  **What this continuation does NOT carry: the ruling's text.** `task run` re-enters at round 1 and dispatches the developer with the frozen brief; no path reads Issue rulings into that dispatch. A Principal whose ruling changes what the developer should do has to say it where the developer reads — the frozen brief, or the objectives — not only in the ruling comment that authorizes the resume. This is the shape the continuation itself has, not something this handler chose: `task run` is the only entry such a pause has.

Two further readers of a pause record had to be brought along with its new shape, neither of them a handler above: `task-status.ts` keeps its own narrow copy of the pause read (its header's split between forge-touching entry points and pure outbox reads) and now carries the same non-positive normalization, and `packages/aeg-core`'s legacy-outbox migration required `prNumber` to be a `number`, so a genuine no-pull-request pause failed its shape guard and migrated as `source: 'fresh'` at round `0` with no `paused` transition at all.

Neither handler accepts a free-text approval field, and neither ever posts a ruling itself — the only decision reference either consumes is a Principal ruling already on the forge, read fresh on every call. Both emit a typed `operation` event (`packages/aeg-core/src/log/schema.ts`) naming the tool, the task target, and the outcome.

## The in-process test seam (issue-709, O2)

`devReviewLoop` already takes its every forge/git/dispatch READ as an injectable `LoopDeps` field, so a test can drive the whole loop in-process by supplying fakes. Five WRITE/read operations that used to shell out to `gh` unconditionally — outside any `LoopDeps` field — are now injectable too, defaulting to their real implementations so a real run is byte-for-byte unchanged:

- `postMarkedComment` — the poster inside every `postForgeEffectOnce` call (the round marker comment, the unpushed-work-resume note, the report-uncitable note).
- `postPauseComment` / `postIssuePauseComment` — the two pause-comment posters (on the PR, and on the Issue before a PR exists).
- `publishRound` — the post-then-re-fetch publication at green.
- `fetchPrBody` — the PR body read `checkPremiseAtHead` performs on EVERY round's gate check (the premise re-assertion). This one is a read, not a write, but it shelled out per round exactly like the others, so an in-process run would otherwise make a real network `gh` call every round. The `--resume` entry reads the paused pull request's body through the same field, so a resumed run is in the harness's scope too. `cancelDevReviewLoop` logs its `cancelled` event through a sink of its own, bound to the same repo its wait path was resolved for, so the line lands where the wait looks even in a process whose default sink already resolved another repo.

This is the ONE seam the in-process harness required; adding it kept the seam inside `dev-review-loop.ts` itself (the composition root that already owns and re-exports these operations), never in a module the loop merely consumes. `apps/cli/tests/lib/dev-review-loop-harness.ts` is the shared harness those fakes live in: one mutable in-memory world (branch/head per push-state, PR state, gate result, posted comments, per-round role outcomes) backs a complete `LoopDeps`, and the driver still writes its real on-disk artifacts (held verdicts, control store, pause state, driver lock, logged events) under a temp `runtimeDir`, so a converted test reads exactly what the driver wrote. Tests whose subject is a real process — exit status, a signal, the driver lock, the start-of-run sweep, stdio shape, or `publishRound`'s own posted-comment re-fetch and manifest re-binding — keep a real subprocess with a `// REAL PROCESS:` reason line, enforced by `apps/cli/tests/lib/dev-review-loop-real-process-debt.test.ts`.
