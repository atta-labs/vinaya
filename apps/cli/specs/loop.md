# The dev-review-loop — command, rounds, exits, publication and pause

Status: draft

`vinaya dev-review-loop --task <n> --agent <claude|codex|gemini>` (`apps/cli/src/commands/dev-review-loop.ts`, `devReviewLoopCommand`) runs the developer/reviewer round loop for one task Issue, unattended, until it publishes or pauses. The full design is the Linear "Tech spec — Developer Review Loop" (rev 4); this file is the durable, in-repo reference for what shipped across `dev-review-loop-v1` tasks 4–6 — the state machine, the driver, publication and pause — not a restatement of the whole spec.

`packages/aeg-core/src/dev-review-loop/` is the policy layer: `assessRound` (task 4, `#414`) is the ENTIRE decision logic — every stop condition, every confidence rule, the `Decision` a round produces — as one pure function, no `fs`/`fetch`/`process.env`/subprocess/prompt anywhere in that directory. `apps/cli/src/lib/dev-review-loop.ts` (`devReviewLoop`, tasks 5–6) is the driver: it turns real forge/dispatch facts into `Observations`, calls `assessRound`, and acts on the `Decision` it returns. It never re-implements a stop condition or a confidence rule.

## The command

`vinaya task run <tranche> <n> --agent <claude|codex|gemini>` (`apps/cli/src/commands/task-run.ts`, `taskRunCommand`, task-run-v1 task 2) is the normal entry: it composes `task brief`'s own preparation (renders and freezes the brief, starts no agent) with this loop, so one command runs the whole way from a planned Issue — `n` a tranche task ordinal there, resolved to its real forge Issue by preparation — to a reviewed pull request, exactly one developer started. `dev-review-loop` below is `task run`'s own debug/direct entry, kept for resuming a paused run and for driving the loop straight off an Issue number without going through preparation:

```
vinaya dev-review-loop --task <n> --agent claude|codex|gemini [--json]
vinaya dev-review-loop --resume <pr> --agent claude|codex|gemini [--json]
```

`--task <n>` starts a fresh loop against task Issue `<n>` — `n` is a GitHub Issue number, not a tranche task ordinal. `--resume <pr>` continues a previously paused loop from its held state (see "Pause and `--resume`" below); it takes a pull-request number, since a paused loop is anchored to an already-open PR, not an Issue. `--agent` falls back to `dispatch.agent` in `vinaya.config.json` when omitted. Both forms build the same `LoopInput` union and make exactly one call into `devReviewLoop` — `apps/cli/specs/surface.md`'s one-command-one-effects-call rule. `task run` never grows a `--resume` flag of its own (O2): a paused run is resumed through this SAME `--resume <pr>` path directly, since `runTask` (`task-run.ts`) composes `devReviewLoop` fresh every call and carries no resume state of its own.

`task run` itself takes the identical `--agent`/config-fallback treatment (task-run-v1 task 13, `#508`, O10): a repository that declares `dispatch.agent` in `vinaya.config.json` once needs no `--agent` flag on `task run`, `dev-review-loop`, or `dispatch` — the whole run and every resume is `vinaya task run <tranche> <n>` with nothing else to remember. A `--agent` flag given with no value is still a usage error, never silently rescued by the config default.

## One driver per task (`review-validity-v1` task 7, `#498`)

`devReviewLoop` refuses a second concurrent start on the same task, on the same machine, before dispatching anything: right after the task is resolved (both the `--task` and the `--resume` path), it reads a pid record at `<outboxRoot>/dev-review-loop/<task>/driver.pid.json`. A record whose pid answers a `process.kill(pid, 0)` liveness probe is alive — the new start throws (the process-level, non-zero-exit refusal `index.ts`'s top-level catch already produces for every other pre-flight error in this driver) and dispatches nothing. A record whose pid does not answer the probe is treated as absent — a prior driver's crash never blocks the next start — and this run takes it over. Both cases print one `vinaya dev-review-loop: `-prefixed line to stderr naming the pid and start time involved, so a double-paste is visible in the terminal; per Issue #498's objectives revision, this is stderr only, no new Vinaya Log event kind — `packages/aeg-core/src/log/schema.ts`'s `DevReviewLoopEventSchema` is outside this task's declared Surface, and none of its ten existing event literals fit a guard refusal that dispatches nothing. The record is written once, right after this check, and cleared in one `finally` that wraps the entire rest of the driver for a normal `publish`/`pause` return and an uncaught error alike — **except** the re-exec hand-off below (`#548`, O1), which clears and re-writes the SAME record explicitly, inline, because that path calls real `process.exit` and never reaches this `finally` at all (see below). The `--resume` path's own earlier validation throws (a stale head, a missing ruling, a missing held state) happen before the task is resolved, so no lock is ever taken on those paths — there is nothing to clean up there either. Everything durable and cross-machine — a real lease, session persistence, crash resume — is `control-store-v1`'s design; this guard is the narrow, machine-local stopgap until then.

## The round-end flush (task-run-v1 task 3, `#482`, O2; guaranteed on every exit — task 21, `#541`, O10)

Every round-end path calls `flushOutbox` (`apps/cli/src/lib/log-flush.ts`) in-process, posting the task's outbox to the Issue and clearing it for the next round — never `vinaya log flush` spawned as a subprocess of the driver's own CLI entry, which `apps/cli/specs/surface.md`'s "commands never call commands" rule forbids through a child process exactly as it forbids a direct call. A thrown `LogFlushError` is caught and logged to stderr; the driver never treats a flush failure as fatal (the lines it would have flushed simply wait for the next round's flush).

Every event the loop is about to emit is checked against its own schema (`DevReviewLoopEventSchema`, minus the `meta`/`subject` envelope fields only `buildHeader` fills) INSIDE `logEvents`, before `log()` ever sees it — a violation throws, naming the failing field, rather than reaching the outbox at all. This is checked HERE, not left to `flushOutbox`'s own re-validation at flush time, so a malformed event is refused the moment it would have been emitted; a thrown error here is caught by the round loop's own outer `catch`, above, and becomes a decided `pause{reason:'infrastructure'}` like any other unexpected failure on this path, never a crash.

`devReviewLoop`'s own outer `try`/`finally` calls `flushOutbox` one more time in that same `finally`, unconditionally, and clears the driver-lock pid record — **except for the two reasons named just below, where it deliberately does not**. Every explicit call site above already flushes before a normal `return` (a `publish`, a `pause`, a crash-recovery escalation); this is the one flush that is NOT conditional on reaching one of them.

**The loop's own exit sites are two: `publish`, and an explicit stop.** Every other failure the round loop can hit — a gate error, a dispatch error, a forge read error, any thrown exception on the driver's own path, a re-exec that cannot proceed — is a decided `pause`, never a re-thrown exception that ends the process. The round loop's own outer `catch` (wrapping `runRoundLoop`) used to log a `driver_exited` trace and re-throw, ending the invocation on ANY uncaught error from anywhere inside it — a `gh` call, `assessRound`, a rejected promise. It no longer does: the SAME trace is logged, but the error becomes `pause{reason:'infrastructure', detail: <the error's own message>}`, written and posted through the identical pause bookkeeping every other pause reason already uses (best-effort, like everything else in this paragraph — a forge write failing HERE too is swallowed, never a second chance to crash on the way out), and the function returns normally with that decision. `'infrastructure'` and `'stale_driver'` are the two reasons this can ever be — the loop's own "the mechanics stalled, not a review verdict" pauses (see "Infrastructure failures" and the re-exec section, below) — and for exactly these two, the outer `finally` skips `clearDriverLock`: the process is not done, it hit a recoverable hiccup, and clearing the lock would make that indistinguishable from a genuine, settled, Principal-decided pause (escalation, max_rounds, confidence, reappearance, no_push, objectives_changed, ruling_posted, brief_superseded, policy_changed — every one of which still clears the lock exactly as before). `task run --issue <n>` is the one command that revives a task in either state, dead lock or not, pause held or not.

## The per-task driver log (task-run-v1 task 15, O6)

Every driver — `task run` and `dev-review-loop` alike, since `task run` is a thin composition that calls `devReviewLoop` internally for the entire developer/reviewer dispatch — tees its own role-prefixed stream to one file: `~/.vinaya/loops/<owner>-<repo>/<issue>.log` (`apps/cli/src/lib/loop-log.ts`, the same `<owner>-<repo>`/`unresolved` directory convention `log-sink.ts`'s outbox already uses, under a separate `loops/` root rather than `outbox/` — this is human-readable narration, never a structured event a check reads). `devReviewLoop` resolves this path once per run, from the same `repo`/`task` every other per-run path already uses, and writes a `=== run started <ISO time> role=… pid=… run_id=… ===` marker before anything else — the delineation a file spanning several relaunches (a pause, a `--resume`, a stale-driver restart) needs to read as one continuous narration rather than an overwritten one. Nothing here ever truncates the file.

`dispatchRole` (`apps/cli/src/lib/dispatch.ts`) is the one place that actually writes to it: when the loop names a `roleLogPath` in its `DispatchOpts`, every lifecycle line it already writes to the terminal (`writeLifecycle` — heartbeats, timeout warnings, the tee-path announcement) and every rendered agent-event line are ALSO mirrored, plainly (no ANSI escape codes — a log file is read later, never through a TTY), into that file — alongside, never instead of, the existing per-dispatch `~/.vinaya/dispatch-output/<effectId>.log` raw-byte tee.

`vinaya task status <tranche> <n> --follow` (and `--issue <n> --follow`) tails this file live, `tail -f` style (`followLoopLog`, `loop-log.ts`): it prints whatever the file already holds, then polls for growth and prints only the new bytes, indefinitely — a file that does not exist yet (no driver has ever run) is simply polled until it appears, never refused. `--issue <n>` names the Issue directly; the `<tranche> <n>` form resolves it through the same read the ordinary single-task status view already uses. Either way, the state of any run is one command away, regardless of where it was launched.

## Rounds

Round 1's entry (`review-validity-v1` task 5, `#488`, O4) checks the forge before dispatching anything: an already-open pull request on the developer's branch means ATTACH — no developer is dispatched at all, the recorded session is read so a later round resumes it, and round 1 enters its gate directly. That read now goes through launch reconciliation (`recoverDeveloperLaunch`/`reconcileLaunch`, `dev-review-loop/developer-dispatch.ts` — `control-store-v1` task 3, O3): every seam that used to read the durable resume record blind (this attach, and the no-push/no-PR resumes in `afterDeveloperTurnBeforePrPoll`) first reconciles the developer's prior launch. A prior launch whose own child process is still alive on this host is `live` — a second worker is never spawned onto the same task; a required session that is genuinely gone (an attempt interrupted before its vendor session was ever bound) throws `LaunchContinuityLost`, which the loop's outer handler turns into a decided `pause{reason:'infrastructure'}` (an explicit pause, never a silent fresh start); a recoverable session — now including one bound on an INTERRUPTED attempt, since `dispatch.ts`'s launch record persists the session across the interruption (`control-store-v1` task 3, O1) — resumes that EXACT session. No launch record at all (the common case) falls back to the same durable resume-record read as before, unchanged. A branch that exists on the remote with no open PR yet resumes that same recorded session ONCE, instructed to open the PR through the validated path, and waits for it. Neither case starts a fresh developer. Only when the branch does not exist remotely at all does round 1 dispatch the developer fresh, brief read verbatim from the task Issue's frozen brief comment (`fetchFrozenBrief`), then wait for the PR it opens. `fetchFrozenBrief`, and every other reader of "the frozen brief" in this codebase, resolve through `@attalabs/aeg-core`'s `resolveNewestFrozenBrief` (task-run-v1 task 4, `#483`, O3): a Principal can correct a wrong frozen brief with `vinaya task brief <tranche> <n> --supersede --reason <text>`, which appends a new, higher-versioned `aeg:brief:v<k>` comment naming its predecessor and the reason rather than editing or deleting the original — the loop always reads the newest version, never the first one posted.

**The round journal is the task's, not this process's (task-run-v1 task 21, `#541`, O9).** `initialLoopState` starts `state.rounds` empty on every process start — a driver that attaches to a PR mid-loop used to publish a table that only ever showed its OWN rounds, even when the task had a longer real history (Origin, PR #536: five real rounds, the published table showed one, because the last driver journaled only its own). On the `existingPr` attach branch, `seedLoopHistory` calls `fetchLoopHistory` (`apps/cli/src/lib/dev-review-loop/journal-history.ts`) before this run logs a single event of its own: it gathers every `dev_review_loop` event this task has ever emitted — already-flushed `<!-- aeg:log:<runId>:<seqFrom>-<seqTo> -->`-marked comments on the task Issue (principal-authored only, the same trust boundary every other forge read in this driver already applies) plus whatever is still sitting unflushed in this machine's own local outbox — and replays them (`reconstructRounds`, `@attalabs/aeg-core`) into one `RoundRecord` per concluded round. Honest about what the log schema actually carries: `round_ended` has no per-severity finding breakdown and `verdicts_read` carries only a `blockers` count, so a reconstructed round's `countsBySeverity` holds only the `blocker` column (never a fabricated count for a severity the log never recorded) and `confidence` is always `null` — what's never dropped is the round's own existence, outcome, and diff stats, which is what the published table actually needs.

Applied only when the newest reconstructed round did NOT conclude green: a green round already published its verdicts and ended the loop, so re-invoking the driver against that same, still-open PR is meant to re-derive that SAME round from scratch, not invent a round that never happened — `assessRound` always APPENDS to `state.rounds`, never deduplicates by round number, so seeding a round this run is about to recompute live would double it. When it does apply, the reconstructed rounds also correct `round` itself (`nextRoundNumber`, never regressing the more-precise, locally-held `latestHeldRequestChanges` recovery above when both agree or the local one is ahead) — an attach with no locally-held request-changes file to recover from (a different machine, or local state already cleaned) no longer restarts numbering at 1 when the durable log shows real, unfinished prior rounds.

**Deliberately never called on `--resume` (PR #544, round 2 review, BLOCKER).** `resumeFrom.round` is the exact round the paused process already logged a `round_ended` for before it exited — that round is already the newest entry `fetchLoopHistory` would replay. Seeding it here too, then letting this same resumed run recompute and append that identical round number again, is the precise double-count the paragraph above guards against — the attach branch never hits it because attach always continues at `held.round + 1`, one past anything replayed, while resume deliberately continues AT `resumeFrom.round` to give the ruling's fix a chance in the same round. `state.rounds` starts empty on resume and accumulates only the rounds this process itself computes from the resume point forward; a resume that goes on to publish reports a published table scoped to this process's own rounds, not the task's full history.

**An ATTACH onto an existing PR also recovers a held REQUEST-CHANGES round, rather than resetting to round 1 (task-run-v1 task 3, `#482`, O4).** A restarted driver's in-memory `LoopState` carries no round history at all, but the outbox's own held-verdict files (`round-<k>-reviewer.md`/`round-<k>-security.md`, `writeHeldVerdict`) do: `latestHeldRequestChanges` reads the highest round with both files still on disk, re-parsed through the same extractors `publishRound` trusts, and treats it as recoverable ONLY when it reads REQUEST CHANGES (never falls back to an older round once the newest one reads clean or fails to parse — that's read as nothing to recover, the same as no held state at all). When the branch's current head has moved past that round's judged head, the driver advances straight to that round's own gate check at round `k+1` — the normal green-gate path from there dispatches round `k+1`'s reviewers, never redelivering round `k`'s findings to the developer. When the head has NOT moved, those findings are delivered once, exactly as a continuous run would; a second attach that still finds the same unchanged head — a marker file (`round-<k>-attach-redelivered`, alongside the held-verdict files) records that the first redelivery already happened — pauses `no_progress` instead of trying a third time (Origin: PR #529, where every attach after a fix push kept re-delivering round 1's stale findings and drifted into a confidence-collapse pause).

**The poll never starts against a branch the developer has not pushed (task-run-v1 task 13, `#508`, O1/O2/O3/O9).** The developer contract (`aeg-root/roles/developer.md`) states the push and the pull-request open are foreground steps — the developer's own turn does not end until `gh pr view` shows the pull request. The loop still checks rather than trusting this: after the fresh round-1 dispatch returns, `afterDeveloperTurnBeforePrPoll` reads the branch's remote head (`git ls-remote`) before ever polling for a pull request.

- No remote head at all, and a refusal/escalation comment (`<!-- aeg:developer:stop -->`, principal-authored) is posted on the task Issue: the loop ends AT ONCE with that reason — `pause{reason:'escalation'}`, posted on the Issue (there is no PR yet) — never entering the poll (O9). This is the origin bug (task #498, `#509`) generalized one step earlier: a developer that never even reaches the remote must not leave the loop waiting for a pull request nobody will ever open.
- No remote head, no stop comment: the loop resumes the SAME developer session ONCE, foreground, with the exact push-and-open commands — never a second resume for this (a repeat failure after the one resume is left to the poll's own bounded timeout, not a second dispatch).
- A remote head exists but no pull request yet (either originally, or after that one resume): resume once more to open it specifically, then poll.

Whichever path is taken, a poll that still gives up names everything it waited for — branch, the developer's own worktree HEAD if `.worktrees/<branch>` is locally readable, the remote head, and whether a pull request exists (O3) — so a principal reading the failure knows exactly which step was skipped, rather than the bare "no open PR appeared… within the poll budget" the original bug reports quoted.

1. **Gate.** `resolveHead`/`fetchCiConclusion` read the branch's live head and CI conclusion — never run locally (Traps: the mechanical gate is the CI system's own verdict, not a local re-run). `fetchCiConclusion` excludes the review gate's own check-run by name (`REVIEW_GATE_CHECK_RUN_NAME`, `review-gate-check-name.ts` — the one constant `check-review-gate.ts` also imports, never a second copy; `review-validity-v1` task 5, `#488`, O1) in every status, so a head with green CI and no verdicts yet reads green, never red because the gate itself hasn't posted one. A `principalOwed` core check (`CheckSpec.principalOwed` — `test-plan` today, the registry flag, never a name list; `review-validity-v1` task 15, `#532`, O1) whose only failures are the Principal's own unticked `[principal]` Test Plan boxes reads the same way: `vinaya check --all`'s own exit code (`isRunFailed`, `apps/cli/src/commands/check.ts`) excludes that check's failure from the run's aggregate verdict whenever every error it reported is `pending: true`, so the ONE GitHub check-run a bundled `scope: 'diff'` run reports under stays green and this gate never sees red for a box only the Principal can tick — enforcement of the unticked box itself lives at `review-gate` instead (O2), which refuses merge while it remains unticked; `test-plan` keeps grading the `[agent]` half and the plan's structure. A structural `test-plan` failure (no Test Plan section at all, a non-pending cause) still counts and still sends the developer back. **The gate also re-asserts the PR body's own `Premise:` pins at this same head** — `reassertPrBodyPremise` (`checks/bin/check-pr-premise-reassert.ts`), re-run every round against the LIVE PR body, never only at Step 0: a pin a later commit falsified (a symbol the head deleted since the brief was authored) reads exactly like a red mechanical check-run, its failing line(s) folded into the same `lastFailingChecks` the gate-red retry prompt already names — a stale premise is a developer finding sent back through the SAME retry path, never a reason for the driver itself to exit; a re-exec'd child re-asserts it again the moment it reaches its own first gate check, no separate re-exec-only path to fall out of sync with this one. A body with no `Premise:` block at all is unaffected, same as every PR before this task. Red sends the developer back for the same round, naming the failing check-run(s) — each by check name AND its own run id/`started_at` (`fetchFailingCheckRuns`/`describeFailingCheckRun`, `#607`, O3), so the evidence a pause is built from is auditable after the fact — never the review gate, which is excluded entirely, and never a bare "CI is red." `fetchFailingCheckRuns` reads the same already-deduped-to-the-newest-per-name list `fetchCiConclusion` does (`#595`'s own O3), so a failure a later same-named run has superseded with a pass never contributes to this list or to the gate's conclusion (`#607`, O1) — a genuinely failing CURRENT run still reads red and still sends the developer back exactly as before (`#607`, O2). After that dispatch the driver waits for the branch head to change (the same gate poll budget, `gatePollMaxAttempts`/`gatePollIntervalMs`) before reading the gate again — it never re-reads a still-unchanged head in a tight loop (`#479`: five re-dispatches in two minutes on one head). A developer turn that produces no push at all is one strike against a small, driver-owned bound (`MAX_GATE_STALLED_TURNS`, `dev-review-loop.ts`); consecutive strikes on one head that reach the bound end in `pause{reason:'infrastructure'}` naming the head and the failing check (never unbounded re-dispatch) — see "Driver-decided pauses," below, for why this reuses `'infrastructure'` rather than a dedicated reason. Green and round 1 goes straight to reviewers; green from round 2 on gates on developer confidence first (below).
2. **Reviewers.** Both roles are dispatched fresh every round (`dispatchRole` called anew — a reviewer session is never resumed; only the developer's is). Each reads facts-only (`renderReviewerPrompt`: objectives, Principal rulings, head, CI conclusion, the frozen brief's own source revision (`fetchSourceRevision` — task 4, `#483`, O2; the `NO_SOURCE_REVISION` sentinel on a brief from before this task that carries no `**Revision:**` line) — never developer- or PR-body-authored prose, `lintReviewerPrompt` enforces this) and writes `findings.txt`/`report.txt` to a driver-chosen work directory, plus `objectives.txt` whenever the task carries objectives (the prompt names the file only then; a task with no `## Objectives` section never asks for it). `resolveIssueObjectives` (`review-validity-v1` task 2, `#476`, O1) is the one source of the `OBJECTIVES:` fact and the version threaded through the round: the newest principal-authored `<!-- aeg:objectives:v<k> -->` edit comment when one exists — its own `Version:` line is read as-is, never recomputed, since `vinaya issue objectives edit` already wrote it from the exact list it spliced into the live Issue body — else the principal-authored frozen brief's verbatim copy of the Issue's `## Objectives` section, versioned by the same `objectivesOf`/`objectivesVersion` pair the merge gate calls on its own live-body read. Never the live Issue body directly (PR #445's security round: any collaborator can edit a body and thereby author every reviewer's prompt). `buildVerdictFromReport` derives the verdict from findings (never hand-typed) and renders the same `VERDICT:`/`Judged head:`/`Objectives version:`/`Ruling ordinal:`/`Brief hash:`/`Policy digest:` shape `review-post.ts` uses elsewhere, carrying the manifest the round was dispatched against and one `O<n>: MET | NOT MET` line per objective. Before it does, it runs the SAME `checkObjectiveIdCoverage` `review post` already applies to a human-posted verdict (`review-validity-v1` task 4, `#478`, O4): an `objectives.txt` missing an id, or carrying an extra one, refuses (`ReviewerReportParseFailure`, the same one-fresh-retry treatment a missing artifact gets) rather than yielding a verdict that silently under- or over-reports what the round actually judged — an under-reporting reviewer never yields a version-bound verdict. `writeHeldVerdict` holds it in the outbox — nothing is posted to the forge before green (Section 10 stop condition, tasks 4–5). A work directory still missing `findings.txt`/`report.txt` (or `objectives.txt` on a task that carries objectives) after the dispatch is an infrastructure outcome, never a clean verdict — an empty `findings.txt` is still clean, exactly as the reviewer contract promises (`review-validity-v1` task 1, `#475`, O1); see "Infrastructure failures," below.

   Right after both reviewers return — before either verdict is written to the outbox — the driver re-resolves objectives one more time and compares the version to the one the round was dispatched against (`review-validity-v1` task 2, `#476`, O3). A mismatch means a principal posted an objectives edit while this round's reviewers were running: both verdicts are discarded in memory, never held and never published, and the round ends in `pause{reason:'objectives_changed'}` (below) rather than judging the round against a list the reviewers never actually saw. The driver does the identical re-check for the newest principal ruling ordinal (`review-validity-v1` task 3, `#477`, O3): a mismatch there ends the round in `pause{reason:'ruling_posted'}` instead, for the identical reason — a ruling the reviewers never saw must not be judged against.

   **A `NOT MET` whose evidence is prose is reclassified before either verdict is even rendered.** `buildVerdictFromReport` runs every parsed `objectives.txt` line through `reclassifyProseOnlyNotMet` (`dev-review-loop/reviewer-dispatch.ts`): a `NOT MET` whose evidence is prose-located — `isProseLocation` (`@attalabs/aeg-core`, the SAME predicate `evaluateReviewFindings`'s body-located `MINOR` cap already applies to a finding's own `location` field, reused here over an objective's `evidence` field instead) reads it as naming only the PR body, a comment, or a role file — becomes `MET`, its evidence annotated `(prose note)`. This runs before the rendered `O<n>: MET | NOT MET` line is built and before the round's own `objectives` observation is assembled, so neither the posted verdict comment nor `assessRound`'s "any `NOT MET` objective is `changes_requested` regardless of findings" rule ever sees the reclassified line as unmet. A `NOT MET` naming a real source or test file is never touched — the same file-shape gate that protects a finding's location protects an objective's evidence here too.

   **The evidence report and the round marker comment are the driver's job now, never the Developer's.** Right after mergeability is confirmed and the round's head is resolved — before either reviewer is dispatched — the driver reads and clears the Developer's own `.vinaya-round-response` file from its worktree (`DEVELOPER_ROUND_RESPONSE_FILE_NAME`, best-effort: missing or malformed yields no citation, never a stall) and posts the round marker comment itself (`Head: <sha>`, `<!-- aeg:developer:round-<n> -->`, and a `FINDING_IDS:` line only when the Developer cited any) — the Developer's own turn ends at the push (`aeg-root/roles/developer.md`) and never posts this comment or runs `vinaya pr report --push` itself any more. `dispatchReviewer('reviewer', …)`, `dispatchReviewer('security', …)`, and the driver's own `runEvidenceReport` (the SAME `apps/cli/src/lib/pr-report-engine.ts` engine `vinaya pr report --push` calls, run in-process rather than shelled out to) all run inside one `Promise.all` — the report never waits on the reviewers, and the reviewers never wait on it. A report failure is logged to the driver's own role log and otherwise ignored: it is never a pause and never counted toward `no_progress` — the origin incident this fix closes was ten-plus minutes lost to exactly that report, run synchronously, blocking the loop on a single tool call. The merge gate's own `evidence-fresh` check, unaffected by this task, is what actually enforces a fresh `AEG:EVIDENCE` block at merge time; the driver's automatic call is what keeps that check from ever finding the block stale in the first place.
3. **Verdicts.** `assessRound` combines both verdicts. Clean (both APPROVE/PASS, every objective MET) → `publish`. An `ESCALATE` from either role → `pause{reason:'escalation'}`, immediately, before any verdict is ever held or posted. Otherwise the findings are relayed to the developer for another round.

Round numbering: `round` advances only when a genuine review round concludes `changes_requested` and hands back another developer dispatch. A mechanical-gate-red retry and the confidence rule's one-extra-turn both resubmit the same round number — advancing on every developer dispatch would make a CI hiccup on round 1 silently trigger the round-1-never-asks confidence question.

## The confidence rule

Round 1 never asks for confidence. From round 2 on, a green gate reads `.vinaya-confidence` (written by the developer per `CONFIDENCE_PROMPT_LINE`'s instruction) before reviewers are ever dispatched:

- absent, asked once already → `pause{reason:'confidence'}`; absent, first time → re-ask once.
- below 50, one extra turn not yet spent → one more developer turn (spent once, ever), no reviewer dispatch; below 50 again → `pause{reason:'confidence'}`.
- 50 or over → dispatch reviewers.

## The four exits

`assessRound` decides every exit — the driver never re-derives one:

| Exit | Trigger | `Decision` |
| --- | --- | --- |
| green | both verdicts clean, every objective MET | `publish` |
| stalled | a fingerprint resolved earlier reappears (`reappearance`); two consecutive rounds resolve nothing (`no_progress`) | `pause` |
| capped | round count exceeds `reviewPolicy.maxRounds` (`doctrine-fixes-v1` task 1, `#543`, O4 — repository policy, default 3, resolved once by the driver into `LoopConfig.maxRounds`; no longer a hardcoded constant) | `pause{reason:'max_rounds', detail:'max rounds: <n>'}` |
| escalated | either reviewer returns `ESCALATE` | `pause{reason:'escalation'}` |

The confidence rule's own collapse (`pause{reason:'confidence'}`) is a fifth practical pause path layered on top of "stalled," gating whether a round even reaches a verdict.

**Escalation closes the journal too (PR #544, round 2 review, BLOCKER).** `assessRound` (`packages/aeg-core/src/dev-review-loop/assess-round.ts`) now emits `journal_finalized{result:'stopped'}` on the `ESCALATE` path, the same as every other pause reason (`reappearance`, `no_progress`, `max_rounds`, `confidence`) already did — an escalation pause previously left the journal without a terminal event, the one pause reason `fetchLoopHistory`'s `actuallyPublished` check (O9, above) could not tell apart from a still-open task.

### Infrastructure failures (O1/O2, `review-validity-v1` task 1, `#475`) and driver-decided pauses (`review-validity-v1` task 5, `#488`, O2/O5)

A review role's dispatch is retried once, into a genuinely fresh work directory (never the failed attempt's own), if its directory is still missing a required artifact after the first attempt; a second miss on the same role, and a red-gate developer turn that produces no push `MAX_GATE_STALLED_TURNS` times in a row on one head, are both `pause{reason:'infrastructure'}` — the driver's own two "the loop's own mechanics stalled, not a review verdict" exits, distinguished from each other only by the pause's `detail` text (the role and missing artifact(s), or the head and the failing check-run(s)).

Neither corresponds to an `Observations` kind `assessRound` accepts, and this task's own declared Surface (Issue #488 §4) excludes `packages/aeg-core` — adding one, or a dedicated `PauseReason`, would mean editing it. `driverDecidedPauseEvents` (`dev-review-loop.ts`) instead hand-builds the exact same `stop_condition_met`/`paused`/`round_ended`/`journal_finalized` events every policy-decided pause gets, reusing the schema's existing, otherwise-unused `'principal_stop'` condition and generic `'principal_item'` paused-reason — never a new schema value — so a reader (or a machine parsing the outbox) sees a real, complete pause record either way. This closes a regression (PR #489 round 2, MAJOR): the reviewer-infrastructure pause used to be built by the driver's own hand-rolled `Decision`, skipping the log entirely. No verdict is held, none is published, and the round number does not advance (the same way a mechanical-gate-red retry never advances it). The pause comment names the failing role and the missing artifact(s), or the head and the failing check-run(s), it observed.

### Unpushed work is resumed once, then `no_push` (`doctrine-fixes-v1` task 1, `#543`, O2)

A gate-red retry or a conflict retry already waited for the branch's head to change before this task (above); if it doesn't, the driver now checks the developer's own worktree before charging the stall to the generic `MAX_GATE_STALLED_TURNS` bound: `git status --porcelain` (dirty files) and how many commits local `HEAD` sits ahead of its upstream, read fresh via `readUnpushedWorkDetail`. Either signal non-zero means the developer did real work and simply never pushed it — resumed ONCE, foreground, with a dedicated commit-and-push instruction (never the CI-red or conflict prompt, and never a second resume for this), recorded BOTH as a real `dev_review_loop` journal event (`unpushed_work_resume` — `branch`, `detail`; `packages/aeg-core/src/log/schema.ts`, round 2 review, MAJOR: only a PR comment used to carry this, invisible to `fetchLoopHistory`/`reconstructRounds`) and, unchanged, as its own marked PR comment (`<!-- aeg:loop:unpushed-work-resume -->`, idempotent per round+head like a pause comment). Still no new head after that resume is `pause{reason:'no_push'}` — a real `PauseReason` member (`packages/aeg-core/src/dev-review-loop/types.ts`), not a reuse of `'infrastructure'`, since a Principal reading the pause needs to tell "stopped after doing real, uncommitted-or-unpushed work" apart from "did nothing at all" — naming the branch and the dirty file(s) (or, worktree clean but commits ahead, saying so). A turn with neither dirty files nor commits ahead is the genuinely idle case and falls straight through to the existing `'infrastructure'` stall, unchanged. `readUnpushedWorkDetail`'s dirty-file list excludes the loop's own two control files by exact name (`.vinaya-confidence`, `.vinaya-round-response`) before either signal is checked — both are written by the developer's own turn at this driver's own instruction and read-and-cleared before this check ever runs again, so a turn that writes only one of them (a confidence line, a round-response citation, nothing else) is a clean turn, never real unpushed work.

This check runs only where a head-change wait already ran before this task (a CI-red retry or a conflict retry) — never the plain review-findings retry, whose own next `dispatch_reviewers` phase re-reads whatever head exists rather than waiting for one to CHANGE; extending it there would need every existing fixture for that path (there is no real push to wait for there today) to start simulating one.

### A reviewer report missing finding ids is resent once, then `report_uncitable` (`doctrine-fixes-v1` task 1, `#543`, O3)

`assessRound`'s `no_progress` exit (below) is derived by comparing finding ids between rounds — but the loop's own per-round `findings.txt` carries no reviewer-authored id at all by construction until this task: the driver used to number findings purely by their position in the file (`F1`, `F2`, …), which is not a stable identity across two SEPARATE dispatches. `renderReviewerDispatchPrompt` now also asks for a `FINDING_IDS:` line in `report.txt` — one id per `findings.txt` line, in the same order, comma-separated — whenever `findings.txt` is non-empty (an empty findings list has nothing to cite and is never sent back for it). `dispatchReviewer` checks this after a report parses successfully; a findings-carrying report with no matching `FINDING_IDS:` line is sent back ONCE — a fresh dispatch (never `--resume`: this file's own module doc states, as a load-bearing invariant, that a reviewer session is never resumed, only the developer's), into a fresh work directory, its actual path named in the resend prompt exactly as the first dispatch's own prompt names its own — with a targeted instruction to cite ids. Still uncitable after that resend is recorded once as a marked PR comment (`<!-- aeg:loop:report-uncitable -->`, naming the role(s)) and threaded into that round's `Observations` as `findingsUncitable: true`: `assessRound` never derives `no_progress` from an uncitable round's id comparison (every other stop condition — reappearance, confidence collapse, max rounds, escalation — is unaffected), and the round's own `previousResolvedEmpty` streak carries the PRIOR value forward unchanged rather than starting or extending it, so a real two-consecutive-round stall either side of an uncitable round is still caught.

### Objectives changed mid-round (`review-validity-v1` task 2, `#476`, O3)

`'objectives_changed'` is a real `PauseReason` member (`packages/aeg-core/src/dev-review-loop/types.ts`) — this task's own declared Surface includes that package, unlike the driver-decided pauses above. The driver still decides it itself, the same way it decides `'infrastructure'`: comparing two `resolveIssueObjectives` reads (the one taken before dispatching this round's reviewers, the one taken right after both return) is not something `assessRound` can do from an `Observations` value, so the comparison lives in `dev-review-loop.ts`, and `driverDecidedPauseEvents` logs it through the same reused event shape. The pause's `detail` names the version the round was dispatched against, the version now current, and the exact `vinaya issue objectives edit` invocation that moved it — reconstructed by `describeObjectivesEdit` from the edit-audit comment's own `Previous:`/`Now:`/`Reason:` lines, never executed. As with the infrastructure pauses above, no verdict is held and none is published for that round, and the round number does not advance.

### Ruling posted mid-round (`review-validity-v1` task 3, `#477`, O3)

`'ruling_posted'` is the ruling-ordinal twin of `'objectives_changed'` above, same `PauseReason` member shape, same detection site, same reason for living in `dev-review-loop.ts` rather than `assessRound`: the driver compares the newest principal ruling ordinal it resolved when it dispatched this round's reviewers (`fetchNewestRulingOrdinal`, captured into `facts.rulingOrdinal`) against the ordinal it resolves right after both return, before either verdict is held. A mismatch means a principal posted a ruling while this round's reviewers were running — that round's verdicts are discarded in memory the same way (never held, never published), and the round ends in `pause{reason:'ruling_posted'}`, its `detail` naming the ordinal the round was dispatched against, the ordinal now current, and the ruling's own marker identifier (`<pr>-<k>`). No reconstructed command here — unlike an objectives edit, a ruling carries no replayable invocation, only its identifier and content. The next round's reviewers see the new ruling automatically: `dispatch_reviewers` re-resolves both `rulings` and `rulingOrdinal` fresh at the top of every round, mid-round check included.

### A conflicting head is sent back to the developer, never to a reviewer (task-run-v1 task 13, `#508`, O4/O5/O6/O7)

Mergeability is a forge fact the driver reads, never re-derives: `gh pr view <n> --json mergeable` returns `MERGEABLE`, `CONFLICTING`, or `UNKNOWN` (the forge still computing it — polled within the existing gate poll budget, never read as clean and never as conflicting, O7). The driver reads it TWICE:

- **Before dispatching reviewers** (O4): a `CONFLICTING` head means no reviewer starts and no CI is waited on for that head — the round instead routes back into the developer-dispatch branch with the loop's own conflict prompt, naming the conflicting file(s) (computed locally with `git merge-tree --write-tree`, since the forge's `mergeable` field alone doesn't name them). This reuses the SAME head-change-wait and `MAX_GATE_STALLED_TURNS` bound the CI-red retry already has — a conflict that never resolves ends in `pause{reason:'infrastructure'}`, its detail naming the head and the unresolved file(s), the same driver-decided-pause shape "Infrastructure failures," above, already documents.
- **Before publication** (O5): reviewers can run long enough that a clean head falls into conflict with the base while they worked. A branch found `CONFLICTING` at this second read has its held verdicts for that round discarded (deleted from the outbox, never posted) and the completion events already queued for that publish are dropped; the developer is resumed with the same conflict prompt, and the round number does not advance — the NEXT reviewer dispatch judges the resolved head.

The developer contract (`aeg-root/roles/developer.md`, O6) states the mirror image: the developer's own turn does not end with the branch behind the base in a way that conflicts — merge or rebase and resolve before pushing, never after. The loop's conflict prompt is what a developer sees if it ends its turn without having done this.

### A stale driver re-execs in place, and pauses only if that fails (task-run-v1 task 13, `#508`, O8; re-exec added by task-run-v1 task 15, O7)

`devReviewLoop` records the base branch's head once, at the very start of a run (fresh or `--resume`), and re-reads it at the top of every iteration of the round loop thereafter. A base that has moved since — and whose new commits touch this driver's own code (`DRIVER_OWNED_PATHS`: `apps/cli/src/lib/dev-review-loop.ts`, `apps/cli/src/lib/dev-review-loop/` — gate reading, reviewer dispatch, round assessment, publication, pause/resume, developer dispatch — `apps/cli/src/commands/review-post.ts`, or any of `packages/aeg-core/src`) — is a stale driver: it is, by construction, still executing the OLD driver's code even after a fix to it merges, and would otherwise keep judging rounds against a gate the new code has already changed the rules for, then publish a verdict the updated gate refuses.

Rather than handing this to a human, `checkStaleDriver` re-execs in place: it pulls the default branch (`git pull --ff-only origin main`), then re-spawns the exact same interpreter and entry script it was itself started with, reattaching to the same task with the same arguments — `dev-review-loop --resume <pr> --agent <vendor>` when this run itself started that way, `dev-review-loop --task <n> --agent <vendor>` otherwise (the loop's own round-1 entry already treats either form as "attach if a PR/pause state exists, start fresh otherwise," so a task-run-started process reattaches through this same door). The re-exec inherits stdio, so its output reaches whatever terminal or log was watching the original process; the original process then exits with the child's own exit code, handing off entirely — a moved base costs a restart, never a hand.

`pause{reason:'stale_driver'}`, naming both shas, is reserved for when the re-exec attempt ITSELF fails — the pull, or the spawn — never for the staleness alone. This is `packages/aeg-core`'s one `PauseReason` member the originating task added (in-Surface per that task's own blast-radius-ack, unlike the driver-decided pauses above); it is now reachable only along this narrower failure path.

**The lock hands off to the child before the spawn, not after (`#548`, O1).** A defect observed live (PR `#547`, 2026-09-12): the parent's own driver-lock record was still on disk, still naming its own live pid, at the exact moment `reexecSelf` spawned the child — the child's own entry-gate lock check (above) read that record, found it alive, and refused to start with "a driver is already running," while the parent (blocked in `spawnSync`, waiting for a child that never started) went on to exit with the child's non-zero code. Both processes ended; nothing paused, nothing posted — a pull request sat with green CI and no reviewers for six hours. The fix is ordering, not a new lease: `checkStaleDriver` now clears its own lock record (`clearDriverLock`) immediately before calling `reexecSelf`, synchronously, in the same tick — the child's entry-gate check then finds no record at all and starts normally, writing its own record under its own pid the same way any fresh invocation does. If the spawn itself never starts (`reexecSelf` returns `null` — the pull succeeded, but the interpreter could not be re-invoked), the parent re-writes its own lock record before falling through to the `pause{reason:'stale_driver'}` path above, since it is still the process driving this task.

**A driver that exits with no decision on record still leaves a trace, inside this task's Surface (`#548`, O2).** A genuinely new forge journal-event kind for this needs a `packages/aeg-core` schema change, out of this task's declared Surface, and is left for a later task with that Surface. What stays in-Surface: the SAME human-readable role log `~/.vinaya/loops/<owner>-<repo>/<issue>.log` (`loop-log.ts`) that `task status --follow` already tails gets one more line, `[dev-review-loop] driver_exited: reason=<reexec|error|signal> last_decision=<...>`, from exactly three call sites — right before the reexec-success `exitProcess` above, inside the round loop's own outer `catch` for a genuinely uncaught error, and from `SIGTERM`/`SIGINT` handlers registered once the round loop's own state exists — guarded so at most one line is ever written per run (`exitTraceWritten`). None of the three sites fire on a normal `pause`/`publish` return, which is what makes the line diagnostic rather than routine. `task-status.ts`'s `deriveLoopState` reads it back: a driver-lock record naming a DEAD pid — itself the signal that the last run never reached its own cleanup — now checks the role log for this trace before falling through to the published/paused reading, and reports a new `exited` state (`kind: 'exited', reason, lastDecision`) when one exists, rendered by both `vinaya task status --issue <n>` and `<tranche> <n>`.

## Which severities block is repository policy (`review-validity-v1` task 8, `#506`)

`buildVerdictFromReport` (`apps/cli/src/lib/dev-review-loop.ts`) derives a round's reviewer/security verdict from the dispatched role's own findings via `deriveCodeReviewVerdict`/`deriveSecurityVerdict` (`apps/cli/src/commands/review-post.ts`), which call `@attalabs/aeg-core`'s pure `evaluateCodeReview`/`evaluateSecurityReview` against `policy` — resolved ONCE per loop run, from the default branch's `vinaya.config.json` (`resolveReviewPolicy(loadTrustAnchorConfig())`), never from the PR's own checkout. `assessRound` (`packages/aeg-core/src/dev-review-loop/`) is unchanged: it still reads only the already-derived `VerdictObservation.verdict`/`objectives` — the policy threshold that decided that value lives entirely in the driver, never in the pure decision layer, matching this file's own layering (`assessRound` is decision logic; the driver turns facts into observations). `publishRound`'s own re-check, below, is the same evaluator applied a second time, against the posted comment's own FINDINGS block, before treating the round as published.

## Publication (O1, task 6)

At `publish`, `publishRound` (`apps/cli/src/lib/dev-review-loop.ts`) posts, through this repo's `gh pr comment` forge-write mechanics, in order: the round's held reviewer verdict, the held security verdict, then one summary comment from `renderSummary` (`@attalabs/aeg-core`) built from the loop's own round records. The round marker comment ("Reviewers," above) is a separate, earlier post — at dispatch time, not publication — and is not one of these three. Each verdict post is re-read straight back off the PR and re-parsed through `extractCodeReviewVerdict`/`extractSecurityReviewVerdict` — the SAME extractors the merge gate itself calls — and refused (thrown) if it does not resolve cleanly to the round's judged head. It is then re-evaluated against `policy` (task 8, `#506`, O3): a posted comment whose `VERDICT:` line reads APPROVE/PASS but whose own FINDINGS block carries a finding at or above the threshold is refused, never published — a reviewer's own clean-looking verdict never overrides the evaluator. The summary is checked BEFORE it is posted: both extractors run over the rendered text, and a summary that resolves as a real verdict through either one is refused rather than posted (`renderSummary`'s own contract is no `VERDICT:`/`Judged head:`/`Objectives version:`/`Ruling ordinal:` line; this is re-verified live rather than trusted).

Idempotency: each of the three posts is wrapped in `postForgeEffectOnce`, which records an effect id in the outbox as `started` before the `gh` call and rewrites it `posted` (with the returned URL) right after — mirroring `dispatch.ts`'s own effect-id-before/checked-after discipline, adapted to a comment post since `DevReviewLoopEvent` carries no `effect_id` field of its own. A rerun that finds an already-`posted` record for a given post returns its recorded URL without calling `gh` again — nothing is posted twice.

Supersession (editing a posted verdict, or marking one superseded after a later push) is out of `dev-review-loop-v1`'s scope: nothing is ever posted before green, so there is nothing to supersede in v1.

## The review-input manifest and its equivalence (`review-validity-v1` task 4, `#478`)

Before dispatching reviewers, the driver builds ONE `ReviewInputManifest` (`packages/aeg-core/src/review-input-manifest.ts`) from forge facts: the round's candidate head, its **base identity** (`baseSha`, `origin/main`'s tip — `control-store-v1` task 5, `#555`, O1), the frozen brief's own hash (`briefHash`, a `sha256` of its posted content — moved here from `dispatch-task.ts` so the read side and the write side share one implementation), the objectives version, the newest principal ruling ordinal, and the effective review policy's digest (`policyDigest`, which folds in the round-policy field `maxRounds` — the COMPLETE effective policy identity, `#555`, O1). This manifest — never separate ad hoc fields threaded past it — is the only source of `renderReviewerPrompt`'s `HEAD:` line (`ReviewerPromptFacts.manifest`) and of every structural line `buildVerdictFromReport` renders into a round's verdict/escalation comment (`Judged head:`, `Objectives version:`, `Ruling ordinal:`, `Brief hash:`, `Policy digest:`, `Judged base:` — the last two of those first four and `Judged base:` rendering unconditionally, `Brief hash:`/`Judged base:` as the literal `(none)` when no frozen brief / no base was resolvable, the same non-hex placeholder the gate's own extractor reads back as "nothing to bind"). `Judged base:` renders LAST of the structural head lines, appended after `Policy digest:`, so it never shifts the lines above out of the exact read windows their extractors pin.

**Parent-built manifest record in the control store (`#555`, O1).** The same manifest the round is dispatched against is persisted as a durable `manifest` record in `control-store-v1`'s store (`packages/aeg-core/src/control-store/`, a fifth record kind beside run/input/ownership/transition), built by the parent in `dev-review-loop/reviewer-dispatch.ts` (`buildManifestRecord`/`persistManifestRecord`) before reviewers dispatch. The record carries repository and work identity (the PR/branch this round belongs to) on top of the binding manifest — one immutable snapshot per `(task, round)`, a durable policy history keyed by round. It is written with the store's atomic, torn-write-free discipline but is NOT epoch-fenced (unlike `writeRun`/`writeInput`): a per-round snapshot is not a mutable state transition two owners could race on, and the driver's own cutover to acquired-epoch ownership is separate, later adoption work. Persisting it is best-effort — a snapshot that cannot be written never fails a round, because the echoed-comment binding is what actually gates a verdict.

**One comparison, three callers (O2/O3).** `compareManifest` — the candidate head/base pair bound together under the bounded acceptance rule below, then `briefHash`, `objectivesVersion`, `rulingOrdinal`, `policyDigest` each their own field — is the SAME function all three binding readers call: `checkReviewGate` (the merge gate), the driver's own pre-hold self-check, and `publishRound` (`dev-review-loop/publication.ts`), which now binds each posted verdict against the round's manifest on EVERY field, not just the head it re-checks (`#555`, O3). No field is bound on one side and ignored on the other: whatever the gate checks against a verdict comment's echoed lines, the loop and publication check too. The "echo" is never trusted as provenance either way — it is the PARENT's own dispatch-time fact, stamped into the rendered comment (or, for the loop's own same-process check, simply the in-memory manifest via `manifestAsEchoed`) and read back only to confirm a comment still covers the CURRENT manifest.

Right after both reviewers return — before either verdict is written to the outbox — the driver re-resolves the current manifest (objectives, newest ruling ordinal, and the frozen brief's hash, all freshly re-read; the policy is resolved once per loop run and so never drifts within a single run) and calls `compareManifest` against the manifest the round was dispatched with. A mismatch discards both verdicts in memory (never held, never published) and ends the round in one of: `'objectives_changed'`, `'ruling_posted'`, `'brief_superseded'` (a Planner superseded the frozen brief mid-round — same shape, new in this task), or `'policy_changed'` (the digest moved — reachable today only if a future change makes the loop's own policy read live, included for symmetry with the gate, which DOES re-resolve policy fresh on every run). See "Objectives changed mid-round" and "Ruling posted mid-round," above, for the two pre-existing reasons' own detail shape — `'brief_superseded'`/`'policy_changed'` follow the identical pattern (old value, new value, named in the pause detail).

**The same-patch rebase equivalence, base identity, and the narrowed acceptance.** A verdict judged one head still counts against a DIFFERENT current head when `patchIdOf` (`git patch-id --stable` between the PR's base and each sha) resolves the same value for both — a merge from `main`, or a rebase, that changes not one line of the PR's own patch does not void an already-cast verdict; only a change to the patch itself does. The `#555` narrowed acceptance, documented explicitly (Traps to avoid: "same patch text on a new base is not automatically equivalent"): base identity is now bound, but as a BOUNDED rule, not a sixth always-checked equality. When the candidate binds by an EXACT head sha, the base is required to match too — a base-only change (identical candidate, moved base) now INVALIDATES where it silently kept before. When the candidate binds by PATCH IDENTITY (a genuine equivalent rebase, the diff proven byte-identical), a base move is TOLERATED — the reviewer judged the patch, not the base. So: an equivalent rebase KEEPS the verdict; a base-only change REFUSES it. The stated limit, unchanged: a base that moved under an identical patch can still hide a semantic conflict the earlier review never saw; CI at the new head — which the gate already requires green — is the guard for that, not a re-review. `git patch-id --stable` also ignores whitespace, so a whitespace-only push keeps the verdict too — deliberate for reformatting, and not free (whitespace can be semantic in some languages), but every non-whitespace change still drops the verdict correctly.

**Formerly deferred, now landed (`#555`).** Base identity and a durable policy history were named in the execution contract but waited for `control-store-v1`'s durable store. That store is now built AND adopted for the manifest record (above): base identity (`baseSha`) is bound under the narrowed acceptance rule, the round-policy field (`maxRounds`) is folded into the policy identity, and the per-round manifest snapshot persisted in the control store IS the durable policy history. What stays deferred is the DRIVER's own wholesale cutover to acquired-epoch ownership (replacing the pid-lock and the pause-state/effect side files) — separate, later adoption work, not widened here.

## Pause and `--resume` (O2, task 6)

At `pause{reason}`, the driver writes the round's held state (task, round, judged head, branch, PR number, reason, and — for `'infrastructure'` (the reviewer case, the gate-stalled-head case, and the conflict-never-resolved case; see above), `'no_push'` (the branch and the dirty file(s) observed after the one unpushed-work resume; see above), `'max_rounds'` (the configured `reviewPolicy.maxRounds` value; see "The four exits," above), `'objectives_changed'` (the old version, the new version, and the superseding command; see above), `'ruling_posted'` (the old ordinal, the new ordinal, and the ruling's marker identifier; see above), `'stale_driver'` (both shas; see above), `'brief_superseded'` (the old and new brief hash; see above), or `'policy_changed'` (the old and new policy digest; see above) — the detail it observed) to the outbox, then posts one comment on the PR marked `<!-- aeg:loop:paused:<reason> -->`, carrying the reason (plus that same detail, where one exists) and the exact resume command (`vinaya dev-review-loop --resume <pr>`, the real PR number substituted in). The pause comment carries no verdict grammar. The CLI command exits non-zero — the process-level signal an unattended dispatcher watches for.

The one exception is O9's before-any-push escalation (above): there is no PR yet, so that pause is posted on the task Issue instead, and its printed resume command is `vinaya task run <tranche> <n>` rather than a PR-anchored `--resume`.

`--resume <pr>`:

1. Reads the PR's body for its `Closes #N` reference to find the task.
2. Reads that task's held pause state from the outbox; refuses if none exists.
3. Requires a Principal-authored ruling comment on the PR (`fetchRulings`, non-empty) — refuses if none exists yet, UNLESS the held reason is `'infrastructure'`: the driver's own recoverable hiccup, never a human decision point (same treatment `'infrastructure'`/`'stale_driver'` already get from the driver-lock cleanup above), so `--resume` continues it on the bare command. Every other reason still requires one. A moved head on an infrastructure resume keeps the held round as-is (there is no ruling to re-derive a round-cap override from).
4. Re-resolves the PR branch's live head and compares it to the held state's recorded head.
5. **Head unchanged**: re-enters the round loop at the held round, dispatching the developer fresh with the Principal's ruling text as context instead of reviewer findings. This path deliberately re-dispatches fresh rather than reconciling a prior launch: a `--resume` after a Principal ruling is a new turn ON that ruling, not a continuation of the pre-pause session. (The vendor session id itself IS now durable across a restart — `dispatch.ts`'s launch record persists it, `control-store-v1` task 3, O1 — and the round-1 attach/no-push seams above DO resume it through reconciliation; the `--resume` ruling path is the one place that intentionally does not.)
6. **Head moved (task-run-v1 task 15, O8)**: accepted, never refused — "a ruling followed by a fix push" (the developer already acted on the ruling before `--resume` ran) is the normal case, not an error. The ruling is itself the round-cap override it declares: the round counter restarts at the ruling's own newest ordinal (`fetchNewestRulingOrdinal`) rather than continuing from the held round, which may already sit past the round cap and would otherwise re-trigger the very pause `--resume` exists to lift. No developer is dispatched on this pass at all (it already pushed) — the loop goes straight to the mergeable/CI-gate check and, once green, dispatches reviewers directly on the new head, exactly like a fresh round-1 attach to an already-open PR. No outbox state is ever reset by hand to reach this path.

**Every prompt a RESUMED developer session receives names the task, branch, worktree, and head (task-run-v1 task 21, `#541`, O11).** `dispatchDeveloper` prepends a small context block — `Resuming task Issue #<n>.` / `Branch: `<branch>`` / `Worktree: `<path>`` / `Remote head: <sha>` — to every prompt sent when `devResumeId` is already set (every dispatch after round 1's own genuinely fresh one, whether that resume happens later in the SAME process or after a relaunch): the push-and-open prompt, the open-the-PR prompt, the conflict prompt, the gate-red retry (which also now names the exact `git push` command rather than a bare "fix and push"), the round-findings/ruling prompt, and the confidence re-ask. Origin (task #538): a loop resumed the developer to open its pull request without naming the branch, and with forty stale worktrees present on the machine the session asked "which branch?" and ended its turn — a resumed session on a shared machine has no other way to know which of many worktrees this run means.

**v1 accepted loss:** resume re-enters with a fresh `LoopState` at the held round number — the round number itself governs the confidence rule's round ≥ 2 branching correctly, but (task 21, O9, above — deliberately NOT applied on `--resume`, see the double-count hazard noted there) the round history is not reconstructed on resume, so neither is the fingerprint/finding-identity memory (`lastIds`, `previousResolvedEmpty`) a full crash-recoverable journal would carry across the pause boundary — the log schema `round_ended`/`verdicts_read` carry no per-finding-id record to replay in any case. A stall trigger that depends on cross-round finding identity (reappearance, no-progress) resets at a resume. No infrastructure exists yet to serialize `LoopState`'s `Map`-typed fields across a process restart; building it is out of this task's boundary.

## The control store (`control-store-v1` task 1, Issue #551) — built; the manifest record now adopted (`#555`)

The "Formerly deferred, now landed" paragraph above named the gap: base identity and a durable policy history waited on a real durable store, because every side file this driver reads and writes today — `driver.pid.json`, `pause-state.json`, the `effect-<key>.json` idempotency records (`apps/cli/src/lib/dev-review-loop/pause-resume.ts`, `publication.ts`) — is unchecked JSON with a plain overwrite, and the one-driver-per-task guard is check-then-write pid liveness (above, "One driver per task"), never a fenced ownership token. `packages/aeg-core/src/control-store/` is that store, landed as a standalone library: four versioned record kinds (run, input, ownership, transition — `records.ts`), a strict parser that refuses an unknown version or torn content as **corrupt**, never as **absent** (the exact defect class every side file above shares, each wrapping `JSON.parse` in `catch { return null }`), one local storage implementation (`local.ts`) with atomic durable writes and an ownership epoch fenced at publish time: an ordinary overwrite writes its full content to a private temp file, `fsync`s it, then `rename`s it into place; an exclusive claim (an ownership epoch, a transition sequence slot) does the same `fsync`ed temp-file write, then publishes with a single `linkSync` — never `O_CREAT|O_EXCL` directly on the final `epoch-<n>.json` name, which would create that name before its content exists and let a second, genuinely concurrent claimant observe it mid-write. Two callers racing from the same observed epoch contend for the identical final name at that one `linkSync`, and the loser's later write is refused inside the store itself, not left to a caller to remember to check — and a one-time migration (`migration.ts`) from the legacy side files above, which refuses rather than guesses whenever ownership would be ambiguous (a legacy driver whose pid still answers a liveness probe, or a task that already holds a control-store epoch).

**Decision recorded here, per that task's own traps-to-avoid:** atomic files (temp file plus `rename` for an overwrite, temp file plus `link` for an exclusive claim) were chosen over a transactional database. This store's only real concurrency requirement is one exclusive owner per task, on one machine — a filesystem's own atomic-rename and atomic-link guarantees already meet it, and a database engine would be the "distributed coordination" the brief says not to introduce for a single-machine guard. PID liveness (`isDriverPidAlive`, above) is deliberately NOT this store's ownership model — it proves a process with that pid still runs, never that it still owns the task; the epoch fence replaces it with a content-verifiable fact instead.

**The manifest record is the first adopted piece (`#555`); the rest is not yet wired.** `control-store-v1` task 1 built and unit-tested the store and its migration path (`packages/aeg-core/src/control-store/*.test.ts`). Task 5 adds a fifth record kind — the `manifest` snapshot (`records.ts`, `writeManifest`/`readManifest` in `local.ts`) — and wires the driver to persist it per round (`dev-review-loop/reviewer-dispatch.ts`'s `persistManifestRecord`, called from `dev-review-loop.ts` before reviewers dispatch); that is the manifest half of "somewhere durable to live" the deferral named. What is still NOT wired: `dev-review-loop.ts` and `pause-resume.ts` continue to read and write the `driver.pid.json`/`pause-state.json`/`effect-<key>.json` side files, unchanged. Cutting the driver's own ownership over — replacing the pid-lock guard with an acquired epoch, and the pause-state/effect-record side files with control-store writes — is later adoption work, not this task's; that is why the manifest write above is deliberately not epoch-fenced.

**Partial adoption (`control-store-v1` task 2, Issue #552): the `effect-<key>.json` idempotency half only.** `apps/cli/src/lib/effects.ts`'s `EffectExecutor` replaced the `effect-<key>.json` local-flag half of the paragraph above with a new control-store `effect` record kind — for the two writers named there, `pause-resume.ts`'s `postIssuePauseComment`/`postPauseComment` and `publication.ts`'s `publishRound`, which now persist an effect's identity through the store before ever posting, and reconcile against the forge before retrying a `'started'`-but-unconfirmed one, rather than trusting a local `'posted'` flag alone. `driver.pid.json` and `pause-state.json` are untouched — the one-driver-per-task guard is still check-then-write pid liveness, and a pause's own durable state is still the legacy side file — and `dev-review-loop.ts`'s own three other `postForgeEffectOnce` call sites (`unpushed-work-resume`, `developer-round-comment`, `report-uncitable`) are untouched too. The epoch this executor fences each write against is acquired fresh per call, not the driver-wide acquired epoch the "Cutting the driver over" paragraph above describes — that broader cutover remains later adoption work.

### Durable launch identity and recovery (`control-store-v1` task 3, Issue #553)

Task 3 gives role launches durable identities and truthful outcomes, WITHOUT yet cutting the driver over to the control store's ownership epochs (that remains the deferred adoption above). Three pieces:

- **Launch intent persisted before spawn, session bound as soon as observable (O1).** `dispatchRole` (`apps/cli/src/lib/dispatch.ts`) writes a durable **launch record** — run id, a per-scope attempt counter, role, the child pid, and the vendor session id — to the same machine-local `~/.vinaya/dispatch-resume/<repo>/<role>-<agent>-<scope>.json` file the resume record already used, BEFORE it spawns; it stamps the child pid the instant `spawn` returns, binds the session id the moment the stream first reports it (not only at a clean exit), and marks the record `interrupted` — never deletes it — on a timeout, crash, or refusal. So an attempt the driver's own death interrupts mid-turn keeps its session for recovery instead of losing it (the "failed attempts can lose session identity" defect, closed). This launch record is deliberately the launcher's OWN machine-local file, not a control-store ownership record: the generic launcher claims no task epoch (adoption deferred, above), and no strict versioned schema — the log's `DispatchOutcomeSchema`, or `control-store-v1`'s own records — carries a `role`/`attempt`/vendor-`sessionId` field. `readResumeRecord` is now a bound-session view over this record; `readLaunchRecord` exposes its full lifecycle with the same corrupt-vs-absent read `control-store-v1`'s `ParsedRecord` established.

- **A parent-validated outcome vocabulary (O2).** `normalizeOutcome` (`packages/aeg-core/src/control-store/outcomes.ts`) classifies a launch into `completed`, `incomplete`, `infrastructure-failed`, `timed-out`, `cancelled`, or `capability-refused`. The `completed`/`incomplete` split is decided entirely by whether the required artifacts exist and the declared postconditions hold — exit code is carried as input only, never the decider, so a process that exits 0 having produced nothing reads `incomplete`, never `completed`. Manner-of-death signals take precedence over the artifact read, so a killed or refused attempt is never blamed on the task. Built and unit-tested here; recovery below is its first consumer, with wider driver adoption deferred alongside the control-store cutover.

- **Recovery reconciles a prior launch before continuing (O3).** `reconcileLaunch` (pure) and `recoverDeveloperLaunch` (its disk-and-pid-reading wrapper) in `dev-review-loop/developer-dispatch.ts` turn a prior launch into one disposition: `live` (its child still runs on this host — never spawn a second worker onto the same task), `finished`, `resume` (continuity required and the exact session available — resume THAT session), `pause` (continuity required but the session gone — pause explicitly), or `none`. The developer's continuity is required; a reviewer's is never (a reviewer is always dispatched fresh, never resumed because the developer resumes — Traps to avoid), so no reviewer path calls this. The driver's round-1 attach and `afterDeveloperTurnBeforePrPoll` resume seams call `reconcileDeveloperResume`, which acts on that disposition — throwing `LaunchContinuityLost` for `live`/`pause` (the loop's outer handler turns it into the decided `pause{reason:'infrastructure'}` every thrown driver-path failure already becomes, so no new pause plumbing or `PauseReason` is added) and setting the exact session for `resume`. `none` — the common case, the only one every existing fixture reaches with its scratch `$HOME` — falls back to the unchanged durable resume-record read.

## A task-operator read interface over these same records (task-operator-v1 task 1)

`apps/cli/src/lib/task-tools/read.ts` reads the pause record, held verdicts and effect markers this file documents — never through a second write path, never through `ps`. Two functions:

- `readTaskLoopStateObserved(root, task)` wraps `task-status.ts`'s own `deriveLoopState` in a timestamp and a `fresh`/`unknown` marker — `unknown` only for `no_driver` (no record of any kind exists yet); every other `TaskLoopState` kind is `deriveLoopState`'s current, fresh answer, since it already resolves a superseded pause into `published` internally.
- `readEscalationPacket(root, task)` reads `pause-state.json` directly — independent of `deriveLoopState` — so it can tell a pause that predates the outbox's own newest published round (`freshness: 'stale'`) apart from the live one (`'fresh'`) apart from no pause ever recorded (`null`). Its result carries the pause's own `reason`/`detail`/`inputs` (task, round, head, branch, PR number — all already on the pause record, this file's own "Pause and `--resume`" section above), the last round's held verdict lines as `evidence`, and a fixed per-reason `requestedAuthority`/`attemptedRecovery`/`permittedNextActions` — `self` for the five driver-decided reasons this file already names (`objectives_changed`, `ruling_posted`, `stale_driver`, `brief_superseded`, `policy_changed` — the loop resumes on its own), `operator` for the two environment-shaped ones (`infrastructure`, `no_push`), `principal` for the four O2-exit reasons that need real judgment (`escalation`, `max_rounds`, `no_progress`, `confidence`, `reappearance`).

`apps/cli/src/lib/task-tools/handlers.ts` binds these to the catalog's `task_status`/`task_escalation_read` tools (`packages/aeg-core/src/task-tools.ts`), composing them with `task-status.ts`'s forge-touching identity/PR lookup. `task_resume`/`task_cancel` still refuse every call unconditionally — no process start, no forge write. `apps/cli/src/lib/task-tools/router.ts` classifies a caller's free-text intent to the one tool that answers it, so an agent surface built on this catalog later never routes a read request into a mutating handler.

## The Operator's start path — `task_start` over `runTask`

`task_start` (`apps/cli/src/lib/task-tools/start.ts`) is the one mutating tool this tranche lands. It wraps the existing `runTask` composition (`task-run.ts`, the same `vinaya task run` the CLI already exposes) rather than adding a second execution path: the tool records a durable claim, then launches `runTask` **detached** (default `vinaya task run <tranche> <n>`, overridable through `VINAYA_TASK_RUN_COMMAND` for an operator who wraps the launch in a supervisor) and returns the durable run identity immediately, while the run continues on its own. The run's PR is discoverable through `task_status` exactly as any other run's is.

Three properties are the point, and each is a deliberate limit:

- **An authenticated caller, from the invocation context.** The tool refuses (`authority`) unless a caller identity is present in the environment the server was started in (`VINAYA_MCP_CALLER`, resolved once by the server — `apps/cli/specs/self-hosting.md`). MCP is a transport, not authorization: the caller is never read from a tool argument. Started with no caller, the server still answers every read tool and refuses only `task_start`.
- **Idempotent per request identity.** The identity is `caller + repo + target + payload digest` (`taskStartRequestIdentity`, `@attalabs/aeg-core`). The first call claims it in a durable store and launches; every later call with the same identity returns the same run and launches nothing. Because the claim is written before the launch, a client that disconnects mid-call leaves at most one run — a reconnect replays the claim, it does not start again.
- **Attended mode only, the caller's own credentials.** The detached run inherits the operator's own environment. There is no unattended start and no attended bypass; an unattended start waits on the worker-isolation boundary and a capability flag a later tranche adds. The tool's own catalog description carries the same limits.

Both runtime adapters register the shared MCP server (`vinaya task-tools serve`) that exposes this tool: Claude through the generated `.mcp.json`, Codex through its documented `[mcp_servers]` TOML — see `apps/cli/specs/self-hosting.md`.
