# Self-hosting — how Vinaya governs a repo that contains Vinaya

Status: draft

The generated CI shape for a repo whose own workspaces declare `@attalabs/vinaya`, why it must differ, and what it costs. This repo is the first such adopter; the rules below are the product's, not this repo's.

This repo's CI is three pieces, not just the generated one below: the four `vinaya-*.yml` workflows (generated, vinaya-managed, regenerated by `upgrade`), and a hand-written `.github/workflows/ci.yml` (repo-own, running `bunx biome check` plus `bunx turbo typecheck`/`test` unscoped) that is neither generated nor vinaya-managed and is invisible to `doctor` by design — it exists because none of the four generated workflows ever run a test, a typecheck, or a linter; they only invoke `vinaya check`/`archive`/`audit`.

`doctor` no longer leaves that gap entirely silent: it names it as a heuristic, narrow-by-design diagnostic (`test-ci`) — a repo declaring a `package.json` `scripts.test` with no workflow anywhere under `.github/workflows/` recognizably invoking it. It accepts false negatives by design (a non-Node runner, a `Makefile` target, a workspace-member-only test script) rather than trying to be exhaustive, and it scans every workflow file in the directory, not only the four vinaya-generated ones — this repo's own `ci.yml` is exactly the hand-written case the scan has to see, and is why the diagnostic stays silent here.

The lint step is the newest of the three and closed a gap of the same shape as the rest of this document's findings: Biome was a devDependency every contributor already installed via `bun install`, and nothing ever ran it, so formatting and lint drifted in whenever someone did not run it by hand. A tool that is present but unrun looks like enforcement and is not. It runs before typecheck deliberately — a formatting failure is the most mechanical one to read, and reporting it first keeps it from being buried under type errors — and without `--write`, because a CI job that rewrites the tree would be pushing to a contributor's branch, which is not a gate's job.

This repo's own generated CI consumes `vinaya check` through a pipe (`vinaya-checks.yml` runs `check --all --diff-only | tee` to build its step summary), the same shape as every other consumer that pipes the CLI's output rather than redirecting it to a file. Self-hosting cannot surface every defect on that path, because this repo's own check output sits far below any pipe buffer a reading process might use — a truncation defect on the piped path is invisible to this repo's own dogfood regardless of how thoroughly it runs. An adopter is not bounded the same way: a `scope: full` custom check scans the whole tree regardless of `--diff-only`, so an adopter's payload can grow arbitrarily large while this repo's stays small by construction. Self-hosting proves the generated CI shape works; it does not prove the CLI's own output survives a pipe at adopter scale, and that gap has to be closed by the CLI's own tests, not by this repo running more of itself.

## One run per pull request

Both `pull_request`-triggered workflows (`vinaya-checks`, `vinaya-review`) carry a `concurrency` group keyed on the pull request number **and its head commit**, with `cancel-in-progress: true`.

This is not tuning. Several of the `types:` each workflow listens for can fire in the same instant — `vinaya pr create` opens the pull request and applies its tranche label immediately after, so `opened` and `labeled` arrive together and GitHub starts **two runs of the same workflow**. Both report under the same check name, and the merge box counts both, so one can go green while its twin holds a stale red. No later verdict clears it: each run only ever re-evaluates itself. Measured on `atta-labs/vinaya#18` — two runs created in the same second, one success and one failure, the pull request blocked with both reviews already approved.

The head commit belongs in the key, and leaving it out is a live failure rather than a missed optimisation. Keyed on the pull request alone, every run for that pull request shares one group — including a rerun of an **earlier** commit's run, which the verdict retrigger performs. Measured: re-running the previous commit's run cancelled the current commit's run one second after it started, so a push appeared to produce a cancelled gate. Runs for different commits must not be able to cancel each other; runs for the same commit still collapse, which is the duplicate this group exists to remove.

`cancel-in-progress` is safe here rather than merely tolerable: these jobs are pure re-evaluations of forge state that take seconds, so a cancelled run had nothing to lose and the survivor reads strictly fresher state.

The `issue_comment`-triggered verdict workflow deliberately has **no** concurrency group. It is not a source of duplicate runs, and serializing it would delay the retrigger that exists to clear a red gate promptly.

The archivist workflow (`vinaya-archivist.yml`) deliberately has **no** concurrency group either, for a different reason than the verdict workflow: its three jobs fire on disjoint triggers (a push to `main`, a daily schedule, `workflow_dispatch`), and the post-merge job archives a specific merge SHA (`--merge-sha`). Unlike the pure re-evaluations above, cancelling an in-progress post-merge run to make way for an unrelated scheduled/dispatch trigger could skip that merge's provenance outright — there is no "newer run covers the same ground" guarantee here, so no group is safer than any group.

This repo's own hand-written `ci.yml` (not vinaya-managed — see the top of this document) carries a concurrency group too, but a deliberately coarser one: keyed on the PR number **alone**, no head SHA, with `cancel-in-progress: true`. Where the three workflows above must survive a later push to keep judging the commit they started on, `ci.yml`'s job is the expensive build+typecheck+test suite — a superseded push's copy of it is pure waste nobody will ever read, and the newer push's own run re-covers the same ground from a fresher head. Cancelling it is exactly the point.

The verdict retrigger re-runs exactly one run of the review workflow: **the one for the pull request's current head commit**, excluding cancelled runs. Selecting by recency instead is subtly wrong — `--status completed` excludes a run that is currently re-running but *includes* cancelled ones, so a verdict arriving while the head's run is still in flight can select a stale cancelled sibling, rerun it, and have the concurrency group cancel the live evaluation it meant to refresh. Re-running every match is actively harmful once the concurrency group exists: completed runs accumulate normally across pushes, so re-running all of them puts several into one group at once and `cancel-in-progress` kills all but the last — cancelled runs report red. Measured: one verdict re-ran four runs, three were cancelled, and a pull request holding a clean approval showed three reds.

The division of labour is the point. The **concurrency group** guarantees one live run per pull request; the **retrigger** only has to tell that one run a verdict landed. Older runs belong to earlier commits, and a check run is scoped to the commit it ran on, so they do not gate the current head.

No workflow re-runs the review gate when CI completes any more, and none needs to: the gate answers for the review verdicts alone. It used to fail whenever any other check-run on the head was red, which is the only reason a CI completion was news to it — and a `workflow_run`-triggered workflow existed solely to carry that news. Every merge condition is its own independent check now, so a red sibling is red under its own name and this gate never had to hear about it.

**What deliberately does not change: the gate still fails when no verdict exists.** "Nobody has reviewed this" must block a merge; reporting it as neutral would let an unreviewed pull request through, which is the thing the gate exists to prevent. The defect was never the failure — it was that a second run could not be told the news.

## The failure it exists to prevent

`init` and `upgrade` generate four workflows, each invoking the published package as `npx --yes @attalabs/vinaya@<exact-installed-version>`. In a repo whose root `workspaces` globs reach a member declaring that exact name, npm never contacts the registry. It matches on the package **name**, before any version spec is read, resolves that member's declared `bin`, and execs a file nothing has built:

```
sh: vinaya: command not found
```

Two consequences follow, and both have been measured rather than reasoned about:

- **Pinning a version cannot fix it.** Every spec form — `@0.4.6`, `@latest`, a tag — is decided after the name match. The name is what npm branches on.
- **Publishing cannot fix it either.** The workflow files are already committed in the adopter's repo. Only a new publish *plus* `vinaya upgrade` rewrites them.

## The two shapes

Detection runs at **generation time** — `init`, `upgrade` and `doctor` all hold the repo root — so the emitted YAML carries no branching logic of its own.

`init` writes **seven** invocations of the tool into an adopter repo: four in generated workflows, three in generated git hooks (`pre-commit`, `pre-push`, and — since Issue #63 — `commit-msg`). Both surfaces branch on the same predicate, and both are described below — the hook half was omitted when the workflow half first shipped, and in a vendoring repo that omission blocked every commit and push.

### CI workflows

| | ordinary adopter | vendoring repo |
|---|---|---|
| detection | no workspace member named `@attalabs/vinaya` | such a member exists |
| setup | `actions/setup-node` | `actions/setup-node` + `oven-sh/setup-bun` |
| build | none | `bun install --frozen-lockfile --ignore-scripts`, `bun run --cwd <member> build` |
| invocation | `npx --yes @attalabs/vinaya@<exact-installed-version> <cmd>` | `node <member>/<bin> <cmd>` |

**The published invocation pins the exact installed version, and an unpinned one would not mean "latest."** Where the generated `vinaya-checks.yml` carries an install step — which it does only when the adopter declares `ci.setup` (see the third emission below) — a repo that also carries `@attalabs/vinaya` as a devDependency already has `node_modules/.bin/vinaya` on disk, and npx prefers it over the registry. Measured 2026-08-17: the same bare command printed `0.8.2` inside `atta-labs/attalabs`, which declares `ci.setup`, and `0.9.0` in `/tmp`. Unpinned, that adopter's CI version is an accident of a devDependency no workflow references, and changing or dropping that dependency moves CI to registry latest with no commit and no diff to review. An adopter that declares no `ci.setup` gets no install step generated at all, so for them an unpinned spec resolved registry latest in all four workflows — the same exposure described for the archivist below, but everywhere. The pin makes the version a reviewed, committed fact; `vinaya upgrade` re-pins it and `doctor` reports a stale pin as drift. `@latest` is deliberately *not* the fix — floating CI is a different product decision, and it is not what the hooks do.

The archivist workflow is the sharp end of this, and its resolution is the opposite one. It emits no install step at all (its jobs spawn no adopter code, so there is nothing to prepare), which means an unpinned `npx` there really did resolve registry latest — in three jobs that all hold `issues: write` — two of them `pull-requests: write`, the third `pull-requests: read` — covering between them every push to `main` (`post-merge`, `direct-main-push-detection`) and a nightly schedule (`daily-drift`). Unpinned, a compromised publish of this package would have run as arbitrary code holding a write token in every adopter, on the next merge, with no diff anywhere to review. So both families were unpinned the same way and, for a default adopter, exposed the same way: all four inherited registry latest, because no generated workflow installs anything unless `ci.setup` is declared. Only where an adopter does declare it do checks/review/review-verdict diverge, inheriting whatever that install resolved instead. One pin, applied at the single emission site, closes both — for every workflow generated from that point on. An adopter whose workflows were generated earlier keeps the unpinned bytes until `vinaya upgrade` rewrites them; `vinaya doctor` reports the stale pin as drift, and nothing in `vinaya check` compares a generated artifact against the installed generator.

A third emission is orthogonal to the two shapes: when the repo-root config declares `ci.setup`, the workflows that execute `vinaya check` (checks, review, review-verdict — never the archivist, whose jobs spawn no adopter code) carry one additional "Adopter CI setup" step running that command verbatim, after setup and before any invocation. It exists because the table above prepares only *vinaya*: an adopter's custom checks are scripts in the adopter's own repo that may import the adopter's own code, and a bare runner has none of it installed — measured on the first non-greenfield adopter, whose two custom checks failed as `error (2ms)` spawn failures on every CI run while passing in the local hooks. The command is declared in the committed config, never inferred (vinaya cannot know an adopter's package manager), and an undeclared key emits nothing — byte-identical output to before the key existed. Read at generation time from the repo root (`readRepoCiSetup`), same regeneration-determinism argument as the detection predicate below.

### Git hooks — `pre-commit`, `pre-push`, `commit-msg`

| | ordinary adopter | vendoring repo |
|---|---|---|
| detection | same predicate | same predicate |
| build | none | none — the hook requires a build, it never performs one |
| guard | none | `[ ! -f <member>/<bin> ]` → message naming `bun run --cwd <member> build`, then exit 1 |
| invocation | `npx --yes @attalabs/vinaya@<exact-version> <cmd>` | `node <member>/<bin> <cmd>` |

The hook's published form carries the same **exact-version pin** the workflow form does — one `ownVersion()` in `lib/artifacts.ts` feeds both — and it carries it for one additional reason of its own: npx's cache is keyed by the invoked spec, and an entry written by one spec does not satisfy a lookup for a different one, so without the pin the first commit after `init` died on npx's non-interactive cancel. That second reason is about cache keys, not about resolution.

**The vendoring repo's `pre-push` carries three further steps this table doesn't cover, after the doctrine gate (O5/O6/O7, `artifacts.ts`'s `prePushBody`): a Biome pass over the files changed since the remote base; `turbo typecheck --affected`; and a file-level test step bounded the same way — never the whole suite, which is what CI is for, and which once made the hook itself take longer than CI.** The test step's selection comes from `lib/test-selector.ts`'s `selectAffectedTestFiles`, resolved through the REAL import graph of the files changed since the remote base (`lib/remote-base.ts`) — never a folder heuristic — and handed to ONE `bun test` invocation covering every selected file across every affected package, printing `selected N of M test file(s)` and its own wall time to stderr on every run, with the selector's own runtime and its compiler program build reported separately from the test run, so a near-empty selection is visible rather than silently trusted.

**The pre-push hook selects at depth one, never the full transitive closure (Issue #707, O1).** It passes `selectAffectedTestFiles`'s `depth: 'one'` option — the same import graph, the same changed-name granularity, but the walk stops after a test's own direct edges: a test file that changed itself, a test that imports a changed name directly (through a resolved re-export hop or a barrel's own module-scope pull, never through a SECOND file's further imports), and `prePush.alwaysRun`. A test that reaches a change only by importing a file that itself imports the changed file is not selected by the hook — that chain is CI's to catch. `depth: 'one'` also defaults the repo-tree-scanner and CLI-spawn-detection categories to `'ignore'`: both earn their edge from what a test file IS, not from what it imports, so no depth bound narrows either of them, and leaving them on would select every one of them on any matching change regardless of depth. Three reference change sets, pinned in `apps/cli/tests/lib/test-selector.test.ts`, each carry a ceiling the depth-one selection must stay under: a change to the log sink (`log-sink.ts`/`config.ts`/`run-paths.ts`) at 20 files, a change to a widely imported export of the shared core package at 25, a change to one leaf module at 5.

**The never-miss guarantee now lives in CI, not in the pre-push hook.** Before this task, pre-push's own full-transitive selection WAS the never-miss claim — the paragraph below still describes and tests that claim, and it still holds for `selectAffectedTestFiles`'s default (`depth: 'transitive'`), which is what CI's own affected-package shards run. Depth-one trades that guarantee away at push time on purpose, in exchange for a push that costs seconds rather than minutes on a change to a widely-imported module: CI's shards still run every test, on every push, regardless of what the hook selected, so a test the hook's depth-one selection missed is still run — just not before the push leaves.

**A green pre-push test run is cached for `pr report` to reuse, per FILE — never only for a Test-plan command matching its exact text (Issue #715, O1).** After the hook's own selected-file test step exits zero, `pre-push-cache-test-run.ts` hands the exact command it ran and its captured output to `pr-report-engine.ts`'s `recordGreenTestRun`, which writes two records into the shared test-run cache: one keyed by the command's own text (exact-command reuse, unchanged), and one keyed by the head/working-tree/machine state ALONE, carrying the resolved, absolute list of files that run covered. A later `vinaya pr report --write`/`--push` grading a Test-plan `bun test <files>` command reuses that second record whenever every file the command names is in the covered list — a Test-plan command naming two of the twelve files a pre-push run just proved green reuses it, without re-running anything, even though its own command text never matched the hook's twelve-file invocation verbatim. Reuse still refuses outright when any named file is missing from the covered list, when the head, working tree, or machine (`hostname()`) differs from the recorded run's, or when the recorded run wasn't itself green — the same four guards the exact-command path already enforced, applied to the file-set match instead of a text match.

**Resolution is the TypeScript compiler's, not a text scan.** A regular expression can read the specifier `'./demo.js'`; it cannot know the file on disk is `demo.ts`. This repository writes 482 of its 1275 relative import specifiers with the extension the EMIT will have, which is what TypeScript's own ESM guidance says to do — and every one of those edges was absent from the regex graph, across 144 importer files and 104 distinct targets. The visible symptom: a change to `apps/cli/src/commands/demo.ts` selected no test at all, though `apps/cli/tests/demo.test.ts` imports it by name. A selector that drops edges does not over-select; it silently under-selects, and its reported reductions are lost edges wearing precision's clothes. `lib/ts-module-graph.ts` now resolves every specifier with `ts.resolveModuleName` and follows each imported name to its defining file along the checker's own alias chain, hop by hop, so a re-export chain and a cross-package barrel both resolve to the file that actually defines the name. The compiler is resolved at runtime from the repository under analysis (`createRequire`), never bundled into the published artifact and never added to an adopter's install; a repository without it falls back to the text-scan graph, which is a strict over-approximation.

**Selection follows the changed exported NAMES, not the changed file.** `lib/changed-names.ts` attributes each diff hunk to the top-level declarations it touches — on both sides of the diff, so a deleted declaration is attributed too — and closes that set backwards over intra-file references, since a change to a local helper affects every exported declaration that uses it. A test is selected when its import closure reaches a USE of an affected name. Any hunk that cannot be attributed to exactly one declaration — module-scope code, an `import`/`export` statement, an `export *`, `export default`, a destructuring binding, an unparseable region, a range outside every declaration — makes the whole file affected, which is the file-level answer; so is a changed file whose names were never computed. Narrowing is something the selector has to earn, every time.

A bare workspace-package import is not treated as a dependency on the whole package: the imported NAMES are resolved through the target package's declared entrypoint (`exports`/`main`, handed to the compiler as `paths` so the answer does not depend on the install layout) and its named, aliased, star and cross-package re-export graph, to the files that actually define them. Every shape the compiler cannot prove keeps the whole-package edge — a namespace, default, side-effect or dynamic import, an `export *` supplying one name from two sources, `import x = require(...)`, an alias chain that does not terminate in a declaration, or a package whose entrypoint cannot be derived from its manifest — so the refinement can over-select but never omits a truly affected test.

**A test whose input is the repository TREE is selected from what it scans.** An allowlist or invariant that walks every source file rather than importing them has no import edge reachability can ever follow, and a change to any file it reads can break it while it stays unselected — which is exactly how a pull request changing one test file passed this hook and failed CI on the test that audits every real-process call site. `lib/repo-scanner-tests.ts` classifies these from their own source: a file that both anchors a path on its own module location (`import.meta.dir`, `fileURLToPath(new URL('.', import.meta.url))`) or the working directory AND calls a tree-reading API (`readdirSync` and siblings, or `git ls-files`) reads the real tree; one that anchors on `tmpdir()` is walking its own fixture and is not this class. On this repository 21 of 313 test files classify, and the rule costs four to five extra files on a typical change. `vinaya.config.json`'s `prePush.alwaysRun` still exists and still forces its own list onto every push, but it is no longer the only way such a test can be selected.

**The never-miss claim is checked against a graph the selector did not build.** `apps/cli/tests/lib/test-selector.test.ts`'s oracle bundles each test file with Bun and reads the module list out of the bundle's own source map, so the resolution being compared against is the bundler's. This matters more than it sounds: the oracle it replaced read imports with its own regular expressions and shared the selector's `.js` blind spot exactly, which is why that defect survived. Inside a package the bundler is authoritative and the selector must be a strict superset of it; across a package barrel it is an over-approximation, because bundling a barrel parses every module the barrel re-exports, so there the test requires instead that every divergence be attributable to the barrel rather than to a lost relative edge.

**The monorepo task runner's own `test` task is never cached** (`turbo.json`'s `tasks.test.cache: false`, the same setting `dev`/`generate`/`clean` already carry) — a cached result, keyed by content hash alone, could otherwise replay a PASS recorded on a quiet run against a later run of the identical files under load, which is a different question from whether those files' tests genuinely pass right now. The hook's own test step never goes through `turbo` at all (it calls the selected files' runner directly), so this setting is defense-in-depth for every OTHER caller of `turbo test` on this repository, present or future, not a change to what the hook itself does.

**`commit-msg` (Issue #63) differs from its two siblings in what it invokes, not in how.** `pre-commit`/`pre-push` both run `vinaya check --all --local`-shaped invocations against `hookRun`'s two branches; `commit-msg` runs `vinaya commit-msg "$1" "$2"` instead — the two positional parameters git itself passes a commit-msg hook (githooks(5)): the message file's path, and, when known, the commit's source keyword. There is no `--local` here and no `check` invocation at all: `commit-msg` validates the message file's first line against `@attalabs/aeg-core`'s `COMMIT_TYPE_STYLE` (the same vocabulary `checkForgeTitle` enforces on PR/Issue titles — one list, never a second copy), never a staged diff, so `check`'s diff-scoping and `requiresOpenPr`-skipping machinery does not apply. A `source` of `merge` skips validation outright, since a merge commit's message is written by git, not the person committing.

**A `token-collection-wired` ring-0 check now rides the same `vinaya check --all --local` invocation these hooks already run (task 5, #272) — no new hook host, no new invocation shape.** It re-uses `resolveMeteringCapability` (`@attalabs/aeg-core`, the same probe backing the transcript-pointer machinery below) and refuses a commit only when the transcript pointer is this session's — either its recorded id matches ours and the transcript it named could not be reached, or its id is unreadable while the file sits at this project's own pointer path owned by this user. A host where nothing was ever wired to meter at all (no pointer, no `--transcript`) passes: that is the sanctioned operator-metered case, never a wiring defect.

**Where the hooks live — the tracked `.vinaya/hooks/` directory, routed via `core.hooksPath` (atta-labs/attalabs#927).** Raw `.git/hooks` is never versioned by git, so a `.git/hooks` install gave the installing machine working ring-0 enforcement while every fresh clone silently had none — the ownership manifest survived the clone, the hooks did not. Non-husky installs therefore write the hook hosts into `.vinaya/hooks/` (committed, so they travel with the repo into every clone and every linked-worktree checkout) and arm `git config core.hooksPath .vinaya/hooks`. The config value is **relative**, so git resolves it against each working tree's own tracked copy, and it is written to the **shared** (non-`--worktree`) config, so one arming covers a clone and all its linked worktrees. The irreducible residue is that git config is never cloned: each fresh clone runs that one `git config` line once (or `vinaya init`/`vinaya upgrade`, which do it). `vinaya doctor` reports an unarmed working copy as an error naming the exact command — hook files present but inert is precisely the state it exists to catch — and warns on a repo still installed at `.git/hooks`. This repo's own install is migrated (see `vinaya.config.json`'s `managed.blocks`). `vinaya upgrade` migrates a legacy `.git/hooks` install, but **refuses** whenever arming `core.hooksPath` would silently disable hooks vinaya does not own — an adopter's own lines in a hook host, or any unmanaged active raw hook in `.git/hooks` — in which case the install stays on the legacy layout and `doctor` keeps warning about the clone gap. `.husky` repos are untouched: husky's own `prepare` step owns per-clone wiring there.

**Where legacy `.git/hooks/*` physically resolves — through `git rev-parse --git-common-dir`, never `join(repoRoot, '.git/hooks/…')`.** Hooks are never per-worktree: every linked worktree shares the primary checkout's hooks directory, and in a linked worktree `<repoRoot>/.git` is a *file* (a gitdir pointer), not a directory. The naive join therefore does worse than miss — a write path that `mkdir`s under that file throws `ENOTDIR` and aborts the entire apply, which is how `vinaya upgrade` crashed outright from any linked worktree (measured live) while `doctor` — which had the common-dir resolution first, for reads — reported the same hooks fine. The resolution rule lives once, in `lib/ops.ts`'s `resolveManagedBlockPath`, and every command that touches a hook path (`doctor`, `upgrade`, `init`/`quickstart` via the shared block helpers, `demo break`'s existence probe) calls it; two copies of this rule drifting apart is exactly how the write half stayed broken after the read half was fixed. `.husky/*` paths are exempt by construction — husky's directory is a real, git-tracked directory present in every worktree checkout — and `.vinaya/hooks/*` paths are exempt the same way (tracked, present per checkout; the naive join is already correct there). One consequence worth stating: in a repo using `.git/hooks`, `upgrade` run from *any* linked worktree writes the one shared hook set, not a per-worktree copy — that is git's own semantics, not a vinaya choice. `eject` shares `gitCommonDir` and the `GIT_DIR_PREFIX` discriminator with that rule, though not the resolver itself — `containedManagedBlockAbs` joins the common dir directly, because it must compute the bound and the target from ONE `gitCommonDir` answer rather than two independent calls. Sharing the resolution was not sufficient on its own, because `eject` deletes: every path it touches must pass a containment check, and `containedAbs` requires containment inside `repoRoot`. Handed the common-dir path, that check would refuse the very hook it was resolving. So the containment invariant is stated per KIND rather than relaxed (`containedManagedBlockAbs`): a whole file vinaya owns must stay inside `repoRoot`, while a `.git/`-prefixed managed block must stay inside the git common dir's own `hooks/` subtree. Both are derived from a single `gitCommonDir` call whose result is threaded into each; computing them from two calls lets a `git` failure between them put the bound and the target on opposite sides of the fallback, so a containment check is only trustworthy against its resolver when the two share an answer, not merely a function. One property worth stating rather than leaving in a review thread, since this is a command that deletes: the bound is derived from `git rev-parse --git-common-dir`, so `GIT_DIR`/`GIT_COMMON_DIR` in the invoking environment move it — pointed at another repository, `eject` bounds its strip to *that* repository's `hooks/`. That is the invoker's own environment rather than anything the manifest can reach, and it already redirected `upgrade`'s writes the same way, so it is inherited git semantics and not a new exposure. An invalid value fails closed: both the bound and the target fall back to `<repoRoot>/.git` together, because they come from one call. The `.git/` discriminator itself is byte-exact — case-sensitive, and requiring the trailing separator — so a non-canonical spelling such as `.GIT/…` or a bare `.git` (no trailing separator) would take the working-tree branch instead of the hooks-subtree one; unreachable from any vinaya-generated manifest, whose block paths are always one of three lower-case literals, and — since issue `#177` — refused earlier still: `config.ts`'s `ManagedBlockRecordSchema.path` rejects any spelling that isn't byte-exactly `.git/…`, `.husky/…`, or `.vinaya/hooks/…` at parse time, so a hand-edited manifest carrying either escape fails to load at all and this resolver never sees it. This resolver's own discriminator is unchanged (belt-and-suspenders to the parse-layer refusal, not a second fix).

For a canonically spelled path the re-based rule is strictly TIGHTER than the old one in an ordinary checkout, where `<repoRoot>/.git` *is* the common dir: `.git/config` and `.git/objects/…` were previously "contained" and are now refused, since no managed block belongs outside `hooks/`. Until this landed, a linked-worktree `eject` did something quieter than refusing. `containedAbs` ACCEPTED the block path — `resolve()` never sees that the worktree's `.git` is a gitlink file, so `<repoRoot>/.git/hooks/pre-commit` is textually contained and passes — it simply named a file that does not exist there. `planEject` recorded `present: false`, the diff printed `gone (managed block already removed)`, and the run exited 0 having stripped nothing, while the real hook stayed armed in the shared directory. An escape would have refused the whole eject and said so; this reported success instead.

**This rule is gate-bound to this document:** `.vinaya/doc-owners` binds `apps/cli/src/lib/ops.ts` here. The binding's outcomes are pinned in `packages/aeg-core/src/doc-owners.test.ts`.

Two alternatives to the guard were rejected. **Auto-building inside the hook** spends an unannounced build on someone's commit and hides staleness. **Skipping the checks when the build is missing** converts a loud breakage into an absent ring 0 with nothing saying so — and since `dist/` is generated and git-ignored, it is legitimately absent in a fresh clone and in every new worktree, which makes the skip the common case rather than the rare one. Failing with the command to run is the only shape that keeps the gate honest.

The ordinary adopter gains **no build step and no third-party action** — the overwhelming majority of adopters have no local copy to build and must not pay for a problem they do not have. That is the load-bearing property, and it is narrower than byte-identity: the adopter shape is *not* byte-identical to the pre-detection generator, because the credential opt-out and the verdict-retrigger fix below are security corrections that belong to every adopter, not only to a vendoring one. What must never leak into it is the vendored machinery.

**The predicate is exactly the misresolution condition** — a workspace member whose `package.json` `name` is `@attalabs/vinaya` — and deliberately nothing more. Not "has a build script", not "is called `apps/cli`". A repo that declares the name is one where `npx` is already broken; narrowing further would hand it an invocation that cannot work, and widening it would give an ordinary adopter a build step it does not need.

Generation-time detection is also what keeps `doctor` honest. `doctor` diffs regenerated content against what is on disk to report drift, and a pure function of the repo's on-disk workspace declaration regenerates the same bytes for the same repo. A runtime branch inside the YAML would not have that property, and logic living in YAML is logic the unit tests cannot execute.

### A fourth managed-block directory: `.claude/hooks/` — not part of the two shapes above

`lib/ops.ts`'s marker-delimited managed-block mechanism (the same one `pre-commit`/`pre-push`/`commit-msg` use) now also writes `.claude/hooks/track-transcript.sh` (task 10, #278) — a Claude Code `Stop` hook that records the session's transcript pointer so `packages/aeg-core/bin/report-tokens.ts`'s `resolveTranscriptPath()` can resolve it without scanning `~/.claude/projects/` (wrong-session risk under concurrent worktrees). `config.ts`'s `CANONICAL_HOOK_BLOCK_PREFIXES` gained `.claude/hooks/` as a fourth entry alongside `.git/`, `.husky/`, `.vinaya/hooks/` — same discipline, one more prefix, not a new mechanism.

This artifact is deliberately **outside** the two-shapes system this document otherwise describes in full: it never invokes the `vinaya` binary at all (no `npx`, no vendored `node <bin>` branch, no `ownVersion()` pin), so the self-hosting detection predicate above does not apply to it — it emits identical bytes whether or not the repo vendors the CLI. Its companion artifact, `.claude/settings.json` (the JSON registration wiring Claude Code to run the script), is a plain refuse-if-foreign whole file (`CreateFileOp`), not a managed block at all — strict JSON has no comment syntax the marker convention could use, so an adopter's pre-existing `settings.json` is left untouched rather than merged into.

The earlier "`.claude/**` is out of v1.0 scope" ruling does not apply here — it was already superseded in practice by `.claude/commands/vinaya.md` (task 5's agent-native emitters) before this task landed.

### The task-tools MCP server — Claude and Codex registration

The task-operator tool catalog (`packages/aeg-core/src/task-tools.ts`) is exposed to an agent runtime through one shared, transport-agnostic MCP server (`apps/cli/src/lib/task-tools/server.ts`), run by `vinaya task-tools serve` over stdio. The server speaks newline-delimited JSON-RPC 2.0 (MCP `initialize`/`tools/list`/`tools/call`), implemented directly rather than through an MCP SDK — this adds no dependency and lets every protocol fixture run hermetically against real framing. The protocol revision it implements, and both adapters target, is **`2025-06-18`** (`MCP_PROTOCOL_VERSION`).

There is one server and two runtime **adapters** (`apps/cli/src/lib/task-tools/adapters.ts`); both register the same `vinaya task-tools serve` command, differing only in the registration file format:

- **Claude** — a project-root `.mcp.json` (`mcpServers.vinaya-task-tools.command`/`args`), generated through `artifacts.ts` (`buildInitOps`) as a **refuse-if-foreign whole file**, the same treatment `.claude/settings.json` gets (strict JSON carries no marker syntax, so never a managed block). It is written only when `claude` is one of the selected `--agents`. The command follows the two shapes above exactly: published `npx --yes @attalabs/vinaya@<exact-version>` (pinned to the same `ownVersion()` the workflows and hooks use) for an ordinary adopter, or the vendored `node <member>/<bin>` form for a repo that vendors the CLI. Verified live against **Claude Code 2.1.197**.
- **Codex** — the documented `~/.codex/config.toml` `[mcp_servers.vinaya-task-tools]` table (`command`/`args`), emitted by the adapter as an exact TOML snippet an operator adds. Codex's config is a **user-home file, not a repo artifact**, so nothing is written into the adopter repo for it — the snippet is documented here and produced by `codexMcpServersToml`. The Codex CLI was **not installed on the authoring host**, so no `codex --version` was captured; the adapter records this honestly (`verifiedLiveOnAuthoringHost: false`) and targets Codex's documented `mcp_servers` config format rather than a version the host could not confirm. When a Codex binary is available, capture its `--version` and pin `CODEX_MCP_ADAPTER.runtimeVersion`.

**MCP is a transport, not authorization.** The server never reads a caller's identity from a tool-call argument; authority is a property of the invocation context — the process environment — carried as `CallerContext` and resolved once at start from `VINAYA_MCP_CALLER`. Absent, the server still answers every read tool and refuses `task_start` (see `apps/cli/specs/loop.md`). An attended operator exports that variable to authenticate themselves; the detached run `task_start` launches then inherits the operator's own credentials. There is no unattended path and no attended bypass — the worker-isolation boundary and a capability flag are what a later tranche adds to enable one.

## Emitted paths are allowlisted, not escaped

The member's directory and its `bin` path are interpolated into a workflow `run:` scalar as **bare, unquoted shell words**, and both originate in the *target repo's* `package.json` — content the CLI does not control. This generator writes CI configuration into other people's repositories, so the values it embeds are constrained rather than sanitized:

```
^[A-Za-z0-9@._-]+(?:/[A-Za-z0-9@._-]+)*$
```

with three further rules on each segment — `.` and `..` are rejected as whole segments, and no segment may begin with `-` — and a whole-path bound of 255 characters. Anything outside this makes detection return `null`.

The path is also required to **resolve inside the repository**. The `..` rule is textual, so it does not see a literal (non-wildcard) workspace segment that is a symlink pointing out of the tree: `workspaces: ["vendored"]` with `vendored -> /elsewhere` yields the clean relative path `vendored`. Detection resolves the member directory and refuses anything landing outside the root. The wildcard route never had this hole — a symlink is not a directory to `readdir`.

`@` is permitted because npm scopes are ordinary directory names — a member at `packages/@attalabs/vinaya` is legitimate, and excluding it would silently degrade exactly the repo this feature exists for into the invocation already known broken there. It is inert in all three layers of the emitted context: it is a YAML indicator only at the start of a plain scalar, which it can never reach (the invocation is always prefixed by `node `, and the `--cwd` line sits inside a literal block); it is a non-globbing literal to `sh`, `bash` and `zsh`; and no Actions expression can form, since `$` and `{` remain excluded.

A leading `-` is refused for the opposite reason: it reaches `node` and `bun` in argument position, where a segment named `-e` or `--eval` is read as an option rather than a path.

**State the reason precisely, because the intuitive version is backwards.** Both runtimes *execute* a detached value — `node -e 'code'` and `bun -e 'code'` both run the code. What they reject is the attached form: `node -e/dist/index.js` and `node -e=/dist/index.js` are both `node: bad option`. The emitted `node <bin>` invocation is safe only because the interpolated path is always a single argv token, and `=` is outside the allowed charset — two separate exclusions, not one.

That invariant does not hold everywhere the values are emitted. `bun run --cwd <dir> build` **already passes the path as its own token**, and bun binds it to `--cwd` unconditionally: with the directory present, `--cwd -e`, `--cwd --eval`, `--cwd --help` all simply build there. That case is safe for a different reason — bun treats the token as a value, not an option — so the leading-`-` rule is what keeps both emissions honest rather than an optimisation on either.

The refusal is therefore not "this would be harmless anyway". It is: no real directory needs a leading `-`, and the property standing between a parse error and `-e` is one nothing else enforces.

Allowlist rather than escaping, for two reasons. Escaping must be correct against every metacharacter, in a `run:` block that is simultaneously YAML, shell, and a GitHub Actions expression context — three layers, each with its own evaluation rules. And a value outside this charset has no legitimate use as a workspace path, so refusing costs nothing real.

`null` is already the safe default: a rejected value degrades to the published `npx` shape, which is wrong for that repo but harmless there, rather than failing `init`. The same rule closes traversal — a `workspaces` pattern reaching outside the repo root produces a path containing `..`, which is refused.

Detection never throws. A missing, unreadable or malformed root `package.json` degrades to `null`; a broken manifest must not take down `vinaya init`. Glob expansion skips `node_modules` and dot-directories, sorts children for determinism, and caps candidate directories.

### Where it degrades silently, and what that costs

Every refusal returns `null`, which emits the published shape. For an ordinary adopter that is correct. For a repo that really does vendor the CLI it is the invocation already known broken there — so these are the cases where a vendoring repo gets a workflow that dies at `vinaya: command not found` with nothing explaining why:

- **A segment with more than four stars after collapsing** is refused outright, to bound glob backtracking.
- **`**` is matched as exactly one level**, so a member at `packages/a/b` under `workspaces: ["packages/**"]` is not found.
- **A member reached through a symlink out of the repo** is refused, as above.

`--ignore-scripts` adds one more, of a different kind: a vendoring repo whose install genuinely depends on its own root or workspace lifecycle scripts gets a build that fails rather than one that silently degrades. That is the intended direction — those scripts are PR-editable, which is the whole reason the flag is there — but it is a real constraint on such a repo, and it fails loudly at the build step rather than at detection.

Two assumptions are deliberately outside the predicate, and they fail later rather than at detection: the vendored shape runs `bun`, and it runs the member's `build` script. A vendoring repo on npm or pnpm workspaces, or one whose member declares no `build`, gets a generated workflow that fails at the build step. Both were left out on purpose — the predicate is exactly npm's own misresolution condition (§ The two shapes) and narrowing it further would hand such a repo the `npx` line that cannot work either. Neither case is diagnosed today; `vinaya doctor` reporting a refused-but-present member is the natural home for it.

## How the published version is produced

`@attalabs/vinaya`'s version is not decided by this package's own changes alone. The build **inlines** the engine — `bun run --cwd apps/cli build` produces a `dist/index.js` with zero `@attalabs/aeg-core` references, because the engine's source is bundled into it rather than required at runtime. So an engine-only commit changes the CLI's shipped bytes exactly as much as a commit inside `apps/cli` does, even though `@attalabs/aeg-core`, `@attalabs/vinaya-sources` and `@atta/typescript-config` sit in `apps/cli/package.json`'s `devDependencies`, not `dependencies` — that placement is deliberate (they are a build-time input, not a runtime one) and does not change.

Changesets' default cascade cannot see that. `@changesets/assemble-release-plan` hard-codes every `devDependencies` edge to bump type `"none"` regardless of range or config — `updateInternalDependents: "always"` does not affect this, and no `dependencies`/`peerDependencies` edge exists to carry it instead. Left at the default, a changeset against `@attalabs/aeg-types` would bump the engine packages and never touch `@attalabs/vinaya`, silently shipping an inlined-bytes change under an unchanged version number.

`.changeset/config.json` closes the gap with a `fixed` group — `@attalabs/aeg-types`, `@attalabs/aeg-forge-state`, `@attalabs/aeg-core`, `@attalabs/vinaya-sources`, `@attalabs/vinaya` — which is a membership relation, not a dependency-graph traversal: `matchFixedConstraint` adds every group member to the release plan, at the group's current-highest version, the moment *any* member is releasing, independent of `dependencies` vs `devDependencies`. `@atta/typescript-config` is left out of the group and out of the released set entirely (`ignore`) — it is a devDependency of every package here but contributes no bytes to any bundle, so folding it in would bump the CLI on pure tooling noise.

The four engine packages publish publicly — no `private` flag, `publishConfig.access: "public"` — so `changeset publish` versions, tags and publishes them alongside `@attalabs/vinaya`, and their membership in the `fixed` group rests on the ordinary mechanism every public package uses rather than on `privatePackages.version`. They *were* `private: true` until August 2026, and an earlier plan would have moved them to a private registry instead; that plan was measured and reversed, for reasons worth keeping. A private registry would have protected almost nothing: the published `@attalabs/vinaya` tarball already ships all the `aeg-root/` doctrine and the unminified compiled engine, publicly under Apache-2.0, since `0.1.0` — the secrecy it would buy is already spent. And it would have carried a permanent cost on a public repo: an auth token in Actions and Vercel that GitHub never exposes to fork PRs, so every external contributor's PR on the public `attalabs` repo would fail at install, forever. Going public closes the fewest doors — future versions can be made private later; versions already published cannot be recalled. The `privatePackages` setting stays in the config as `{ version: true, tag: true }`, but after this reversal it governs only packages that are still private — and since the sole remaining private package, `@atta/typescript-config`, is also `ignore`d and never releases, the `tag` flip is effectively a no-op today: the engine's tags now come from the ordinary publish tagging, not from this key. It is kept as `true` so a future private-but-released package would tag rather than silently not.

One constraint of publishing the engine packages is invisible in every dry run and fails only at a consumer's install: **internal dependencies between the four must be concrete version pins, never `workspace:*`.** Under bun, `changeset publish` resolves no pnpm/yarn and falls through to spawning plain `npm publish` per package, and neither npm nor `changeset version` rewrites the `workspace:` protocol — the tarball ships whatever range the manifest declares, and a consumer's npm fails with `EUNSUPPORTEDPROTOCOL`. `npm pack --dry-run` and `npm publish --dry-run` both succeed regardless, which is why this cannot be caught by packing alone: prove installability by extracting `package.json` from the packed tarball and scratch-installing the tarball outside the workspace. The pins stay in lockstep automatically — all four sit in the `fixed` group, so `changeset version` bumps the pinned ranges together with the versions (exact-pin style is preserved), and bun still links the workspace copies locally because the pinned version matches the sibling's.

`.github/workflows/release.yml` opens a "Version Packages" PR from pending changesets on push to `main`, running the same version-plan logic described above. It carries no `publish` step and no publish credentials, so it can only ever propose the version bump.

That PR is opened with a repository-scoped fine-grained token (`RELEASE_TOKEN`), not `GITHUB_TOKEN`, because of a ceiling rather than a preference. The `atta-labs` organization leaves "Allow GitHub Actions to create and approve pull requests" off for its repositories, and a job's own `permissions:` block cannot grant past that — declaring `pull-requests: write` does not lift it. **The resulting failure is asymmetric and worth naming**, because it went unnoticed for two days: the workflow computes the version plan, commits it, force-pushes `changeset-release/main`, and only then fails the single create-pull-request call. The release branch is left correct and current; the only missing artifact is the PR. Anyone watching for "did a Version Packages PR appear" reads that as *nothing to release*.

The organization setting stays off deliberately. That one checkbox covers create **and** approve together, org-wide, and an Actions run able to submit approving reviews is the specific grant that would hollow out the review gate this document describes elsewhere — a required check is satisfied by an approving report, whoever produces it. A token scoped to this repository alone, with contents and pull-requests write and nothing else, buys back PR creation without buying approval. Its cost is an expiry date. A lapsed `RELEASE_TOKEN` fails earlier and harder than the ceiling did — at `actions/checkout`, before any version plan is computed or any branch is pushed — so it leaves no half-finished release state behind. It is still silent in the same place that matters: no Version Packages PR appears, which is indistinguishable from having nothing to version.

**The token has to be given to `actions/checkout`, not only to the changesets step**, and the reason is a credential-precedence detail with a delayed and silent failure. Checkout persists whatever token it is given as an `http.extraheader` in `.git/config`, and that header takes precedence over any credential the action later supplies for its own `git push`. Pass the fine-grained token to the step's `env` alone and the PR is created by that token while the branch is still pushed by `GITHUB_TOKEN`.

That split matters because **GitHub does not trigger workflows on pushes made with `GITHUB_TOKEN`**. Creation is an API act, so the first Version Packages PR gets its checks and looks healthy. Every later force-push to that same branch then arrives as a `synchronize` carrying a new head SHA with no check runs against it, and required checks that never ran cannot be satisfied. The PR is unmergeable and shows its required checks as *pending* — which is the trap, because pending reads as "still running" rather than "will never run". Changesets land in batches, so force-pushing an open Version Packages PR is the steady state rather than the edge case, and this is the same silent-stall shape as the missing-PR failure above: the visible artifact exists, the invisible one does not.

With the token on checkout, both the push and the API calls run on it, and `GITHUB_TOKEN` is spent by nothing in the job — hence `contents: read` in the `permissions:` block. Declaring the write scopes it no longer uses would misstate which credential does what.

The action's `commit` and `title` are set to `Chore(release): Version packages` rather than left at its `Version Packages` default, because that default does not meet this repo's `Type(scope): Description` convention. Nothing mechanically rejects it — there is no commitlint here, deliberately, and adding husky to get one would fight `core.hooksPath` with the tracked ring-0 hooks — so the convention holds only where it is actually set, and this is the one commit no human writes. `setupGitUser` stays at its default: the commit remains authored by `github-actions[bot]`, because a machine did write it. The message follows the convention; the author stays honest about what produced the commit.

Publishing itself is `vinaya release`, run by hand with npm credentials rather than wired into `release.yml` — **on this repo's own toolchain**, `bun run release` is that command. Two reasons, not one: no `NPM_TOKEN` secret is provisioned for this repo's Actions runner yet, and even once it is, a human-triggered publish is the more defensible default for a package whose releases are still infrequent and each one is irreversible on the registry. Automatic publish-on-merge is a later, separate decision — not a gap in this pipeline. The command refuses to start unless HEAD is `main`, the tree is clean, HEAD equals `origin/main`, HEAD's commit is a "Version Packages" commit (or `--allow-any-commit` is passed), and `npm whoami` succeeds — the preconditions a human used to have to check by eye before typing `bun install --frozen-lockfile`, `bun run build`, and `bun run changeset:publish` in order. `--dry-run` prints the plan and publishes nothing.

**The publish is not finished until the tags reach `origin`.** `changeset publish` creates the annotated tag `@attalabs/vinaya@<version>` on the local commit it published from, but never pushes it. `vinaya release`'s last step is `git push origin --tags`, so this is no longer a separate step to remember — skip it and the registry gains a version while the repo's history shows nothing, which is exactly what happened for every release before `0.6.0`: fifteen npm versions, one pushed tag. Those tags were backfilled onto their publish commits from `npm view` gitHead metadata and content-identical-tree evidence (task 65) — except `0.1.0`, whose tarball was built from an intermediate PR-branch state that squash-merging destroyed, so no commit that built it exists on `main` and it stays honestly untagged. The tag is the only durable link from a registry version back to a commit; treat the push as part of the publish, not an optional afterthought. That push is a real `git push`, reaching the repo's own generated pre-push hook exactly as any other push would — `main-branch-refusal` passes a tag-only push (Issue #407, O2), so this step never needs `--no-verify`, unlike the hand-typed recipe it replaces. After the push, `vinaya release` prints `npm view <pkg> version` for every tag it just pushed, noting that `@attalabs/vinaya` is expected to lag the registry by around twenty minutes.

## Verifying a release — and why its expectations are derived, never written down

`apps/cli/scripts/verify-published-lifecycle.ts` installs the published tarball into a scratch directory outside this repo and exercises every shipped command against it. It is the only instrument that measures what adopters actually receive rather than what this working tree intends, and it is meant to be run green after each publish. Exercising a command does not always mean a happy-path run: `check --all` outside a workspace and the forge-write commands (`pr`/`issue` `create`/`edit`, run `--validate-only`) both assert their own by-design non-green shapes rather than being exempted for not succeeding cleanly. `studio` is no longer one of these — `prepack` now fetches attalabs' published Studio release artifact (`scripts/bundle-studio.ts`) and ships it in the `files` allowlist, so the exercise spawns the command, polls until it answers on its bound port, and asserts a real launch.

**Every expectation in it is derived from current source. That is a hard rule, and it was learned the expensive way.** The first run after `0.6.0` shipped exposed three hand-maintained constants, all stale, each failing in a way that could not announce itself:

- The version under test was pinned to `0.4.6`. A green run had been certifying an artifact three releases old. A stale pin cannot fail loudly, because the version it names is a real published version that really does pass — the run stays honest about the wrong subject.
- The `init` row asserted a hook at `.git/hooks/pre-commit`, in two separate copies of the same probe. Tracked hooks moved a fresh install to `.vinaya/hooks`, so both copies went wrong at once — and neither could notice, because the pin held the run at a release predating the move. **The two stale things hid each other**; un-pinning the version is what exposed the probe.
- The check count was the literal `15`. `review-gate` became an own-workflow check and correctly dropped out of `--all`, so the artifact reported 14 and the script called that a regression.

The shared defect is not that the numbers were wrong. It is that a hand-maintained expectation cannot distinguish *the published artifact is stale* — the one thing this script exists to detect — from *the expectation is stale*, and it blames the artifact either way. That turns the instrument into a source of false findings about the product, which is worse than having no instrument, because the findings are credible.

So the version comes from `apps/cli/package.json`, the check count from `coreCheckRegistry()` filtered by `runsUnderAll` — the same exported predicate `check --all` itself applies, not a re-derived `!ownWorkflow` copy, because a verifier that re-implements its subject's selection rule is testing its own copy and would go stale the moment `--all` gained a second condition — and the hook probe accepts every shape `resolveHookDir` chooses between. The command coverage set was already derived this way, from `@attalabs/vinaya-sources`' `COMMANDS` registry; the rest of the script now matches that discipline.

One ordering constraint follows from deriving the version, and it is the normal release sequence rather than an edge case: between merging the Version Packages PR and running `changeset publish`, `package.json` names a version the registry does not have, so the default mode cannot pass. That window is what `--local-pack` is for.

## What self-hosting costs, stated plainly

A repo on the vendored shape still runs ordinary content checks from its pull request working tree. Those checks are intentionally unprivileged: `vinaya-checks.yml` uses `pull_request`, checks out the proposed source, and may run adopter `ci.setup`. Vendoring therefore lets a pull request change the content checks that inspect it, and the install uses `--ignore-scripts` to block root/workspace lifecycle hooks and PR-added `trustedDependencies`. Do not treat those checks as merge authority.

The review gate is different. All three workflows that decide or refresh merge authority execute only trusted default-branch source:

- `vinaya-review.yml` uses `pull_request_target`, explicitly checks out `github.event.repository.default_branch`, and takes the PR number only from the server-created event payload. It never checks out, installs, builds, or executes pull-request content. It does not pass the contributor-chosen branch name into the authority check, and no branch prefix exempts that check.
- `vinaya-review-verdict.yml` is loaded from the default branch by `issue_comment`. Its evaluator also explicitly checks out the default branch. PR metadata is input data, not an executable source. The evaluator has read-only permissions; the separate retrigger job has only `actions: write`, checks out no repository code, and runs no Vinaya command.
- `vinaya-body-checks.yml` is the same boundary applied to `body-bare-digits`: its Changesets-release exemption live-fetches the PR's real author, keyed on the PR number, which `vinaya-checks.yml`'s `pull_request` job cannot resolve safely (that job's own workflow copy is the PR's, so the PR could redirect the fetch). This workflow runs `body-bare-digits` only, `pull_request_target`, same default-branch checkout, no PR content. `vinaya-checks.yml` never runs `body-bare-digits` — that check is `ownWorkflow: true`, same reasoning as `review-gate`.
- Adopter `ci.setup` is absent from all three authority workflows. In the published shape the trusted workflow invokes the exact published Vinaya version embedded in the default-branch file. In the vendored shape it installs and builds the default-branch checkout.

`pull_request_target` runs have the default branch as their Actions `head_sha`, so the verdict workflow cannot find a PR run by that field. The required workflow records the event's PR number and head SHA in its run name when the event is created; the retrigger selects that exact immutable title. It does not trust the mutable `pull_requests` snapshot returned for an old rerun.

This boundary has a bootstrap rule: a pull request that introduces or edits an authority workflow is still governed by the version on the default branch. The new boundary becomes live only after a principal reviews and merges it. `CODEOWNERS` ownership plus a repository rule requiring that owner's approval is the complementary control for changes to `.github/workflows/**`; it protects changes to the boundary but is not a substitute for the boundary itself.

One more generated workflow, `vinaya-task-log-collector.yml` (task-log-v1 task 4), uses the same default-branch trust boundary for a different purpose — publishing task-path CI evidence, never deciding merge authority. It triggers on `workflow_run`, loading from the default branch, and its one real content step downloads `vinaya-checks.yml`'s own uploaded artifact by the trusted `run-id` the `workflow_run` event names — never a value taken from the artifact's own bytes. The artifact's content is still treated as untrusted data: it is parsed (schema, size, redaction, repo-provenance checks — `apps/cli/specs/log.md` § CI task evidence outlives job logs) and never executed. `github.event.workflow_run.pull_requests` being empty for a fork-originated pull request — a documented GitHub Actions limitation — is this workflow's fork boundary: with no PR to resolve, it runs nothing.

That bootstrap rule describes the steady-state case: editing a workflow that already declares `pull_request_target`. A distinct and worse case is an adopter's first crossing of the `pull_request` → `pull_request_target` boundary — for example `vinaya upgrade` regenerating `vinaya-review.yml` from a pre-0.17.1 install, which shipped that exact migration. There, the pull request carrying the change is governed by *neither* version, not the old one: as a `pull_request` event it no longer matches (the pull request branch's own copy now declares `pull_request_target`), and as a `pull_request_target` event it still doesn't match (the base branch's copy, which is what GitHub actually evaluates for that event type, still declares the old `pull_request` trigger until the pull request merges). No workflow run fires under either event class, so the required check-run for that workflow never appears on the pull request — not failing, not pending, simply absent — which permanently blocks merge on a repo whose ruleset or branch protection requires it, recoverable only through a temporary ruleset bypass actor or admin override. `vinaya upgrade` now detects this transition by comparing the regenerated workflow's trigger type against what's on disk and prints an explicit warning, with the concrete recovery step, before the adopter pushes — surfacing it at upgrade time rather than leaving it to be discovered as a stuck pull request with no explanation.

One publication note: `aeg-root/` is in this package's `files` array and reaches every adopter in the tarball, while `specs/` is not published at all. `README.md` carries a short form of this claim, and together with `enforcement.md` it is the account an adopter actually gets. The sibling packages `@attalabs/aeg-core`, `@attalabs/aeg-forge-state`, `@attalabs/vinaya-sources`, and `@attalabs/aeg-types` carry their own `files` arrays now too (`atta-labs/vinaya#180`) — each scoped to `src` minus its own test files, `aeg-core` additionally dropping `bin/` and `src/fixtures/**`, since none of those are reachable from a real import of the package's `exports`. Internal-only test fixtures for these packages (captured Issue bodies, synthetic doctrine trees, a golden tranche snapshot) live in a `tests/fixtures/` sibling to the suite that reads them, not under `src/`, so relocation — not just the allowlist — is what actually keeps them off the registry. How a repo *reaches* that doctrine is deliberately indirect: the committed root `VINAYA.md` pointer names the package, never a filesystem path — an install location is a property of one machine, and the pointer is committed for every clone — and hands the reader `vinaya doctrine`, which resolves the bundled `aeg-root/` at read time wherever the CLI physically sits. In the vendored shape the bundled copy is a gitignored pack-time artifact, so `vinaya doctrine` falls back to the monorepo root's own `aeg-root/` — the same directory `bundle-doctrine` copies from.

`doctrinePointer()` (`atta-labs/vinaya#41`, superseding `atta-labs/attalabs#684`) generates more than that one resolution step. The pointer also names the three enforcement rings by one sentence each; where governance actually lives *in the adopter's own repo* — `vinaya.config.json` plus the real, dotted `.vinaya/` (hooks, doc-owners) — deliberately never the bundled `aeg-root/`, which is package content, not repo content; how to inspect what's running (`vinaya check --plan`, `vinaya doctor`); how to extend, naming only commands `COMMANDS` (`packages/sources/src/commands.ts`) marks `shipped` at authoring time (`vinaya new check`, `vinaya new noop-check`, `vinaya new role`, and the `roles` config block — the `new role`/`new noop-check` scaffolding commands `atta-labs/vinaya#42` shipped); and the env-allowlist/audit-trail security paragraph. Every fact the pointer states must stay reachable by an agent reading a freshly-initialized repo — a claim `doctor` can't resolve or a command `COMMANDS` doesn't carry as `shipped` is exactly the failure mode `atta-labs/attalabs#684` shipped and `atta-labs/vinaya#41` exists to kill.

Resolution has one rule stated plainly, not two shapes to keep straight: inside the author repository — this one, or any repo that carries its own `aeg-root/roles/` at its git toplevel — the tree is the doctrine, full stop; the bundle `bundle-doctrine` produces is a copy taken at publish time, for adopters who install the package without vendoring the tree itself. `resolveDoctrineRoot()` tries the tree first, whatever binary runs it — a globally-installed `vinaya` invoked inside the author checkout reads that checkout's own tree rather than whatever release the binary shipped with — and only falls back to the package-relative bundle where no such tree exists, which is every ordinary adopter, unaffected. `vinaya doctor` names which root a given checkout actually resolved and why (`tree` or `bundle`), so the distinction is never left to be inferred (`atta-labs/vinaya#408`).

The authority split is generated identically for published and vendored installations. A generated-workflow regression test must keep both shapes covered, because making only the vendored form trusted would leave ordinary adopters bypassable.

## Cutting a tranche natively — what the first forge-native walk measured

The first tranche cut directly in this repo (Milestone + `vinaya/tranche:*`-labeled Issues, no topology file) proved the gates decide from the forge — `branch-topology`, `dispatch-readiness` and `first-push-dispatch` all passed and refused correctly with no `AEG_REPO` override — and surfaced three facts a self-governing repo should know:

- **PR-body validation is two layers, and they can disagree.** `vinaya pr create` validates the body against `vinaya.config.json`'s `briefSchema.pr` sections; CI's `brief-shape` check additionally enforces the full brief-validation set (surface map, documentation-update list, worktree Step 0, stop conditions, autonomy clause) on any task branch. A body that satisfies the configured sections can therefore pass authoring and fail CI — measured live on this repo's first native task PR. Until the two read one section set, task-branch PR bodies must carry the full canonical form (`aeg-root/templates/pr-report-template.md`), not just the configured minimum.
- **Some refusal text used to still speak file-topology.** With `aeg-root/tranches/` absent by design, the gates' *decisions* were always forge-derived and correct, but `branch-topology`'s refusal message used to cite `aeg-root/tranches/<slug>.md` as if it were the source — a cosmetic degradation, not a wrong verdict, but one that could send a reader hunting a file that cannot exist in any repository, adopter or author. Fixed (Issue #232): the message now names the forge-registered topology honestly instead of a literal path.

  The coherence baseline used to be listed here too — `verify-dispatch` reported `UNAVAILABLE` because `verify-coherence --json` emitted git `fatal:` probe noise on stderr and the baseline capture concatenated stderr into the JSON it parsed. Both halves are fixed: the capture keeps the streams apart and the coherence path parses stdout alone, and the two probes whose miss is the expected answer no longer print. It was never merely cosmetic — concatenation made a genuinely crashed run and a chatty healthy one indistinguishable, so the field could not surface the one condition it exists for.
- **The Planner's forge surface is Issues-only.** `vinaya issue create` validates and writes task Issues, but no CLI command created the Milestone or the per-tranche `vinaya/tranche:<slug>` label (`init` cannot seed a label whose slug is unknowable at install time). Cutting a tranche meant two raw `gh` writes (milestone, label) followed by validated `vinaya issue create` calls.

  The label half is fixed (Issue #54): `vinaya issue create`/`vinaya issue edit` now create-if-absent the target `vinaya/tranche:<slug>` label themselves, right before the write reaches `gh` — the prefix family's suffix is still open-ended by design and unknowable at install time, so `init` still cannot seed it, but the label is minted the first time a task Issue names it rather than requiring a hand-run `gh label create`. The Milestone half is unchanged: cutting a tranche still means one raw `gh` write for the Milestone, followed by validated `vinaya issue create` calls.

**A tranche's identity is its `vinaya/tranche:<slug>` label, not a Milestone (`vinaya-milestone-model-v1` task 1).** The Milestone this repo's own first native tranches were cut with is still read the old way, forever — a Milestone titled exactly a tranche slug remains a valid, sufficient tranche marker, and none of this repo's existing tranches needed any change. What changed is what a NEW tranche requires: a Milestone is no longer necessary to exist at all (lifecycle is computed from the label's own Issues — `planned` with none, `active` with any open, `complete` once at least one exists and all are closed), and one Milestone may legitimately hold several tranches' labels at once. `vinaya archive tranche <slug>` now resolves "is this tranche done" from the Issues carrying its own label, not from a Milestone's `?milestone=<number>` Issue listing — the older query would have returned every sibling tranche's Issues too, the moment a Milestone held more than one.

## Dispatching a Milestone natively — what the first milestone wave measured

Attaching real task Issues to a shared Milestone (rather than tracking a tranche by label alone) surfaced two more forge-scale facts, both in `verify-dispatch`'s bare-edge qualification:

- **A Milestone's Issue count is unbounded, and a raw `gh api` fetch of it is not.** The bare-edge qualification reads every Issue attached to a task's Milestone to know whether a bare `Depends-on`/`Conflicts-with` id is ambiguous. Fetching them the ordinary way — one unpaginated request, full Issue bodies included — overran the shell-out's default output buffer the moment a real Milestone held enough Issues with real-sized bodies, failing the whole gate with `ENOBUFS` rather than a verdict. Fixed: the reader now asks `gh` itself to filter each Issue down to its `labels` before anything reaches this process's stdout, walking the Milestone page by page — a Milestone's size no longer bounds this read at all, only how many pages it takes.
- **A `Depends-on` edge naming a tranche-less backlog Issue must resolve through that Issue's own pull request, not its closed/open state.** A task's dependency can be a backlog fix with no tranche of its own; the resolver's branch-to-PR mapping only recognized a tranche task's `task/<tranche>/<n>` branch, so a merged backlog dependency was read as still unmerged. Fixed: a bare Issue number also resolves through its `task/issue-<n>` branch or a `Closes #<n>` PR-body reference, checking that pull request's own merge state — never inferring "merged" from the Issue being closed, since a backlog Issue can close without ever merging.
