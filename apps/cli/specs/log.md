# The Vinaya Log — header, families, and the outbox

Status: draft

One `log(e)`, one sink, one outbox per task. The full design is the Linear "Tech spec — The Vinaya Log"; this file is the durable, in-repo reference for what has shipped — the schema, the header, and the append — not a restatement of the whole spec.

## The envelope: `schema: 1`, `2` and `3`

`meta.schema` is a discriminated union. `1` is the original header — every field below in "The header, on every line," nothing more — and stays exactly as it was: a line already on disk, or a fixture recorded before these fields existed, keeps parsing without a schema violation just because it predates the fields below. `buildHeader` (`packages/aeg-core/src/log/envelope.ts`) builds `3` for every event (see "`schema: 3`" below); `1` and `2` are read-side compatibility shapes only, never something a caller asks `buildHeader` to produce, and a line of either reads back unchanged.

`schema: 2` adds:

```
event_id: string        // stable per-event identity, generated once per log() call
process_id: string      // opaque per-process identifier — distinct from run_id, which
                         // correlates a whole dispatch chain across processes
actor_id: string | null // opaque, UNVALIDATED role/actor claim from the environment —
                         // deliberately not checked against ROLE_VALUES; a doctrine role
                         // name and a role this schema has never heard of are equally
                         // valid here. subject.role (unchanged) keeps its own closed
                         // Role-union-or-'unattributed' meaning — the two fields answer
                         // different questions at different trust levels.
lineage: {
  run: string | null       // this process's run identity — VINAYA_RUN when a caller sets
                           // one (devReviewLoop sets it to its own loop_id), else this process's own run_id (never null)
  attempt: number | null   // VINAYA_ATTEMPT
  parent: string | null    // VINAYA_PARENT_EVENT — the event_id this one continues from
}
input_versions: {
  objectives_version: string | null  // mirrors review-input-manifest.ts's field set —
  brief_hash: string | null          // independent of subject.objectives_version
  ruling_ordinal: number | null      // (kept, unchanged); a producer may set either,
  policy_digest: string | null       // both, or neither
}
provenance: 'parent_attributed' | 'env_correlated' | 'self_reported' | 'unavailable'
                         // trust ordering the spec names: parent-generated attribution
                         // is stronger than worker-controlled environment correlation;
                         // self-reported text proves no authorization. buildHeader never
                         // upgrades itself to 'parent_attributed' on its own — it derives
                         // 'env_correlated' when VINAYA_ROLE/VINAYA_TASK are present,
                         // else 'unavailable'; only a caller that structurally knows it
                         // just spawned this exact child (a future dispatch.ts change,
                         // not wired yet) can assert a stronger value.
```

Every new field is declared here and honestly `null`/`'unavailable'` until a later producer starts setting it for real — "provenance fields are declared here, enforced later."

`packages/aeg-core/src/log/` is the policy layer: the zod schema (`LogEventSchema`), the pure envelope builder (`buildHeader`), and `redact`. No filesystem, no network, no process (`surface.md` "The rule"). `apps/cli/src/lib/log-sink.ts` is the one write: every environment read, remote read, package read, hostname and git call lives there, and it is the only file that opens the outbox path — proved by `apps/cli/tests/lib/log-callers.test.ts`.

**A `log-sink.ts`-only change is now reachable by pre-push selection through every test that exercises it by spawning the built CLI, not only the tests that import it directly.** Measured live: a change to this file alone made `vinaya check --all` print a warning twenty-five times instead of once, a real regression the file-import-only selector (`apps/cli/src/lib/test-selector.ts`) had no edge to catch, caught only because CI runs everything — `apps/cli/tests/commands/check.test.ts`, which spawns `bun apps/cli/src/index.ts check --all` as a subprocess and imports neither this file nor anything that does, stayed unselected. `apps/cli/src/lib/cli-spawn-tests.ts` closes this the same way `repo-scanner-tests.ts` closes the analogous gap for a test that reads the repository tree instead of importing it: a synthetic edge from the spawning test straight to the CLI entrypoint's own `all:` node, so the entrypoint's real, already-computed import edges (which reach this file) do the rest.


### `schema: 3` — the work, the way of working, the runtime and the source

`schema: 3` is every `schema: 2` field, unchanged, plus four more. It is a new version rather than extra fields on `2` on purpose: a log server that knows only `1` and `2` stores a `3` line verbatim as an unknown-version record (`apps/log-server/specs/server.md` § 3), where an extra field on `2` would make it reject the line as invalid and lose the event.

```
work: {
  ref: string | null       // the unit of work, OPAQUE — an Issue number as text, a ticket key,
                           // a branch name; never parsed. VINAYA_WORK_REF, else the Issue
                           // number subject.issue carries (as text), else null
  repo: string | null      // the repository, as meta.repo
  change: string | null    // the change under review (a pull request, a merge request); null until named
  revision: string | null  // the revision (a commit); null until named
}
flow: {
  id: string | null        // the way of working this event belongs to. VINAYA_FLOW; unset reads
                           // 'vinaya', because Vinaya's own process genuinely is that flow
  version: string | null   // VINAYA_FLOW_VERSION, else null
}
runtime: string | null     // the runtime that produced the event (VINAYA_RUNTIME), else null
source: string | null      // the source that emitted it (VINAYA_SOURCE), else null
```

Every value is `null` where unknown and never invented. `subject.issue` is unchanged: a Vinaya task's Issue number still fills it, and still becomes `work.ref` as text when `VINAYA_WORK_REF` is unset. An empty environment variable reads as unset. `actor_id`, `work.ref` and `flow.id` are all opaque, so an event from a process with no tracker Issue, an actor that is not a doctrine role and a flow that is not `vinaya` is written and read back through the storage contract unchanged. Any other `meta.schema` number stays an unknown-version record.

## The header, on every line

```
meta: {
  schema: 1
  ts: string          // ISO 8601, UTC, millisecond precision
  run_id: string       // VINAYA_RUN_ID; generated per process when absent
  seq: number          // per-process counter from 0; a reader sorts by this, never by file position
  repo: string | null  // 'owner/name' from the origin remote; null when it cannot be resolved
  vinaya: string       // the CLI version that wrote the line
  doctrine: string     // 'aeg-root@<sha>' for a tree checkout, the package version for a bundle, 'unknown' when git is unreachable
  host: 'hook' | 'ci' | 'cli' | 'loop'
  machine: string      // sha256 of the hostname; never the name itself
}
subject: {
  issue: number | null          // VINAYA_TASK; the checked-out task branch's Issue when that is unset; null when neither names one
  pr?: number
  sha?: string                  // a gate event only: the full 40-character commit id of the checkout's HEAD; absent when unresolvable
  role: Role | 'unattributed'   // VINAYA_ROLE; never self-declared by the caller
  round?: number                // VINAYA_ROUND
  objectives_version?: string   // deviation from the spec's `number`
                                 // hashes the objectives block to a sha256 hex string
}
```

`Role` is the doctrine-facing spelling from the spec's Role union: `planner | developer | code-reviewer | security | principal | archivist | architect` — not the `roles/*.md` filenames `resolveDoctrineRootInfo` resolves those names to.

**`subject.sha` on a gate event.** Every `gate` event — a run's `summary` and each `checked` event — records the commit it was checked at: the full 40-character id `git rev-parse HEAD` names in the sink's own working directory. The field is omitted — never a branch name, never a guess — when `git` is missing, the directory is in no repository, or the answer is not a 40-character hex id. It is resolved once per process and directory, lazily, only when a gate event is written, and reused for every later gate event, so no event costs a `git` call; a process recording nothing never reads it. No other family carries it yet. `HEAD` is what the checkout holds, not what the change's author pushed: a pull-request CI job checks out a merge commit of the pull request into its base, so a gate event from that job records that merge commit, not the pull request's head. The field is not part of `input_fingerprint`, which hashes the check's allowlisted environment and, for a diff-scoped check, the sorted changed-file list, never file contents; the two answer different questions. Together they tell a repeat of a run on unchanged code (same commit, same fingerprint) from a re-run on new code (a different commit) — and let a gate result be joined to the commit a run was made on.

## The families shipped so far

`kind` is a closed union of `'dispatch' | 'dev_review_loop' | 'forge_write' | 'gate' | 'operation' | 'usage' | 'role_attempt' | 'handoff' | 'effect' | 'custom'` — `custom` being the one family whose events a consumer declares itself (§ Custom events, below). `command`/`tokens` are still refused by name — `command` folds into `operation`, `tokens` into `usage`, so neither is a separate `kind`. Every event carries `duration_ms?` and a `payload` field; every family puts its real content in named top-level fields instead, so `payload` ships as an empty, `.strict()` object (an extra key inside it is still a schema violation).

**`dispatch`** — `target_role`, `model`, `round?`, `effect_id` on every event:

- `dispatched` — `prompt_hash`
- `outcome_received` — `outcome: DispatchOutcome` (a `type`-discriminated union: `pr_opened`, `round_pushed`, `verdict`, `escalation`, `brief`, `plan`, `archive`, `completed` — the generic "exited cleanly, no specific forge outcome" member, carrying no invented identifier), `usage: { input, output } | null`
- `dispatch_failed` — `reason: 'timeout' | 'crash' | 'refused' | 'unattributed_write'`, `usage: { input, output } | null` — a run's token record survives the manner of its death: the parent parses whatever the child had already printed to stdout at the moment it ends the child (a SIGTERM/SIGKILL timeout, a non-zero exit), the same `stdoutBuf` a clean `outcome_received` reads, rather than hardcoding `null` on every non-clean exit. `null` here means the buffer genuinely carried no parseable usage line, not that the path never looked.

**`dev_review_loop`** — `loop_id` on every event, fifteen events: `loop_started`, `round_started`, `gate_result_read`, `verdicts_read`, `findings_compared`, `stop_condition_met`, `paused`, `resumed`, `cancelled` (the `resolveEscalation(..., 'cancel', ...)` twin of `resumed`, always `by: 'principal'`: a cancel always requires an authenticated ruling, unlike a `resumed` bare infrastructure recovery), `unpushed_work_resume` (`branch`, `detail` — the driver's own mid-round resume of a developer who stopped without pushing), `round_ended`, `journal_finalized`, `infrastructure_retry` (`failure_kind`, `attempts`, `outcome` — below), and the `driver_heartbeat`/`driver_exited` liveness pair (below). Field-for-field these match the spec's §5.2 block exactly (`infrastructure_retry` is additive, a member the spec's §5.2 does not yet list); this file does not re-list every field to avoid a second copy drifting from the source. `resumed.by` widens additively from the spec's `'principal'`-only literal to `'principal' | 'driver'`: a bare `--resume` past an `'infrastructure'` recoverable hiccup authenticates as the driver's own recovery (`resolveEscalation`'s `authenticatedBy: 'driver-self'`), never a ruling this run never actually read — `devReviewLoop` logs `resumed` once, right after `resolveEscalation` succeeds, before the round loop re-enters; `cancelDevReviewLoop` logs `cancelled` once, right before returning. `verdicts_read.findings` is the one addition since: an optional `ReviewFinding[]` (empty findings lists still set it to `[]`) carrying every finding from both roles' verdicts this round, with its own `severity_scale`/`policy_treatment` populated from the real reported severity and the effective review policy — never only the coarse `blockers` count `assessRound` already logged. Optional, not required, so a `verdicts_read` line written before this field existed still parses. `gate_result_read` widens the same additive way, with the developer's stated confidence: `confidence_value` (a whole number 0–100) and `confidence_reason` (bounded, one line) for a real statement, `confidence_unavailable: true` for a missing or malformed one — never a fabricated `confidence_value` — and `extra_turn_spent`, whether the confidence rule's one extra developer turn had already been spent before THIS read (`apps/cli/specs/loop.md` § The confidence rule). All four optional and unset on round 1 and on a red gate. The event fires on every gate call, not only a round's first — a re-ask's own second read gets its own line rather than leaving the round's log on the first read's stale `confidence_unavailable: true` — so a `gate_result_read` line written before this addition still parses.

**`infrastructure_retry`.** Logged once per retry episode around one of the driver's own two infrastructure-class hiccups — never one line per attempt, which would make `attempts` redundant with the line count itself: `failure_kind: 'pause_comment_post'` for a pause/escalation comment post that failed at least once before succeeding or exhausting its bound (`pause-resume.ts`'s retry-with-backoff around `postPauseComment`/`postIssuePauseComment`), `'developer_connection'` for a developer dispatch that ended on the launcher's own `'connection-failed'` classification (`dispatch.ts`, below) and was waited-and-re-dispatched on the SAME session. `attempts` is the total number of attempts the episode made (always `≥ 1`); `outcome` is `'recovered'` once a later attempt succeeded — for a `'developer_connection'` episode this is the common case, and the round often continues straight to publish with no pause ever logged — or `'exhausted'` once the shared `MAX_INFRASTRUCTURE_RETRIES` bound (`round-assess.ts`) was reached with no success, which for `'developer_connection'` is followed by the ordinary `pause{reason:'infrastructure'}` every other infrastructure hiccup already produces. This is what lets a run that survived a network drop be told apart, after the fact, from one that did not: the pause/publish record alone cannot distinguish "never had a hiccup" from "recovered from one."

**`driver_heartbeat` / `driver_exited`.** The Log's own liveness pair for Mission Control — the one thing the Log could not show before: whether a loop for an Issue is *running right now*, as opposed to finished, paused or dead. Before them, a loop in its first Developer turn and one that died before pushing both looked identical from the Log (a `loop_started` with nothing after it), and a Developer turn can run for an hour with no other Log event, so silence could never mean dead.

- `driver_heartbeat` — `task` (the task Issue), `pr` (the pull request, present only once one exists — absent on a first Developer turn before any PR has opened), `round`, `phase` (the loop's current round and phase; `phase` is the same free-form string the control store's own `loop_state.phase` carries — `dispatch_developer`, `publish`, `pause`, …). While a review-loop driver process is alive it records one at most every five minutes — a `.unref()`'d timer, so it never keeps the process alive past the loop's own work, and a failed delivery is dropped like any other event, never a blocked or failed round. Only the driver ever emits it, never a reviewer or Developer child.
- `driver_exited` — `task`, `reason` (`finished` for a clean publish, `paused` for a decided pause, or `reexec` / `error` / `signal` for the three abnormal exits the driver already traces in its own role log), and `last_decision` (the driver's last decision, e.g. `publish` or `pause(infrastructure)`). Recorded exactly once per process exit, on every exit path — the clean publish/pause return as well as the three abnormal ones — from the one guarded function that also writes the role-log trace, so one exit writes it once. The heartbeat timer is always stopped before this line, so a stray tick can never land after it.

**How a reader decides, from the Log alone, whether a loop for an Issue is running.** Read that Issue's `dev_review_loop` lines in time order and apply the ten-minute rule: the loop is **running** when its newest lifecycle line (any `dev_review_loop` event — a `driver_heartbeat`, or any round/lifecycle event) is within the last ten minutes AND no `driver_exited` is newer than it; **exited**, **finished** or **paused** when the newest line is a `driver_exited` (`reason` tells which — `finished`, `paused`, or an abnormal `reexec`/`error`/`signal`); and **stale/presumed-dead** when the newest line is older than ten minutes with no `driver_exited` — a process that died without recording its exit (a hard `SIGKILL`, an OOM-kill, a reboot). Ten minutes is twice the five-minute heartbeat interval, so a single dropped or delayed heartbeat never flips a live loop to dead. The machine a loop runs on is `meta.machine`, on every line already — so the same read tells Mission Control *where* each loop is running, across every machine reporting to one Log. The log server stores a `driver_heartbeat`/`driver_exited` line it has not yet been redeployed to know verbatim as `unknown_version`, which a reader still parses.

**`forge_write`** — `op: ForgeOpSchema` (`pr.create`, `pr.comment`, `pr.body.replace`, `pr.refreeze`, `issue.create`, `issue.edit`, `issue.comment`, `milestone.create`, `milestone.edit`, `milestone.close`, `label.add`, `label.remove`) and `target: { issue?: number; pr?: number }` on every event:

- `validated` — the payload passed its schema check, about to be posted
- `refused` — `reason: string`; the forge write failed (or a pre-flight check refused it)
- `written` — `comment_ids: string[]`; every comment id the forge returned

No producer emits `forge_write` any more (§ No path to a tracker or a code host, below): the comment-posting flush that used to be its one caller, using only `issue.comment`/`pr.comment`, is deleted outright. The family stays in the schema so an already-posted comment line still parses; `apps/cli/tests/lib/log-callers.test.ts` carries its three events as an explicit coverage exemption. The other ten ops remain shaped for future forge-write call sites, not yet wired to one.

`dispatchRole` is the `dispatch` family's real caller, in `apps/cli/src/lib/dispatch.ts` — not `dispatch-role.ts`, this file's own earlier forward-looking guess at the filename. `devReviewLoop`/`cancelDevReviewLoop` (`apps/cli/src/lib/dev-review-loop.ts`) are the `dev_review_loop` family's real callers.

**`effect`/`operation` real callers.** `EffectExecutor` (`apps/cli/src/lib/effects.ts`) — the shared effect executor every idempotent forge write already runs through (`postPauseComment`/`postIssuePauseComment`, `pause-resume.ts`) — logs ONE `effect` `verified` event per call, carrying the write's final outcome (`'success' | 'failure' | 'uncertain'`): `success` once the write is durably recorded, `failure` when the poster threw, `uncertain` when a reconciliation came back `'ambiguous'` or the existing record is corrupt — a gap is a line in the log, never a fabricated success. An idempotent replay of an already-`'verified'` record logs its own one `verified` event. The local control-store record still advances through `started`/`verified`/`uncertain` — that is what recovery reads, and it is unchanged. **Expected per forge write: one `effect` event** (never `attempted`, never `observed`; those two stay in the schema so a line stored earlier still parses). `effect_id` is the SAME control-store key the write's own retry identity is keyed on, so every line for one write — across a crash, a retry, an idempotent replay — shares one identity. The broker (`apps/cli/src/lib/broker.ts`) logs one `operation` event for `authenticateWorkerInvocation`/`authenticateOperatorInvocation` (`operation: 'authenticate-invocation'`) and one for `requestEffect`'s own grant/target/replay checks (`operation`/`target` from the request), `result: 'ok'` when every check passes, `'refused'` naming the throwing error's own class otherwise — before ever reaching the effect executor's own sequence.

**`dispatchRole` is now also the `role_attempt`/`usage` families' real caller.** Per attempt — the pre-spawn refusal paths, a spawn-time crash, a timeout, and a clean exit alike — it logs one `role_attempt` `attempted` line (`actor`: the vendor; `attempt`: the same per-scope `LaunchRecord.attempt` counter this file already keeps for recovery; `effect_id`/`model` matching the paired `dispatch` line for the same attempt; `outcome` from `classifyRoleAttemptOutcome`, the generic launcher's own honest classification — refused, then timed out, then crashed, take priority over a bare exit code, which is `completed` only on a clean exit and `incomplete` otherwise; it never claims `normalizeOutcome`'s stronger `artifactsPresent`/`postconditionsMet` proof, which only a role-aware caller can check) and one `usage` `observed` line (`model`, `source`: the vendor, `semantics: 'cumulative'` — one dispatch is one full vendor invocation, so the parsed line already represents that invocation's own total, never a delta between two observations — `units`, `unknown_reason`). Both survive the manner of the attempt's death exactly as the `dispatch` family's own usage field already did: read from the same buffered stdout at the moment the child is ended, on every exit path.

Vendor usage parsing reads more than before: Claude's `cache_creation_input_tokens`/`cache_read_input_tokens` sum into one `units.cache` figure (both real Anthropic Messages API fields, present — `0` when unused — on every genuine `usage` object); Codex's `cached_input_tokens` is read the same defensive way when present. Gemini's real usage shape (`stats.models.<model>.tokens`, confirmed live, never a single `{ input, output }` pair) is not yet read for its inner fields — every Gemini dispatch reports `units: { input: null, output: null, cache: null }` with an `unknown_reason` naming that confirmed shape explicitly, never a guessed field name.

A caller that already resolved an objectives/brief/ruling/policy identity before dispatching (`dev-review-loop.ts`'s reviewer dispatch, from its `ReviewInputManifest`) can pass `DispatchOpts.inputVersions` to thread it straight into every line that attempt logs' `meta.input_versions` — the generic launcher itself never resolves one.

**`dispatchRole`'s own `outcome_received` lines no longer carry a placeholder `outcome`.** `DispatchOutcomeSchema` gained an eighth variant, `completed` — carrying no invented identifier at all, exactly the "completed, no specific forge outcome recorded here" gap this file used to name as missing. A successful dispatch's `outcome_received` line now reports `{ type: 'completed' }` honestly, never the `{ type: 'plan', issues: [] }` placeholder borrowed from an unrelated variant.

**Review finding metadata** — a `verdict` outcome's `findings` array widens additively. The pre-existing `id`/`severity`/`state?` shape stays exactly as it was (`id` is this finding's identity AS REPORTED in one round's comment — stable within that comment only; a reviewer's own positional numbering is never advertised as stable across rounds). New, all optional: `severity_scale` (a free string, not a closed enum — this doctrine already has two, code-review's and security's, and a third reviewer type should never need a schema change to name its own), `policy_treatment` (`'blocking' | 'non_blocking' | 'unavailable'` — a separate fact from `severity`: the same reported severity can bind or not bind a verdict depending on the effective review policy's threshold at review time), `confidence` (`0..1`, self-reported, never treated as calibrated correctness), `confidence_scale`, `confidence_source`. None of the four are required — an old finding missing them all still parses. No caller constructs a `dispatch`/`verdict` outcome yet; `dev_review_loop`'s `verdicts_read.findings` is this shape's first real producer, populating `severity_scale`/`policy_treatment` on `dev_review_loop`'s own `verdicts_read.findings` instead (above) — `reviewer-dispatch.ts` computes `policy_treatment` from the SAME `isProseLocation`/blocking-severities rule `evaluateReviewFindings` applies internally, over the same finding, since that evaluator's own return value has no per-finding annotation to reuse. `confidence`/`confidence_scale`/`confidence_source` stay unset — no reviewer grammar reports one yet.

## Six more families

Additive to the three above — nothing about `dispatch`/`dev_review_loop`/`forge_write` changed. Every one of these six carries `meta`/`subject` (the same versioned envelope) and `.strict()` payloads, same as before.

- **`gate`** — one gate runner's check run, two events. `summary`, one per run: `ran` (checks that executed, so `passed` + `failed`), `passed`, `failed` (every executed check that did not pass — a failure, a wait, a timeout or an error), `skipped` (not in `ran`), `failed_checks` (the names of the `failed` ones) and the run's total time as `duration_ms`. `checked`, only for a check that did not pass: `check`, `check_version`, `policy_version`, `input_fingerprint`, `outcome: 'pass' | 'fail' | 'wait' | 'skip' | 'invalid_input' | 'unavailable_dependency' | 'timeout' | 'cancelled'` and an optional `reason`. `pass` and `skip` stay in the outcome enum so a `checked` line stored before a passing check stopped recording one still parses; the runner no longer records either.
- **`operation`** — a normalized operation/tool call (the spec's "command dispatcher"): `operation`, `target`, one event `completed` with `result: 'ok' | 'error' | 'refused' | 'timeout' | 'cancelled' | 'unavailable'` and `error_class`. An optional `field_names` lists the field names an outcome concerns — set only by a refused custom event (§ Custom events), never a value. Never raw secret-bearing arguments — `redact()` still runs over the full event regardless.
- **`usage`** — the spec's "usage collector", and the one record of a dispatched turn's token use: a pull-request body carries no token table, and no role reports its own figures onto the forge for a dispatched turn — the Log is the one place that figure is recorded. What follows is that family's shape: `model`, `source`, `semantics: 'cumulative' | 'delta'`, one event `observed` with `units: { input, output, cache }` (each `nonnegative().nullable()` — unknown usage is `null`, never coerced to `0`) and `unknown_reason`. `dispatchRole` is its real caller (above) — always `semantics: 'cumulative'`, since one dispatch is one full vendor invocation.
- **`role_attempt`** — a role ATTEMPT's own normalized outcome, distinct from `dispatch`'s parent-side view of dispatching one: `actor` (opaque, NOT `RoleSchema` — this family is not limited to the closed doctrine `Role` union), `attempt`, `effect_id` (mirrors the paired `dispatch` line's own field — the evidence identity a reader joins the two families on), `model` (the runtime's own genuine receipt when the vendor gave one, else the pre-completion request label), one event `attempted` with `outcome: 'completed' | 'incomplete' | 'infrastructure_failed' | 'cancelled' | 'timed_out' | 'capability_refused'` and the same nullable `usage` shape `dispatch_failed` already uses. Named `role_attempt`, not `role`, so it never collides with this module's own `Role`/`RoleSchema` export. `dispatchRole` is the family's per-vendor-launch caller (above); `devReviewLoop` is a second caller for a narrower case — when a reviewer/security report itself fails to validate (`ReviewerReportParseFailure`/`ReviewerInfrastructureFailure`, `apps/cli/specs/loop.md`), it logs one more `role_attempt` line (`outcome: 'incomplete'` or `'infrastructure_failed'`, `usage: null`) so that failure is a durable record distinct from a clean, empty `verdicts_read`.
- **`handoff`** — a human handoff/escalation, raised then resolved: `class` (`'authority' | 'strategy' | 'product'`, reusing `dispatch`'s own `escalation` outcome enum rather than inventing a second name for the identical concept), `reason`; `raised` carries `requested_decision`, `resolved` carries `resolution`/`resolved_by` — two disjoint `.strict()` shapes, not one shape with everything optional.
- **`effect`** — the spec's "shared effect executor": a generic external effect's final outcome, one `verified` event with `'success' | 'failure' | 'uncertain'` (`attempted` and `observed` still parse, for a line stored earlier, and nothing records them), keyed by `effect_id` and an opaque `target: { kind, ref }`. Additive to, and does not replace, `forge_write` above, which stays exactly as it was — one specific effect this schema does not yet generalize `forge_write` into. Fail-open observation only ("telemetry never substitutes for required intent," the spec's own words) — never the fail-closed control store.

**`gate`'s real caller** — `apps/cli/src/checks/runner.ts`'s `runChecks`/`runOne` is the chokepoint: one `checked` observation per terminal outcome a single check attempt reaches that is not a `pass` or a `skip` — a passing or skipped check records none, only a count in the run's one `summary`, which `runChecks` records after every check has finished (a run of thirty checks with two failures records one `summary` and two `checked` events; a run where everything passes records one `summary`; **expected per check run: one `summary` plus one `checked` per check that did not pass**). This is what keeps the Log inside a log server's free daily write limit, where a `checked` line for every passing check was most of the day's events. A check killed mid-flight by SIGINT/SIGTERM is recorded as a `checked` event too (`outcome: 'cancelled'`, from the signal handler itself, since a killed check never reaches one of `runOne`'s own return statements to log itself — and suppressed there if it does, closing a real double-emission race the fixture tests caught live). `check_version` is fixed to `CHECK_SCHEMA_VERSION` (the check contract's own schema version); `policy_version` is honestly `null` — no per-check policy-version concept exists in the registry yet, left for a later task to set for real, the same "declared, not yet real" pattern this file already documents for `input_versions`/`lineage`. `input_fingerprint` is a `sha256` digest of the check's own constructed input (its allowlisted env plus, for a diff-scoped check, its sorted changed-file list) — never the values themselves, so a forwarded secret never reaches the log even hashed-and-readable. `reason` is always a short structured code (`missing_env:<KEY>`, `spawn_failed:<code>`, `timeout_ms:<n>`, `malformed_output`, `unexpected_exit_code:<n>`, `errors:<n>`, `pending_principal_action`, `signal:<SIGINT|SIGTERM>`), never a check's own free-text `CheckError.message`, which can itself echo PR/Issue body content the check was validating. Hook and CI invocations are distinguished from a plain interactive CLI run by `meta.host` alone (`'hook'`/`'ci'`/`'cli'`) — the generated pre-commit/pre-push hooks (`apps/cli/src/lib/artifacts.ts`) now set `VINAYA_HOST=hook` before invoking `vinaya check`; CI is already `GITHUB_ACTIONS`-derived. The other five families in this section still ship with zero real callers.

## Custom events: a consumer's own, declared in configuration

A repository records events Vinaya does not know about by declaring them in its own `vinaya.config.json`, under the existing `logs` key — no code written, and no new top-level key:

```json
{
  "logs": {
    "events": {
      "acme.deploy": {
        "fields": { "env": ["prod", "staging"], "count": "number", "note": "text", "ok": "boolean" }
      }
    }
  }
}
```

**The declaration.** Each entry of `logs.events` names one event and its flat fields. A field's type is `"text"`, `"number"`, `"boolean"` (yes/no), or a list of words the value must be one of. The rules, checked when the config loads — a declaration that breaks one is refused with a message naming the entry (and the field, when a field is at fault):

- The name is `<namespace>.<event>`, matching `^[a-z][a-z0-9_]*\.[a-z][a-z0-9_.]*$`, at most 64 characters.
- The `vinaya.` namespace is reserved for Vinaya's own events and cannot be declared.
- At most 20 fields per event; a field name is lowercase letters, digits and `_`, starting with a letter, at most 64 characters.
- A list of words names at least one word and at most 50, none twice; a word is lowercase letters, digits, `_` and `-`, at most 64 characters.
- Nothing else sits beside `fields`: no nested values, no lists as values, no free-form JSON.

`logs.events` is not a destination — it says what may be recorded, never where to — so it is not subject to the default-branch-only rule `logs.folder` and `logs.url` carry for an unattended caller. An events-only `logs` setting declares no destination, and the default folder applies.

**The `custom` family.** One event, `recorded`, carrying `name` (the declared name — data, never the discriminator) and `fields` (the values, flat: text of at most 500 characters, a finite number, or a boolean). `kind` and `event` are fixed; a `custom` event never sets its own header, kind or family. A `custom` line is valid only under a `schema: 3` header — the family is newer than `1` and `2`, so a line claiming either with a `custom` body is one this log never wrote.

**Recording one.** `emitCustomEvent(name, fields)` (`apps/cli/src/lib/log-custom.ts`) reads the declarations from the loaded config, checks the event (`checkCustomEvent`, pure, `packages/aeg-core/src/log/custom.ts`), and writes through `log()` — the same header, destination and redaction as every other event. A declared name with every declared field present, each of its declared type, and no other field writes exactly one `custom` line. Every declared field is required.

**A refusal is recorded, never silent.** When the name is undeclared, or a field is missing, extra, of the wrong type or too long, no `custom` line is written. Instead exactly one `operation` event is: `operation: 'log.emit'`, `result: 'refused'`, `error_class` the reason class (`undeclared`, `missing_field`, `extra_field`, `wrong_type`, `too_long`, the first that applies in that order), `field_names` the fields in that class, and `target` the name when it is shaped like one. Never a field value — a rejected value may be the secret — and an extra field name not shaped like one is recorded as `<unrecordable>`. The caller receives the same refusal as the return value.

**Redaction.** A secret-shaped value in a custom field is redacted exactly as in every other event: `redact()` walks every string leaf of the line, `fields` included (§ Redaction).

## The storage contract

`packages/aeg-core/src/log/store.ts` is the typed storage contract the sink and the flush share: one `LogStore` interface — `append`, `readPage`, `acknowledge`, `size` — plus the pure helpers both backends build on (`recordIdentity`, `classifyStoredLine`, `readPageFrom`) and a deterministic in-memory fixture backend (`createFixtureStore`). It is policy-layer pure — no filesystem, no network, no process (`apps/cli/specs/surface.md` "The rule") — so the adversarial fault cases below are provable against the fixture with no I/O.

<!-- AEG:CLAIM: packages/aeg-core/src/log/store.ts contains:export interface LogStore -->

- **Stable identity across retry, concurrent append and a lost acknowledgement.** `recordIdentity` reads a `schema: 2` line's `event_id` (generated once per `log()` call), falling back to `${run_id}:${seq}` for a `schema: 1` line — the same pair the flush's `<!-- aeg:log:… -->` marker is keyed on. `append` is idempotent by that identity: re-appending an already-stored batch is a no-op (reported in `AppendOutcome.duplicates`), so a retry after a lost acknowledgement collapses to one record rather than a duplicate.
- **Acknowledged records alone are removed.** `acknowledge(identities)` removes exactly the identities it is handed — never a positional truncation that could drop a record the forge never confirmed.
- **Overflow is reported, not silent.** A capacity-bounded store's `append` returns an `OverflowDiagnostic` naming the dropped identities — the observable loss the outbox rotation's single overwritten `<name>.1.ndjson` slot never surfaced.
- **Read-back validates version and provenance, and keeps unknown-version records.** `classifyStoredLine` / `readPage` run the full `LogEventSchema` (validating a `schema: 2` line's provenance), re-apply `redact()` at the read (transport) boundary, and — for a line whose `meta.schema` is outside `KNOWN_SCHEMA_VERSIONS` (`1`, `2`, `3`) — return an `unknown_version` record that keeps the line verbatim for diagnosis rather than dropping it or failing the whole page. A known version that fails validation is `invalid` (corrupt), a distinct outcome from `unknown_version`.

**Both backends implement the contract.** The deterministic fixture backend (`createFixtureStore`) is the in-memory twin the tests exercise (`packages/aeg-core/src/log/store.test.ts`). The real one is the live `logs` destination below: the sink's append is its write side, `classifyStoredLine` its read/transport-redaction side (run again before a server drain posts), and a server destination's tail-preserving, per-chunk truncate-on-confirmed-delivery is its acknowledgement side — the GitHub-comment adapter that used to fill this role (`vinaya log flush`) is deleted. Redaction runs at BOTH boundaries — `log()` redacts before the append (sink), `classifyStoredLine` redacts again before a drain (transport) — so a secret is filtered even if one boundary's pattern set has a gap.

## Fixture executions: named streams with a hand-written answer key

`packages/aeg-core/src/log/fixtures/` holds the deterministic event streams the tests of whatever reads the log are written against, reached through the package's `log` subpath (`buildExecution`, `buildExecutions`, `FACT_SHEETS`). Each execution exists to exercise one behaviour: green in one round; three rounds with a recurring finding and a stated confidence, with and without the extra turn; a pause and a resume; an escalation to a handoff; one check and input fingerprint at two commits with different outcomes, with no commit, and twice at one commit; cumulative and delta usage across two models with a retried attempt whose units are unknown; and the lines of an old or damaged store — schema `1`, schema `2`, a low-trust line from a CLI older than `0.33.0`, a schema version no build knows, a line that fails validation, and one event delivered twice.

<!-- AEG:CLAIM: packages/aeg-core/src/log/fixtures/executions.ts contains:export function buildExecutions -->

- **Generated, never committed.** Every valid line is built by the real header builder and parsed by the real event schema in the fixtures' own test, so a schema change that would invalidate a fixture fails there first. A deliberately invalid line (an unknown version, a failing line, a repeat) is raw text kept beside the valid ones and marked with how a reader should classify it (`valid`, `unknown_version`, `invalid`).
- **Deterministic.** Every time, event id, run id and commit derives from a seed and the execution's name — never the clock, a random source or a counter that outlives the call — so the same call returns the same lines byte for byte.
- **The answer key is written by hand.** `fact-sheets.ts` states each execution's line count, schema versions, round count, events per kind, distinct finding identities and models from the scenario, and the test compares each sheet with the lines. A later expected result is worked out from a sheet by a person, never from the code under test.

## The destination

Telemetry is never written to a tracker or a code host: no Issue or pull-request comment, no CI artifact. `vinaya.config.json`'s `logs` setting names where every event goes instead, live, as `log()` emits it — no end-of-round batch, no flush (§ The round-end flush's own removal, `apps/cli/specs/loop.md`). Exactly one of a folder or a server, resolved once per sink instance (`log-sink.ts`'s `resolveLogDestination`):

```
{ "logs": { "folder": "/var/lib/vinaya/logs" } }
{ "logs": { "url": "https://ingest.example.com/vinaya", "headers": { "authorization": "Bearer ${VINAYA_LOG_TOKEN}" } } }
```

**Reading it back.** Whichever destination holds the events, reading them back — paging a folder or a server, normalising each line into a dataset row or a quarantine record, caching the rows and querying them — is its own path with its own contracts: `log-sync.md`.

**A folder — the default.** Absent, `logs` resolves to a folder under this repository's own `runtimeDir` (`apps/cli/specs/loop.md` § Where the driver's own files live): `<runtimeDir>/logs/`. Either way, `log()` appends straight into `<folder>/<owner>-<repo>/<issue-or-none>.ndjson` — one line per event, in the order the run produced them, readable while the run is still going, and rotated exactly the way the local retry queue below already is. There is nothing to wait for and nothing to ship afterward: the append **is** the delivery.

**A server.** `logs.url` (optionally with `headers`) delivers each event as it occurs too: `log()` appends it to the local retry queue first (below), then drains that queue with the webhook sender (`drainOutboxToWebhook`, `apps/cli/src/lib/log-webhook-drain.ts` — renamed from `flushOutboxToWebhook`/`log-webhook-flush.ts` now that the one-shot `logPublish.webhookUrl` posting mode it used to also serve is deleted; its `outboxTask` argument accepts `null` for an unattributed process). The queue holds events only while the server is unreachable, and it catches up after an outage of any length: the drain delivers it from the HEAD in chunks of at most `MAX_WEBHOOK_BODY_BYTES`, oldest first, so a backlog larger than one POST is delivered over as many POSTs as it takes instead of failing forever behind the cap (§ The local retry queue). Drains are serialized onto one promise chain per sink instance, so two drains from the SAME process can never race each other's read-then-truncate of the same queue file; across processes — the loop's own reviewer and security roles, each with their own `vinaya` invocations, run concurrently against the same task — `drainOutboxToWebhook` also takes a cross-process `O_EXCL` lock on the queue file for the WHOLE drain, every chunk of it, so two processes contending for the same drain never race either: the loser returns immediately, untouched, and catches up on its own next event's drain.

A lock abandoned by a holder that crashed mid-drain still has to be stolen, or it would jam every later drain of that queue forever — but "abandoned" is decided by IDLENESS, never by how long the drain has been running. The holder renews the lock before every chunk it POSTs, so `WEBHOOK_DRAIN_LOCK_STALE_MS` bounds the gap between two renewals rather than the length of a drain, and one chunk is itself bounded by `WEBHOOK_FETCH_TIMEOUT_MS`. This is what a fixed multiple of one POST's timeout could not do once a drain covered several buckets and several chunks each: a slow-but-responding endpoint could hold the lock legitimately for many times that timeout, and a second process would then steal it from a holder still actively delivering, leaving both reading and truncating the same bucket. A holder whose lock is taken over anyway learns at its next renewal and stops there rather than writing alongside the new owner; because every acknowledged chunk is already cut from its bucket's head, the new owner resumes from exactly that point, in order, with nothing posted twice.

<!-- AEG:CLAIM: apps/cli/src/lib/log-webhook-drain.ts contains:export function renewDrainLock(lockPath: string, token: string): boolean -->

**Header values come from an environment variable.** `logs.headers`' values are substituted through `${VAR_NAME}` (`resolveLogsHeaderValues`, `apps/cli/src/lib/config.ts`) at delivery time, by the process actually posting — read only from that process's own environment, never stored as a literal secret in the committed config, and never resolved by, or handed to, a dispatched worker's own environment. There is one source and no platform-specific second one: a consumer points `logs.url` at a server and exports the token the referenced variable names, on any platform. A `${VAR_NAME}` whose variable is **not set** resolves to the empty string rather than a throw — an authentication failure at the destination stays the observable signal, never a crashed sink — and a variable set to the empty string (a withheld fork secret) resolves to the empty string too.

**Default-branch only, for an unattended caller.** `logs.folder`/`logs.url` is a filesystem path or a URL a pull request under review could otherwise redirect in its own diff — `resolveTrustAnchorLogsDestination` (`apps/cli/src/lib/config.ts`) gates it exactly the way `runtimeDir` already is: an unattended process (`isUnattendedProcess` — every dispatched role's child, since `VINAYA_ROLE` is always set) honours a working-tree value only when the repository's DEFAULT BRANCH declares the identical one; anything else falls back to the default folder, never to "no destination." An attended, human-run command honours the working tree directly. `logs.folder` must also be an absolute path — a relative one is refused at config-load time, the same rule `runtimeDir` carries. A `logs.folder` naming the repository itself, or anything inside it, is refused outright for either caller, attended or unattended — `runtimeDir`'s own `isInsideRepo` rule — since a confined role's own write access must never reach the append-only log recording its own task.

**The trust-anchor read that decides the destination has its own deadline, not the per-event one.** For an unattended caller the anchor read (`gh api` for the default branch's `vinaya.config.json`, `loadTrustAnchorConfigAsync`) is what decides where a whole run's telemetry goes, and it happens ONCE per process PER REPOSITORY — cached by resolved repository root (`processTrustAnchorByRepo`, `log-sink.ts`), off `log()`'s own return path (`log()` stays fire-and-forget; only the first line's landing waits on it). Keying by repository root, not one process-wide slot, is what lets a process that logs from two repositories — a `bun:test` runner loading many test files, each in its own fixture repository — read each repository's config exactly once and never serve one repository's config to another (see "The anchor read is cached per repository" below). It is bounded by `LOG_DESTINATION_ANCHOR_DEADLINE_MS` (`log-sink.ts`, `8s`), deliberately longer than the per-event `LOG_CONTEXT_LOOKUP_DEADLINE_MS` (`3s`) the branch/repo/doctrine reads use: a per-event lookup that expires under-attributes one event, but this one expiring reroutes the ENTIRE run silently. A developer's Mac clears the read in a few seconds (keychain-backed `gh` auth cold-start plus a home-network round-trip); a datacenter VPS clears it in well under one. Under the old `3s` bound the Mac expired on every run and resolved the local folder while the VPS resolved the configured server. The bound sits above a real Mac read but below the inner `gh` timeout (`config.ts`, `10s`, which kills a genuinely hung child with `SIGKILL`), so a hung read falls back at this deadline rather than waiting for the child's own kill, and the reroute is bounded by one value here. `vinaya doctor`'s own `[logs]` probe bounds this identical read by the identical deadline, so it can never report a folder the sink no longer uses.

**The anchor read needs `gh` to START, and the CLI's entry path guarantees it can.** The trust-anchor read invokes `gh` by name and relies on the process PATH to find it. A `gh` that cannot even start — not merely one that is unauthenticated — makes `loadTrustAnchorConfigAsync` return `null`, and an unattended sink with a null anchor falls back to the local folder. That is how every review-loop run a Mac Operator started delivered its round events to the folder instead of the configured server (2026-09-28): the Claude desktop app starts `task-tools serve` with a PATH that lacks `/opt/homebrew/bin`, where Homebrew keeps `gh`. The CLI's entry path (`apps/cli/src/index.ts`'s `ensureGhOnPath`) closes this at the source, once, before any command runs: when `gh` is not already reachable it appends a standard install folder (`/opt/homebrew/bin`, `/usr/local/bin`) that holds an executable `gh` to this process's own PATH, so this read — and every other `gh`-by-name call site — resolves it, and every child the CLI spawns inherits the amended PATH. A PATH that already finds `gh` is left unchanged. When `gh` is at none of those locations and not on PATH, `vinaya doctor` reports it missing and names where it looked (its `[gh]` finding).

**A fallback to the folder says why, once.** When an unattended run DID configure a `logs.url` server the trust-anchor gate then refuses, the resolved folder destination carries a `FolderFallbackReason` (`log-sink.ts`) rather than rerouting silently. Two kinds, named apart because they are different incidents with different fixes: `anchor-unreadable` — the default branch's config could not be read AT ALL to confirm the url (offline, unauthenticated, or slower than the deadline `gh`), transient and recoverable (nothing is lost; the events wait in the folder and `vinaya log send` delivers them); `anchor-mismatch` — it WAS read and declares a different url, so the working-tree value is refused (a pull request cannot redirect telemetry), a standing configuration divergence. `log()` prints the reason once per process (never once per event, `describeFolderFallback`), and `vinaya doctor` reports the same reason through the same function — `info` for `anchor-unreadable` (offline loses nothing), `warn` for `anchor-mismatch`. The ordinary default folder — no `logs` configured anywhere — carries no reason and stays exactly as silent as before. This is scoped to a configured SERVER not being used: a working-tree folder the anchor disagrees with still falls back silently, since there is no "server not used" to name.

**The reason is durable, not only on standard error.** The one-per-process standard-error line above is lost when the launch path does not keep the run's stderr — which is exactly how a Mac Operator's review-loop run rerouted all 47 of its round/dispatch/usage events to the local folder on 2026-09-28 with nobody able to see why: the Claude desktop app that started `task-tools serve` kept no standard error. So the SAME fallback branch in `log()` (`recordFolderFallback`, `log-sink.ts`), once per process alongside the stderr line, also writes the reason where the driver already writes its narration — the task's own `driver.log` (`<runtimeDir>/tasks-execution/<issue>/output/driver.log`, `loop-log.ts`), when the event names a task — AND records it in one machine-local state file, `~/.vinaya/fallback/<owner>-<repo>.json` (keyed the same `<owner>-<repo>` way the outbox is, `unresolved` when the remote cannot be resolved, never in the repository tree). It carries the time, the rendered reason, the intended url and the fallback kind. The runtime dir for `driver.log` is `dirname(destination.folder)`: a refused `logs.url` always falls back to the DEFAULT `<runtimeDir>/logs` folder, never a configured one, so its parent is the task's runtime dir. Every write here is best-effort and never throws — a narration/state write must never break the run it is narrating. `vinaya doctor` then reports the state file as one `[logs-fallback]` finding, `info`, `last fallback: <time>, <reason>` — a historical fact that never reddens the command on its own (the live `[logs]` finding already reports where events go now); absent when no fallback is recorded.

### Sending a local folder's events to the server

`vinaya log send` (`apps/cli/src/commands/log-send.ts`) delivers a repository's locally-held events to the configured `logs.url` server, once. It exists for exactly the state the fallback above leaves behind, and for a retry queue a dead drain stalled: events written to the local default folder because an unattended run fell back there, and events (including a `<name>.draining.ndjson` a dead drain left) sitting in the retry queue for a task whose run has ended, which nothing else will ever drain.

It resolves the destination the SAME way a live event does — the sink's own decision function over `vinaya.config.json`'s `logs` setting, trust-anchor-gated for an unattended caller, bounded by the same deadline — never a URL passed on the command line; a repository whose destination is a folder or `none` has nothing to send to a server and the command says so and exits non-zero. It moves each folder file's lines into the retry queue with the sink's own hardened append and then drains every queue for this repository through `drainOutboxToWebhook`, the identical webhook delivery a live event uses — so the folder's events are validated, chunked, and set-aside-on-corruption exactly as any other, and a stale draining file is picked up by that same drain. Delivery is idempotent: the server stores by `event_id` and ignores a line it already holds (`apps/log-server/specs/server.md`), so a re-sent chunk creates no duplicate, and removing each folder file after moving it into the queue keeps a second run from re-appending — a second `vinaya log send` finds the folder emptied and the queue drained.

**`vinaya doctor` reports where the log credential was found.** Beside the `[logs]` destination finding, a `[log-credential]` line names, for each variable a `logs.headers` value references, whether it was found in the **environment** or is **not set** there — the one source delivery reads (`resolveLogsHeaderValues` substitutes each `${VAR}` from the environment), so the two can never disagree about where the value comes from. It is always `info` and never the value itself: only the environment variable's presence is inspected. A variable set in the environment (even to the empty string) is reported as the environment; anything else is not set.

**`vinaya doctor` reports whether the destination works.** Fail-open is what makes this necessary: a destination that refuses everything it is sent looks exactly like a healthy one from the config's side, and the run it belongs to never slows or fails to say otherwise. This repository's own server refused every event with `401 Unauthorized` for most of a day, local queues grew, CI's died with their runners, and nothing surfaced it. Doctor's `[logs]` finding answers the question the config cannot: for a server destination, whether it is reachable and whether it accepts THIS machine's credential — naming the environment variable to set when it does not, never the value in it; for a folder destination, whether the folder (or, when it does not exist yet, the nearest existing parent the sink's own recursive create would reach) is a writable directory. A `none` destination is reported as what it is and is never a failure, but the variable its absence turned on is still named: "this job holds no delivery credential" is the incident shape itself, and the name is what makes it fixable.

The check stores nothing. It resolves the destination through the sink's OWN decision (`resolveLogDestinationFrom`, never a second reading of `logs`), takes the repository identity from the same `resolveRepo` the sink's own default dep uses, and bounds the trust-anchor read with the same deadline the sink bounds it with — all three so the two can never disagree about where events go, and so a lost child exit cannot hang the command where the sink would merely degrade. It then POSTs one EMPTY body to that destination: the ingest route authenticates before it reads anything and a body with no lines stores no rows (`apps/log-server/specs/server.md` § `5`).

**Only a `2xx` is an acceptance.** `401`/`403` is the credential being refused; every other status is the destination refusing delivery and is reported as an error too, never as health. A wrong path in `logs.url` answers `404` — produced before any token is compared, so it authenticates nothing — and a destination missing its own ingest secret answers `500`; each discards every event exactly as silently as the `401` this check was written after, which is the whole failure it exists to end. A destination nothing answers from at all is neither: it is reported and never fails the command, because an offline machine loses nothing — its events wait in the local retry queue for the next run.

**A caller on a CI host is treated as unattended whatever `VINAYA_UNATTENDED` says.** Delivery already refuses a working-tree destination the default branch does not declare; a diagnostic that reaches the network must not be the one caller exempt from that gate, or a pull request could redirect this probe — and with it the job's own environment — to a host it chose in its own diff.

**What is kept out of the printed finding.** Three spellings of the credential are removed from any text the destination composed: the resolved header value, the credential inside it without its scheme word, and the value of each variable the headers reference (which covers a header whose credential is only part of its value). The URL is printed with its userinfo and any credential-shaped query value replaced, since `logs.url` is a bare URL in the schema and can carry a credential itself — `userinfo` genuinely functions as one, `fetch` turning it into an authorization header. Refusing such a URL at config-load time would be the stronger fix and belongs to the config surface, not here.

### The self-test: delivery proven end to end

`vinaya doctor`'s `[logs]` probe POSTs an EMPTY body — it proves the destination authenticates this machine, not that a real event survives the full round trip. `vinaya log selftest` (`apps/cli/src/commands/log-selftest.ts`) is the stronger proof the Principal asked for: whether logs work must be a check the machine answers, not a claim from code or agents. It resolves the destination EXACTLY as an unattended review-loop run does — `resolveUnattendedLogDestination` (`log-sink.ts`) forces `unattended: true` through the SAME memoized trust-anchor read (`processTrustAnchor`), the SAME trust-anchor rule (`resolveLogDestinationFrom`), and the SAME credential lookup (`resolveLogsHeaderValues`) the sink uses, so running it by hand proves the launch path's own resolution rather than a human's attended one. It then sends ONE marked test event to the configured server and reads it back from the server by the event's own `event_id`, through the server's cursor read (`GET …/events?after=`, paging until found or a bounded `LOG_SELFTEST_MAX_PAGES`).

It prints `PASS` and exits `0` only when the event round-trips. Otherwise it prints `FAIL: <reason>` and exits `1`, naming the ONE reason that stopped it: no server is configured (a folder destination with no fallback, or a `none` destination's own reason), the default branch's config could not be read to confirm the url and why (`describeFolderFallback` on an `anchor-unreadable`/`anchor-mismatch` fallback), this host holds no ingest or no read credential (named by the variable to set), the server refused the send or the read with its HTTP status, or the event was accepted but could not be read back. It never prints a credential value — a reason names the variable, never its contents.

**The credential check reads the environment, exactly as delivery does.** The "holds no ingest credential" reason is `logsCredentialMissing` (`apps/cli/src/lib/log-sink.ts`), the same check the CI destination path uses — and it reads the one place delivery substitutes a `${VAR_NAME}` from: the process environment. A variable absent or empty there is missing (an empty value — a withheld fork secret — is no credential either), so the self-test names the variable to set rather than proceeding; a variable set there is present and the self-test proceeds to a real send.

**The read credential is `logs.readHeaders`, separate from the write-only `logs.headers`.** The server refuses an ingest token on a read route (its `INGEST_TOKEN` is write-only, `READ_TOKEN` read-only, `apps/log-server/specs/server.md`), so reading the event back needs a READ credential. `logs.readHeaders` carries it, resolved through the identical `${VAR_NAME}` environment substitution `logs.headers` uses, and is NOT trust-anchor gated the way `url` is: it is this machine's own credential for reading back from a url that gate already approved, not a destination a pull request's diff could redirect. A run with no `logs.readHeaders` fails with exactly that reason.

**This repository declares the read credential in its own `vinaya.config.json`.** Both tokens reference distinct environment variables: `logs.headers` references `${VINAYA_LOG_TOKEN}` (the write-only ingest credential) and `logs.readHeaders` references `${VINAYA_LOG_READ_TOKEN}` (the read-only credential). CI is given the ingest credential only; `vinaya log selftest` on a machine that holds both credentials sends one event to this repository's log server and reads it back by its id, proving end-to-end delivery.

**The test event is marked so a reader can exclude it.** It is a `kind: 'operation'`, `operation: 'log.selftest'` event — a real, schema-valid line built through the same `buildHeader` every event uses, carrying the self-test's own minted nonce as its `meta.event_id` so the read-back matches it precisely. The fixed `operation` marker is what a log page or an event count uses to leave self-test traffic out of real telemetry. Delivery reuses the server's ingest contract (a `POST` of `application/x-ndjson`, the same content type `drainOutboxToWebhook` sends); the self-test sends its one event directly rather than through the retry queue, so it proves delivery in isolation without draining or disturbing a task's real queue.

**Fail-open, always.** A destination that cannot accept an event never fails or slows the run producing it: `log()` never throws, a folder append that cannot be written funnels into the sink's existing one-per-process `warn`, and a server drain that fails only warns and leaves the event queued for the next attempt. **Drained once, on an abrupt exit — never per event.** `log()` stays exactly as fire-and-forget as it always was: nothing about it changed. What changed is that a `log()` call is asynchronous under the hood (the shared repo/doctrine/destination resolution, `createLogSink`'s own `context()`) — a caller that calls `process.exit()` before that resolution settles would otherwise drop the write entirely, since `process.exit` tears the process down with no microtask draining, unlike letting a process fall off the end of `main` (which already lets everything already scheduled finish). `createLogSink`'s returned `drain()` — and the module-level `drainLogSink()` for the default sink's own `log()` — waits for every `log()` call still in flight to land, then for any webhook drain those writes scheduled to settle. **Held by a real signal test, not by inspection alone.** `apps/cli/tests/lib/log-destination.test.ts` spawns a real subprocess that logs one event and sends itself `SIGTERM` in the same synchronous turn, once with a handler that awaits `drainLogSink()` before exiting and once without — the write lands in the first case and is genuinely dropped in the second, proving the guarantee above by the failure it would actually produce if a future signal handler stopped awaiting the drain, not merely by reading the code that calls it.

### Recording an event at process exit

`logSync(e)` (`log-sink.ts`, and `logSync` on every `createLogSink` instance) is `log(e)` for a caller that ends the process straight after it: the event's line is appended before the call returns, so a `process.exit` on the next line loses nothing. Use it where awaiting `drainLogSink()` is not possible — a command that ends the process from any of many places — and use `log()` everywhere else; `logSync` does not replace the drain for events already in flight.

**What it does.** It builds the header with the same `buildHeader`, validates the line against `LogEventSchema` and redacts it exactly as `log()` does, and appends it through the same hardened append to the same file: a folder's `<repository>/<task>.ndjson`, or the local retry queue a server's drain reads. Both functions share one writer inside the sink, so the two lines cannot differ in how they are built or placed. It uses the same `run_id`, `process_id` and `seq` counter as the sink's `log()` calls, and a fresh `event_id`.

**What it never does.** It spawns no process and awaits nothing. It never reads `git`, `gh` or the default branch's config. It reuses only what the sink has already resolved: the repository, the doctrine and the destination once the sink's shared context has settled (its warm-up, or an earlier `log()`), plus the branch's Issue and a gate's commit once an earlier lookup has answered them. A field it cannot know is not guessed. `meta.repo` and `subject.issue` are `null`, `meta.doctrine` is `unknown`, and a gate event carries no `subject.sha`. A failure to write never throws and never changes the caller's exit code: it is reported through the sink's one-per-process warning and dropped.

**Where it writes before the destination is resolved.** `unresolvedLogDestination` decides this from the environment and the working tree's own `vinaya.config.json` only. On a CI host it records nothing and says why once, as `log()` does with no server destination. A folder there is never a destination, and a server cannot be confirmed without the default branch's config. Anywhere else it writes to the folder `log()` falls back to when a server cannot be confirmed. That is the working tree's own `logs.folder` for an attended caller, and otherwise `<runtimeDir>/logs`. It never picks a server here: the retry queue a drain reads is named by the repository, which is still unknown at this point, so a queued line would never be delivered. A folder line is delivered later by `vinaya log send`. The warning names the folder.

**What it cannot promise.** It does not deliver. On a server destination the line waits in the local retry queue until the next drain for that task: a later event's own drain in any process, or `vinaya log send`. That drain posts it once, with the `event_id` it was written with, and the server keeps one copy per `event_id`. A process that never runs again on that machine, such as a discarded CI runner, never delivers it. `logSync` also does not order itself behind earlier `log()` calls still in flight. Its line can land ahead of theirs, and those are lost at `process.exit` unless the caller awaits `drainLogSink()`. `meta.seq` still numbers the events in call order.

**Held by tests.** `apps/cli/tests/lib/log-sink.test.ts` covers five things. The line is on disk when the call returns. The real default sink in its own process makes no spawn, synchronous or not, before a `process.exit`. The line matches a `log()` line apart from `meta`, and an invalid or unwritable one only warns. A CI host records nothing. A line written just before a warmed-up server-destination process moves on waits in the queue, is posted once by the next process's drain with its original `event_id`, and is not posted by a further drain.

## The local retry queue

One file per task Issue under the machine-local home `~/.vinaya/` already used by `config.json` and `tokens-collect-trust.json` — never in the repository (doctrine forbids task state in the tree; per-task worktrees would fragment a repo-local file):

```
~/.vinaya/outbox/<owner>-<repo>/<issue-or-none>.ndjson
~/.vinaya/outbox/unresolved/<issue-or-none>.ndjson   // when the origin remote cannot be resolved
```

No longer where `log()` delivers by default — that moved to a folder destination, above — but still where `log()` itself appends first for a configured `logs.url` server destination before draining it (the only remaining reader/truncator now that the tracker-posting flush and its artifact commands are deleted). Deliberately NOT under `runtimeDir` (`apps/cli/src/lib/run-paths.ts`) even so: a retry queue is machine-local plumbing, not one task's own run file, and `<owner>-<repo>` already keeps two repositories' identically-numbered tasks apart without collision. `log-sink.ts`'s `telemetryOutboxRoot` is the named home for this decision, and `apps/cli/tests/run-paths-only.test.ts` — which fails the build when any other source file assembles a run-file path — names this module as its single exception.

`<issue-or-none>` is `subject.issue` when it resolved to a number, else the literal `none`. The append is hardened the same way the Stop hook's own scratch-then-rename write is, adapted for an append rather than a full-file replace (a rename would drop every earlier line): `mkdirSync(dir, { recursive: true, mode: 0o700 })`; `lstatSync` the target and refuse — write nothing — when it exists and is not a regular file or is a symlink; `openSync(path, 'a', 0o600)` and one `writeSync` ending in `\n`; close. The file rotates to `<name>.1.ndjson` (overwriting an older one) once it crosses 8 MiB, before the append that would have exceeded it — one rotation slot, not a numbered series. A folder destination's own file rotates identically.

Before that overwrite, `reportRotationOverflow` reads whatever the existing `<name>.1.ndjson` backup holds and reports the loss: each line's identity via the storage contract's own `recordIdentity`, folded into an `OverflowDiagnostic` (`{ reason: 'capacity', dropped, droppedIdentities }`), emitted through the sink's one-per-process `warn`. No prior backup (the first-ever rotation) reports nothing.

<!-- AEG:CLAIM: apps/cli/src/lib/log-sink.ts contains:function reportRotationOverflow( -->

`log()` never throws. Every failure path — an invalid payload, an unwritable directory, a symlinked target — returns without writing, and at most one line reaches `process.stderr` per process, guarded by a module-level flag: a broken destination must never spam a gate or redden a check.

### The queue drains in bounded chunks, each acknowledged on its own

A server destination's drain takes the queue from its HEAD, in chunks of at most `MAX_WEBHOOK_BODY_BYTES`, and removes exactly the bytes a `2xx` acknowledged before it builds the next chunk. A queue bigger than one POST is therefore an ordinary backlog, not a permanent failure: at this repository's own event volume a server outage of about three quarters of a day already carries the queue past that cap, and a whole-file POST would have thrown before sending anything on every drain from then on.

The queue only ever grows at its tail, so the head chunk is stable: a drain whose acknowledgement is lost — a timeout, a killed process — re-sends the identical head chunk on its next attempt, and the server collapses the two by the stable event identity every line carries (§ The storage contract). Delivering the same chunk twice is safe; skipping one is not, so the drain always prefers the resend.

A chunk the server does not accept ends the drain. The queue is left holding exactly what was never confirmed: everything, when the server was unreachable from the first chunk, or the remainder alone when part of a backlog had already been accepted — waiting under the private name below, which is where a later drain picks it up.

### Every bucket is renamed aside before it is drained, oldest first

A drain never reads or writes a path a producer can touch. `log-sink.ts`'s append and its rotation both act on `<name>.ndjson`, and neither takes the drain lock — an append must never block on a network call — so the drain moves each bucket to one private name, `<name>.draining.ndjson`, before reading a byte of it, and delivers it there.

That rename is what makes removing bytes safe, and it is the whole guarantee: a drain that removed bytes from the shared live path could have that path renamed out from under it at any moment, including while a chunk is in flight. The rotation would move the file being drained to `<name>.1.ndjson` and create a fresh one at the same path, and the next removal would then truncate THAT file using byte offsets computed against the old one — destroying every line appended since, while bytes the server had already acknowledged sat in the new backup slot waiting to be posted a second time. A queue large enough to need several chunks is by definition near the rotation cap, so this is the ordinary shape of an outage recovery, not a remote one. With the bucket renamed aside, a producer's appends land on a fresh `<name>.ndjson` the drain never touches, and the next drain delivers them. Note the consequence for a reader: while a drain is running, or after one that failed, the events it is carrying are in `<name>.draining.ndjson` rather than at the live path.

Buckets are drained oldest first, one at a time: whatever a previous drain left behind, then the rotation backup slot `<name>.1.ndjson`, then the live file. A bucket is claimed by the rename alone — never a size check taken before it — so the bucket a drain goes on to deliver is exactly the one its own rename moved, whatever a concurrent rotation does to the source path on either side of that instant. Each is delivered and its file removed before the next is renamed into its place, so exactly one `<name>.draining.ndjson` exists at a time and it always holds the oldest undelivered events; every failure throws before the next rename, so nothing already claimed can be overwritten. A drain that dies leaves that file for the next drain, which delivers it before anything newer. "The next drain" is any drain for that task — a fresh event's own, or `vinaya log send`'s (above), which is what recovers a draining file for a task whose run has already ended and will log no further event of its own.

**What the drain cannot protect: a bucket nobody has claimed yet.** `appendLine` replaces `<name>.1.ndjson` on every rotation, unconditionally, without taking the drain lock — an append must never wait on a network call. So a batch sitting in that slot is destroyed if a rotation arrives before a drain claims it, and that is exactly what happens while the server is refusing: a failed drain throws on the older bucket and never reaches the slot, so a long enough outage at a high enough volume overwrites it once per rotation. This is the rotation's own single-slot retention policy — one slot, overwritten each time, as this document has always described it — not a new loss introduced by the drain, and it is reported rather than silent: `reportRotationOverflow` names the identities each overwrite destroys. Delivering the slot whenever a drain does reach it strictly reduces the loss against never reading it at all. Removing the loss entirely would mean the rotation retaining more than one slot, which trades bounded local disk for unbounded, and is a change to the retention policy rather than to the drain.

The rotation's own overflow diagnostic is unchanged and stays truthful: it reports what a rotation is about to destroy, and it now usually has nothing to report, because the slot was delivered instead of lost.

### A line that cannot be vouched for is set aside, not posted, and blocks nothing

Every line is re-validated and re-redacted through `classifyStoredLine` before it is sent. A line that fails that validation, carries a schema version this build does not know, or is by itself larger than one POST is appended to `<name>.rejected.ndjson` — beside the queue, in the same machine-local outbox directory, with the same `0o700` directory, `O_NOFOLLOW` open and `0o600` mode the queue itself carries (`log-sink.ts`'s `appendHardenedLine`, shared rather than copied) — carrying the reason, the classification, the identity where one is readable, and the original line verbatim. A rejected line is still telemetry: it is kept, never dropped, and never posted. The lines after it keep delivering, so one corrupt line costs one line's worth of telemetry instead of every later event.

A line is filed before its bytes leave the queue, never after, and whatever chunk was accumulating ahead of it is delivered first so that those two steps are adjacent. A process killed between them leaves the line still queued, so the next drain files it a second time: a rejected file can hold the same bad line twice, and never zero times. That is the side of the trade-off to be on.

One line reaches `process.stderr` per process for this, however many lines a drain sets aside — the same bound the sink's own warning keeps, on its own flag so neither warning can swallow the other. A rejected file that cannot be written ends the drain instead, with the bad line still queued and the real cause named: losing telemetry silently is never the fallback.

A failure status is never treated as a content fault. An endpoint answering `401` is a misconfigured credential, not a bad line: the queue is kept whole and the sink warns, exactly as for any other refused POST.

## No path to a tracker or a code host

Logs never reach a tracker or a code host, in any form — not as an Issue or pull-request comment, not as a CI artifact. Every producer delivers live through the `logs` destination (above) and the developer-review loop's own round-end flush calls nothing, so the tracker-posting machinery that flush left behind is deleted, since nothing calls it any more: `vinaya log flush --issue <n> | --pr <n>` (the comment-posting command, its chunking, its `<!-- aeg:log:… -->` marker, and its idempotent-retry read against existing comments), `vinaya log export-artifact` and `vinaya log collect-artifact` (the CI-artifact export/collect round-trip and the trusted collector workflow that published it), and the `logPublish` config key that backed all three (`issue`, `pr`, `webhookUrl`, `headers`, `maxChunksPerFlush`). A configuration that still declares `logPublish` is refused at load, naming `logs` as its replacement, rather than silently ignored.

The `<!-- aeg:log:… -->` marker convention, the `FORGE_COMMENT_MAX_CHARS` chunk limit, and every test that covered the deleted commands are gone with them. The schema keeps every `forge_write` operation the flush used to emit (`validated`/`refused`/`written`) so a comment line already posted before the deletion still parses — reading old evidence is still supported, only writing new evidence is not — but no producer emits them any more; `apps/cli/tests/lib/log-callers.test.ts`'s producer-coverage table carries them as an explicit exemption, the same shape `handoff.raised`/`handoff.resolved` already used for a family with no real caller.

**The webhook drain survives, renamed to what it now is.** `flushOutboxToWebhook` (`apps/cli/src/lib/log-webhook-flush.ts`) used to serve two callers — `logPublish.webhookUrl`'s one-shot posting mode, and the live `logs.url` server destination's own per-event drain (below). Only the second caller is left, so the function and its module are renamed to `drainOutboxToWebhook`/`apps/cli/src/lib/log-webhook-drain.ts` — unmodified behavior, a name that no longer implies a one-shot "flush" concept that no longer exists.

## CI delivery: a server or nothing

A task-path CI job's own gate/operation/usage events (`runChecks` logging into `runner.ts`) are produced on an ephemeral GitHub Actions runner — its local disk dies with the job. That gap used to be closed by exporting the outbox as a build artifact and validating/publishing it from a trusted collector workflow; that whole round-trip is deleted along with the tracker-posting flush it fed. In its place, a CI job delivers through the exact same `logs.url` server-destination mechanism every other producer already uses (§ The destination) — with one CI-specific rule layered on top, since an ephemeral runner changes what "no destination" safely means (Linear "Tech spec — The Vinaya Log" rev 8, § 4, Diagram K):

**A CI job never falls back to a folder, credentialed or not.** `resolveLogDestinationFrom` (`apps/cli/src/lib/log-sink.ts`) checks `meta.host === 'ci'` (`GITHUB_ACTIONS` set) after resolving the trust-anchor-gated destination the same way every unattended caller does: a folder there would write to a disk the job is about to discard, which is a silent no-op wearing delivery's clothes, not a real destination. A CI run that would otherwise resolve a folder resolves `{ kind: 'none', reason }` instead — nothing is recorded, and `log()` warns once per process (never once per event, which would spam a job's output once per check), naming the reason in the job's own output.

**Two reasons land on `none`, both sanctioned outcomes, neither a failure:**

- **No server is configured.** The default branch's `vinaya.config.json` declares no `logs.url` at all (or the working tree's own copy isn't trust-anchor-approved — the same anti-redirect rule every unattended caller already carries).
- **This job holds no delivery credential.** A `logs.url` destination IS configured, but a `logs.headers` value referencing `${VAR_NAME}` is not set in the one place delivery substitutes it from — the process environment (`logsCredentialMissing`, `log-sink.ts`). GitHub withholds every repository secret from a fork-originated `pull_request` run — the env var a generated workflow step sets from `secrets.*` is empty there, not merely unset — so "empty" and "absent" are the same signal. A destination declaring no `headers` at all has no credential concept and is never affected by this check.

**Delivery, when both checks pass, is unmodified from § The destination:** the event appends to the local retry queue first, then `drainOutboxToWebhook` POSTs it, exactly as any other unattended `logs.url` caller. The generated `vinaya-checks.yml` job's own env carries what makes this real rather than theoretical:

```yaml
env:
  VINAYA_UNATTENDED: '1'
  VINAYA_LOG_TOKEN: ${{ secrets.VINAYA_LOG_TOKEN }}
```

`VINAYA_UNATTENDED` is what makes the trust-anchor gate apply to this job's `vinaya check` invocation at all — without it, the run would be classified attended and would honour a fork PR's own working-tree `logs.url`/`headers` directly, exactly the redirection the gate exists to prevent everywhere else. `VINAYA_LOG_TOKEN` is a write-only ingest credential referenced from `vinaya.config.json`'s own `logs.headers` (e.g. `{ "authorization": "Bearer ${VINAYA_LOG_TOKEN}" }`) — never read back by this job, and never a value that widens `checksWorkflow`'s own `permissions:` block, which stays exactly `contents: read, pull-requests: read, issues: read, actions: read`. A same-repository or default-branch run has the secret; a fork PR does not, and needs no code path to say so — the empty string GitHub already produces there is the signal.

## Attribution

`VINAYA_RUN_ID`, `VINAYA_ROLE`, `VINAYA_TASK`, `VINAYA_ROUND` are read from `process.env` by the sink, never passed as an argument — a caller cannot override its own attribution. Absent: `role: 'unattributed'`, `issue: null`, a `run_id` generated once per process (`crypto.randomUUID()`). `host` is `'ci'` when `GITHUB_ACTIONS` is set, else `'hook'`/`'loop'` from `VINAYA_HOST`, else `'cli'`. A session not started through `vinaya dispatch` is `unattributed`, which is the truth about it — the same class of honesty as `role: 'unattributed'` anywhere else in this doctrine.

**The branch names the task when the environment does not.** Most of what a log server actually holds is produced with no `VINAYA_TASK` at all — a `vinaya check` run by the pre-push hook or by CI carries no dispatch identity — and those events used to read `issue: null`. When, and only when, `VINAYA_TASK` is absent, the sink asks the checked-out branch instead: `task/issue-<n>` names Issue `<n>`, confirmed to exist in the repository `gh` resolves from that directory, and `task/<tranche>/<n>` names the Issue whose `vinaya/tranche:<slug>` label and `[<slug>] <n> — …` title resolve to that task ordinal (`resolveTaskIssueRef`, the same parser the task list and the task tools share; `--state all`, since a branch stays checked out after its Issue closes). Both shapes are put to the forge before an event is filed under them, and the answer is three-way, not two: a branch name is caller-supplied — a contributor's pushed branch, a fork's, a reviewer's checkout of a pull request — so a number the forge DENIES is never filed, which is the attribution this confirmation exists to prevent. But a `gh` that is missing, unauthenticated, offline or rate-limited has said nothing about the number, and reading its silence as denial would throw away the case this fallback exists for: a local pre-push run, on a task branch, on a machine with no forge access. Silence therefore leaves the branch's own claim standing (`task/issue-<n>` gives `<n>`, as the objective says), and the event never claims the forge agreed — `meta.provenance` stays `'unavailable'` either way. Existence in THIS repository is what a confirmation checks, deliberately not "is a vinaya task Issue": a backlog task Issue carries no tranche label, so requiring one would refuse exactly the branch shape this exists to read. The repository asked is the one the event will be FILED under — `--repo` from the already-resolved `meta.repo`, never the directory's own git remote, which `AEG_REPO` can legitimately disagree with. An event whose environment already names its task keeps that number — the branch is a fallback, never an override — and a branch that names no task, a checkout `git` cannot read, a number the forge will not confirm, and a number no Issue can be (a digit run past the safe-integer range, or zero) all stay `issue: null`, never a guess.

**CI has no branch checked out, so it names one.** A job triggered by a pull request checks out the merge commit in DETACHED HEAD — `git rev-parse --abbrev-ref HEAD` answers the literal string `HEAD` — so the branch read alone would leave every CI event `issue: null`, half of the reason this fallback exists. The head ref the CI system itself reports for the pull request (`GITHUB_HEAD_REF`, set on a `pull_request` event and empty on every other) is read in exactly that case, and goes through the identical shape rules and the identical forge confirmation. It is not a stronger claim than a local branch name: both are caller-supplied, both leave `meta.provenance: 'unavailable'`, and neither can name an Issue the forge does not confirm.

The lookup runs at most **once per process, per working directory and repository** (`branchIssueByCwd`), lazily: a process whose events already name their task never makes the call at all, and one that does caches the answer — `null` included — for every later event AND for every other sink it builds. Keyed by the pair the read actually depends on — the directory it reads and the repository it asks: two sinks reading one directory and asking one repository cannot honestly disagree, and two reading different worktrees, or asking different repositories, must not share. A process that builds several sinks without a task in the environment (`dispatchRole` called without `--task`, a cancel's own sink, the module-level default one) therefore still pays exactly one `git` read and one `gh` round trip, not one per sink. Each is bounded by the same `LOG_CONTEXT_LOOKUP_DEADLINE_MS` the sink's other context lookups carry, and the child process is killed at that deadline rather than left running, so a slow, missing or unauthenticated `gh` costs one deadline once and then answers `null`; no event is ever delayed past it and none is dropped. That one deadline is additive to the shared context's, not overlapped with it, and deliberately so: the destination is decided first, which is what lets a process recording nothing spend no forge call at all. Only the first event a process logs against a given directory-and-repository pair can pay it — a `dispatchRole` that names another worktree through `opts.cwd` reads that second directory once too. A process that records nothing at all (`{ kind: 'none' }` — no server configured, or a CI job holding no delivery credential) reads no branch and makes no forge call, in `log()` and in `resolveLogAppendPath` alike: both decide the destination first. The read follows the SINK's own `cwd`, the directory every other read it makes already uses, so an event's `meta.repo` and its branch-derived `subject.issue` can never come from two different checkouts. A branch-derived issue does not change `meta.provenance`: a checkout is not an environment correlation, so such an event reads `'unavailable'` unless the caller itself asserted a stronger claim — **even when the environment named a role**. One field describes the whole subject, so there is no way to say "the role was env-correlated, the issue was guessed"; reading `'env_correlated'` beside a guessed number would present the guess as a correlation, and a process with `VINAYA_ROLE` set and `VINAYA_TASK` absent or unparseable is exactly that shape. Under-claiming about the role is the safe direction.

**A process that serves several tasks turns the fallback off.** The fallback assumes a one-task process: a `vinaya check` on a task's branch. `vinaya task-tools serve` is the opposite — it holds calls for different tasks in flight, runs in the MAIN checkout, and emits events that belong to no task by design (the broker's Operator-channel `authenticate-invocation` lines, its refusals of forged invocations included). Its entry point calls `setBranchIssueFallback(false)` (`apps/cli/src/lib/log-sink.ts`) before it builds a sink, so every such event keeps the honest `issue: null` rather than being filed under whatever unrelated task the main checkout sits on — and memoised there for the life of the server, across every branch switch.

**The path a caller polls is derived the same way.** `resolveLogAppendPath` — the mirror `dispatchRole` and the loop driver use to watch for their own lines, and the exact file a confined dispatch grants its child — applies the identical fallback under the identical condition (no issue named, no `VINAYA_TASK`, fallback on). Otherwise the sink would write `<branch issue>.ndjson` while the caller watched `none.ndjson`, and a sandboxed child would append to a file its profile never granted, losing its whole telemetry stream to a swallowed `Operation not permitted`. A task-less dispatch grants every file its child could honestly write (`outboxGrantsFor`, `apps/cli/src/lib/dispatch.ts`): the branch-derived one, the one for the child's own `cwd` when the caller named another worktree, and the unattributed `none` file — because a CONFINED child cannot resolve the branch at all (the boundary denies read over the real HOME where `gh` keeps its credential, and passes no forge token), so its events land in the `none` bucket and a grant naming only the branch-derived file would cost it every line it writes.

**The child dies with the deadline.** Both reads (`git rev-parse`, and `gh issue list` for a tranche branch) spawn with `timeout: LOG_CONTEXT_LOOKUP_DEADLINE_MS` and `SIGKILL`, not just a deadline on the promise: a hanging, proxied or unauthenticated `gh` that outlived the answer would hold the event loop open and delay the whole process's exit — on the pre-push-hook path above all.

`VINAYA_RUN`, `VINAYA_ATTEMPT`, `VINAYA_PARENT_EVENT` are read the same way, into `meta.lineage` on a `schema: 2` or `3` header. `VINAYA_WORK_REF`, `VINAYA_FLOW`, `VINAYA_FLOW_VERSION`, `VINAYA_RUNTIME` and `VINAYA_SOURCE` are read the same way, into `meta.work.ref`, `meta.flow` and `meta.runtime`/`meta.source` on a `schema: 3` header. `VINAYA_ATTEMPT`/`VINAYA_PARENT_EVENT` read back `null` on every current line, honestly, until a later task sets them.

**`lineage.run`.** `devReviewLoop` sets `VINAYA_RUN` to its own run's `loop_id` at the very top of `runDevReviewLoopBody`, before this process logs a single line — every `dev_review_loop` event it emits AND every `effect`/`operation` event a downstream call into `effects.ts`/`broker.ts` fires in the SAME process (a pause post, an escalation write) therefore share one `lineage.run`, which is what makes the history one correlated history. A caller that never sets `VINAYA_RUN` still gets an honest, non-`null` value — the sink defaults `lineage.run` to this process's own `run_id` (already the identity every line this process writes shares via `meta.run_id`) rather than leaving the slot `null` for want of an opt-in producer. A DIFFERENT process — a `--resume` continuing a paused run, a `--cancel` invocation, a driver re-exec — mints its own fresh `loop_id`/`run_id` and therefore its own `lineage.run`, distinct from whatever process paused it: `lineage.run` correlates one PROCESS's own lines, not a task's entire cross-restart history (`subject.issue`, unchanged, is what already ties every process's lines to the same task).

`vinaya dispatch <role> --agent claude|codex|gemini` (`apps/cli/src/lib/dispatch.ts`) is the real mechanism: it sets all four variables on the CHILD process's environment only — via `spawn`'s own `env` option, never by mutating the parent's `process.env` — and separately calls `createLogSink({ env: () => ({ ...process.env, VINAYA_ROLE, VINAYA_TASK, VINAYA_ROUND }) })` once per dispatch so its OWN `dispatched`/`outcome_received`/`dispatch_failed` lines carry the same attribution without ever touching the parent's real environment. `--task` is optional: given, the line's `issue` is that number; absent, `issue: null` and `role` still comes from the `<role>` argument — never `unattributed`, since the role is always known at the point of dispatch. The child inherits the SAME `run_id` the parent's three lines used, so every `vinaya` call the child makes in turn (its own Stop hook, a nested dispatch) joins under it.

## Redaction

`redact(value, home)` (pure — `home` is passed in, never read under `packages/aeg-core/src/log/`) walks every string field: a GitHub token (`gho_`, `ghp_`, `github_pat_`) or an `Authorization: Bearer <token>` value becomes `<redacted>`; an absolute path under `home` is rewritten to `~/…`. Applied to the full event, header included, before it is serialized to the outbox line.

## Producer coverage is enforced, not assumed

The families and their real callers documented above ("The families shipped so far", "Six more families") are cross-checked against `schema.ts` itself, not trusted as a standing claim: `apps/cli/tests/lib/log-callers.test.ts`'s `log coverage` describe block derives every `kind`/`event` pair the schema declares straight from that file's own text and requires each to be claimed by a maintained producer-boundary table (`dispatchRole`, `assessRound`, the dev-review-loop driver, `runOne`, `EffectExecutor`, `broker`, the `task-tools` cancel/resume handlers) whose own claim is checked against that boundary's own source. `handoff.raised`/`handoff.resolved` and `forge_write`'s three events (`validated`/`refused`/`written` — the deleted comment-posting flush's own line) — families with zero real callers, named as such throughout this file — are the pairs carried in a source-visible `LOG_COVERAGE_EXEMPTIONS` list rather than silently passing or failing the check. `packages/aeg-core/src/log/store.test.ts` and `packages/aeg-core/src/log/compat.test.ts` carry the companion fault-driven and retention-gap fixtures: success, rejection, infrastructure failure, retry, pause, stale input, cancellation and recovery each become an ordered raw-event sequence validated end to end through the storage contract, and the newer families' minimal shapes are proven to parse with every optional/nullable slot reading back exactly what was sent, never a fabricated default.
