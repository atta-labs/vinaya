A task whose start was accepted reads as starting until its driver is confirmed, never as `no driver`. `task_start` answers as soon as the process it launched is alive and keeps its claim, but the run's own driver lock appears only after `task run` has rendered and posted the frozen brief and run its start-of-run sweep — forge-bound steps that routinely take tens of seconds. A status read taken in that window found no lock and reported `no driver`: a successful start reported as a task nobody had started, which a caller reasonably answers by starting it again. `vinaya task status` and `task_status` now consult the start claim `task_start` already writes, as their last resort. A claim still inside the start handler's own stale-claim window — or one past it whose launched process is still alive — reads `starting`, naming the start request; a claim past that window whose process is gone, with no driver lock to show for it, reads as a start that did not come up, naming the request and when it was accepted, rather than as an absence. A task whose brief that launch has not frozen yet reads starting too, rather than `not started`. Every other state is untouched and every one of them still wins over a claim: a live lock reads running, a pause reads paused, a published round reads published, and a dead lock with an exit trace reads exited. The window comes from the start handler's own staleness predicate rather than a second copy of it, and the claim files are read through that handler's own path builder and parser, so nothing else needs to know where they live.

A claim also stops being evidence long before it is deleted, so the new states can never be the old false report with its sign flipped: a driver lock on disk — even a dead one with no exit trace — is proof the driver appeared and the claim is not consulted, a launch the handler confirmed marks its own claim, and a claim past its reporting window answers neither state. A recorded pid is checked for identity against the snapshot captured at launch before it counts as the launch still coming up, so a recycled pid cannot park a task in `starting`, and a pid of `0` or a negative one — both of which address a process group — is rejected by the store's own parser. A claim's own strings are scrubbed and bounded before they reach the status table or the `task_status` state string, the claim folder is listed once per status read rather than once per row, and a task in either start state stays unaddressable by the tools that act on a prepared run.
