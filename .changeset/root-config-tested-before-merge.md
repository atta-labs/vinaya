A pull request that changes the root `vinaya.config.json` is now tested, before merge, as if that configuration were already the default branch's. Trust-anchored settings — the `logs` destination, `runtimeDir`, `principals`, the review policy — are read only from the default branch, so a pull request under review cannot redirect them; but that also meant a pull request that *changed* the root configuration was never tested against its own post-merge value, and one that set `logs.url` passed every check and broke the default branch the moment it merged. A new `test-cli-config-anchor` CI job re-runs the apps/cli suite with the pull request's own configuration standing in for the default branch's, but only when the diff touches the root `vinaya.config.json` exactly (never a fixture copy); every other pull request runs as before. The mechanism is `resolveCiTrustAnchorProbeRef`, a test-only seam that serves the trust-anchor read from a local git ref instead of the `gh api` default-branch read — and only when the ref opt-in, the Actions-runner marker, and the absence of any forge credential all hold, so nothing a real unattended run or a developer's shell does can turn it on. The job holds no repository secret and no forge-write credential (`permissions: contents: read`, no `secrets.*`), and every merge-authority read still runs in a credentialed default-branch job the seam is inert in.
