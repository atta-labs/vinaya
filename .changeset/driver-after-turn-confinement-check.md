After every Developer and Reviewer/Security turn, the driver now checks from outside the agent, never from inside it: the control store, the Documentation read-gate's own required-sources manifest, every other role's session record and round work directory, and the repository's `vinaya.config.json` are hashed right before the dispatch and re-hashed the moment it returns, and the turn's own raw output (plus, for a Developer, its worktree diff) is scanned for a recognized credential shape — a GitHub/AWS/Anthropic/OpenAI/Slack token's own prefix, a PEM private-key header, a three-part JWT, never a generic field name. A violation refuses the turn, naming every changed path and where a credential pattern appeared, never the matched value itself: a Developer turn is reasked, bounded the same way a bad commit header already is, and nothing it produced is ever committed or pushed; a Reviewer/Security turn's hand-off files are never trusted as a verdict.

`worker-boundary.ts` gains the mechanism (`protectedPathsForTurn`, `snapshotProtectedPaths`/`changedProtectedPaths`, `findCredentialPatterns`); `dev-review-loop.ts` wires it into `dispatchDeveloper` and `dispatchReviewer` at the one place each kind of turn already ends.

`isolation.md` gains a new section stating plainly that this is detection after a turn, never confinement during one, and naming what it cannot see: a read of a secret, a request to an already-allowed host, a change reverted before the check runs, or access through a route outside the vendor sandbox. It also gains the one table this task's brief asked for — all six boundaries (environment, HOME, Keychain, credential helper, socket, parent process), the mechanism holding each for Claude and for Codex, and the test proving it. Five of the six are not held, for at least one vendor, by this table's own evidence (HOME and Keychain are open for Codex outright; Keychain, credential helper, socket and parent process have no named mechanism for either vendor at all) — so the hand-built Seatbelt profile (`resolveWorkerBoundaryLaunch`/`buildWorkerSandboxProfile`) is NOT removed by this task. It stays exactly where it already was (built, proved, unreferenced from the live dispatch path for either vendor), and this task escalates the five gaps, naming the boundary and vendor for each, for an explicit Principal decision.
