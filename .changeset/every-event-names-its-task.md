Every log event names its task, derived from the checked-out branch when the environment does not name one, and events produced inside a repository's own test run are marked as tests. Most of what a log server holds is produced by a `vinaya check` run from the pre-push hook or from CI, which carries no `VINAYA_TASK` at all and so recorded `subject.issue: null` — the event happened on a task's branch, but the record could not say which task. The sink now asks the branch, and only when the environment is silent: `task/issue-<n>` names that Issue and `task/<tranche>/<n>` resolves through the same `vinaya/tranche:<slug>` label and `[<slug>] <n> — …` title parser every other caller already shares, both put to the forge before an event is filed under them, and the answer is three-way: a number the forge DENIES is never filed (a branch name is caller-supplied, so an unchecked number would write a process's telemetry into whatever Issue that name mentioned), while a forge that cannot be asked at all — missing, unauthenticated, offline — has said nothing, so the branch's own plain claim stands and a local run with no forge access still names its task. The repository asked is the one the event is filed under, never the directory's own git remote. A CI job triggered by a pull request has no branch checked out at all (detached HEAD at the merge commit), so the head ref CI itself reports for the pull request is read there, on identical terms. An event whose environment names its task is untouched — the branch is a fallback, never an override — and an unresolvable branch stays `null` rather than a guessed number, as does a branch naming a number no Issue can be. The lookup runs at most once per process per working directory and repository, lazily (a process whose events already name their task never makes it, and a process that records nothing never makes it either), from the sink's own working directory, caches its answer including a failure, and is bounded by the same deadline the sink's other context lookups carry, so a slow, missing or unauthenticated `gh` delays no event and drops none — and the child process dies with that deadline rather than outliving the answer and holding the run's exit open. The fallback applies to one-task processes only: `vinaya task-tools serve`, which holds calls for several tasks at once and runs in the main checkout, turns it off so its task-less events keep an honest `issue: null`. The path a caller polls for its own line, and the exact file a confined dispatch grants its child, are derived through the same fallback, so they still name the file the sink actually writes. An issue that came from the branch never reads `provenance: 'env_correlated'`, even when the environment named a role: a guess is not a correlation.

Separately, a repository's own tests deliver to the same destination a real run does, so fixture traffic and real traffic were indistinguishable on the server; the header now carries `meta.test: true` for a process whose environment says it is a test run — `AEG_LOG_TEST`, set by a preload both `bunfig.toml` files declare so it covers a run started from the repository root as well as one started inside `apps/cli`, or `NODE_ENV=test` as a backstop. The marker deliberately does not rest on that backstop: a runner sets `NODE_ENV` only when nothing already exported one. It also travels into a confined dispatch child, whose environment is a closed allowlist. It is a label, not a switch: it changes nothing about where an event goes, and there is no `false` to write — real traffic is said by the field's absence. It is also self-reported: any process can mark its own events, so a reader should separate marked traffic, never silently drop it.

Upgrading: the marked line is an additive field on the existing `schema: 2` header, so every line written before it existed still validates — but the header object is strict, so a log server still running an earlier `@attalabs/aeg-core` rejects a MARKED line instead of storing it. If you deploy your own copy of `apps/log-server`, redeploy it at or past this version; until you do, your test traffic lands in that server's `rejected` table and real traffic is unaffected.
