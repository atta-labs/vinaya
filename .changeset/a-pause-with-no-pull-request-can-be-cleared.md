A run that paused before its pull request existed can now be cancelled and resumed. The loop's before-any-push escalation posts its pause on the task Issue, because there is no pull request yet, and it recorded that absence as a `-1` sentinel in the pause record. Every consumer's own "no pull request" test asks whether the value is absent, which `-1` is not, so both Operator tools read it as a real pull request and shelled `gh pr view -1`; `gh` parses that as a flag — "unknown shorthand flag: '1' in -1" — and the call failed as an infrastructure error with the run untouched. Such a pause could not be cleared by any tool at all. The pause record and the task-tool catalog's own escalation inputs now carry the pull request as either a real number or nothing, and both writers that have none — the before-any-push escalation, and the crash handler, whose pull-request number is still at the placeholder it starts every run with — record nothing, matching what the durable escalation record already stored. Reading a pause record is the one place every consumer goes through, so that is where a record already written with the old sentinel is read as having no pull request: fixing only the writer would have left exactly the pauses that are already stuck stuck forever. The ruling that authorises clearing such a pause is read from the task Issue, where that pause's own comment was posted and where the only ruling answering it can be. The Issue readers sit beside the pull-request ones and hand the same comment read to the same parser under the same principal allowlist, so an Issue comment authenticates a resume or a cancel on exactly the terms a pull-request comment does: principal-authored, carrying the ruling marker on its own first line, and newer than the ruling the pause was already raised under. A cancel of such a pause is addressed by its task rather than by a pull request, skipping a derivation there is no pull request body to perform, and the resolution it consumes binds against an escalation whose own pull request is equally absent — so a resolution meant for a pause with no pull request can never be pointed at a real one, nor the reverse. Resuming cannot delegate the way cancelling does, because the resume entry derives its task from a pull request's body and has no path in for a pause without one. So for that one case the tool consumes the ruling itself, as that escalation's own single-consumption resolution, and only then relaunches the task through the one continuation such a pause has. Consuming first is what makes a second resume of the same escalation a refused replay rather than a second run of the same task; the price is that a launch failing after the ruling is spent needs a new ruling to retry, and the refusal says so rather than leaving it to be discovered. The command the pause comment prints is now one the reader can run verbatim: it named a tranche placeholder it never filled in, with the Issue number standing in the ordinal's position, and now names the task by its Issue number, carries the agent the run was dispatched under, and names the Operator's own tools as the other way out. The escalation packet a reader fetches names that same command instead of a resume against a pull request that does not exist, and the resume entry, asked to continue such a pause directly, refuses by naming the command that does work rather than failing on a pull-request read. A resume or cancel result reports the pull request as absent rather than inventing one.

The command such a pause names is the one that works for the task it belongs to. `vinaya task run` takes two address forms and they are not interchangeable: addressing a task by its Issue number is the tranche-less backlog path, and rendering a brief for an Issue that belongs to a tranche is refused outright — a refusal the run does not tolerate, so the process exits. Every pause this escalation actually fires on belongs to a tranche, so naming the Issue form would have consumed the ruling and then exited without continuing anything. The address form now comes from the pause's own branch, where it was already recorded when the run was dispatched, at no cost and with no possibility of disagreeing with the branch the run is on. One builder renders it for all three places that name this command — the pause comment on the Issue, the escalation packet a reader fetches, and the argv the resume tool actually spawns — and the agent and the model the paused run was dispatched under now travel with all three, the launch included, where the launch had been dropping the model and silently re-resolving one from the task's own agent-class mapping. The two printed forms render that argv element by element, shell-quoted, rather than joining it with spaces. That is not cosmetic: the tranche segment is not a slug this code chose but text taken from the task's title, and it lands inside a fenced command block a human or an agent is told to run, so a title carrying shell syntax would have been handed over as a command to run rather than as an argument. The spawned form was always safe, being an array with no shell involved, which is exactly why the printed form has to be that array's own shell encoding — a space-join was a second, weaker renderer wearing the single builder's name, and it produced a different command than the one that runs for any tranche containing a space.

The pause comment also names the marker line a ruling must carry, and names one a reader can actually use. No command posts a ruling on an Issue: the one that posts rulings counts and writes them through a pull request. So a Principal writes that comment by hand, and the readers recognise nothing without an exact marker on the comment's own first line and an ordinal higher than the one the pause recorded. Telling a reader only that a ruling must be posted left both facts unguessable. That marker carries two numbers — the pull request or Issue it concerns, then the ordinal — and the ordinal every reader compares is the second one. A first cut of this comment put the ordinal first and fixed the second number at one, so a ruling written exactly as instructed always parsed as ordinal one and was refused by the very freshness gate it was posted to satisfy, for any pause whose recorded baseline had reached one: the pause was unclearable again, by following the printed instruction. The marker is now built by one function living beside the expression that parses it, and the tests assert it by feeding the rendered marker back through that parser rather than by comparing a literal string, which is what let the two slots disagree while the suite stayed green.

The ordinal to exceed is also a real number rather than always zero: a pause with no pull request recorded its freshness baseline as zero, because the baseline was only ever read from a pull request, which made the Issue-side freshness check vacuous — any ruling ever posted on that Issue satisfied it, including one an earlier pause had already spent, so a single stale approval would have authorised every later resume and cancel. The baseline is now read from the Issue, where the ruling answering that pause can only be. And a baseline that cannot be read is no longer recorded as zero: zero is not a missing value there, it is the positive claim that the Issue carries no rulings, which a failed read never established — so that read propagates instead, no escalation record is written, and both tools refuse on machinery that already existed, while the pause stays continuable by the command it prints, which needs no ruling at all.

What a consumed decision cannot do is be reopened, and the refusals now say so. A consumed resolution is refused for that escalation however many rulings land afterwards, and a pause raised again with the same round, head, branch, reason and detail reuses the same escalation identity — so both the replay refusal and the refusal after a launch that never came up name the command to run directly, instead of promising that a new ruling reopens anything. What the relaunched continuation does not carry is the ruling's own text: it re-enters at the first round with the frozen brief, and nothing reads Issue rulings into that dispatch, so a ruling that changes what the developer should do has to say it where the developer reads. That is the shape of the only continuation such a pause has, not a choice made here.

One more pause writer was brought into line too: the main round-loop pause site was the last one storing the pull-request number unnormalised, with no guard on the comment it posts. It is not reachable with a non-real number today, so nothing was broken by it — but it left the conversion for that path resting entirely on the read side, and a future path arriving there before the pull request resolved would have written the sentinel straight back in.

Two other readers of a pause record were brought along with its new shape. The status reader keeps its own narrow copy of that read and now applies the same normalisation, rather than being a second reader that disagrees about the value. And the legacy-outbox migration required the pull-request field to be a number, so a genuine no-pull-request pause failed its shape guard entirely: it migrated as a fresh run at round zero with no paused transition recorded — silently losing the one pause shape that is hardest to reconstruct by hand.
