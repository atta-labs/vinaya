A run that paused before its pull request existed can now be cancelled and resumed. The loop's before-any-push escalation posts its pause on the task Issue, because there is no pull request yet, and it recorded that absence as a `-1` sentinel in the pause record. Every consumer's own "no pull request" test asks whether the value is absent, which `-1` is not, so both Operator tools read it as a real pull request and shelled `gh pr view -1`; `gh` parses that as a flag — "unknown shorthand flag: '1' in -1" — and the call failed as an infrastructure error with the run untouched. Such a pause could not be cleared by any tool at all. The pause record and the task-tool catalog's own escalation inputs now carry the pull request as either a real number or nothing, and both writers that have none — the before-any-push escalation, and the crash handler, whose pull-request number is still at the placeholder it starts every run with — record nothing, matching what the durable escalation record already stored. Reading a pause record is the one place every consumer goes through, so that is where a record already written with the old sentinel is read as having no pull request: fixing only the writer would have left exactly the pauses that are already stuck stuck forever. The ruling that authorises clearing such a pause is read from the task Issue, where that pause's own comment was posted and where the only ruling answering it can be. The Issue readers sit beside the pull-request ones and hand the same comment read to the same parser under the same principal allowlist, so an Issue comment authenticates a resume or a cancel on exactly the terms a pull-request comment does: principal-authored, carrying the ruling marker on its own first line, and newer than the ruling the pause was already raised under. A cancel of such a pause is addressed by its task rather than by a pull request, skipping a derivation there is no pull request body to perform, and the resolution it consumes binds against an escalation whose own pull request is equally absent — so a resolution meant for a pause with no pull request can never be pointed at a real one, nor the reverse. Resuming cannot delegate the way cancelling does, because the resume entry derives its task from a pull request's body and has no path in for a pause without one. So for that one case the tool consumes the ruling itself, as that escalation's own single-consumption resolution, and only then relaunches the task through the one continuation such a pause has. Consuming first is what makes a second resume of the same escalation a refused replay rather than a second run of the same task; the price is that a launch failing after the ruling is spent needs a new ruling to retry, and the refusal says so rather than leaving it to be discovered. The command the pause comment prints is now one the reader can run verbatim: it named a tranche placeholder it never filled in, with the Issue number standing in the ordinal's position, and now names the task by its Issue number, carries the agent the run was dispatched under, and names the Operator's own tools as the other way out. The escalation packet a reader fetches names that same command instead of a resume against a pull request that does not exist, and the resume entry, asked to continue such a pause directly, refuses by naming the command that does work rather than failing on a pull-request read. A resume or cancel result reports the pull request as absent rather than inventing one.
