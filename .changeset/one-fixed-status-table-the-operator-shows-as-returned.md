`task_status` returns one fixed status table that an Operator shows exactly as returned. Three Operators asked for the same status on one day and answered in three different layouts, each missing a different field, because the tool returned rows and every Operator laid a table out itself — and the pull request's CI and verdicts lived in a second tool, so no single read showed whether a task was ready to merge. The result now carries a `table` field beside its `items`, rendered by the SAME function `vinaya task status` prints, so the tool and the command carry the same columns in the same order for the same records and there is no second renderer to drift. It is markdown and padded: the pipes make it a table wherever it is pasted, the padding keeps it readable in a terminal. Pagination still bounds `items`; the table covers every task the call matched, so a call with no `task` lists every open task in the repository. Every field the result already carried is unchanged — the table is added, never substituted.

Each row also carries what its own pull request reports on its head: the head itself (abbreviated as git abbreviates), the mechanical CI suite as `green`, `red` or `running`, the newest code-review and security verdict values, and the review gate's own conclusion. All five come from ONE forge read per pull request — `gh pr view` asked for the head, the status-check rollup and the comments together — reusing `task_pr_read`'s own check flattening and review-record derivation rather than a second copy of either, and reading no job log: a failure summary is what `task_pr_read` exists to give, and this table's cell shows one word. A task with no pull request reads one dash in each of those columns; a pull request whose read failed reads `not read`, because a forge read that never answered is an unknown and not an absence. The CI word excludes the review gate's own check-run and the principal-test-plan wait, the same two exclusions the driver's own gate read makes and for the same reasons, and it is computed with the same precedence — anything still running wins over a failure, since a suite that has not finished has not failed — over nodes already deduped to the newest run per check name, so a failure its own re-run superseded never reads as red. A verdict counts only on the head it judged: one bound to an earlier head reads as absent rather than as an approval of what is there now. None of these columns is cached between reads, unlike the confidence column's own comment read — a published summary never changes, but a check that was green on the last read is not green now.

The table ends with one footer line naming the read time in UTC, the host that read it, and how many tasks it lists, so a table pasted into an answer carries its own read time and nobody has to ask whether they are looking at a fresh reading or an earlier one. It is still never a forecast: no ETA, no remaining time and no deadline appears anywhere in it, and the typical-time column stays labelled as history with its own sample count.

Each row also names, in a `next` column, the one thing to do about it: `wait`, `merge`, `rule`, `start`, `cancel` or `investigate`. The mapping is the Operator doctrine's own state-to-action table, read out of that file by a conformance test rather than kept in step by hand, and it is a `Record` over the state kinds — a state added to the reader without a next action beside it is a typecheck error, not a row that silently renders nothing. A pause is routed by what it is actually waiting for rather than by the word `paused` alone, through the same disposition reader `task_start`'s own gate consults: a decision the Principal owes reads `rule`, one already taken as resume (or a hiccup the loop resumes itself) reads `start`, one already taken as cancel reads `cancel`, and a pause record this host cannot read reads `investigate`. Merge-readiness — the review gate green and both verdicts on this head clean — wins over the state's own action, because it is the newer fact: a run whose driver vanished on a green, approved head is one to merge, not one to restart. It never overrides a cancel already decided or a record that would not read.

And a phase that has already run past twice what the same phase typically took on this repository's recently merged tasks carries a `⚠` in its time-in-phase cell. Both sides of that comparison are recorded history and it is still not a forecast — it says where this run sits against what already merged, never when it will finish. A phase with no typical time never carries the mark: there is nothing for it to be twice of.

Four guards on those columns, each closing a way the table could have told the Principal something the merge gate would refuse. Both `ci` and `gate` read the rollup's check runs and drop its commit statuses: a commit status is posted by anything holding `statuses:write`, its context is a free string, and the flattening treats one as a completed check whose conclusion is its own state — so a status whose context was spelled exactly like the review gate's check-run name read as a green gate, and with both principal-authored verdicts already on the head the table then named `merge` for a head the real gate was refusing. Dropping them also removes the divergence they created in the `ci` word, whose whole claim is that it reads the head by the same rule the driver's own gate read does — the driver reads check runs and never sees a commit status. That word now also reads a completed check carrying no conclusion at all as red rather than as still running, which is what the driver reads it as. `merge` requires `APPROVE`, not the `LGTM` the verdict extractor also accepts and the merge gate does not, and it no longer overrides a state where a driver is still live: the head a read judged is not the head a running loop will finish on. And a cell's own value can no longer break the table it is in — a vertical bar is escaped and a line break becomes a space, because the tranche slug is whatever the forge label carried and one bar would silently add a column to a table the Operator is required to relay exactly as returned.

The pull-request read is also bounded within one status read, at the same figure and for the same stated reason as the confidence column's own bound: these reads are synchronous and the long-lived task-tool server chains every request through one promise, so an unbounded number of them would hold every other task's queued call behind a listing of a busy repository. Past the budget the remaining rows read `not read`, and the row an Operator is acting on is read by name — one row, always inside the budget. A published row now pays one read for two columns rather than two for the same payload: the facts read already carries that pull request's comments, and the published summary the confidence column wants is in them, with that column's own bounded reader kept as the fallback.

A named status read also builds only the row it named. The reader takes the selector itself and skips every task the call did not name before any per-row read is made — previously the handler filtered the rows after building them all, so the pull-request budget was spent in listing order and a named task listing past it reported `not read` in every pull-request column, with no way for an Operator to get them at all; a named read also paid one Issue read per open task instead of one. The gate cell narrows further, because it is the one cell a `merge` word rests on: a run counts as the gate only when it carries both the gate's check name and the `name:` of the workflow that posts it, rendered from the same two constants the generated workflow itself is, and the gate's own run is chosen among gate-shaped runs before the newest-per-name dedupe — so a run that merely claims the name can neither become the gate nor suppress the real one. Every cell now leaves through the same neutralization the pull-request read already applies to unauthored forge text: a tranche slug is whatever the forge label carried, and a label beginning with an HTML-comment opener swallowed every following cell and row in any markdown renderer, hiding columns while the Operator believed it had relayed the table intact. A rollup page that may be full is reported as a read that could not answer rather than summarized over a partial set, and a pull-request number is checked before it reaches an argument list, the same guard the comment read states at the identical boundary.
