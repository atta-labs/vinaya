`task_status` returns one fixed status table that an Operator shows exactly as returned. Three Operators asked for the same status on one day and answered in three different layouts, each missing a different field, because the tool returned rows and every Operator laid a table out itself — and the pull request's CI and verdicts lived in a second tool, so no single read showed whether a task was ready to merge. The result now carries a `table` field beside its `items`, rendered by the SAME function `vinaya task status` prints, so the tool and the command carry the same columns in the same order for the same records and there is no second renderer to drift. It is markdown and padded: the pipes make it a table wherever it is pasted, the padding keeps it readable in a terminal. Pagination still bounds `items`; the table covers every task the call matched, so a call with no `task` lists every open task in the repository. Every field the result already carried is unchanged — the table is added, never substituted.

Each row also carries what its own pull request reports on its head: the head itself (abbreviated as git abbreviates), the mechanical CI suite as `green`, `red` or `running`, the newest code-review and security verdict values, and the review gate's own conclusion. All five come from ONE forge read per pull request — `gh pr view` asked for the head, the status-check rollup and the comments together — reusing `task_pr_read`'s own check flattening and review-record derivation rather than a second copy of either, and reading no job log: a failure summary is what `task_pr_read` exists to give, and this table's cell shows one word. A task with no pull request reads one dash in each of those columns; a pull request whose read failed reads `not read`, because a forge read that never answered is an unknown and not an absence. The CI word excludes the review gate's own check-run and the principal-test-plan wait, the same two exclusions the driver's own gate read makes and for the same reasons, and it is computed with the same precedence — anything still running wins over a failure, since a suite that has not finished has not failed — over nodes already deduped to the newest run per check name, so a failure its own re-run superseded never reads as red. A verdict counts only on the head it judged: one bound to an earlier head reads as absent rather than as an approval of what is there now. None of these columns is cached between reads, unlike the confidence column's own comment read — a published summary never changes, but a check that was green on the last read is not green now.

The table ends with one footer line naming the read time in UTC, the host that read it, and how many tasks it lists, so a table pasted into an answer carries its own read time and nobody has to ask whether they are looking at a fresh reading or an earlier one. It is still never a forecast: no ETA, no remaining time and no deadline appears anywhere in it, and the typical-time column stays labelled as history with its own sample count.
