A spec holds only durable product knowledge, and the task plan lives only on the forge. The doctrine named no difference between the two, so a spec could carry a copy of its tranche's task list — numbers, order, dependency and conflict edges, per-task surfaces — and an adopter's did: a split and a renumbering then took three pull requests against that spec in one day, each one only restoring agreement between the copy and the Issues it was copied from, and none of them recording anything about the product. The glossary now defines both words. Plan is the tasks that build a product — their list, their numbers, the order they run in, which of them depend on or collide with which, and the file surface each one touches — and it lives in exactly one place, the forge, as a tranche's task issues; nothing else keeps a copy. Spec is the durable statement of what a product is and must do, true after the work that built it has merged, and it never copies the plan: where a spec must refer to the work at all, it points at those issues instead of restating them.

The Planner's own doctrine now refuses the write rather than describing it. Plan data asked into a spec — or into any other committed document — is a hard gate alongside the role's other refusals, with the refusal line it answers in, naming the tranche's task Issues as the one home for that data and a pointer to the tranche as what a spec carries instead. A spec that already holds plan data is not kept in step with the Issues: the copy is deleted and replaced with that pointer in the same change, since keeping two copies in agreement is the failure the gate exists to prevent rather than a milder version of it. The seat file states the same refusal in one line, and both files point a reader at the two new glossary entries.
