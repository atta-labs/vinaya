The monorepo `test` task is never cached (`turbo.json`'s `tasks.test.cache: false`), so no caller of `turbo test` on this repository — present or future — can ever replay a stale pass instead of genuinely re-running.

`vinaya.config.json`'s `prePush.alwaysRun` now names two files the file-level pre-push selector's own reachability can never select on its own: `apps/cli/tests/lib/log-callers.test.ts`, a repo-wide invariant test whose import-graph reachability check walks the whole source tree rather than importing the files it checks, and `apps/cli/tests/commands/task-status.test.ts`, which drives the built CLI as a real end-to-end subprocess with no static import edge into `src/` at all. Two real pushes passed the hook and failed CI on the first gap; a third, structurally different CI-shard failure (reachability can never reach a file with no import edge, regardless of what changed) motivated the second.

Every real-subprocess test fixture under `apps/cli/tests` that spawns the `vinaya` CLI through the same driver/dispatch/control-store code path (`dev-review-loop.test.ts`, `dispatch.test.ts`, `dispatch/launch-intent.test.ts`, `dispatch/reconcile-launch.test.ts`, `dispatch/unattended.test.ts`, `task-tools/cancel.test.ts`, `task-tools/protocol.test.ts`, `commands/task-run.test.ts`, `commands/task-status.test.ts`, `commands/dispatch-task.test.ts`, and the shared `conformance/harness.ts` used by the Claude/Codex adapter suites — both the `lib/` and `commands/` layer, and both `bun:test`/`vitest`-style files) no longer inherits this process's own `VINAYA_*` environment (most importantly `VINAYA_RUNTIME_DIR`) into the subprocess it spawns — a dispatched session's own environment previously redirected every fixture's driver to this machine's real, shared runtime directory regardless of the fixture's own isolated `$HOME`, racing its driver lock and control-store files against every other concurrent task run. Each fixture's subprocess is now also bounded by an explicit, generous budget (a fixed timeout for a single-shot command, or a captured-stderr-plus-kill-on-timeout for a long-lived JSON-RPC server) that fails with the child's own captured stdout/stderr on expiry, rather than a bare test-framework timeout with no diagnostic.

Round 5 (Principal ruling: "O3 becomes a check, and this round closes it") extracts that pattern's both halves into one shared module, `apps/cli/tests/lib/process-fixture.ts` (`stripVinayaEnv` + `spawnSyncBudgeted` + `spawnBudgetedAsync`), migrates the two build spawns (`package-root.test.ts`, `commands/check-json-pipe.test.ts`) and the `vinaya log flush` sibling group (`lib/log-flush.test.ts`, `lib/log-webhook-flush.test.ts`, `commands/log-flush.test.ts`) onto it, and adds `apps/cli/tests/process-fixture-coverage.test.ts`, an architecture test with a `GRANDFATHERED_FILES` list of every remaining non-compliant file.

Round 6 review, BLOCKER F1 — that first architecture test compared the env-strip/kill-budget patterns against a file's WHOLE TEXT (or treated any import of the shared helper as clearing the entire file), which let one hardened call in a file mask a completely unrelated, fully raw call elsewhere in the SAME file: `conformance/harness.ts`'s `ensureCliBuilt` build spawn, `commands/dispatch-task.test.ts`'s identical build spawn, and `package-root.test.ts`'s `run()` CLI-invocation helper (used for the actual defer-to-source assertion, not the build) all carried zero env override and zero timeout while their files read as fully migrated. `commands/check-json-pipe.test.ts`'s own test-body `node` subprocess had the same gap. `lib/dev-review-loop/gate-reading.test.ts` — one of round 4's three explicitly-named sites — had been left on the grandfather list untouched rather than hardened. This round fixes all five call sites (the last two build spawns onto `spawnSyncBudgeted`, `check-json-pipe.test.ts`'s test body onto the new `spawnBudgetedAsync`, `package-root.test.ts`'s `run()` onto `spawnSyncBudgeted` with `stripVinayaEnv`, and `gate-reading.test.ts`'s `runGateReading` onto the same pair), and replaces the architecture test's whole-file comparison with a call-site-precise one: every real spawn is matched against sanitized (comment/string-stripped) text, an inert-utility exemption list (`git`, `chmod`, …) skips setup calls the ruling itself named as out of scope, and every remaining call's own nearest top-level function/class/`it(...)` callback — never the whole file — must carry the kill-budget evidence. A new regression test proves the exact BLOCKER shape (two top-level functions, one hardened, one raw) is now caught. Re-verifying every already-"compliant" file against this stricter check found and fixed two further gaps this precision now catches that whole-file matching missed: `conformance/harness.ts`'s `SpawnRpcClient` needed no code change (its budget genuinely lives in a sibling method of the same class, correctly read as one scope), but `commands/task-status.test.ts`'s `--follow` fixture was missing `killSignal: 'SIGKILL'` on one call, fixed directly.

Ninety-two test files spawn a real process; 52 remain on `GRANDFATHERED_FILES` after this round (down from 76, reflecting both the real fixes above and false positives the whole-file version's own imprecision had counted). The test fails if the list grows, if a listed file stops needing the entry, or if a new spawning file appears outside it — the list is data the build enforces, not a waiver. Burning it down further is a later task.

Round 7 (Principal ruling: "a shell is not a utility") removes `sh` and `bash` from the scan's inert-utility exemption list: unlike `git`/`chmod`/`mkdir`, a shell doesn't do one fixed thing — it runs whatever string it's handed, so `spawnSync('bash', ['-c', 'bun ...'])` (or the `sh` equivalent) hid an arbitrary command, including the `vinaya` CLI itself, behind a "safe" wrapper the scan never looked past. This reclassifies three files from silently-safe to real offenders — `claude-command-emitter.test.ts`, `claude-stop-hook-emitter.test.ts`, `init.test.ts` — none of which already routed through the shared helper, so all three are added to `GRANDFATHERED_FILES` rather than hardened inline. The list grows from 52 to 55 entries.

Round 8 review closed two further gaps in the scan itself, both found by the same reviewers, no fixture changes: `SPAWNS_REAL_PROCESS` had never matched `execSync`/`exec`, despite both running their argument through a shell exactly like the `sh`/`bash` case round 7 just closed (`apps/cli/tests/checks/runner.test.ts`'s three `execSync('ps -eo ...')` calls, with no timeout and no `VINAYA_` stripping, were the live instance found) — both are now matched, with a `(?<!\.)` carve-out on the bare `exec` alternative so it doesn't collide with the unrelated `RegExp.prototype.exec` idiom several of these same test files use for pattern matching. Separately, `isSafeCommand`'s identifier fallback had matched any spawn-target hint merely containing "git" by name (`gitLikeWrapper` would have scored safe regardless of what it actually resolved to at runtime); it now requires the file to prove, by assignment, that the identifier resolves to the real git binary. Re-running the scan with both fixes found no new offender and no stale grandfather entry — `GRANDFATHERED_FILES` is unchanged at 55 entries after round 8.

Round 9 review closed three precision gaps in the scan itself, no fixture changes: the two compliance checks (`fileHasVinayaStrip`, the kill-budget scope test) ran against raw file text, so a comment merely NAMING `stripVinayaEnv`/`SIGKILL` could mark a file compliant with no such code present — they now run with comments blanked (string literals deliberately left intact, since the real evidence is very often itself a string used as actual call/property syntax — `killSignal: 'SIGKILL'`, `.kill('SIGKILL')`, `startsWith('VINAYA_')`), and both patterns are tightened to require that call/property syntax rather than matching a bare word. Separately, `SPAWNS_REAL_PROCESS` matched neither `execFile` in any form nor a member-call `exec` (`cp.exec(...)`) — the former is now in the main alternation, the latter matched separately and gated on the receiver provably resolving to `node:child_process` by import/require, never by name alone. Re-running the fixed scan found no new offender and no stale grandfather entry — `GRANDFATHERED_FILES` is unchanged at 55 entries after round 9. This round's own scan (with the fixes above) reports **ninety-one** test files spawning a real process, not the ninety-two this changeset and the architecture test's own doc comment previously stated.
