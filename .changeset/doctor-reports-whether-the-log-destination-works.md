`vinaya doctor` reports whether the configured log destination actually works. Log delivery is fail-open by design — a destination that refuses everything it is sent never slows or fails the run producing the events — so a broken one is invisible: events queue locally, a CI job's queue dies with its runner, and the config still reads as healthy. One repository's server refused every event with `401 Unauthorized` for most of a day before anyone noticed. The new `[logs]` finding answers what the config cannot: for a server destination, whether it is reachable and whether it accepts this machine's credential, naming the environment variable to set when it does not; for a folder destination, whether the folder — or the nearest existing parent the sink's own recursive create would reach — is a writable directory. A destination resolving to nothing at all is reported as that, and is never a failure. The check stores no event: it resolves the destination through the log sink's own decision rather than reading `logs` a second time — same repository identity, same bounded trust-anchor read — then posts one empty body, which the ingest route authenticates before reading and which carries no line to store. Only a `2xx` counts as acceptance: `401`/`403` is the credential being refused, and every other status is the destination refusing delivery, reported rather than passed off as health, because a `404` from a mistyped path or a `500` from a destination missing its own ingest secret discards every event just as silently. A destination nothing answers from never fails the command, since an offline machine loses nothing: its events wait in the local retry queue. A caller on a CI host is treated as unattended whichever way it was launched, so a pull request cannot redirect this probe, and the printed finding keeps out the credential in each of the three spellings it can reach a message in, as well as one carried inside the URL itself.
