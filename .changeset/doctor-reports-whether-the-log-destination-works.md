`vinaya doctor` reports whether the configured log destination actually works. Log delivery is fail-open by design — a destination that refuses everything it is sent never slows or fails the run producing the events — so a broken one is invisible: events queue locally, a CI job's queue dies with its runner, and the config still reads as healthy. One repository's server refused every event with `401 Unauthorized` for most of a day before anyone noticed. The new `[logs]` finding answers what the config cannot: for a server destination, whether it is reachable and whether it accepts this machine's credential, naming the environment variable to set when it does not; for a folder destination, whether the folder — or the nearest existing parent the sink's own recursive create would reach — is a writable directory. A destination resolving to nothing at all is reported as that, and is never a failure. The check stores no event and prints no credential: it resolves the destination through the log sink's own decision rather than reading `logs` a second time, then posts one empty body, which the ingest route authenticates before reading and which carries no line to store — `401`/`403` is the credential being refused, any other answer is it being accepted. The request is bounded by a short timeout, and a destination nothing answers from is a warning rather than an error, because an offline machine loses nothing: its events wait in the local retry queue.
