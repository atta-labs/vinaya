The whole CLI test suite passes with this repository's own log events going to a server. Two `cancel.test.ts` fixtures spawned their child with this repository as its working directory, and `findLocalConfig()` walks up from the child's working directory: the child therefore read this repository's own `logs` setting, and once a `logs.url` was declared there it resolved a server destination — the local outbox is only that destination's retry queue, drained and cleared asynchronously, so the `<task>.ndjson` file the env-restore case reads existed or not depending on how fast the drain ran. Both fixtures now spawn with `isolatedConfigFixture`'s own working directory, whose empty `vinaya.config.json` is where that walk stops, so no repository setting, present or future, is in scope for them; every assertion is unchanged. An empty configuration was not isolation on its own, and that is the substantive half of this fix: the destination resolver reads a working directory's configuration, but an unattended caller whose local configuration declares no `logs` setting still honours the DEFAULT BRANCH's declared destination, read over the forge with an identity taken from the Actions runner rather than from any directory. So a fixture given an empty configuration still delivered to the configured server wherever it ran — on a CI runner, with a real repository identity and a real token, while the same fixture passed on a laptop, where the fixture's own `$HOME` hides the credential that read needs. `isolatedConfigFixture` now declares its own `logs.folder`, and declares it as the very folder it already advertised as `logsDir`: the trust-anchor gate refuses a local value the default branch does not declare identically and falls back to the default folder, which is that same path, so an attended child and an unattended one write to one place with no repository setting in scope for either. The isolation guard that forbids a test from reading this repository's own log destination previously inspected spawn calls only, and accepted any named working directory — including this repository's own. It now recognises a default log file read through a home-rooted `.vinaya` tree, refuses a working directory that resolves to this repository, and flags a subject file that calls Vinaya code in this process, where the working directory is this repository's by construction.
