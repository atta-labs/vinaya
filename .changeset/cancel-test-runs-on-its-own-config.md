The whole CLI test suite passes with this repository's own log events going to a server. Two `cancel.test.ts` fixtures spawned their child with this repository as its working directory, and `findLocalConfig()` walks up from the child's working directory: the child therefore read this repository's own `logs` setting, and once a `logs.url` was declared there it resolved a server destination — the local outbox is only that destination's retry queue, drained and cleared asynchronously, so the `<task>.ndjson` file the env-restore case reads existed or not depending on how fast the drain ran. Both fixtures now spawn with `isolatedConfigFixture`'s own working directory, whose empty `vinaya.config.json` is where that walk stops, so no repository setting, present or future, is in scope for them; every assertion is unchanged. The isolation guard that forbids a test from reading this repository's own log destination previously inspected spawn calls only, and accepted any named working directory — including this repository's own. It now recognises a default log file read through a home-rooted `.vinaya` tree, refuses a working directory that resolves to this repository, and flags a subject file that calls Vinaya code in this process, where the working directory is this repository's by construction.
