The whole CLI test suite passes with this repository's own log events going to a server. Two `cancel.test.ts` fixtures spawned their child with this repository as its working directory, and `findLocalConfig()` walks up from the child's working directory: the child therefore read this repository's own `logs` setting, and once a `logs.url` was declared there it resolved a server destination — the local outbox is only that destination's retry queue, drained and cleared asynchronously, so the `<task>.ndjson` file the env-restore case reads existed or not depending on how fast the drain ran. Both fixtures now spawn with `isolatedConfigFixture`'s own working directory, whose `vinaya.config.json` is where that walk stops; every assertion is unchanged. That configuration also declares a destination, and an empty one would not have been isolation at all, which is the substantive half of this fix: the destination resolver reads a working directory's configuration, but an unattended caller whose local configuration declares no `logs` setting still honours the DEFAULT BRANCH's declared destination, read over the forge with an identity taken from the Actions runner rather than from any directory. So a fixture given an empty configuration still delivered to the configured server wherever it ran — on a CI runner, with a real repository identity and a real token, while the same fixture passed on a laptop, where the fixture's own `$HOME` hides the credential that read needs. `isolatedConfigFixture` now declares its own `logs.folder`, and declares it as the very folder it already advertised as `logsDir`: the trust-anchor gate refuses a local value the default branch does not declare identically and falls back to the default folder, which is that same path, so an attended child and an unattended one write to one place with no repository setting in scope for either. The isolation guard that forbids a test from reading this repository's own log destination previously inspected spawn calls only, and accepted any named working directory — including this repository's own. It now recognises a default log file read through a home-rooted `.vinaya` tree, refuses a working directory that resolves to this repository however it was named or imported, and flags a subject file that calls Vinaya code in this process, where the working directory is this repository's by construction. Each half is judged by what the code really does rather than by a token that happens to appear. The scan reads two views of every file it walks, produced by one string-aware pass rather than by a regex, so a `//` inside a URL literal no longer ends the line for it and a program written inside a fixture's template literal is read as the child's code, not the file's own. An inert `git init` names a directory for `git` and nothing else, a captured `process.cwd()` chooses no directory, a `process.chdir` into this repository is the offence rather than the isolation, and a `logs.folder` a file writes for a child says nothing about its own in-process read. The in-process half no longer turns on whether the file spawns anything at all: it fires on a real call to a Vinaya Log producer, and is settled only by moving this process with `process.chdir` out of the repository or by handing that producer its own destination — decided per call, in that call's own scope, so a `chdir` in one function or a sink built in one test case vouches for nothing elsewhere, and a chdir back into a captured directory is read as the restore it is. The producer vocabulary is checked against the authoritative boundary table rather than maintained by hand alone, and it follows an import alias and a namespace import. A repository-rooted directory is recognised wherever it is written — named, re-bound to an alias, carried in an options object, or inlined into the call that runs it — so the offence cannot be hidden by dropping the name, and an inline `process.chdir` into this repository is read as the offence rather than as a move out of it. A boundary producer counts as isolated only when the dependency it is handed is the caller's own, not the module-level producer under another name, and the scan covers the tests colocated with the sources as well as the test directory. Conformance servers now run in their sandbox with a configuration of its own too: run from this checkout, they resolved this repository's `logs.url` and posted their fixture events to the real log server.
