The `task_start` catalog text now states what the tool does. It opened "Distinct from `task_resume`: this tool starts a run, it does not continue a paused one" — false since the start handler began continuing a run that had already stopped: an exited or driverless run, a pause whose ruling was already consumed as a resume, or an `infrastructure` pause still under the loop's own retry bound. That text is the only documentation an Operator is served for the tool, so denying the continue cases pointed it at `task_resume` for runs `task_resume` launches nothing for, which is how a stopped run was left with no working action at all.

The text now names those continue cases and the tool that owns each state this one does not act on — `task_resume` for a pause still awaiting a decision, `task_cancel` for one already resolved as cancel — and, rather than promising a refusal the launched path does not perform, says where that path is weaker than the tool owning the state: `dev-review-loop --resume` accepts any Principal ruling standing on the pull request, including one left over from an earlier round, where `task_resume` requires a ruling newer than the one the pause was already raised under; and a pause recorded before any pull request existed is unreachable by that continuation, so the launch falls through to the fresh-attach path and continues the task with its escalation still unresolved. The loop's bare no-ruling allowance is named by its real reason, `infrastructure`, since a `stale_driver` pause inside the same bound still requires a ruling. An Operator reading this text now routes an undecided pause to the tool that authenticates it, and knows what it risks if it does not — where before the text implied a gate that only `task_resume` has. A test in the catalog's own suite pins the continue cases, both handoffs, the weaker-path disclosure, and the absence of each retired claim.
