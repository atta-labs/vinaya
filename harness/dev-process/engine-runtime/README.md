# harness/dev-process/engine-runtime

Runs a loaded process's Flow on Atta Engine. The process supplies an action registry (mechanical action name to in-process function), a decision registry (deciding step id to a boolean read from the examined result) and a role launcher built from the agent adapters' generated settings; a name the Flow uses that has no entry is refused before any step runs.

## Checkpoints

`SqliteCheckpointer` (`sqlite-checkpointer.ts`) is the checkpoint saver a run keeps beside its other run files: one SQLite file opened with `bun:sqlite`, no added dependency. A runner process started later on the same file opens a new saver and `resumeProcessRun` continues from the last completed step; completed steps do not run again. A mechanical step whose result is marked `refused` paused the run instead of completing: it halts at its own boundary with no result written, so the resume runs it again. Every checkpoint row records the code revision of the checkout that wrote it, the model the run was started with, the checkpoint format version (`CHECKPOINT_FORMAT_VERSION`) and the Engine runtime version (`ENGINE_RUNTIME_VERSION`, the packed Engine and executor at their versions), and the saver reads all four back for any checkpoint (`provenanceOf`) or a thread's latest one (`latestProvenance`). `checkpointRefusal` says when a runner must refuse to resume one: a row that records neither version, another format, or a runtime outside the running one's caret range — never a moved revision or model. A file or a row the saver cannot read raises `CheckpointCorruptError`; a file written before the versions were recorded opens, its rows recording neither. State a step carries to a later step (the round assessment's loop state, say) lives in that step's recorded result, so it is part of the checkpoint rather than held in memory. The run's execution round is one such state: the step that ends a round records it in its own result (`checkpoint-round.ts`), a resume reads it from the effective resumed state (the latest full checkpoint with the pending writes stored after it applied), and each committed write that moves it is mirrored through the saver's `onCommit`; a mirror that fails stops the run at the next step's persistence barrier. A run stopped after a step's writes were stored but before the next full checkpoint is folded into that checkpoint on resume, so it continues after the step. Each row also records the agent the run was started with, read back by `readAgentProvenance` (null on a row written before it was recorded).
