# processes/vinaya/executing

The roles that do and check the work. Belongs to the "Any Process, One Harness" project.

`actions.ts` binds the Flow's mechanical steps to the review loop's functions. Every round outcome is the shared assessment's (`assessRound`): the deciding steps (`validate-developer-output`, `assess-gate`, `validate-reviewer-outputs`, `assess-round`) each report the observation's decision, its Log events and the loop state as JSON in their result, under a sequence number, so the events travel with the step and the next step starts from the newest state. A red gate, a rejected turn result, a reviewer with no usable review and a turn that published nothing are decisions there, never thrown errors. `tests/round-decisions.test.ts` drives each decision end to end on both vendors.

`log-events.ts` supplies the Log producers for the harness translator in `harness/dev-process/logging`: the events each deciding step recorded when it completes or pauses (a reviewer's role attempt among them), and the pause, resume, cancel and exit records at the edges of a leg.

`log-inventory.ts` is the inventory table. It holds one row for each event the review loop's driver wrote (its fifteen loop events, the handoff events and the role attempt): produced by a producer, dropped with a reason, or deferred with the reason it is not produced yet. `tests/log-events.test.ts` is the coverage test: it fails when an event name in the loop schema or the role-attempt schema has no row, when any row is dropped, when the deferred row is not exactly the handoff `resolved` event, or when a produced row names an event no producer wrote in the test's runs. The same file runs the Flow on stubs and checks the exact event sequence of a green run, a revision loop-back, a halt then resume and an exhausted revision ceiling, with every event parsed against its family's schema.

`developer-prompt.ts` builds the Developer's prompt exactly as the standalone review loop's `dispatchDeveloper` does, using the same builders.
- **First turn:** required sources, the developer doctrine block, the publishing line, the Issue's rulings after the brief, the kept-work note, the turn-result instruction, the full context packet, then the frozen brief.
- **Later turns:** required sources, the delta context packet naming the continued session, the resume context (Issue, branch, worktree, remote head), the previous round's held review findings with their ids (or the failing `check --all` output after a red gate), the publish-the-fix line, then the turn-result instruction. A turn the driver sent back only to answer it gets that answer's text instead: the correction prompt for a rejected turn result, the push-and-open or commit-and-push instructions for a turn that published nothing, or the request to restate the turn result when no confidence was read.
- **Conflict turns:** a conflict send-back names the conflicting files and the commit to merge: the default branch's tip the driver fetched for the repair when one was recorded, else `origin/main`, after the reason an earlier repair was not proven. A conflict turn with no session to continue (a fresh run re-entering a conflicting pull request) gets the whole first-turn prompt, led by that conflict text; the runner's pre-turn merge of the default branch adds no second conflict text to it.
- **Session:** the runner continues the Developer's own vendor session across turns (`continueSessions: ['develop']`): `claude -p --resume <id>`, `codex exec resume <id>`.
- **Tests:** `tests/developer-prompt.test.ts` compares both prompts with the loop's for the same inputs; `tests/developer-session.test.ts` checks that turn 2 launches with turn 1's session id on both vendors.

`handoff.ts` is the one place a pause on the Engine path is made durable. Every deciding step's `pause` decision and every error that reaches the runner uncaught call it: it writes the escalation record, then the pause record (both are the review loop's own writers, imported), posts the pause comment once on the pull request, or on the task Issue while none exists, and halts the run through its run control, so the run ends `paused` and never `failed`. An infrastructure pause spends the retry budget through the same rule the review loop applies, and the count is read back from the pause record a prior run left. A pause raised before a pull request existed is bound to the pull request once the reconcile step finds one open. It raises the `raised` handoff event, through the escalation record, and the `infrastructure_retry` event for a comment that took more than one attempt or never landed; `resolved` is raised by the review loop's `resolveEscalation` when the pause's resolution is claimed: by the halted runner itself, which keeps polling the forge at the review loop's watch interval for a ruling newer than the one the pause was raised under and for a cancel, or by `run-engine --resume <pr>`. Either way the resolution is claimed at most once, and the run continues from its checkpoint with the model `--model` names, else the one the checkpoint recorded. A pause decision does not consume its round: the resumed run revises on the same round number. `tests/handoff.test.ts` runs it for both vendors.
